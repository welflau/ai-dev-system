# Action 成套插件与公共工具边界

日期：2026-10-19
状态：实施完成（注册表 + UE 套件 + 内容/设计套件）
前作：`docs/20261015_01_能力自描述与动态组装框架方案.md`、`docs/20261017_01_能力自描述与动态组装框架_架构升级回顾.md`

本文记录一轮讨论的结论：10 月 15 日的能力自描述框架解决「流水线怎么组装」，没有解决「工具实现放在哪」。UE 编译等 Action 仍堆在公共模块。可以把领域工具收成套件插件，且不改那次升级的组装器。

---

## 一、和 AgentFlow 的关系

AgentFlow（`D:\A_Works\agentflow`）是多 Agent 领活的任务板：Goal 拆 Task，外部 Agent `claim`，做完 `report`，经验进 Skill DNA。ADS 是软件交付流水线：Orchestrator 按 SOP **推送**阶段，Role Agent 在进程内执行。

两边相同的一点，是顺序来自依赖而不是站位：

| | AgentFlow | ADS（20261015） |
|---|---|---|
| 顺序依据 | Task 的 `deps` | skill 的 `consumes` / `produces`，Kahn 拓扑排序 |
| 执行者拿到什么 | claim 返回的 execution pack | ArtifactStore 把上游 kind 注入下一 skill |
| 谁决定下一阶段 | 外部 Agent 自己领 | Orchestrator + `compose_sop()` |

20261015 因此**不需要**从 AgentFlow 抄一套工作流拼装。AgentFlow 仍有用的是另一层：多外部 Agent 抢同一执行权、心跳、僵尸回收、失败经验进化。若以后要「外面的 Agent 来领某一 stage」，领的应是执行权，阶段推进仍归 Orchestrator；接口对齐 `consumes` / `produces`，不要让外部 Agent 直接改 `TicketStatus`。

ADS 现有的「多种 Agent」也不是这种领活模型：

- 角色 Agent（`PlannerAgent` … `DeployAgent`）在进程内，由 SOP 指派。
- `claude` / `codebuddy` / `cursor` 是 LLM/CLI 后端，换的是模型出口，不是工单主权。
- 聊天、`@mention`、MCP 确认卡是对话入口，不认领工单阶段。

## 二、UE 工具今天怎么进系统

项目带上 `engine:ue5` 之后，三处同时生效，描述的是同一件事：

| 声明什么 | 位置 |
|---|---|
| CLI 规则、斜杠命令 | `backend/config_packs/ue5-dev/pack.json`（`auto_traits`） |
| 工单插在哪一步 | `backend/sop/fragments/engine_compile.yaml` 等（`insert_after` + `required_traits`） |
| 提示词注入给谁 | `backend/skills/skills.json`（`unreal-cpp-dev`、`unreal-editor-control`） |

真正干活的代码在公共 Action 里，不在套件里：

| 能力 | 实现 | 谁调用 |
|---|---|---|
| 编译 | `actions/ue_compile_check.py` | `DevAgent.run_engine_compile`、自测、CI |
| 编辑器 Python | `actions/ue_run_python.py` | `ChatAssistant`、`/ue-run` |
| 何时跑编译 | `sop/fragments/engine_compile.yaml` | `compose_sop()` |

`SkillRunner._build_actions()` 只认写死的名字：`write_file`、`read_file`、`shell`、`gen_image`，然后从 `backend/actions/` import。插件目录里的 Python 不会被加载。所以「Action 必须留在公共模块」是加载器的限制，不是 Action 不能进插件。

`x-runner.cli_tools` 已经可以在 skill 里声明一条命令，由公共的 `GenericCLIAction` 去跑。带重试、解析日志、回写工单状态的类，今天还进不了插件目录。

## 三、目标

一套领域能力放在同一个插件目录里管理：

```
plugins/ue5/
  plugin.json
  skills/engine-compile/SKILL.md   # x-workflow + x-runner，trait = engine:ue5 / ue4
  actions/ue_compile_check.py
  actions/ue_run_python.py         # 尚未迁入
  ...
  prompts/                         # 原 skills.json 里的 UE 提示词（尚未迁入）
```

- 流水线位置仍由 `consumes` / `produces` 决定，不写 `insert_after`。
- `SkillRunner` 见到 `builtin_tools: [ue_compile]` 时，用本插件注册的类，不再只查公共白名单。
- 类文件可以跟 SKILL 放在一起，运行时仍在 ADS 进程里。编译要碰本机 UBT、仓库和 P4，不会因为换目录就变成独立进程。

## 四、对 20261015 框架的影响

组装器、kind 注册表、`_relink_stage_transitions`、Orchestrator 状态链**不改**。补的是 SkillRunner 的工具绑定：插件可以注册 Action。

必须处理的调用方：`DevAgent.run_engine_compile`、`actions/self_test.py`、`ci/strategies/ue.py` 现在直接 import `UECompileCheckAction`。类搬走后，这三处改为向插件取，或在公共目录留一层转调，避免旧路径立刻断掉。

`engine_compile.yaml` 里还有 `x-workflow` 表达不了的字段：`reject_goto: development`、`max_retries`、对 development 阶段的 `ue_precompile` 覆盖。第一版插件只接管「何时跑、用哪个 Action」；失败打回和预编译开关先留在 fragment，等 `x-workflow` 补上这些字段再删 yaml。

## 五、Action 边界（统计）

`backend/actions/` 里大约 75 个可执行 Action。判定标准：任何项目的工单循环或聊天都要用的留在公共模块；只在一种引擎或一种设计流水线里出现的，可以整包进插件。

### 公共（53）

| 类别 | 数量 | 代表 |
|---|---|---|
| 文件与命令 | 8 | `write_file`、`read_file`、`shell`、`glob`、`grep`、`list_directory`、`read_files`、`read_local_file` |
| Git | 6 | `git_log`、`git_read_file`、`git_list_branches`、`git_switch_branch`、`git_merge`、`resolve_merge_conflict` |
| 工单流水线本体 | 14 | `decompose`、`write_prd`、`design_architecture`、`plan_code_change`、`write_code`、`code_review`、`acceptance_review`、`self_test`、`diagnose_ticket`、`reflect`、`summarize_code`、`voting`、`skill_extractor`、`knowledge_distill` |
| 需求与确认卡 | 12 | `confirm_requirement`、`confirm_requirements_batch`、`confirm_direct_ticket`、`confirm_bug`、`confirm_project`、`confirm_save_doc`、`confirm_skill`、`create_requirement`、`pause_requirement`、`resume_requirement`、`close_requirement`、`dispatch_subtask` |
| 查询、记忆、联网、生图 | 13 | `get_ticket_status`、`get_bugs`、`search_ticket_history`、`search_knowledge`、`get_memory`、`save_memory`、`web_search`、`fetch_url`、`load_skill`、`manage_skill`、`browse_marketplace`、`gen_image`、`generate_image` |

`gen_image` / `generate_image` 归公共：生图不绑定内容流水线，代码项目、聊天、UE 截图后处理都可能调用。`SkillRunner` 里已有的 `gen_image` 白名单保持为公共工具，不随内容插件搬走。

`generic_cli`、`base`、`executor` 是加载器，留在公共模块。

`self_test` 留在公共模块。它是开发阶段的总入口；其中调用 UE 编译的分支改为向 UE 插件要 `ue_compile_check`，不要把整个自测搬进 UE 套件。

### UE 插件（16）

`ue_compile_check`、`ue_playtest`、`ue_run_python`、`ue_call`、`ue_editor_control`、`launch_ue_editor`、`install_ucp`、`ue_blueprint_gen`、`ue_level_gen`、`ue_screenshot`、`ue_package`、`ue_test_gen`、`ue_uproject_heal`、`instantiate_ue_template`、`propose_ue_framework`，以及 `ue_lint` 规则包。

触发条件：`engine:ue5` 或 `engine:ue4`。编辑器里的 UnrealClientProtocol 仍是 UE 工程自己的插件，ADS 侧只保留调用它的 Action。

### 内容与设计插件（6）

`generate_assets`、`write_ux_design`、`write_art_design`、`write_html_prototype`、`search_art_assets`、`search_design_knowledge`。

## 六、实施顺序

1. ✅ `SkillRunner` 走 `plugins.registry.create_action`：公共白名单仍可用，skill 目录内 Action 与 `plugins/<id>/actions/` 可被 `builtin_tools` 点名。
2. ✅ 先搬 UE 编译一套（`plugins/ue5/skills/engine-compile/SKILL.md` + `plugins/ue5/actions/ue_compile_check.py`）。`engine_compile.yaml` 的 `reject_goto` / `ue_precompile` 暂留；skill 的 `stage_id` 与 fragment 同名，组装器跳过插入，避免双阶段。
3. ✅ DevAgent / self_test / CI / ue_test_gen 经注册表取 `ue_compile_check`；`actions/ue_compile_check.py` 留转调。
4. ✅ 其余 UE Action 与 `ue_lint` 已迁入 `plugins/ue5/actions/`。内容/设计 6 个已迁入 `plugins/content/actions/`。生产调用方经注册表取实例。不在本方案里改 AgentFlow 对接。

项目启用插件仍是 trait 驱动（`engine:ue5` / `engine:ue4`），没有「每项目勾选插件」清单。
