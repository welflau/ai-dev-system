## 一、结论

UE 套件的正向能力是齐的：能定位引擎、跑 UBT、跑 Automation、打包、截图、生成测试，`plugin.json` 与 `trait_taxonomy.yaml` 里的 `engine:ue5` / `engine:ue4` 已登记。按 H5 标杆要求的失败闭环和可观测性还没有进插件目录。

缺三块：

1. 没有 `backend/plugins/ue5/reflection.py`。编译失败、Playtest 失败、自测失败的诊断仍写在宿主 `agents/dev.py` 与 `actions/reflection.py` 的分支里，也没有确定性快修。
2. 没有 `backend/plugins/ue5/acceptance.py`。产品验收拿不到 UBT 日志、Automation 结果和截图摘要。
3. UBT / Playtest / 打包 / 截图 / 测试生成都是 Action 内直接 `Popen`，没有 `record_traced_command`，时间轴没有 📟 后台任务。

`data["command"]` 已经是字符串。找不到引擎、缺 UBT、零输出退出会返回 `status="error"`，不会打回开发空改。这两项保持不动。

| 约束 | 结论 | 证据 |
|---|---|---|
| 1 门禁反思 | 缺失 | 插件目录无 `reflection.py`。宿主仍按状态名分支：`agents/dev.py` 的 `engine_compile_failed` / `play_test_failed` / `self_test_failed`；`actions/reflection.py` 同名三段信号拼装。`plugins.registry` 已有 `enrich_plugin_fix_context`、`build_plugin_reflection_signal`、`apply_plugin_deterministic_fixes`，UE 未接入。 |

- 编译与 Playtest 的 `ActionResult.data["command"]` 为 `str`。
- 引擎缺失、UBT 缺失、零输出退出走 `error` → Orchestrator `blocked`。

## 三、修改原则

1. 失败诊断进 `backend/plugins/ue5/reflection.py`。宿主 `agents/dev.py`、`actions/reflection.py` 删掉上述 UE 状态的专用分支，不再新增 `if/elif`。
2. 分发继续走现有注册表：`is_plugin_failure_type`、`enrich_plugin_fix_context`、`build_plugin_reflection_signal`、`apply_plugin_deterministic_fixes`、`build_plugin_acceptance_evidence`。不新增第二套插件协议。
3. 确定性快修只覆盖「编译器或静态规则已经点名文件和行，且修法唯一」的情况。覆盖不了的错误仍交给现有编译错误快通道，只改报错文件。
4. 命令记录失败不得让编译或试玩本身失败。写法对齐 H5：`try/except` 包住 `record_traced_command`，异常只打 debug。
5. 环境问题继续返回 `status="error"`。只有 UBT 或 Automation 已经给出可定位的代码或测试失败，才返回 `*_failed`。

## 四、修改方案

### 4.1 新增 `backend/plugins/ue5/reflection.py`

声明：

```python
HANDLED_FAILURE_TYPES = frozenset({
    "engine_compile_failed",
    "play_test_failed",
    "self_test_failed",
    "ue_test_gen_failed",
    "packaging_failed",
    "ue_content_failed",
})
```

三个函数的职责：

**`enrich_fix_context`** 把现在散落在 `DevAgent._do_fix_issues` 里的字段读取挪过来。

| 失败类型 | 从 reject `detail` 或工单 `result` 写入 context |
|---|---|
| `engine_compile_failed` | `compile_errors`、`compile_warnings`、`compile_command`、`compile_hints`、`compile_raw_tail`、`compile_err_brief` |
| `play_test_failed` | `failed_tests`、`playtest_summary`、`playtest_command`、`compile_raw_tail`（用 `raw_tail`）、`module_load_errors` |
| `self_test_failed` | `ue_blocking_issues`（来源仍是 `tickets.result.self_test.ue_blocking_issues`；detail 里若已有同名字段则优先用 detail） |
| `ue_test_gen_failed` | `compile_errors`、`compile_raw_tail`、`compile_command`、`compile_err_brief` |
| `packaging_failed` | `compile_command`、`compile_raw_tail`、`compile_err_brief`、`compile_errors`（RunUAT 能解析出的行） |
| `ue_content_failed` | `compile_err_brief`、`compile_raw_tail` |

`command` 入库前已是 `str`。`enrich_fix_context` 再 `str()` 一次，避免历史日志里残留 list。

Playtest 现在在 `dev.py` 里额外调 `ue_editor_control.get_actors` 注入 `editor_state`。这个查询依赖正在运行的编辑器，失败就跳过。迁到 `enrich_fix_context` 会把反思模块变成 async，和现有同步签名不一致。处理方式：留在 `DevAgent._do_fix_issues`，条件改成「`failure_type == "play_test_failed"` 且 `ucp_available`」，放在插件 `enrich` 之后。这是编辑器现场查询，不是失败信号格式化，不新增状态分支。

**`build_reflection_signal`** 原样迁入现在 `actions/reflection.py` 里三段 UE 文案，并补上规范要求的三样东西：

1. 每条错误写到 `文件:行:列`、错误码、描述。编译错误用 UBT 解析结果里的 `file` / `line` / `column` / `code` / `msg`。自测用 `rule` / `file` / `line` / `msg` / `suggest`。
2. 领域提示保持现有清单：同名头文件、漏 `UCLASS` / `GENERATED_BODY()`、`Build.cs` 缺模块、`.generated.h` 与类名不一致、Automation 未注册、Enhanced Input 未绑定、`-nullrhi` 下不要依赖渲染。
3. 剥 ANSI 后附上 `raw_tail`。结构化错误为空时，信号正文就是这段尾部和 `err_brief`，不能变成空字符串。

零错误的 `engine_compile_failed` 今天会在 `ReflectionAction` 里直接返回一份置信度 0.2 的环境反思，不调用 LLM。插件信号接口返回的是字符串，接不住这份结构化反思。允许的宿主改动只有一处通用槽，不写 UE 状态名：

- `build_reflection_signal` 在「编译失败且 `compile_errors` 为空」时，除了返回环境说明文本，还写入 `context["_reflection_override"]`（含 `root_cause`、`strategy_change`、`specific_changes`、`confidence=0.2`）。
- `ReflectionAction.run` 在调用 LLM 之前若发现 `context["_reflection_override"]` 是 dict，直接把它当作反思结果返回。

这样 P0 已有的「零输出不空转」保留下来，宿主不再出现 `failure_type == "engine_compile_failed"`。

**`apply_deterministic_fixes`** 第一期只做两件已经由 `ue_lint` 证明过、修法唯一的事。输入是 `compile_errors` 或 `ue_blocking_issues` 点名的文件，输出 `{相对路径: 全文}`。读文件优先磁盘原文；内容里若带 `文件截断显示` 标记则跳过该文件。

| 规则 | 触发 | 改法 |
|---|---|---|
| 补 `GENERATED_BODY()` | 头文件在 `UCLASS` / `USTRUCT` / `UINTERFACE` 之后 10 行内有 `class`/`struct` 的 `{`，且没有 `GENERATED_*BODY()`。与 `ue_lint.rules.rule_R1_uclass_genbody` 同一判定。 | 在类左花括号下一行插入 `    GENERATED_BODY()` |
| 补 `.generated.h` | 报错信息含 `generated.h` 或 `Please define ... with UCLASS`，且该头文件已有 `UCLASS`、没有 `#include "<同名>.generated.h"`。 | 在最后一个 `#include` 之后插入 `#include "文件名.generated.h"` |

以下情况第一期不自动改，只写进反思提示：

- `Build.cs` 缺哪个模块（候选不唯一）。
- Playtest 断言失败、超时、关卡或输入配置。
- 打包 Cook 失败、内容生成失败。

`DevAgent._do_retry_with_reflection` 已有逻辑：报错文件都被确定性修复覆盖时跳过 LLM 反思。UE 接入后自动生效，不必再改跳过条件。

### 4.2 宿主删除清单

`plugins.registry.is_plugin_failure_type` 在 `reflection.py` 存在后会对上述六个状态返回真。删除因此变成死代码的分支，避免两套文案以后各改各的。

`backend/agents/dev.py` 的 `_do_fix_issues`：

- 删除 `cur_status == "engine_compile_failed" / "play_test_failed" / "self_test_failed"` 三个 `elif`。这三个状态改由前面的 `is_plugin_failure_type` 接管。
- 删除紧随其后的三段手工解析（编译 errors、自测 issues、playtest tests）。字段改由 `enrich_plugin_fix_context` 写入。
- 保留 `development_failed`、`testing_failed`、`acceptance_rejected`。
- 保留 Playtest 的 UCP `get_actors` 查询，位置放到插件 enrich 之后。
- `_do_retry_with_reflection` 里把失败摘要拼进 `ticket_description` 的分支，去掉单独点名 `engine_compile_failed`。有 `compile_errors` 时用通用「编译/门禁错误」摘要即可；H5 两个状态已由插件信号覆盖，这段只是反思被关闭时的降级。

`backend/actions/reflection.py` 的 `run`：

- 删除 `engine_compile_failed` 零错误提前返回、`engine_compile_failed` 信号、`play_test_failed` 信号、`self_test_failed` 信号。
- 在 `build_plugin_reflection_signal` 之前增加对 `context["_reflection_override"]` 的通用判断。
- 保留 `acceptance_rejected`、`testing_failed`、`development_failed`。

### 4.3 命令落库与时间轴步骤

新增 `backend/plugins/ue5/command_trace.py`，给不经过 SkillRunner 的 Action 用。形态对齐 `plugins/h5/actions/h5_playtest.py` 的 `emit_step` 与 `run_and_trace`，但 UE 侧继续用现有 `Popen` + 线程读 stdout，不改成 `asyncio.create_subprocess_exec`（`ue_compile_check.py` 里记录过 Windows 上该 API 会抛空异常）。

两个函数：

1. `emit_ue_step(context, step_name, phase, task_id="", duration_ms=0, reason="")`  
   写 `ticket_logs.action = skill_step_start | skill_step_done | skill_step_error`。`detail.task_id` 放 `TCMD-*`。`phase` 只用 `start` / `done` / `error`。
2. `trace_ue_command(...)`  
   调 `command_log.record_traced_command`。参数：`source`（action 名）、`tool`（`ubt` / `ue-cmd` / `runuat` / `automation`）、`command`（必须是 `str`）、`cwd`、`exit_code`、`status`、`duration_ms`、`output`、工单与项目 id。返回 `record_id`；没有 `ticket_id` 或写库失败时返回空串。

接到这五个 Action 的进程结束处（成功、失败、超时、启动异常都要记）：

| Action | source | 步骤名 |
|---|---|---|
| `ue_compile_check.py` | `ue_compile_check` | UBT 编译 |
| `ue_playtest.py` | `ue_playtest` | UE Automation |
| `ue_package.py` | `ue_package` | RunUAT 打包 |
| `ue_screenshot.py` | `ue_screenshot` | UE 截图 |
| `ue_test_gen.py` | `ue_test_gen` | 单文件编译验证 |

时序：`emit_ue_step(start)` → `Popen` → 进程结束 → `trace_ue_command` → `emit_ue_step(done|error, task_id=record_id)`。`ActionResult.data` 增加 `task_id`（即 `record_id`），`command` 继续用现有 `cmd_str`。Orchestrator 写 `complete` / `reject` 时已经会从 `data` 抄 `task_id` 的，不改编排器。

`output` 传入完整控制台文本，供后台任务面板查看。Action 自己的 `raw_head` / `raw_tail` 截断逻辑保留，避免 reject detail 过大。

### 4.4 Playtest 超时分流

`ue_playtest.py` 超时分支现在一律 `playtest_failed`。改成按已经读到的输出分流：

| 超时前的输出 | 返回 |
|---|---|
| 已经解析出失败用例（`summary.failed > 0`） | `playtest_failed`，打回开发 |
| 有 Automation 输出且用例都通过，只是进程没退出 | `playtest_failed`，信号里写明「测试已有结论，进程未退出」 |
| 零行输出，或只有引擎启动日志、没有测试行 | `status="error"`，走 blocked，不改业务代码 |

缺引擎、缺 `UnrealEditor-Cmd.exe`、游戏模块 DLL 不存在维持现有 `error`。模块未加载（`module_load_errors` 非空）且没有任何失败用例时，同样返回 `error`：这是工程或插件没装上，不是本次业务代码的断言失败。

### 4.5 `git clean` 排除 UE 产物目录

`git_manager.switch_branch` 现有调用：

```text
git clean -fd --exclude=.env --exclude=openspec --exclude=node_modules
```

追加：

```text
--exclude=Binaries --exclude=Intermediate --exclude=Saved --exclude=DerivedDataCache
```

`git clean -fd` 默认不删已被 ignore 的文件。排除项保护的是「模板还没写 `.gitignore`、这些目录仍是未跟踪文件」的仓库，避免切到主干时把本机编译结果清掉，下一单又全量编译。`_SKIP_DIRS` 已包含这四个名字，文件树扫描不用再改。

### 4.6 状态标签与看板列

`backend/models.py` 的 `STATUS_LABELS` 补：

| 状态 | 中文 |
|---|---|
| `packaging_pending` | UE 打包排队 |
| `packaged` | UE 已打包 |
| `packaging_failed` | UE 打包失败 |
| `ue_content_pending` | UE 内容生成排队 |
| `ue_content_done` | UE 内容已生成 |
| `ue_content_failed` | UE 内容生成失败 |
| `ue_content_in_progress` | UE 内容生成中 |

不改 `deploy_ue.yaml` 的 `success_status: packaged`。改状态名会碰到已有工单和转移规则。看板归类在 `api/tickets.py::_classify_board_column` 加两个精确名字，放在后缀判断之前：

- `packaged` → `in_review`（本阶段通过，后续还有审查或验收，不直接算工单完成）
- `packaging_pending`、`ue_content_pending` → `in_progress`

`packaging_failed`、`ue_content_failed` 已能被 `*_failed` 归入「已阻塞」。`ue_content_done` 已能被 `*_done` 归入「审核中」。

### 4.7 新增 `backend/plugins/ue5/acceptance.py`

实现 `async def build_acceptance_evidence(context) -> dict`，返回 `evidence_markdown`、`extra_check_items`、`acceptance_rules`。注册表会按 `engine:ue5` / `engine:ue4` 自动注入，验收 Action 不用加引擎分支。

证据从该工单最近的 `ticket_logs` 读取，来源 action 为 `complete` 或 `skill_step_done`：

- `engine_compile_passed`：exit、耗时、error/warning 计数、`command`。
- `play_test_passed`：`summary`（passed/failed/total）、失败用例名（若有）、截图相对路径、`command`。
- `self_test`：blocking issue 条数；为 0 时写明静态预检通过。
- 打包阶段若已有 `packaged`：平台、配置、耗时。没有则注明尚未打包，不因此判失败。

`evidence_markdown` 再附本次改动里最多 3 个 `.h` / `.cpp` 的摘要（每个截断到约 80 行），来自 `context["existing_code"]` 或 `dev_result`。路径含 `Binaries`、`Intermediate`、`Saved` 的文件不要贴进去。

`extra_check_items`：

- UBT 最近一次结果为通过，或工单没有 C++ 改动因而未跑编译。
- Automation 通过，或项目无项目级测试且 Playtest 按「0 测试视为通过」结束。
- 需要玩法验证的工单带有截图路径或预览说明。
- 改动的反射类型具备 `GENERATED_BODY()` 与对应 `.generated.h`。

`acceptance_rules` 写明：CLI 纯文本评审读不到 png 时，以本节的编译退出码、测试摘要和源码片段打分；禁止因「工作目录里没有截图文件」打 0 分。截图路径只作为证据索引。

### 4.8 测试

扩展 `backend/tests/plugins/test_ue_compile_plugin.py`，或另建 `backend/tests/plugins/test_ue5_plugin.py`。原有「skill 可发现、SOP 不重复插入 `engine_compile`」用例保留。新增：

1. `HANDLED_FAILURE_TYPES` 含第二节列出的六个状态；`is_plugin_failure_type("engine_compile_failed")` 为真。
2. `enrich_fix_context("engine_compile_failed", detail, ctx)` 后，`ctx["compile_errors"]` 与 `compile_raw_tail` 与 detail 一致；`command` 即使传入 list 也被收成 `str`。
3. `build_reflection_signal` 在有错误时包含 `文件:行` 和错误码；无错误时包含 `raw_tail` 文本，并写入 `_reflection_override`。
4. `apply_deterministic_fixes`：给一份只有 `UCLASS()` + `class AFoo : public AActor {` 的头文件，返回内容含 `GENERATED_BODY()`；文件未被报错点名时不改。
5. 看板：`_classify_board_column("packaged", {}) == "in_review"`，`packaging_failed` 为 `blocked`，`ue_content_done` 为 `in_review`，`ue_content_pending` 为 `in_progress`。
6. `build_acceptance_evidence` 在日志 detail 含编译通过与 Playtest summary 时，`evidence_markdown` 同时出现这两段，且 `acceptance_rules` 含「不得因读不到截图判 0 分」的语义。
7. `trace_ue_command` 用假的 `record_traced_command` 断言收到的 `command` 类型是 `str`。不启动 UBT。

## 五、实施顺序

按依赖从底向上，每步都可以单独提交和回归：

1. `reflection.py` + 宿主删除对应分支 + 反思单测。先让打回能看到结构化错误，再动命令日志。
2. `command_trace.py` 接到五个 Action，确认一条工单时间轴能点开 📟 后台任务。
3. Playtest 超时分流。
4. `git clean` 排除项。
5. `STATUS_LABELS` 与 `packaged` 看板归类。
6. `acceptance.py` 与验收单测。
7. 跑 `pytest backend/tests/plugins/test_ue_compile_plugin.py` 以及新增的 UE 插件测试。H5 套件测试应保持通过，用来确认注册表分发没有被 UE 状态误伤。

不在本方案里做的事：

- 不改 `engine_compile.yaml` 等 fragment 的 `reject_status` 名字。
- 不把 Godot / Unity 编译塞进 `ue5/reflection.py`。`engine_compile` fragment 的 traits 还包含 Godot 与 Unity，那些引擎若走到同一 `engine_compile_failed`，会命中 UE 插件的 `HANDLED_FAILURE_TYPES`。第一期在 `build_reflection_signal` 里若 `raw_tail` 明显不是 UBT（没有 `UnrealBuildTool`、也没有 MSVC `error C`）就退回通用「引擎编译失败 + raw_tail」文案，不套 UE 宏提示。Godot / Unity 以后各自的套件上线时，再把 `engine_compile_failed` 从 UE 的集合里拆成引擎专属状态名。
- 不自动改 `Build.cs` 模块依赖，不自动改关卡、输入和蓝图。
- 不重启服务、不改正在跑的工单数据。
