# 已部署工单「打回重做」方案

> 日期：2026-11-10
> 触发：人工验收发现已部署工单不符合要求，但系统无打回入口

## 一、背景与问题

用户在看板发现某需求下的工单已全部流转到 `deployed`（已部署），但人工复查实际效果不符合要求。此时系统**没有操作入口**能把这些工单打回重做。

- `deployed` 是硬终态（`orchestrator.py:211` `_HARD_TERMINAL`），不再自动派单。
- 打回端点 `POST /tickets/{id}/reject`（`api/tickets.py:1452`）只允许从 `development_done`（→验收打回）和 `testing_in_progress`（→测试打回）打回，**deployed 不在允许列表**。
- 前端看板/工单抽屉对已完成工单没有任何「重做」按钮。

唯一变通：在对话里描述问题，让 AI 新建一个 bugfix 工单重走流程——上下文割裂，原工单历史不连贯。

## 二、目标

给已部署工单提供「打回重做」能力，**复用既有 rework 返工链**，改动最小、语义连贯。

## 三、现状盘点

### 3.1 返工链（已存在，无需改动）

`_core.yaml` 里验收 + 返工的闭环：

```
acceptance（ProductAgent）
  trigger_on: review_passed
  success_status: acceptance_passed
  reject_status: acceptance_rejected
  reject_goto: rework

rework（DevAgent.fix_issues，branch_only）
  trigger_on: acceptance_rejected
  success_status: development_done
```

完整链路：`acceptance_rejected → rework → development_done → code_review → review_passed → acceptance → acceptance_passed → deploy → deployed`

**关键洞察**：只要把 `deployed` 转成 `acceptance_rejected`，orchestrator 会自动走完整返工链，无需改派单逻辑。

### 3.2 reject 计数（需兼容）

`orchestrator.py:2114` 全局 reject 上限 `MAX_RETRIES = 5`，`_reject_count_since_reset()` 统计 `action='reject'` 日志条数，累计 ≥5 次 → `blocked` 硬停。

人工打回 deployed 会写 reject 日志 → 计入计数 → 累计超限后 blocked。**这是合理行为**：人工打回也算一次返工机会，防止无限打回空转。

### 3.3 硬终态恢复派单

`orchestrator.py:2085` 按当前状态判断硬终态。`deployed → acceptance_rejected` 后状态不再是硬终态，轮询器自然恢复派单，无需改 orchestrator。

## 四、方案设计

### 4.1 状态流转

```
deployed ──(人工点「打回重做」+ 理由)──> acceptance_rejected
   └── 触发 rework（DevAgent.fix_issues）→ 重走 code_review → 验收 → 测试 → 部署
```

打回目标选 `acceptance_rejected` 而非 `pending`，理由：
1. 复用既有 rework 链，DevAgent 带「反思 + 反馈理由」修复，不是从零重做。
2. reject 计数天然生效，防无限打回。
3. 不动 SOP 配置，零风险。

### 4.2 后端改动

1. **扩展 `reject` 端点**（`api/tickets.py:1452`）：
   - `allowed_reject_from` 增加 `deployed`
   - `deployed → acceptance_rejected`（与 development_done 打回同目标状态，但 source=human）
2. **`TicketRejectRequest` 加 `source` 字段**（`models.py:376`）：
   - `source: str = "agent"`（agent 验收打回）/ `"human"`（人工复查打回）
   - 日志与 SSE 事件透传，时间轴可区分来源
3. **日志**：`_log_ticket(..., "reject", ...)` 带 `source=human`，detail 写「人工复查打回：{reason}」

### 4.3 前端改动

1. **看板卡片**：`deployed` 状态卡片加「打回重做」按钮（hover 菜单或卡片操作区）
2. **工单抽屉**：对 deployed 工单显示「打回重做」按钮
3. **交互**：点击弹理由输入框 → 调 `POST /tickets/{id}/reject`（带 `source=human`）→ toast + 刷新看板 + SSE `ticket_rejected` 事件已触发刷新

### 4.4 SSE 事件

`ticket_rejected` 事件已存在，增加 `source` 字段。前端监听处可区分：
- `source=agent`：验收/测试自动打回（现有行为）
- `source=human`：人工复查打回（本次新增）

## 五、关键决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 打回目标状态 | `acceptance_rejected` | 复用 rework 链，最小改动 |
| 是否计入 reject 计数 | 是 | 防无限打回，超 5 次 blocked 转人工 |
| 入口位置 | 看板卡片 + 工单抽屉 | 覆盖两个常用操作面 |
| 端点 | 扩展 reject（不加新端点） | 语义同构，少一个端点 |

## 六、实施清单

- [ ] `models.py`：`TicketRejectRequest` 加 `source` 字段
- [ ] `api/tickets.py`：reject 端点放行 `deployed`，`deployed → acceptance_rejected`，日志/事件带 source
- [ ] `frontend/app.js`：看板卡片 + 工单抽屉对 deployed 工单加「打回重做」按钮 + 理由输入框
- [ ] 验证：deployed 打回后 orchestrator 自动派 rework → 重走验收 → 部署

## 七、风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 打回后 reject 计数逼近上限 | 已返工过多次的工单，人工打回可能直接 blocked | 合理（该转人工了）；unblock 会清零计数，人工可解阻塞后重来 |
| deployed 打回语义 vs 测试打回混淆 | deployed 打回走验收链，测试打回走 fix_issues | 用 source 字段区分来源，日志清晰 |
| 前端按钮误触 | 已完成工单被误打回 | 理由输入框 + 二次确认 |

## 八、附：与「验收边界」的关联

本次「打回重做」补的是**下游**（部署后人工复查不通过怎么办），与 20261105_07 文档「八、验收边界」补的**上游**（验收判定边界约束）互补——上游保证验收判得对，本方案保证判错/复查不通过后能重新执行。
