## 1. 背景与结论

目标模型（**来源已确认**：`AIGameAgent/docs/ARCHITECTURE.md:9-31` 逐字定义了下面六层与「严格 DAG：下层永远不能导入上层的代码」；两个参考仓库的关系见 §12）：

```
L5  桌面 UI 层     — Tauri + React 配置界面，独立 EXE
L4  CLI / 安装器   — doctor / install / config / catalog / update 命令
───────────────── 以上是分发层，以下是插件运行时 ─────────────────
L3  Pack 层       — 通用 Pack（修复/增强）+ 领域 Pack（游戏定制）
L2  基础设施层     — 日志、追踪、路径、无 schema 配置加载、Tool Catalog
L1  内核 + 策略层  — collect-and-merge 引擎 + 模型路由策略
L0  契约层         — 映射到 Agent 6 原语的 provider 接口
```

**实测结论：ADS 现状不是 DAG，也不是这套分层。** 它是一个以 `backend/orchestrator.py` 为中枢的 hub-and-spoke 单体：中枢直接引用 `agents/ actions/ api/ plugins/ sop/ hooks/`，同时这些包又反向引用中枢，形成 60 模块的强连通分量。ADS 文档里的「5 层纵向栈」（`README.md:12-33`）、「7 层 Harness」（`docs/20260413_01_系统技术架构文档.md:30-70`）、「三层融合」（OpenSpec/Superpowers/Harness）都是**职责分层**，从未声明依赖方向规则。

本方案回答的是：**如何从现有单体，在不中断服务的前提下，渐进收敛到这套严格 DAG**。关键判断：

- 改造的主战场不是「重新命名目录」，而是**依赖倒置** —— 把 `orchestrator` 对上层的 30 处直接引用抽成 L0 契约；
- 「严格 DAG」必须由**机械校验**保证（`layers.toml` + 静态检查器 + CI 门禁），否则会像过去一样靠 29.4% 的函数内延迟 import 把环压到运行时；
- L4/L5 与运行时**物理分离**（不同进程、不同依赖图），这是分界线最容易守住的做法。

## 3. 目标架构

### 3.1 分层职责（ADS 语境下的具体化）

| 层 | 职责 | 允许依赖 | 禁止事项 |
|---|---|---|---|
| **L5 桌面 UI** | Tauri + React 配置界面，独立 EXE | 仅 L4 CLI / L1 的 **HTTP API** | 不得 import 任何 `backend.*`；不得直连 DB |
| **L4 CLI / 安装器** | `doctor` / `install` / `config` / `catalog` / `update` | L3 Pack 元数据、L2 配置读写（文件契约）、L1 HTTP 健康检查 | 不得 import 运行时 Python 模块 |
| **L3 Pack** | 通用 Pack（修复/增强）+ 领域 Pack（游戏定制），声明式 | L0 契约、L2 基础设施 | 不得 import L1 内核实现、不得 import 其它 Pack |
| **L2 基础设施** | 日志、追踪、路径、无 schema 配置加载、Tool Catalog | 仅 L0 | 不得 import L1/L3/L4/L5；不得引用任何业务概念 |
| **L1 内核 + 策略** | collect-and-merge 引擎（`sop/loader.py`）+ 模型路由策略 + 编排状态机 | L0、L2 | 不得 import L3/L4/L5；不得硬编码任何具体 Agent / Action / Pack |
| **L0 契约** | 领域无关接口：6 原语 → 7 类 provider + `CatalogEntry`，`ProviderRegistry`，纯数据结构（无实现） | 无（纯接口层） | 不得 import 任何上层；不得含业务逻辑；`type` 字段保持开放（具体值由 L2 校验） |

### 3.2 四条铁律（机械可判）

1. **方向律**：`layer(src) >= layer(dst)`。低层 import 高层即违规。
2. **无环律**：依赖图任意强连通分量大小必须为 1。
3. **跨层律**：L1 ↔ L3 之间只能经 L0 契约（注册/发现），不得直接 import。
4. **分界律**：L4/L5 与 L0~L3 **不在同一张依赖图里** —— 通过进程间通信（HTTP/JSON-RPC）+ 文件契约交互，不共享 Python import。
   - 补充（参考实现 `AIGameAgent/docs/ARCHITECTURE.md:23` 的硬约束）：**CLI 是 UI 的后端**。L5 通过 `L4 --json` 子命令取配置与 catalog，不得自行解析配置文件或跑健康检查，确保 CLI / UI / 运行时三个视角数据一致。参考实现自身尚未完全做到（`AIGameAgent/docs/20261117_02_模块依赖与核心机制.md:168` 指出 Rust 仍直改配置，`AIGameAgent/docs/ARCHITECTURE.md:326` 列为待办），ADS 应从一开始就写进铁律。

> 分界律是这套模型最容易被守住的一条：分发层是独立 EXE / 独立进程，物理上无法 import 运行时模块，DAG 自动成立。

### 3.3 L0：Agent 6 原语与 provider 契约（**已有正式定义，见 §12**）

「Agent 6 原语」不是本方案按 ADS 能力归纳出来的，而有明确出处：`AIGameAgent/docs/ARCHITECTURE.md:5-7` 与 `AIGameAgent/docs/20261117_02_模块依赖与核心机制.md:35-50`。**初稿归纳的 `read/write/exec/search/generate/delegate` 是错误猜测，已全部作废**，以参考实现的正式定义为准：

| 原语 | 语义 | Provider 接口（L0） | 目标 Hook | ADS 侧对应能力 |
|---|---|---|---|---|
| 身份 Identity | 定义 Agent | `AgentProvider` | `config` | `agents/`、`agent_registry.py` |
| 思考 Think | 模型选择与参数 | `ModelPolicy` | `config` | `llm_client.py:522` `CLI_MODEL_OPTIONS`、`config.py` |
| 感知 Perceive | 注入上下文片段 | `ContextProvider` | `system.transform` / `compacting` | `memory.py`、`knowledge_loader.py`、`_build_context()` |
| 行动 Act | 自定义工具 / 工具拦截 | `ToolProvider` / `StateProvider.buildTools` | `tool` / `tool.execute.before/after` | `actions/`、`plugins/registry.py`、`PUBLIC_TOOL_NAMES` |
| 记忆 Remember | 持久化状态 | `StateProvider` | `event` | `database.py`、`artifacts/`、`checkpoint/`、`failure_library.py` |
| 观测 Observe | 追踪与监控 | `Observer` | `event` | `session_logger.py`、`events.py`、`hooks/` |
| 命令式扩展 | 直接提供宿主 Hook | `HookProvider` | 对应 hook | `hooks/registry.py`、`sop/fragments/` |
| 工具注册 | 声明健康检查 / 安装规格 | `CatalogEntry[]` | CLI `doctor` / `catalog` | 无（待新增 L2 Tool Catalog） |

参考实现的两个关键约束，本方案直接沿用：

1. **6 原语 → 7 类 provider + `CatalogEntry`**（`AIGameAgent/src/kernel/types.ts`），不是 6 个接口一一对应；
2. **L0 类型可扩展**：`HealthCheckSpec.type` / `InstallSpec.type` / `CatalogEntryCategory` 用 `string` 而非封闭联合，具体值由 L2 schema 校验（`AIGameAgent/docs/ARCHITECTURE.md:31`）。ADS 侧对应做法：`Provider.kind: str` 保持开放，L2 `ToolCatalog` 负责合法性校验，避免每加一种 provider 就改 L0。

L0 只定义 `Provider` 协议（方法签名 + 输入/输出 DTO）与 `ProviderRegistry`，**不含任何实现**。实现放在 L3 Pack 或 L2 适配器里，启动时注册进 Registry。

### 3.4 依赖倒置前后对比

```
现状（环）:  orchestrator ──import──> agents.test / actions.* / api.*
                  ↑                          │
                  └────────import───────────┘   （agents.test:408 反向引用 orchestrator）

目标（DAG）: L1 orchestrator ──> L0 ProviderRegistry.get("delegate")
                                        ↑ 注册（启动时，L3 单向）
                              L3 TestAgentPack implements Provider
```
L1 只认字符串 key + L0 接口，L3 单向注册；L1 不 import L3，环消失。

### 4.2 `ProviderRegistry`（演进 `plugins/registry.py`）

保留 `ensure_discovered()` / `require_action()` 的现有语义，新增：
- `register_provider(primitive: str, provider: Provider)` — L3 单向注册
- `get_provider(primitive: str) -> Provider` — L1 单向查询
- `catalog() -> Dict` — 供 L4 `catalog` 命令读取（经 HTTP，不 import）
- 启动时校验：每个原语至少一个实现；缺失则 `doctor` 报错

`PUBLIC_TOOL_NAMES`（4 个）保留为旧工具名别名，避免破坏 `run_action()` 派发；Registry 另按参考实现的 7 类 provider（`AgentProvider` / `ModelPolicy` / `ContextProvider` / `ToolProvider` / `StateProvider` / `Observer` / `HookProvider`）与 `CatalogEntry` 组织注册，6 原语是这些接口背后的语义分组，而不是 6 个平级注册槽。

### 4.3 事件化替换 `api.*` 反向引用

`orchestrator` 里的 `from api.milestones import ...` 是典型的「内核感知 UI 层」。改为 L0 定义 `DomainEvent`，L1 只 `emit(event)`，L3 侧订阅者执行具体副作用（FTS 更新、里程碑刷新）。`events.py` / `event_bus.py` 已是现成通道，只需把「直接函数调用」换成「事件发布 + 订阅」。

## 6. DAG 守卫（让「严格 DAG」可机械校验）

这是本方案最关键的增量：**没有自动门禁，分层约定会在三个月内腐化回去**（29.4% 延迟 import 就是前车之鉴）。

> **参考实现同样缺这一步**：`AIGameAgent/docs/ARCHITECTURE.md:27` 把「严格 DAG：下层永远不能导入上层的代码」写成文字规则，但仓库里没有任何层级检查脚本 / `dependency-cruiser` / `madge` 配置，`package.json` 的 `scripts` 也无 layer 校验（`AIGameAgent/docs/20261117_02_模块依赖与核心机制.md` 与 `AIGameAgent/docs/architecture-patterns.md` 均只做定性描述）。也就是说六层原型靠的是**代码自觉 + review**。ADS 的 §6 守卫因此不是照抄，而是对参考实现的必要补强 —— 也印证了为什么初稿把「机械校验」列为最关键的增量。

### 6.1 新增 `backend/layers.toml`

[levels]

## 12. 参考实现：AIGameAgent 与 AGA 两个仓库

### 12.1 六层模型的真实来源

用户给的六层描述逐字来自 `AIGameAgent/docs/ARCHITECTURE.md:9-31`（同目录 `AIGameAgent/docs/architecture-patterns.md`、`AIGameAgent/docs/20261117_01~04_*.md` 是 2026-11-17 生成的配套分析）。它是**一个严格 DAG 的真实实现**，不是示意模型：

> 下表「关键文件」列的路径均相对 `AIGameAgent/` 仓库根（外部参考实现，非本 ADS 项目内文件）。

| 层 | 参考实现落点 | 关键文件 |
|---|---|---|
| L0 | 领域无关接口 | `src/kernel/types.ts`（Pack / 7 类 Provider / `SessionTracerAPI` / `HealthCheckSpec` / `InstallSpec` / `CatalogEntry`） |
| L1 | collect-and-merge + 模型策略 | `src/kernel/create-plugin-kernel.ts`、`src/model/default-policy.ts` |
| L2 | 基础设施（纯引擎） | `src/infra/paths.ts` / `logger.ts` / `tracer.ts` / `config-loader.ts` / `catalog.ts` |
| L3 | 通用 Pack + 领域 Pack | `src/packs/{core-game,rtk,state,trace,catalog,custom-tools}-pack/` |
| L4 | CLI + 安装器 + 部署 | `packages/app/index.ts`（commander）、`commands/{doctor,catalog,config,install,update,ui}.ts`、`bootstrap/` |
| L5 | Tauri v2 + React 独立 EXE | `packages/config-ui/src`（React）、`src-tauri/src/main.rs`（Rust TCP server 委托 CLI `--json`） |

`src/assembly.ts` 是唯一组合根，`src/index.ts` 是唯一运行时入口；CLI 的 `commands/_shared.ts` 复用同一组装逻辑，保证 CLI 与运行时看到同一份工具目录（`AIGameAgent/docs/20261117_02_模块依赖与核心机制.md:12-14`）。

### 12.2 可直接借鉴 vs 不适用于 ADS

| 可直接借鉴 | 不适用（领域不同） |
|---|---|
| 6 原语 → 7 类 provider + `CatalogEntry` 的抽象 | OpenCode Hook 名（`system.transform` / `chat.message` / `tool.execute.before`） |
| L0 开放 `type: string`、具体值由 L2 schema 校验 | 「宿主是 OpenCode」这一前提 —— ADS 宿主是自己的 FastAPI + 工单状态机 |
| Kernel 只做收集/合并/分发、不解析 rawConfig | `disabled_packs` / `agents` 模型覆盖等面向编码 Agent 的配置 |
| `safe()` 错误隔离、priority 排序、工具后写覆盖 | 6 个 Pack 的具体业务（Hermes / Argus / RTK / Langfuse） |
| Tool Catalog 是纯注册引擎（不知道该有哪些工具） | L5 Rust 直改配置文件的既有架构债（`AIGameAgent/docs/ARCHITECTURE.md:326` 自列为待办） |
| CLI 是 UI 的后端（`--json` 契约） | CodeBuddy 双轨 prompt 生成 |
| 编译期嵌入插件 JS / UI EXE、安装期释放的单 EXE 分发 | fork 上游的同步成本（AGA 路线的问题） |

ADS 是 **Python FastAPI 的工单编排系统**（Agent = Product/Architect/Dev/Test 等 Role，产物 = 代码文件 + 工单状态），AIGameAgent 是 **OpenCode 插件**（Agent = Hermes/Argus，产物 = hooks + 工具）。**六层与 DAG 规则可移植，provider 的具体语义与 Hook 映射必须重新定义** —— 这也是 §11 #1 改成「契约裁剪范围」的原因。

### 12.3 AGA 是另一条路线，不是六层 DAG

同目录的 `AGA`（独立 git 仓库、与插件版互不引用）是 **fork OpenCode 源码、把游戏能力内置进宿主**的方案：`AGA/docs/20261117_01_项目架构概览.md` 描述为「入口层 → Server/API 层（Hono + SSE）→ 领域层（agent/session/tool/provider）→ 基础设施层」的分层单体，**不采用 L0–L5**。两仓库是同一产品的前后演进关系（插件版 2026-03-31~04-10，AGA 04-15 fork），prompt 逐字节同源（`argus.txt` 完全一致、`hermes.txt` 差 2 行产品名），规模差约 50 倍（125 文件 / 2.3 MB vs 4562 文件 / 119 MB）。详见 `AIGameAgent/docs/20261117_04_两仓库对照说明.md`。

**对本方案的含义**：改造目标应锁定「插件版 AIGameAgent 的六层 DAG」；ADS 现状的 hub-and-spoke 单体在形态上更接近 AGA，恰恰是要改造掉的部分，不要被产品级单体带偏。

### 12.4 参考实现暴露的三点警示

1. **规则只在文档里**：`AIGameAgent/docs/ARCHITECTURE.md:27` 写了严格 DAG，但全仓无层级检查脚本、`package.json` 无 layer 校验 → 佐证 §6 守卫的必要性。
2. **prompt 双份漂移**：`AIGameAgent/docs/20261117_04_两仓库对照说明.md:78-81` 记录 `argus.txt` 完全一致、`hermes.txt` 已差 2 行 → ADS 的 P4 Pack 必须保留单一真相源。
3. **L5 委托未做干净**：Rust 后端仍直改配置文件（`AIGameAgent/docs/ARCHITECTURE.md:326` 列为待办）→ ADS 的分界律要把「CLI 是 UI 的后端」写成铁律（§3.2 已补）。
