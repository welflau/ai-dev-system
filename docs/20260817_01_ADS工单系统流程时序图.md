## 一、总览时序（对标 AgentFlow 风格 · 代码实名）

四条生命线与仓库实体对应：

| AgentFlow | ADS |
|-----------|-----|
| 用户/团队 | `User` |
| AgentFlow | `Orchestrator` |
| AI Agent | `BaseAgent` |
| Dashboard | `Frontend` |

箭头只保留**短标识**；完整 API / 方法见下方对照表。

```mermaid
sequenceDiagram
    participant User
    participant Orchestrator
    participant BaseAgent
    participant Frontend

    User->>+Orchestrator: create ticket
    Orchestrator-->>-User: ticket created

    BaseAgent->>+Orchestrator: claim ticket
    Orchestrator-->>-BaseAgent: dispatch action

    BaseAgent->>Orchestrator: report progress
    Orchestrator->>Frontend: publish status

    BaseAgent->>+Orchestrator: report result
    Orchestrator->>Orchestrator: handle result
    Orchestrator->>Orchestrator: finalize
    Orchestrator-->>-BaseAgent: ack

    Frontend->>User: show board
```

### 箭头 ↔ 代码对照

| 图上短文案 | 代码实际调用 |
|------------|--------------|
| `create ticket` | `POST .../chat/confirm-create-requirement` 或 `POST .../tickets/create-direct` |
| `ticket created` | 落库 `tickets` / `requirements`，再调度 `handle_requirement` 或 `process_ticket` |
| `claim ticket` | `poll_loop` / `ticket_ready` → `process_ticket` → `_try_claim_ticket` |
| `dispatch action` | `compose_sop(traits)[status]` → `{agent, action, next_status}` |
| `report progress` | Agent 执行中写 timeline / logs；状态切 `*_in_progress` |
| `publish status` | `event_manager.publish_to_project(..., "ticket_status_changed", ...)` |
| `report result` | Agent `return` → `Orchestrator._handle_agent_result` |
| `handle result` | success → SOP 下一状态；reject → rework/fix；error → `blocked` |
| `finalize` | `_finalize_openspec_after_done` / Checkpoint / 全部完成后 merge |
| `show board` | `frontend/app.js` 看板 + 时间轴 + `STATUS_LABELS` |

`BaseAgent` 运行时具体类：`PlannerAgent` · `ArchitectAgent` · `DevAgent` · `ReviewAgent` · `ProductAgent` · `TestAgent` · `DeployAgent` 等（见 `backend/agents/`）。

## 二、系统结构总览

ADS 以**工单（Ticket）**为执行单元。用户侧通过聊天确认卡创建**需求**或**直接工单**；后端 **Orchestrator** 按项目 **SOP**（`compose_sop(traits)`）轮询/事件驱动，依次调度 Agent；**OpenSpec**（Propose → Apply → Verify → Archive）作为并行 Spec 层叠在 Harness 之上。

```
用户 ──► 聊天/CLI/MCP 确认卡 ──► API 落库
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
            需求拆单路径                        独立工单桶路径
         (Product 拆成多单)                  (create-direct)
                    │                               │
                    └───────────► Orchestrator ◄────┘
                                      │
                         SOP[status] → Agent.action
                                      │
                              Git 提交 / UE 编译·测玩
                                      │
                                 完成 / 部署 / 阻塞
```

## 四、路径 A：需求确认卡 → 拆单 → 工单流水线

适用于「做一个某某功能」等偏大的需求。

```mermaid
sequenceDiagram
    autonumber
    actor User as User
    participant FE as Frontend
    participant Chat as Chat/CLI
    participant MCP as MCP ads_data
    participant API as Backend API
    participant Orch as Orchestrator
    participant Product as ProductAgent
    participant Git as Git

    User->>Chat: 描述需求（如「做一个技能系统」）
    Chat->>MCP: confirm_requirement(title, description…)
    MCP-->>API: mcp-action / 流内 ActionEvent
    API-->>FE: SSE / 流式确认卡
    FE-->>User: 「确认创建需求」绿卡

    User->>FE: 点击确认创建
    FE->>API: POST .../chat/confirm-create-requirement
    API->>API: requirements.status = submitted → analyzing
    API->>Orch: 调度 handle_requirement

    Orch->>Product: analyze_and_decompose
    Product->>Git: 写入 PRD / 需求文档
    Product-->>Orch: 工单列表 + 复杂度
    Orch->>API: INSERT tickets<br/>(pending / planning_done / architecture_done)
    Orch->>API: requirement = decomposed
    API-->>FE: SSE requirement_decomposed

    loop 每个就绪工单
        Orch->>Orch: process_ticket（见第六节）
    end
```

### 复杂度 → 初始工单状态

| 复杂度 | 初始 status | 含义 |
|--------|-------------|------|
| XS（simple / ≤1 单） | `architecture_done` | 跳过策划+架构 |
| S（medium / ≤2 单） | `planning_done` | 跳过 Planner |
| 其它 | `pending` | 完整 SOP 从策划开始 |

## 五、路径 B：直接工单（独立工单桶）

适用于「建个工单修 XX」「改一下 README」等原子任务（设计目标 ≤~4h）。

```mermaid
sequenceDiagram
    autonumber
    actor User as User
    participant FE as Frontend
    participant Chat as Chat/CLI/MCP
    participant API as Backend API
    participant Orch as Orchestrator
    participant Hook as 建单后 Hook

    User->>Chat: 「建个工单 / 修复 X」
    Chat->>API: confirm_direct_ticket → 确认卡
    API-->>FE: 推送绿卡
    User->>FE: 确认创建工单
    FE->>API: POST .../tickets/create-direct<br/>{title, start_from, …}

    API->>API: _get_or_create_standalone_req<br/>(status=standalone)
    API->>API: INSERT ticket<br/>status = start_from
    Note over API: start_from =<br/>pending \| architecture_done \| development_in_progress

    alt start_from = pending
        Hook->>Orch: 推入策划（planning_in_progress）
    else 跳过策划
        Hook->>API: Architect OpenSpec Propose（可选）
    end

    API->>Orch: auto_start → process_ticket
```

## 六、Orchestrator 单工单调度时序

```mermaid
sequenceDiagram
    autonumber
    participant Timer as poll_loop(~30s)<br/>/ ticket_ready
    participant Orch as Orchestrator
    participant DB as DB
    participant SOP as compose_sop(traits)
    participant Agent as Agent
    participant Git as Git
    participant FE as Frontend(SSE)

    Timer->>Orch: 唤醒
    Orch->>DB: 认领就绪工单（非终端 / 依赖满足 / 需求未暂停）
    Orch->>SOP: rule = SOP[current_status]
    Note over SOP: { agent, action, next_status }

    Orch->>DB: status → *_in_progress
    Orch-->>FE: SSE 状态变更 / 时间轴

    Orch->>Agent: action(context)
    Agent->>Git: 写产物（可选）
    Agent-->>Orch: success / reject / error

    alt success
        Orch->>DB: status = next_status / success_status
        Orch->>Git: _handle_git_files 提交
    else reject（验收/测试/编译失败）
        Orch->>DB: 进入 rework / fix_issues 状态
    else error / 超限
        Orch->>DB: blocked
    end

    Orch->>Orch: 释放锁，派发下一就绪工单
    Orch-->>FE: SSE
```

## 七、典型 Agent 流水线时序（Trait-first + UE）

实际跳转由 `backend/sop/_core.yaml` + `fragments/*`（如 `engine_compile`、`play_test`）决定。下图为常见 UE 项目路径。

```mermaid
sequenceDiagram
    autonumber
    participant Orch as Orchestrator
    participant Planner as PlannerAgent
    participant Arch as ArchitectAgent
    participant Dev as DevAgent
    participant UE as UE 编译/自测
    participant Review as ReviewAgent
    participant Product as ProductAgent
    participant Test as TestAgent
    participant Deploy as DeployAgent
    participant Spec as OpenSpec

    Note over Orch: ticket.status = pending

    Orch->>Planner: write_prd
    Planner-->>Orch: planning_done

    Orch->>Arch: design_architecture
    Arch->>Spec: Propose → openspec_stage=proposed
    Arch-->>Orch: architecture_done

    Orch->>Dev: develop
    Dev->>Spec: Apply（若有 change/tasks）→ applied
    Dev->>UE: SelfTest / 可选
    alt 自测失败
        Dev-->>Orch: self_test_failed → fix_issues 循环
    else 开发完成
        Dev-->>Orch: development_done
    end

    opt trait engine:ue5
        Orch->>Dev: run_engine_compile
        alt 编译失败
            Dev-->>Orch: engine_compile_failed → fix（max_retries）或 blocked
        else 通过
            Dev-->>Orch: engine_compile_passed
        end
        opt play_test fragment
            Orch->>Test: run_playtest → play_test_*
        end
    end

    Orch->>Review: code_review → review_passed

    Orch->>Product: acceptance_review
    alt 验收不通过
        Product-->>Orch: acceptance_rejected → Dev.rework
    else 通过
        Product-->>Orch: acceptance_passed
    end

    Orch->>Test: run_tests
    Test->>Spec: Verify → verified
    alt 测试失败
        Test-->>Orch: testing_failed → Dev.fix_issues
    else 通过
        Test-->>Orch: testing_done
    end

    Orch->>Deploy: deploy → deployed
    Deploy->>Spec: Archive → archived

    Note over Orch: 需求下全部工单完成时<br/>可合并 feat → develop
```

### Web 默认 SOP（无 traits）差异

`default_sop.yaml` 常见路径更短：

`pending → Architect → Dev → Review → Product 验收 → Test`，完成后 Orchestrator 做分支合并；Deploy 更常出现在 trait-first / UE fragment 路径。

```mermaid

    planning_in_progress --> planning_done

    development_in_progress --> development_done

    development_done --> engine_compile_pending: UE fragment
    engine_compile_pending --> engine_compile_passed
    engine_compile_pending --> engine_compile_failed
    engine_compile_failed --> development_in_progress: fix / 超限→blocked

    development_done --> review_in_progress: Review
    engine_compile_passed --> review_in_progress

    review_in_progress --> review_passed

    review_passed --> acceptance_rejected
    acceptance_rejected --> development_in_progress: rework

    acceptance_passed --> testing_in_progress: Test

    testing_failed --> development_in_progress: fix

    testing_done --> deploying: Deploy

    deploying --> deployed

    pending --> blocked: error / 人工
    development_in_progress --> blocked
    [*] --> cancelled: 用户取消
    deployed --> [*]

    blocked --> [*]
```

## 九、OpenSpec 与 Harness 并行层

```mermaid
sequenceDiagram
    participant Harness as Harness(SOP/Agent)
    participant Spec as OpenSpec

    Note over Harness,Spec: 同一工单生命周期上的两条线

    Harness->>Harness: Architect.design
    Harness->>Spec: Propose → proposed

    Harness->>Harness: Dev.develop
    Harness->>Spec: Apply → applied

    Harness->>Harness: Test.run_tests
    Harness->>Spec: Verify → verified

    Harness->>Harness: Deploy / finalize
    Harness->>Spec: Archive → archived
```

三层 UI（Spec / Discipline / Harness）见前端 `HARNESS_PHASES`；OpenSpec 阶段字段为 `tickets.openspec_stage`，**不是** `TicketStatus`。

## 十二、阅读提示

1. **时序以 SOP 为准**：项目 traits 不同，插入的 fragment（UX / 美术 / HTML 原型 / 编译 / 玩法测）不同。  
2. **确认卡不落库**：MCP/`confirm_*` 只推草稿；用户点「确认」才调创建 API。  
3. **阻塞与循环**：验收/测试/编译失败会回到 Dev 修复；超限或硬错误进入 `blocked`。  
4. **在支持 Mermaid 的查看器中打开本文**（GitHub / VS Code / Cursor 预览）即可渲染全部时序图与状态图。
