# QA 引擎日志闭环设计方案

> 设计日期：2026-11-05
> 借鉴来源：MagicAI 的 QA 理念——「用引擎跑场景验证，不是逐文件检查；引擎日志是主要证据」，报告强制表格化（编译表/场景表/交互表/问题表）+ PASS/FAIL + A-F 评级
> 状态：Phase 1 已实现并提交（commit 6c02048），Phase 2/3 待做

---

## 一、目标与定位

对标 MagicAI 的 QA：**QA Agent 不再读代码给意见，而是跑引擎拿日志当证据**，输出四表结构化报告。

ADS 的 UE 项目 QA 链由**两个独立阶段**组成（`sop/plugins/ue5/fragments/`）：

```
engine_compile (priority 95) ──> play_test (priority 85)
  DevAgent.run_engine_compile      TestAgent.run_playtest
  UECompileCheckAction             UEPlaytestAction
  产出 compile_log                 产出 playtest_log
```

**缺口**：两个阶段各自产出结构化日志（引擎日志已解析），但**没有整合成统一 QA 报告**。

---

## 二、现状盘点（已有能力，勿重复造轮子）

| 阶段 | Action | 结构化产出 | artifact kind |
|---|---|---|---|
| 编译 | `UECompileCheckAction` | `errors: [{file, line, code, category, severity, msg}]` + warnings | `compile_log` |
| 试玩 | `UEPlaytestAction` | `tests: [{name, result, errors}]` + summary + screenshots | `playtest_log` |

两个 Action 都已经**把引擎日志解析成结构化结果**——这正是 MagicAI 的核心难点（引擎日志→结构化证据），ADS 已经做完。

**Phase 1 已实现**（`agents/test.py::run_playtest`）：把 `UEPlaytestAction` 的结构化结果渲染成 `playtest-report.md`，含：
- 结论 PASS/FAIL/ERROR + A-F 评级（`_grade_playtest`）
- 汇总表 + 测试结果表 + 问题清单 + 截图

**Phase 1 的局限**：只覆盖 `play_test` 阶段，未整合 `engine_compile`（编译表缺失），未区分交互类测试（交互表缺失）。

## 三、完整设计（四表，对齐 MagicAI）

### 3.1 四表映射（MagicAI → UE）

| MagicAI 表 | UE 对应 | 数据来源 |
|---|---|---|
| 编译表 | UBT 编译错误 | `compile_log` 的 `errors`（file/line/code/category/msg） |
| 场景表 | Automation 测试结果 | `playtest_log` 的 `tests`（name/result/errors） |
| 交互表 | Functional/Input 类测试 | `tests` 里 name 含 `Functional`/`Interaction`/`Input` 的子集 |
| 问题表 | 编译错误 + 失败测试汇总 | 合并 errors + failed tests |

### 3.2 统一报告结构

```markdown
# QA 报告 — {ticket_title}

> 引擎 UE 5.5 | 编译 {compile_duration}s | 试玩 {playtest_duration}s

## 结论：PASS / FAIL（评级 B）

## 编译表
| 文件 | 行 | 错误码 | 分类 | 信息 |
|---|---|---|---|---|
| Source/Player.cpp | 42 | C2065 | compile | undefined identifier |

## 场景表
| 测试名 | 结果 | 错误 |
|---|---|---|
| Project.Functional.Smoke | ✅ passed | — |

## 交互表
| 交互测试 | 结果 |
|---|---|
| Project.Functional.Input_Jump | ✅ passed |

## 问题清单
- [编译] Source/Player.cpp:42 C2065 ...
- [试玩] Project.Functional.Move: assertion failed ...

## 截图
- path
```

### 3.3 综合评级

编译 + 试玩都通过才 PASS；任一失败 → FAIL。评级按综合通过率：
- 编译通过 + 测试通过率 ≥ 100% → A
- 编译通过 + 测试通过率 ≥ 80% → B
- 编译失败 → F（编译不过直接判死，无需看测试）

## 四、整合方案

### 4.1 整合点

`play_test` 阶段（QA 链最后一环）**回溯读取 `compile_log` artifact**，合并成统一报告。

```python
# run_playtest 里，生成报告前
compile_data = await _load_compile_log(context)   # 读 artifacts 表 compile_log kind
report_md = self._render_qa_report(context, compile_data, playtest_data)
```

### 4.2 compile_log 读取

- 从 `artifacts` 表查 `type='compile_log'` 且 `ticket_id` 匹配的最新一条
- 解析 JSON content（errors/warnings/summary）

### 4.3 交互表（Phase 3）

对齐 MagicAI 的「交互安全追踪」（qa 4.2）：枚举交互入口 → 追踪调用链 → 查空引用/信号不匹配/递归/连点崩溃。这是**静态代码分析**，不是运行时测试。

#### MagicAI → UE 交互入口映射

| MagicAI（Godot） | UE 对应 |
|---|---|
| `pressed.connect` 枚举 | C++ `BindAction`/`AddDynamic`；Blueprint `OnClicked`/`OnPressed` |
| `_gui_input` | UMG `UButton.OnClicked`、`InputComponent` |
| 查空引用 | 回调里 `IsValid` 检查 |
| 信号不匹配 | `AddDynamic` 委托签名 |
| 递归 | `OnClicked` 里触发自身 |
| 连点崩溃 | 无防抖/冷却 |

#### 分两层

**3a 渲染层（快速，纯渲染）**：从 play_test 的 tests 筛选 `Functional`/`Interaction`/`Input` 子集，单列交互表。无新工具。

**3b 静态检查层（完整，对齐 MagicAI）**：LLM 读 C++ 源码，枚举交互入口 + 按检查清单逐项检查：
1. 空引用：回调里是否 `IsValid` 检查
2. 委托配对：`AddDynamic` 是否配对 `RemoveDynamic`
3. 递归：`OnClicked` 里是否触发自身
4. 防抖：连点是否加冷却/防抖

#### 范围限制

- C++ 项目可静态检查（grep 源码）；Blueprint 项目（.uasset 二进制）无法静态 grep，只能靠 3a 的 Functional 测试。
- 3b 需要 LLM 读源码 + 新检查流程，改动较大。

### 4.3.1 Phase 3b 评估结论（暂缓）

#### 现状盘点（关键发现）

- `_static_analysis_ue`（test.py:498）已复用 `ue_lint` 规则集（R1-R8），但 8 条规则**全是编译正确性/工程结构**（GENERATED_BODY / OnRep / include 路径 / Build.cs 依赖 / uproject 模块 / include 顺序 / 类型头文件 / 文件类型），**零交互检查**。
- `_code_review`（CodeReviewAction）是通用 LLM 审查，不专门针对交互。

#### Phase 3b 独特价值 vs 限制

| 维度 | 评估 |
|---|---|
| 独特价值 | 静态枚举能发现「未写测试的交互入口」，补 Functional 测试盲区 |
| Blueprint 限制 | .uasset 二进制无法静态 grep，而 UE 项目大量用 Blueprint → **覆盖面受限** |
| 复杂度 | UE 委托（AddDynamic/UPROPERTY 反射/动态绑定）比 Godot pressed.connect 复杂，静态追踪调用链很难 |
| 成本 | LLM 读源码 + 逐项检查，且 LLM 检查有不确定性（不如确定性规则可靠） |

#### 替代方案（更务实）

**扩展 `ue_lint` 规则集，加 R9+ 交互安全规则**（确定性正则，而非 LLM 检查）：
- R9：`AddDynamic` 后无配对 `RemoveDynamic`（委托泄漏/悬挂指针）
- R10：交互回调（OnClicked/OnPressed/BindAction 回调）内无 `IsValid` 检查（空引用）
- R11：交互回调内递归触发自身（无限递归）

优点：确定性、便宜、可复用 ue_lint 的 blocking/warning 分级 + 逃生注释 + 现有测试框架。

#### 建议

**暂缓 Phase 3b（LLM 检查版）**。若要做交互静态检查，走 ue_lint 扩展路线（R9+ 确定性规则），而非独立 LLM 检查流程。

## 八、验收边界（对标遗漏补记）

> 补记日期：2026-11-10，由一次真实误判触发（TK-20261110-48b6af）。

### 遗漏点

对标 MagicAI 时，本方案关注的是 QA 闭环的**下游**（检查结果怎么展示：编译表/交互表/报告渲染），漏了**上游**——验收判定的边界约束（工单级 vs 需求级）。

`acceptance_review`（ProductAgent 验收）是 ADS 自己的 SOP 阶段，早在 MagicAI 对标前就存在，对标时没有深入它。

### 问题表现

工单「初始化项目脚手架与技术栈」（描述：搭建 Vite+TS+Three.js 骨架）的验收反馈，通篇在讲「驾驶物理四要点已完整覆盖」（加减速/转向/抓地力/赛道碰撞），配图却是只有骨架占位卡的空页面——反馈像在验收整个赛车游戏，实际上物理功能一行未写。

### 根因

1. **CLI 纯文本模式看不到截图**：验收 prompt 明确告诉模型「截图你看不到，请结合代码判断」，验收模型只能靠代码判断。
2. **验收 Agent 自主探索仓库失控**：codebuddy 验收时自己读了仓库，看到脚手架交付的类型定义文件（为后续物理模块预定义了 acceleration/turnRate/grip 等字段），把「类型字段存在」当成了「四项验收要点覆盖」。
3. **验收 prompt 无边界约束**：没有告诉模型「类型定义/接口预留 ≠ 功能实现」「验收对象是本工单交付物，不是整个需求」。

### 修复（e91260f）

`acceptance_review.py` 加验收边界约束：

1. `req_context` 加「验收边界」段：验收对象 = 本工单交付物；类型定义/接口预留 = 为后续工单准备的脚手架，「字段存在」≠「功能实现」；严禁把整个需求的验收要点套到本工单。
2. 验收标准改为「功能符合**本工单描述**」（不是整个需求）。
3. `node_instruction` 加反馈格式约束：第一句先明确「本工单交付物是否完成」。

### 启示

QA 闭环不止「结果怎么展示」，还包括「判定怎么约束」。若 MagicAI 有工单级 vs 需求级验收的区分机制，是后续可继续对标的方向。
