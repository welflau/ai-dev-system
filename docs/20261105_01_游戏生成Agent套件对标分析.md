> 目的：从 MagicAI 的"游戏生成 Agent 套件"提炼可借鉴的设计模式与反面教训，映射到本系统（ai-dev-system）

## 一、定位

MagicAI 的"游戏生成 Agent 套件"是基于 CodeBuddy Agent SDK 的多智能体系统：

- **1 个 Lead（GameDirector）+ 5 个子 Agent**：designer / developer / artist / qa / publisher
- 从零自动生成 Godot 游戏

与本系统（Orchestrator + 7 Role）**同构**：编排器 + 专业子 Agent + SOP + Skills + 闭环验证。差别只在产出物——它产出游戏，本系统产出软件/UE 内容。因此它的设计决策对本系统有直接迁移价值。

## 二、可借鉴的设计模式（5 个高价值点）

### 1. 请求分类入口（Phase -1）—— 最值得抄

GameDirector 在做任何事之前先对请求分类：

| 类别 | 触发 | 处理方式 |
|---|---|---|
| **A 大改** | 涉及多模块/新增系统 | 3 步：理解现状 → 追问 → 定计划 |
| **B 小改** | 1-2 模块、局部调整 | 只调必要 Agent，跳过无关阶段 |
| **C 问答** | 纯咨询 | 直接答，不启动流水线 |

代码实现：`MODIFY 模式关键词评分只注册必要 Agent`（`agent_session.py:203-231`）。

**本系统差距**：需求进来直接进 SOP 状态机，缺少廉价的前置分类层。

**迁移方向**：在 `compose_sop(traits)` 之前加一步意图分类（大改/小改/问答），小改只派最小 Agent 集，省 token。

### 2. 强制闭环验证：QA 用引擎日志当证据，不逐文件检查

qa 核心理念：**用引擎跑场景验证，不是逐文件检查**。引擎日志是主要证据，输出强制结构化：
- 编译表 / 场景表 / 交互表 / 问题表
- PASS / FAIL + A-F 评级

**本系统现状**：已有 `UECompileCheckAction` + `UEPlaytestAction`，但 QA 阶段的价值判断未与引擎日志打通。

**迁移方向**：让 QA Agent 跑 Playtest、解析引擎日志出结构化报告，而非读代码给意见。

### 3. 文档驱动通信 + 断点续做

Agent 之间**不直接发消息，全部通过 `designs/` 目录文档传递**，天然可追溯、可断点续做。

**本系统现状**：已有 OpenSpec / Checkpoint，但"文档是 Agent 间唯一契约载体"这条原则可以更明确，避免 Orchestrator 在 prompt 里转发消息造成的损耗。

### 4. 确定性约束清单

给每个 Agent 写死"代码规范清单"（全类型注解、`_physics_process`、空守卫、`clamp` 钳制、实体数量上限、输入归一化），以及资产获取的**四级 fallback 优先级**（搜库 → AIGC → 本地 PIL → 兜底）。

本质：**用确定规则压缩 LLM 的随意性**。

**本系统现状**：Trait-First 技能注入是同方向的，但可补显式 fallback 链（如 UE 资产先查库再生成）。

### 5. 显式协调信号

- **TODO 独占**：只有 Lead 能创建/勾选 TODO
- **完成信号**：`<DIALOG_ALREADY_FINISHED/>`，否则系统持续追问

成本极低，但能消除"任务到底结束没结束"的歧义。

## 三、反面教训（代码级验证暴露的真实问题）

| 坑 | 详情 | 本系统对照 |
|---|---|---|
| **双实现漂移** | CLI/Web 两套 Agent 定义、两套工具命名长期并行维护 | 需警惕"聊天助手"和"工单流水线"两条路径重复定义 Agent |
| **Skills 注入失效** | `load_agent_prompt_with_skills()` 只定义从未被调用，Web 主力路径里 5 个 skill prompt 根本没注入 | **务必自查** Trait-First 注入是否在真正主路径接线，而非"定义了但没调"的死代码 |
| **约束只在 prompt 无代码兜底** | QA 失败回退 3 次、资产优先级，都只是 prompt 约定，无代码计数器强制 | Reflexion 反思/失败重试需加代码层硬计数器 |
| **神文件** | `file_tools.py` 2550 行 + 资产 tools 1748 行，占 MCP 代码 72% | `frontend/app.js` 16000+ 行是同类问题 |
| **prompt 逼近 Windows 32K 上限** | system_prompt 有告警但只打日志无截断兜底 | 本系统同为 Windows 平台，system prompt 拼接需防溢出 |
| **死代码直接崩溃** | `load_config()` 缩进错位导致隐式返回 None，运行时 TypeError | 配置加载路径要加启动自检 |

## 四、落地建议（按性价比排序）

1. **加"请求分类"前置层**：在 `compose_sop` 之前加廉价意图分类（大改/小改/问答），小改只注册必要 Agent。最成熟、最省 token。

2. **打通 QA 与 UE Playtest**：让 QA Agent 跑 Playtest、拿引擎日志当证据出结构化报告。`UEPlaytestAction` 已具备能力，缺的是接进 QA 判定闭环。

3. **自查 Skills 注入是否真生效**：对着"Skills 定义但未接线"的坑，grep `use_skills` 加载链路，确认主路径（而非 CLI 调试路径）真的把 skill prompt 拼进 Agent prompt。

### 发现的问题

| # | 级别 | 问题 | 证据 |
|---|---|---|---|
| 1 | 🔴 确凿 | **双实现漂移**：`_build_system_prompt` 两套并存，旧版零 skills 注入，降级时 skills **静默消失** | `chat_assistant.py:1607` vs `api/chat.py:3346` |
| 2 | 🟡 确凿 | **死代码 + 过时注释**：`self._skills_prompt`（base.py:55 全文计算）对 ChatAssistant 从未被读取，但注释仍写"ChatAssistantAgent 直接读 self._skills_prompt" | grep 全项目 `_skills_prompt` 仅在 base.py + 测试出现 |
| 3 | 🔴 历史事故 | server.log 有 3 处 `'ChatAssistantAgent' object has no attribute '_build_system_prompt'`，双实现迁移期发生过方法缺失 | server.log:106782/106783/119720 |
| 4 | 🟡 语义分裂 | 同一 skill 两条路径表现不同：工单 Agent 全文注入，ChatAssistant 只注入索引（有意，v0.20 主动触发） | `build_prompt_for_agent` vs `build_index_for_agent` |
| 5 | 🟢 无代码兜底 | traits 拉取失败只 `logger.warning` 静默回退静态版，无可观测计数 | base.py:137-139 |

### 结论

主路径（工单 + ChatAssistant 默认）的 Skills 注入**确实接线了**，不是 MagicAI 那种"定义了从未调用"的死代码。但存在同构隐患——**双实现漂移 + 降级时 skills 静默消失**，正是 MagicAI 文档警告的坑。建议后续清理链路 3 旧实现（或让降级路径也复用新 prompt 构建），消除双实现。

## 六、美术工作流体现分析（2026-11-05）

针对"美术工作流在游戏生成流水线中是否有体现"的专项核查（来源：`20261103_04 资产库管理机制` / `20261103_05 AI生成场景工作流` / `20261103_08 Agent套件` / `20261104_01 代码分布统计`）。

### 体现情况：流程层充分、代码层有缺口

| 层 | 体现 | 说明 |
|---|---|---|
| 设计层 | ✅ | designer 分两次调用，第二次专门产出 `art_requirements.md`（美术+音频需求文档） |
| 生成层 | ✅ | artist 是 5 子 Agent 之一，专职资产获取；**严格串行**：artist 先、developer 后，保证资产先存在、代码引用真实路径 |
| 约束层 | ✅ | 四级优先级 fallback：search_assets（搜库）→ generate_asset（AIGC）→ 本地 PIL 占位 → 跑脚本兜底，每项资产须有 search 记录为证据 |
| 支撑层 | ✅ | 独立资产库子系统：元数据进 PG，7 个 MCP 工具，文件三层存储，编辑器同步（HTTP transfer 优先 / base64 fallback，512KB 阈值） |
| 场景级 AIGC | ❌ | 只落地单资产粒度（3d-model/sprite/texture/music/sfx/animation/vfx），`generate_scene` 是 README 蓝图，`src/asset_generation/` 只有 README 无 generator.py |

### 美术工作流的三个接线缺口（代码级验证）

1. **pixel-art 技能未注入**：artist 的美术创作指南在 Web 主力路径不被加载（`load_agent_prompt_with_skills()` 只定义未调用）—— 是"Skills 注入失效"的美术版。
2. **四级优先级无代码强制**：artist 工具白名单同时暴露全套资产工具，优先级只写在 prompt，代码未强制"先 search 再 generate"，artist 可能跳过复用直接 AIGC。
3. **AIGC 任务态纯内存**：`_task_store = {}`，重启丢失 in-flight 任务与 `_asset_id` 关联；`file_url` 指向第三方临时 URL，无自有对象存储，缓存默认落在用户 home 多实例漂移。

### 对本系统的启发（美术资产库 + AI 生图导入 UE）

1. **四级 fallback 链可直接移植**：本系统已有 `art_asset_searcher.py`（搜 G_ArtRes）+ `image_processor.py`（生图）+ AI 生图导入 UE，但缺显式 fallback 链 —— 可定义为「搜本地资产库 → AIGC 生图 → 占位符 → 兜底」，并加代码级强制（而非仅 prompt）。
2. **资产先于开发**：借鉴"artist 先、developer 后"的严格串行，UE 内容工单里美术资产先就位，再让 DevAgent 引用真实资产路径，避免占位符漂移。
3. **优先级要代码兜底**：MagicAI 的反例证明，只写在 prompt 的优先级会被 LLM 跳过，应在 searcher 层强制"先查库、未命中才生成"。

## 七、art_asset_searcher fallback 链接入评估（2026-11-05）

### 现状：三个独立模块，无统一 fallback 链

| 模块 | 能力 | 入口 | 缺口 |
|---|---|---|---|
| `art_asset_searcher.py` | 搜外网（Pexels/unDraw/Poly Haven）→下载→入库 | `search_and_store()` | 只搜外网，无本地库/AIGC/占位 |
| `plugins/content/actions/generate_assets.py` | 搜本地库(33000条,打分+反义词否决)→PIL 占位图 | `GenerateAssetsAction.run()` | **两级 fallback 已有，缺 AIGC 中间层** |
| `image_processor.py` | AIGC 生图（LightAI 异步队列） | `request_image()` | 已接入，但独立队列未接到 generate_assets |

### 关键矛盾

`generate_assets.py:9-11` 注释写"系统当前没有接入图像模型"，但 `image_processor.py` 早已接入 LightAI —— 注释过时。且 `request_image()` 的 `requester` 参数默认值就是 `"ArtAgent"`（image_processor.py:592），说明当初设计时就是给美术用的，只是从没接上。

### 现有 fallback 链（`_resolve_one`，generate_assets.py:206）

```
1. _search_library() → sourced        ✅ 已有（代码强制优先级）
2. [缺失] AIGC 生图 → generated       ❌ 待接入
3. _make_placeholder() → placeholder  ✅ 已有
4. manual_required / not_found        ✅ 已有
```

### 接入方案（推荐：异步投递 + 占位图先行）

基础设施已基本就位：`request_image(requester="ArtAgent")` 默认给美术用；非 chat 分支自动下载到 `G_ArtRes/2d/generated` 并入库（image_processor.py:392-396）；`callback_doc`/`callback_tag` + `_replace_placeholder` 已实现占位符回填（image_processor.py:399-400）。

最小改动 —— 在 `_resolve_one` 未命中本地库后（约 generate_assets.py:222 之后）插入：

```python
# 未命中本地库 → 投递 AIGC（异步），同时保留占位图兜底
if allow_aigc and not needs_frames:
    from image_processor import request_image
    tag = await request_image(
        prompt=f"{aid} {desc}",
        project_id=context.get("project_id", ""),
        ticket_id=context.get("ticket_id", ""),
        requester="ArtAgent",
    )
    # 记录 aigc_tag，占位图照出，生图完成后由 _replace_placeholder 回填
```

设计决策：

1. **异步而非同步**：生图几十秒/张，同步会拖垮工单流水线。`request_image` 投递后立即返回 `[IMG_PENDING:id]`，占位图照出，生图完成后台回填。
2. **SOP 开关**：仿照已有 `fallback_to_placeholder`（generate_assets.py:103），加 `use_aigc`（默认 false，生图有成本）。
3. **优先级天然代码强制**：`_resolve_one` 的执行顺序即优先级，AIGC 插在搜库之后、占位图之前，就实现了 MagicAI 做不到的"代码强制四级 fallback"。

### 与 MagicAI 的关键差异

MagicAI 的优先级是 prompt 约定（artist 自己决定先搜还是先 AIGC，代码无强制）；本系统 `_resolve_one` 的执行顺序天然保证"先搜库、未命中才 AIGC、再占位"。这是本系统对 MagicAI 反面教训（"优先级只在 prompt 无代码兜底"）的正面回应。
