# MagicAI 与 ADS 对比总表

> 汇总日期：2026-11-05
> 依据：`20261105_01`~`_03` 三份对标分析 + MagicAI 源码（`G:\B_OA\AI\MagicAI`）+ ADS 源码（本仓库）
> ADS = ai-dev-system（AI 自动开发系统，本系统）

---

## 一、基本定位

| 维度 | MagicAI | ADS |
|---|---|---|
| 全称 | MagicDawn AI 平台 | AI 自动开发系统 |
| 目标 | 从零生成 Godot 游戏 | 从自然语言到代码部署的全链路自动化 |
| 对标对象 | —（自研游戏生成平台） | Claude Code |
| 技术栈 | FastAPI + PostgreSQL + Next.js + Godot WASM | FastAPI + SQLite + 原生 JS + UE |
| 引擎 | Godot 4.6（浏览器 WASM） | UE 5.x（本机 Editor） |

## 二、多智能体架构

| 维度 | MagicAI | ADS |
|---|---|---|
| 编排模式 | 1 Lead（GameDirector）+ 5 子 Agent | Orchestrator + 7 Role + ChatAssistant + UEEditorAgent + SkillAgent |
| 子 Agent | designer / developer / artist / qa / publisher | Architect / Planner / Dev / Test / Deploy / Art / UX 等 |
| Lead 职责 | 纯调度，不碰文件，只有 Task 工具 | 编排引擎，SOP 状态机驱动 |
| 职责分层 | Lead 不碰文件 / designer 不碰源码 / artist 不写逻辑 | ArtAgent(要什么) / ArtistAgent(从哪来) 分离 |
| 通信方式 | 文档驱动（`designs/` 目录） | artifacts 表 + 磁盘文档 + 事件总线 |

## 三、编排与调度

| 维度 | MagicAI | ADS |
|---|---|---|
| 请求分类 | Phase -1：A 大改 / B 小改 / C 问答 | 无前置分类（直接进 SOP）⚠️ |
| 调度配置 | `agent_session_config.py` 硬编码 | SOP YAML 热插拔 + traits 条件 ✅ |
| 串行控制 | prompt 约定"严格串行" | 代码强制（状态机）✅ |
| TODO 独占 | 仅 GameDirector | —（无此机制） |
| 完成信号 | `<DIALOG_ALREADY_FINISHED/>` | 状态机终态 |
| 优先级强制 | ❌ prompt 约定 | ✅ 代码强制（_resolve_one 顺序） |
| 断点续做 | project_memory + MODIFY 模式 | Checkpoint + OpenSpec |

## 十、核心差异一句话总结

| 系统 | 一句话 |
|---|---|
| **MagicAI** | 设计漂亮、集中式架构，但**代码接线滞后于文档**（Skills 失效、双实现、AIGC 任务态纯内存） |
| **ADS** | 调度配置成熟、代码强制优先级，但**能力分散 + AIGC 断链**（资产工具散落、ArtistAgent 未接生图） |

**双向可借鉴**：
- ADS → MagicAI：任务态落库、代码强制优先级、SOP YAML 热插拔
- MagicAI → ADS：fix_output_path 路径纠偏、AIGC 接入 ArtistAgent、请求分类前置层
