## 一、背景与动机

### 前作留下的半步

`20260802` 那篇方案做到了「**接新工具集 = 一个 SKILL.md + 一个 SOP fragment，零 Python 改动**」。SkillRunner / GenericCLIAction / SkillAgent / executable_loader 都已落地并在 OpenSpec 上跑通。

但那个等式右边还有两项。本方案要把它变成「**= 一个 SKILL.md**」。

### 为什么 fragment 那一项是多余的

一个能力目前要在三个地方声明，描述的却是同一件事：

| 声明什么 | 住在哪 | 匹配字段 |
|---|---|---|
| 插在流程哪一步 | `backend/sop/fragments/*.yaml` | `required_traits` + `insert_after` |
| 给哪个 Agent 注入什么知识 | `backend/skills/skills.json` | `traits_match` + `inject_to` |
| 能调哪些工具 | `executable_skills/*/SKILL.md` | `x-runner` |

三套 trait 匹配逻辑、三个文件，彼此之间没有一致性校验。加一个能力要改三处。

更能说明问题的是：`grep skill_id backend/sop/` **零结果**。SkillAgent 注册在 `agent_registry.py:100`，设计上就是给 SOP 用 `config.skill_id` 调度的，但没有任何 fragment 用它。唯一在跑的 executable skill 是 `agents/architect.py:103` 里硬编码的 `load_executable_skill("openspec-propose")`。

**这条路修好了，但没人走。** 本方案让它成为主干道。

### 为什么位置锚点是错误的抽象

`insert_after: development` 表达的是**位置**，不是**依赖**。后果有三：

1. **顺序硬编码进每个能力**。想在 A 和 B 之间插 C，要改 B 的锚点。
2. **LLM 无法动态组装**。让 LLM 吐 `insert_after` 序列，它一定会编出锚点不存在的 stage。
3. **锚点失效是静默的**。`loader.py:134-145` 对找不到锚点的 fragment 只是 warning 后追加到末尾。

正确的声明是**数据契约**：我消费什么 kind，我产出什么 kind。顺序由拓扑排序得出。

### 关键洞察：下游零改动

`backend/sop/loader.py:231` 的 `_relink_stage_transitions()` 会**覆盖** fragment 自己声明的 `trigger_on`，按线性位置重新链状态：

```python
# loader.py:260
if prev_success:
    s["trigger_on"] = prev_success
```

所以 `insert_after` 本质只是个**排序 hint**，真正的状态链是组装后推导出来的。

**把排序依据从位置锚点换成数据依赖，`sop_to_transition_rules` / orchestrator / 前端全部无感。** 这是本方案成本可控的根本原因。

## 三、详细设计

### 3.1 base_stages 可裁剪

**问题**：`loader.py:70` 无条件 `base_stages = list(core.get("base_stages", []))`，8 个阶段（planning → architecture → development → code_review → acceptance → deploy + rework / development_retry 两个 branch_only）一个都跳不过。内容生成类项目会被迫先跑架构设计、代码开发、代码审查、部署才能到达 skill 链。

**做法**：给 base_stage 支持 `required_traits`，在第 70 行后插一次 `_fragment_matches()` 过滤（函数原样复用，把 stage 当 frag 传）。

```yaml
# _core.yaml
  - id: development
    required_traits: {none_of: [pipeline:content]}
```

`trait_taxonomy.yaml` 加新维度：

```yaml
pipeline:
  description: "主流程形态。决定 base_stages 裁剪与 skill 链锚点。"
  values: [code, content]     # 缺省 = code（无此 trait 时行为完全不变）
```

**三个必须同时处理的连带问题** —— 这是裁剪的真实成本：

| # | 问题 | 处理 |
|---|---|---|
| a | `_relink_stage_transitions:256` 对 `i == 0` 是 `pass`（保留原 `trigger_on`）。裁掉 planning 后首个 stage 变成 acceptance，`trigger_on` 仍是 `review_passed` → **工单卡在 pending 永不启动** | 裁剪后**强制**把首个非 branch_only stage 的 `trigger_on` 覆盖为 `pending` |
| b | 7 个 fragment 锚在 `development`（engine_compile / i18n_check / play_test / smoke_test / ue_test_gen）或 `insert_before: development`（asset_gen）。锚点消失时 `loader.py:134-145` 只 warning 后追加末尾，**静默错位** | 这些 fragment 的 trait 恰好都是代码/游戏项目，`pipeline:content` 不会命中。**但这是隐含耦合**，靠两套独立 trait 条件碰巧对齐。加失锚校验：裁剪后有 fragment 找不到锚点 → ERROR + diagnostic |
| c | `_core.yaml:146` 的 `pipeline_view.stages` 里 `sop_stages: [development, code_review, acceptance, rework]` 引用了可能被裁的 stage，前端会显示空组 | `_merge_pipeline_view` 清理失效引用；某组清空后整组移除 |

### 3.2 artifact kind 注册表

新建 `backend/artifacts/kinds.yaml` + `kinds.py`。

```yaml
version: 1
kinds:
  ticket_brief:
    description: 工单需求的结构化快照（框架内置，ArtifactStore 自动产出）
    mime: application/json
    builtin: true          # 天然源，不需要任何 skill produces
  content_outline:
    mime: text/markdown
legacy_type_aliases:       # 老 artifacts.type → kind，只读不写
  prd: ticket_prd
```

**防漂的三道闸**。`trait_taxonomy.yaml` 失守的根因是「只有文档约定、没有代码校验」—— `config_packs/content-creation/pack.json` 已经在用词表里没有的 `category:content`：

| 闸 | 位置 | 行为 |
|---|---|---|
| 扫描期 | `discover_workflow_skills()` | 未注册 kind → **该 skill 出局 + ERROR 日志**（不是 warning —— trait_taxonomy 就是因为 warning 没人看才漂的） |
| 写入期 | `ArtifactStore.put()` | 未注册 kind → raise |
| CI 期 | `test_kinds_registry.py` | 扫所有 SKILL.md 断言 kind 全在词表 |

第三道才是真正的保险。集中词表意味着加一个 skill 要改两个文件 —— 接受这个摩擦，换「consumes 永远匹配不上」这类静默失败变成启动即报错。

### 3.3 x-workflow schema

与 `x-runner` 并列的第二个 frontmatter 命名空间。**只声明身份与数据契约，状态链全部推导。**

```yaml
---
name: demo-draft
description: 按大纲写成稿
x-workflow:
  version: 1
  stage_id: demo_draft                 # 必填，全局唯一，= SOP stage.id
  stage_name: 正文撰写                  # 可选，默认取 name
  consumes:
    - kind: content_outline            # 简写 = {kind: ..., required: true, mode: path}
    - {kind: style_guide, required: false, mode: path}   # path(默认) | text
  produces:
    - {kind: draft_article, glob: "draft.md", mime: text/markdown}
  required_traits: {any_of: [pipeline:content]}
  required_ticket_type: {none_of: [bug-fix, rollback]}
  priority: 50                         # 仅用于同层稳定排序
  fanout: false                        # 预留，见 §五-1
  pipeline_view_contrib:               # 原样复用 fragment 的语义
    group: content_pipeline
    create_if_missing: {name: 内容流水线, icon: 📝, insert_after: requirement_analysis}
x-runner:
  builtin_tools: [write_file, read_file]
  outputs:
    root: "artifacts/{req_short}/{ticket_short}/draft_article"
    globs: ["draft.md"]
  budget: {max_rounds: 10, max_seconds: 300}
---
```

**推导规则**（都不写在 SKILL.md 里）：

| 字段 | 推导 | 理由 |
|---|---|---|
| `agent` | 固定 `SkillAgent` | 决策 2 |
| `action` | `skill_{stage_id}` | 避开 `loader.py:500` `by_action` 先到先得的碰撞 |
| `success_status` | `{stage_id}_done` | — |
| `reject_status` | `{stage_id}_failed` | — |
| `trigger_on` | 由 `_relink_stage_transitions` 覆盖 | 写了也白写 |
| `reject_goto` | **不配** | `loader.py:395` 会据此派生回跳规则，指向 SkillAgent 会变成无限重试 |
| `config` | `{skill_id, _stage_id, _success_status, _consumes, _produces}` | 经 `orchestrator.py:1833` 自动进 `context["sop_config"]` |

traits 过滤**复用 fragment 的 `required_traits`** 而非 `skills.json` 的 `traits_match` —— 同一套 all_of/any_of/none_of 语义，名字不同而已，`_fragment_matches()` 原样可用，零新代码。

### 3.4 拓扑排序组装器

新文件 `backend/sop/workflow_composer.py`：

```python
@dataclass
class WorkflowSkill:
    skill_id: str; stage_id: str; stage_name: str
    consumes: List[ConsumeSpec]; produces: List[ProduceSpec]
    required_traits: Optional[dict]; required_ticket_type: Any
    priority: int = 50
    source_path: Path = None
    pipeline_view_contrib: Optional[dict] = None

def discover_workflow_skills(repo_path: str = "") -> List[WorkflowSkill]:
    """扫 backend/skills/executable_skills/*/SKILL.md +
       <repo>/.claude/packs/*/skills/*/SKILL.md，取有 x-workflow 的。
       项目级同 stage_id 覆盖内置（与 _find_skill_dir 优先级一致）。"""

def compose_workflow_stages(
    skills, traits, ticket_type, available_kinds,
) -> Tuple[List[Dict], List[str]]:     # (stages, diagnostics)
```

`discover_workflow_skills` 是新增函数 —— 现有 `executable_loader.py` 只能按 id 加载，没有发现机制。

**五种边界情况的裁决**：

| 情况 | 处理 | 理由 |
|---|---|---|
| 缺源（required kind 无 producer 且非 builtin） | 该 skill 出局，fixed-point 级联重算（它 produce 的 kind 也消失，下游跟着出局） | 不是错误，是「这个项目用不上这个能力」 |
| 歧义（一 kind 多 producer） | 按 `(-priority, stage_id)` 取首，**其余剔除**出本次组装 + diagnostic | 装两个会在同一 kind 上互相覆盖，产物总线语义被破坏。真要分叉应该用不同 kind。不要「都装」 |
| 成环 | **整条 skill 链不组装**，退化成纯 fragment SOP + ERROR | 部分组装会产出「看着能跑但中间断链」的 SOP，比没有更危险 |
| 同层顺序 | Kahn + heap，key `(-priority, stage_id)` | 稳定且可预测，便于写测试 |
| 可并行但被串行化 | diagnostic 记「检测到 N 处」 | 见 §五-1 |

### 3.5 skill 子链插入锚点

`_core.yaml` 新增顶层字段：

```yaml
skill_block_anchor: {insert_before: acceptance}   # 缺省 = 末个非 branch_only 之后
```

整条 skill 子链作为**一个块**插入该锚点，块内按拓扑序。一个字段同时服务两种 profile：

- 代码项目：缺省追加在 deploy 之后（skill 链是对代码流程的增强）
- 内容项目：锚在 acceptance 之前（生成 → 人工验收）

**必须插在 branch_only 区块之前** —— `_relink_stage_transitions` 跳过 branch_only，插在后面会让 skill 的 `trigger_on` 接错。

锚点放在 `_core.yaml` 而不是每个 skill 里：skill 不该知道自己在流程的哪个位置，那正是本方案要消除的耦合。

### 3.6 ArtifactStore（产物总线）

新包 `backend/artifacts/{kinds,store,injector}.py`。

```python
@dataclass
class ArtifactRef:
    id: str; kind: str; name: str
    rel_path: str          # 相对 repo_path，POSIX
    abs_path: str
    mime: str; size: int
    ticket_id: str; requirement_id: str; project_id: str
    metadata: Dict[str, Any]; created_at: str

class ArtifactStore:
    async def put(*, project_id, ticket_id, kind,
                  src_path="", content=None, ...) -> ArtifactRef
    async def get(artifact_id) -> Optional[ArtifactRef]
    async def list(*, ticket_id="", kinds=None,
                   latest_per_kind=False) -> List[ArtifactRef]

artifact_store = ArtifactStore()   # 模块级单例，与 db / git_manager 一致
```

**落盘约定**（对齐 `orchestrator.py:3770` 的 `docs_prefix` 风格）：

```
<repo>/artifacts/{req_id[-6:]}/{ticket_id[-6:]}/{kind}/{filename}
```

按 ticket 再按 kind 分目录：一个工单的产物聚在一起便于人工翻看和 git diff 审阅，kind 作末级目录让 glob 与 consumes 的映射直观。`x-runner.outputs.root` 直接写这个模板 → SkillRunner 写出来就在位，`put` 只登记不搬运。

**表改动**：`artifacts` 加 4 列，走 `database.py:51` 的 `_auto_migrate`：

```python
("artifacts", "kind",        "TEXT"),
("artifacts", "mime",        "TEXT"),
("artifacts", "size_bytes",  "INTEGER DEFAULT 0"),
("artifacts", "produced_by", "TEXT"),
```

`database.py:1002` 那条「不要把列挪去 _auto_migrate」的警告针对的是**被索引引用的列**（`executescript` 一条语句失败会整段中止）。这 4 列无索引，migrations 列表里已有大量同类先例。

**老路径一律不动**。`orchestrator.py` 的 13 处 `db.insert("artifacts")` 里 `content` 存的是 `result_json`，被 `_build_context`（orchestrator.py:3787-3803）反序列化成 `architecture` / `dev_result` / `test_result`。改成路径会直接炸。`put` 时**双写 `type = kind`**，让老的 `WHERE type IN (...)` 查询也能命中新产物。

**consumes 注入**（`injector.py`）：

```python
async def build_consume_context(consumes, project_id, ticket_id,
                                requirement_id, repo_path) -> Dict[str, Any]:
    """→ {"_artifacts": {kind: {path, abs_path, mime, size, text?}},
          "_artifacts_missing": [kind, ...]}
       mode=path 只给路径；mode=text 额外读文本（上限 8000 字符，二进制跳过）。
       同 kind 多条取 created_at 最新。"""
```

SkillAgent 在 `_run_skill` 里调它并入 `run_ctx`，`SkillRunner._build_system` 渲染成：

```
## 上游产物（已就绪）
- content_outline: artifacts/a1b2c3/d4e5f6/content_outline/outline.md (2.1KB)
  用 read_file 工具读取（path 相对仓库根）

## 缺失的可选产物
- style_guide（上游未产出，按默认风格处理）
```

**路径为主 + 显式提示自取**，不把全文塞 system —— 对二进制和大文件都成立，也省 token。

### 3.7 SkillRunner 改造

```python
@dataclass
class ArtifactOut:
    rel_path: str; abs_path: str
    kind: str = ""; mime: str = ""
    size: int = 0; is_binary: bool = False

@dataclass
class SkillRunResult:
    status: str
    outputs: List[ArtifactOut]       # ← 破坏性变更（原 Dict[str, str]）
    rounds: int = 0
    message: str = ""

    @property
    def text_outputs(self) -> Dict[str, str]:
        """兼容属性，只收文本扩展名。让两个 OpenSpec 调用点零改动。"""
```

`_collect_outputs`（runner.py:241）**完全不读内容**：

```python
result.append(ArtifactOut(
    rel_path=p.relative_to(out_root).as_posix(), abs_path=str(p),
    kind=kind_by_glob.get(pattern, ""),
    mime=mimetypes.guess_type(p.name)[0] or "application/octet-stream",
    size=p.stat().st_size,
    is_binary=p.suffix.lower() not in _TEXT_EXTS,

```

这是二进制硬伤的根治 —— 原第 251 行 `p.read_text(encoding="utf-8", errors="replace")` 会把 PNG / MP3 / MP4 读成乱码塞进内存。需要内容的调用方自己读 `abs_path`。

**kind ↔ 文件映射：一个 glob 对一个 kind**。不改 `x-runner.outputs.globs` 的结构（`expected_output_count` 还在用）。多文件同 kind 就把 glob 写成 `images/*.png`，一个 glob 命中多文件、全归同一 kind。

**媒体工具**：`_build_actions`（runner.py:139）加分支，新建 `backend/actions/gen_image.py`，复用 `image_processor.py` 的 `_create_lightai_task` / `_poll_lightai_task` / `_download_image`（已是 `await asyncio.sleep` 的非阻塞 IO），**阻塞等待直到出图**。

不走 `image_requests` 表 + `[IMG_PENDING:id]` 占位符那套：它服务于「文档先写、图后补」，与 skill 链「产物须在 stage 结束时就绪」的语义冲突。返回 `request_id` 让 LLM 自己写轮询循环会烧 turn 且容易卡死在「再查一次」。

### 3.8 orchestrator 的 SkillAgent 分支

插在 `orchestrator.py:2232`（ArtistAgent 分支）**之前**，与其它 early-return 并列，不碰 12 个现有分支的 elif 链。

缺这个分支会落到第 3108 行 `else: new_status = current_status` → 状态不推进 → 同一条 rule 反复命中死循环烧 token。`orchestrator.py` 的 2233 和 2369 行注释都明确警告过这个坑（ArtistAgent 和 UEEditorAgent 都是因为踩了才补的分支）。

```python

    sop_cfg = result.get("sop_config") or {}
    st = result.get("skill_status")
    if st in ("success", "partial"):
        new_status = result.get("success_status") or sop_cfg.get("_success_status")
        for a in result.get("artifacts") or []:
            await artifact_store.put(kind=a["kind"], src_path=a["abs_path"], ...)
    elif st == "skipped":          # availability 不满足，跳过别卡流水线
        new_status = sop_cfg.get("_success_status")
    else:
        new_status = TicketStatus.BLOCKED.value
    ...
    return
```

**`budget_exceeded` 但 produces 的 kind 已全部扫到 → 按 success 处理。** `query_engine/engine.py:391` 的 `Budget.check()` 只在轮与轮之间生效，`gen_image` 阻塞完回来下一轮开头就可能触发超时 —— 此时图已落盘，判 blocked 等于白烧一次钱。

**失败不自动重试**：重跑一个 LLM 自由发挥的 skill，烧 token 的风险远大于收益。

## 五、风险与局限

### 本次不解决，明确记录

**1. 阶段间并行度被压平**

拓扑排序能表达「A、B 并行后汇入 C」，但 `_relink_stage_transitions` 会压成 A→B→C 串行链。根因比表面更硬：orchestrator 的 `transition_rules` 是 `Dict[status → rule]` **单链模型**，一个状态只能映射一条规则。改它等于重构整个调度器。

**出路是阶段内扁出子工单**：给 SkillRunner 的 builtin 池加 `dispatch_subtask` 工具。这套机制 `backend/actions/chat/dispatch_subtask.py` 已完整实现 —— 父工单进 `waiting_subtasks` 等齐、深度上限 3、循环检测。`orchestrator.py:57` 的 `_MAX_CONCURRENT_SUBTASKS = 3` 需要调高。

本次只在 x-workflow 预留 `fanout` 字段 + diagnostics 输出「检测到 N 处可并行但已串行化」。

**2. base 裁剪与 fragment 锚点是隐含耦合**

§3.1-b 说的「trait 条件碰巧对齐」不是结构性保证。失锚校验只能在运行时报，无法静态证明。

**3. 新旧产物语义不完全互通**

`put` 双写 `type = kind` 只能让新产物被老查询命中；老代码 `WHERE type IN ('prd','ux_design')` 不认新 kind 名（如 `ticket_prd`）。`legacy_type_aliases` 只在读侧生效。这是「老路径不动」的直接代价。

**4. availability 不满足时下游照常启动**

producer skipped 后，下游 required consumer 拿不到产物仍会跑。严格做法是「producer skipped → 下游 required consumer 也 skip」，但需要运行时重算拓扑。本次靠 `_artifacts_missing` 让 LLM 在 prompt 里看到缺什么。

**5. 无产物版本语义**

同一工单返工第二次跑，会在同一路径覆盖文件并在表里插第二条记录。`latest_per_kind` 能正确取新的，但旧文件已被物理覆盖，无法回溯（git 历史是兜底）。

**6. compose_sop 无缓存但开始扫磁盘**

`_sop_stage_for`（orchestrator.py:309）每次都调 `compose_sop`，加扫 SKILL.md 后单次开销从 13 个 yaml 变成 13 + N 个 md。`_project_rules_cache` 只缓存 rules 不缓存 config。步骤 9 顺手加 `lru_cache`（key = traits tuple + ticket_type + repo_path），invalidate 挂到现有 `invalidate_project_rules`。上线前量一下真实调用频率。

### 实战验证样本仅为 1

`executable_skills/` 目前只有 3 个 skill，全是 openspec 相关，且只有 `openspec-propose` 真正被调用过。**x-runner 机制的实战验证样本 = 1。** 本方案把工作流编排的重心压上去之前，步骤 13 的端到端 demo 是必要的前置验证，不能跳。
