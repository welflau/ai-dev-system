## 一、背景：三层架构全景

基于《OpenSpec ≠ Harness Engineering》文档，AI 工程化存在三个独立但互补的层次：

| 层级 | 工具 | 职责 | 类比 |
|---|---|---|---|
| **规范层** | OpenSpec | "做什么" — proposal/specs/design/tasks | 产品经理 / 施工图纸 |
| **纪律层** | Superpowers | "怎么做" — TDD/调试/验证/Worktree 铁律 | 施工规范手册 |
| **编排层** | Harness / ADS | 多 Agent 协作、权限、门禁、反馈回路 | 公司制度 / 项目经理 |

**铁律**：没进 OpenSpec 之前，任何人（包括 Agent）不准动手写代码。

**缺哪层就有哪种症状**：

| 缺 | 症状 |
|---|---|
| 缺 OpenSpec | Agent 各做各的，返工率高，无"真相源"文档 |
| 缺 Superpowers | 不写测试不审查，代码质量失控，声称完成但没验证 |
| 缺 Harness | 多 Agent 协作混乱，权限冲突，并行变串行 |

## 二、ADS 当前位置

```
规范层  OpenSpec      ← ADS 没有这层，需求直接进了 Agent
纪律层  Superpowers   ← ADS 没有这层（已打包为 Pack，待注入）
编排层  Harness       ← ADS 本质上是这层，但不完整
```

**ADS 已有**（Harness 已实现部分）：
- 多 Agent 流水线（Architect/Dev/Test/Review/Deploy）
- PermissionGate 权限门禁
- PreToolUse/PostToolUse Hooks
- 评论参与系统（异步人工反馈回路）
- Ticket 时间轴日志

**ADS 缺失**：
- OpenSpec 规范生成与验证
- Superpowers 执行纪律注入（TDD/调试/验证铁律）
- 生成者与评审者分离（ReviewAgent 和 DevAgent 同模型实例）
- 关键里程碑通知
- 三层可观测性

## 三、把关方式：自动化与人工的折中

**不采用 OpenSpec 同步阻塞门禁**（影响自动化速度），而是：

> 人通过工单评论参与，作为**异步非阻塞的人工把关**。

| 触发 | 机制 |
|---|---|
| 关键里程碑 | 系统推送通知，人看一眼决定是否介入 |
| 异常/阻塞 | 自动暂停 + 等待人工评论 |
| 人主动评论 | Agent 以最高优先级响应，调整方向 |

ADS 评论系统 = Harness 反馈回路的人工扩展版：**人发现问题 → 评论 → Agent 收到 → 修正 → 继续**

## 八、一句话原则

> **ADS 负责编排自动化（速度），Superpowers 负责 Agent 纪律（质量），OpenSpec 负责需求对齐（规范），人通过评论+通知参与把关（安全）。四者缺一，则失速、失质、失准、失控。**

> **时间轴 = 过程记录，三层总览栏 = 状态快照，OpenSpec 面板 = 规范对照，思考面板 = 执行细节。四个视角组合，人随时知道"AI 在做什么、依据什么、到哪一步了、有没有出轨"。**

## 九、评论变更触发机制

### 9.1 核心问题

人工评论中涉及需求改动时，**不应全部重来**，而是按变更影响范围分级响应。

### 9.2 变更分级

| 级别 | 触发条件 | 回滚到 |
|---|---|---|
| **none** | 无需求变更（问题、澄清、鼓励） | DevAgent 正常响应 |
| **tweak** | 只影响实现细节，specs 不变 | Phase 3 开发阶段重跑 |
| **partial** | 影响 1-2 条 specs，架构不变 | Phase 1 更新 specs → Phase 3 重跑 |
| **breaking** | 需求根本改变，原 specs 大部分失效 | 关闭当前工单 → 创建新工单 → 全流程 |

### 9.3 整体流程

```
用户评论提交
      │
      ▼
┌─────────────────────────────┐
│  ChangeImpactAnalyzer       │  轻量 LLM 调用，~1s
│  输入：评论 + 当前 specs     │
│  输出：none/tweak/partial/  │
│        breaking + 影响范围  │
└──────────┬──────────────────┘
           │
    ┌──────┴──────┬──────────────┐
    ▼             ▼              ▼
  none         tweak/partial  breaking
    │             │              │
    ▼             ▼              ▼
 DevAgent     SpecUpdate     TicketReplace
 正常响应      Flow           Flow
```

**触发条件**：只在工单处于 `in_progress` 及以后阶段触发分析；`pending`/`architecture` 阶段评论直接走正常 DevAgent 处理。

### 9.4 变更分析器（ChangeImpactAnalyzer）

```python
class ChangeImpactAnalyzer:
    async def analyze(self, comment, current_specs, ticket_title) -> ChangeImpact:
        prompt = f"""
        工单：{ticket_title}
        当前验收规范摘要：{current_specs[:2000]}
        用户评论：{comment}
        
        判断：
        1. 类型：none / tweak / partial / breaking
        2. 若 partial：列出哪些 specs 场景需要更新
        3. 若 breaking：说明哪个核心假设被推翻
        
        JSON: {{"type":"...","reason":"...","affected_specs":[...]}}
        """
        result = await llm_client.chat(prompt, max_tokens=500)
        return ChangeImpact.parse(result)
```

### 9.5 三种流程

#### Tweak Flow（细节调整）
1. 记录变更日志，不更新 specs
2. 重置阶段：development → testing → verify
3. DevAgent 以评论 + 原 specs 为上下文重新实现
4. 通知：「🔧 检测到细节调整，已重新触发开发阶段」

#### Partial Flow（局部需求变化）
1. **版本化当前 specs**：`specs.md → specs.v{n}.md`
2. LLM 生成 spec 增量（只生成变化部分，追加场景）
3. 写入 `openspec/changes/{ticket_id}/specs.md`
4. 判断是否影响架构：是 → 从 architecture 重跑；否 → 从 development 重跑
5. 通知：「📐 规范已更新至 v{n}，影响阶段：开发→测试→验证」

**Specs 版本化目录结构**：
```
openspec/changes/{ticket-id}/
├── specs.md          ← 当前最新版
├── specs.v1.md       ← 初始版本
├── specs.v2.md       ← 第一次变更后
└── changelog.md      ← 变更记录（版本/来源评论/变更摘要）
```

#### Breaking Flow（根本性变更）
1. 当前工单状态 → `cancelled`，附原因
2. 从评论中提取新需求标题和描述
3. 创建新工单，关联原工单（`source_ticket_id`）
4. 新工单走完整三层流程（从 Phase 0 重来）
5. 原工单留记录：「⚠️ 已关闭，新工单 #xxx 已创建」

### 9.6 阶段重置机制（Phase Reset）

```python
async def reset_phases(ticket_id, from_phase, reason):
    """将指定阶段及后续重置为 pending，保留历史日志"""
    PHASE_ORDER = ["propose","architecture","development",
                   "testing","verify","review","deploy"]
    phases_to_reset = PHASE_ORDER[PHASE_ORDER.index(from_phase):]
    
    # 重置状态，累加 reset_count
    await db.execute("""
        UPDATE ticket_phase_status
        SET status='pending', reset_count=reset_count+1,
            last_reset_reason=?, last_reset_at=?
        WHERE ticket_id=? AND phase IN (?)
    """, reason, now_iso(), ticket_id, phases_to_reset)
    
    # 写时间轴日志（layer: harness）
    await add_ticket_log(ticket_id, action="phase_reset", layer="harness",
        detail={"from_phase": from_phase, "reason": reason})
```

**防无限循环**：`reset_count >= 3` 时自动 blocked，推送人工介入通知。

### 9.9 关键边界

| 场景 | 处理方式 |
|---|---|
| 评论无需求变更 | 返回 none，走正常 DevAgent 路径 |
| 工单在 pending/架构阶段 | 不走变更流程，直接 DevAgent 处理 |
| 工单已 done | 不可变更，提示创建新工单 |
| 变更时 Agent 正在执行 | 等当前阶段完成再应用变更 |
| reset_count >= 3 | 自动 blocked，推人工介入 |
| Breaking 新工单也被变更 | 独立走本机制，独立追踪 |
