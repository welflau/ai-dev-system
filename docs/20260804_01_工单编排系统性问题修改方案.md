# 工单编排系统性问题修改方案

日期：2026-08-04  
状态：方案待评审（未实施）  
关联：活库工单 `TK-20260802-f60699`（TestFPS「新建角色测试地图」→ `blocked`）  
关联 DevNote：`dev-notes/2026-08-02_01_OpenSpec可见性修复与时间轴后台任务增强.md`（编译止损 / 非代码跳编译启发式）

---

## 一、背景与结论

对活库 `backend/data/ai_dev_system_new.db` 与 `orchestrator` / SOP 代码对照后，结论是：

**存在系统逻辑问题**，不是单次 LLM 失手。

当前唯一活跃卡死单 `TK-20260802-f60699` 的轨迹典型：

1. 直接建单 → `architecture_done` → 立刻 `develop`
2. OpenSpec Propose 与 Develop / UBT **并行**（Architect 还在写四件套时已在编译）
3. 两次 `compile_failed`，明细均为 **「UBT 编译失败 · 0 errors」**
4. `fix_issues` / `develop` 因 **「LLM 输出无效，UE/C++ 无通用降级」** → `blocked`
5. 已 `blocked` 后仍有在途 `fix_issues` 跑完并写 `blocked → blocked`

同项目成功单 `a8c8c7` 能 deploy，说明不是整站故障，而是 **UE 管线 + 并发 + 失败语义** 把内容/地图类工单送进死胡同。

## 二、问题清单（系统层）

| ID | 问题 | 根因位置 | 后果 |
|---|---|---|---|
| P1 | SOP 只按**项目 traits** 组装，不按工单类型 | `orchestrator._get_rules_for_project` → `compose_sop(..., ticket_type=None)` | 凡 `engine:ue5` 一律挂 `engine_compile`；地图/内容工单也被当成 C++ 功能单 |
| P2 | `required_ticket_type` 门控形同虚设 | dispatch 始终 `ticket_type=None`；`_fragment_matches` 在 None 时直接排除声明了 rtt 的 fragment，却拦不住「只靠 traits」的 compile fragment | 无法用 ticket_type 关掉编译环 |
| P3 | 编译失败信号空/弱仍进修复环 | `compile_failed` + `errors=[]` → `reject_goto → fix_issues` | 反思无料可修 → 空转 / 乱猜；再叠加 UE 无降级 → hard blocked |
| P4 | UE 路径 LLM 无效 = 硬终态 | `WriteCodeAction` UE 分支拒绝通用降级模板 | 模型波动直接变成工单 `blocked`，无重试策略 |
| P5 | Propose ∥ Develop 竞态 | 直接建单异步 `_post_create_layer_hooks` + 同步 `process_ticket` | 规范未齐就开发/编译；抢 LLM；日志交错难读 |
| P6 | `blocked` 不取消在途任务 | `create_task(process_ticket)` / Agent 执行无取消令牌 | 终态不终；重复 diagnose / fix_issues |
| P7 | 止损策略语义不一致（次要） | 全局 `reject≥5` → force `testing_done`；compile `max_retries=3` → `blocked` | 运维语义混乱 |

已合入但仍不够的补丁（08-02 DevNote）：

- UBT **stdout 全空** → 环境级 `error` → blocked（不进 fix 环）—— 盖不住「有输出但 0 errors」
- `_is_noncode_ticket` 关键词启发式跳编译 —— 补救手段，非根治；且「新建地图」类描述未必命中关键词

---

## 三、目标

1. **按工单装 SOP**：内容/关卡/验证类工单默认不进或弱化 `engine_compile` 环  
2. **失败可分类**：环境/配置 vs 可修编译错误 vs LLM 无效，走不同下一跳  
3. **终态真终**：`blocked` / `cancelled` 后同工单在途任务可取消或被忽略  
4. **规范先于实现（可配置）**：直接建单时 Propose 与 develop 默认可串行  
5. **UE LLM 失败可恢复**：有限次重试，而不是一次 invalid 即 blocked  

非目标（本方案不做）：

- 重写整套 SOP / 换掉 QueryEngine  
- 保证任意 LLM 都能一次写对 UE 地图  
- 自动修好人机环境（引擎未装、模块未编）—— 只负责正确分类并停机

---

## 四、方案总览

```
                    ┌─────────────────────────────────────────┐
  建单 / 状态推进    │  orchestrator.process_ticket              │
                    │  1. 组装 rules = compose_sop(traits,      │
                    │        ticket_type=ticket.type)           │  ← P1/P2
                    │  2. 若 status∈终态 → return（忽略迟到结果）│  ← P6
                    │  3. 派单前登记 run_id；完成时校验 run_id   │  ← P6
                    └───────────────┬─────────────────────────┘
                                    ▼
         ┌──────────────────────────┼──────────────────────────┐
         ▼                          ▼                          ▼
  engine_compile              fix_issues / develop         OpenSpec Propose
  结果三（或四）分：            LLM invalid → 重试 N 次      与 develop 串行闸门
  · success                   仍失败 → blocked             （直接建单可配）
  · compile_failed+errors→fix
  · empty/0-error→env error
  · (可选) content_skip
```

## 五、分阶段改动

### 阶段 A — 止血（优先，改动面可控）

#### A1. dispatch 传入 `ticket.type`

**改动**

- `orchestrator._get_rules_for_project`：增加可选 `ticket_type`；cache key 改为 `(project_id, ticket_type 或 "")`
- `process_ticket` / 相关调用点：`compose_sop(traits, ticket_type=ticket.get("type"))`
- 确认 `_fragment_matches`：`ticket_type is None` 时对 `required_ticket_type` 的行为保持「严格」；有 type 后 fragment 才能按类型启用/禁用

**SOP / fragment**

- 为「内容/关卡」增加显式策略（二选一，评审拍板）：
  - **方案 A1-a（推荐）**：新增 fragment 或 stage_override：当 `ticket.type in (doc, …)` 或 `module in (map, content, art, …)` 时 **不插入** `engine_compile`；或插入 `skip` 阶段直接 `engine_compile_passed`
  - **方案 A1-b（过渡）**：保留现有 `_is_noncode_ticket`，但把关键词表迁到配置，并增加 `module` / `type` 硬规则（`type=doc` 必跳；`module=map|level|content` 默认跳）

**验收**

- TestFPS 上「新建测试地图」类工单 compose 结果 **不含** `run_engine_compile`，或仅含 skip→passed  
- 真实 C++ feature 工单 compose 结果仍含 compile，行为与现网一致

#### A2. 编译结果四分类（强化 P0）

在 `ue_compile_check` + orchestrator UE 编译分支统一：

| 条件 | status | 下一跳 |
|---|---|---|
| exit=0 且无 error | success | `engine_compile_passed` |
| exit≠0 且解析到 errors | compile_failed | `fix_issues`（受 max_retries） |
| exit≠0 且 errors 空（无论 stdout 是否空） | error（环境/配置） | **直接 blocked**，不进 fix |
| （可选）内容跳过 | skipped | `engine_compile_passed` |

**验收**

- 复现「0 errors」失败时：日志 action=`blocked` 或 `error`，**不得**再 `reject → engine_compile_failed → fix_issues`  
- 真编译错误（有 error 行）仍进 fix 环，且受 `max_retries`

#### A3. 终态门闩 + 在途忽略

**改动**

- `process_ticket` 入口：若 `status in (blocked, cancelled, deployed, …终态)` → 直接 return（已部分存在于「无 rule」；补全显式终态集）
- Agent 结果回写前：再读一次 DB status；若已是终态且本次 action 不是「人工解锁」→ **丢弃结果**，只打 warning 日志  
- （增强，可选 A3+）为每张工单维护 `current_run_id`；`create_task` 携带 run_id；完成时不一致则忽略

**验收**

- 人为/自动进入 `blocked` 后，迟到的 `fix_issues` 完成 **不再**写 `blocked→blocked` 与二次 diagnose

---

### 阶段 B — 时序与恢复

#### B1. Propose 与 Develop 串行闸门

**直接建单路径**（`create-direct` / Operator）：

1. 若项目启用 OpenSpec：先跑 Propose（或至少等到 `openspec_propose` / `_partial` / 失败日志之一）  
2. 再 `process_ticket` 进入 develop  
3. 配置项建议：`OPENSPEC_BEFORE_DEVELOP=true`（默认 true）；关闭则保持现状并行（兼容旧习惯）

**验收**

- 新地图工单时间轴顺序：`openspec_propose_*` 结束 → 才出现 `develop` / `run_engine_compile`  
- Propose 失败/超时：工单可配置为继续 develop（warning）或 blocked（严格）

#### B2. UE LLM 无效有限重试

**改动**（`agents/dev.py` / `actions/write_code.py` 或 orchestrator 包一层）：

- UE/C++ 路径检测到「LLM 输出无效 / 无降级」时：
  - 同一 action 自动重试最多 `UE_LLM_INVALID_RETRIES`（默认 2）次  
  - 仍失败 → `blocked`，detail 标明 `reason=llm_invalid_exhausted`  
- 不把「无效输出」伪装成成功或通用 Web 模板

**验收**

- 人为注入一次无效输出：出现重试日志，最终仍失败才 blocked  
- 有效输出：无额外重试开销（首次成功即过）

---

### 阶段 C — 治理与可观测（可并行）

#### C1. 统一止损语义

- 废除或降级「reject≥5 → force testing_done」（危险：把失败标成完成）  
- 统一为：可修复失败受 `max_retries`；环境/LLM 耗尽 → `blocked`  
- 时间轴对止损原因打标准 `detail_data.reason` 枚举：`max_retries_exceeded` / `env_compile_error` / `llm_invalid_exhausted` / `noncode_skip`

#### C2. 诊断可信度

- `_diagnose_blocked_ticket` 输出增加 `evidence`：引用 `ticket_logs` 原始 reject/tool_done 摘要，禁止只靠 LLM 编造  
- 前端诊断卡标注「基于日志证据 / 含模型推断」

#### C3. 工单类型与 module 规范

- 建单 UI / Agent：地图、关卡、纯资产默认 `module=map|content` 或 `type` 扩展值（若扩 type 需迁移枚举）  
- SOP 文档写明：何种 type/module 会挂哪些 fragment

## 七、实施顺序与风险

| 顺序 | 项 | 风险 | 缓解 |
|---|---|---|---|
| 1 | A2 0-error→blocked | 真有「解析失败但可修」的漏网 | 保留 raw_tail 进 detail；人工可解锁重跑 |
| 2 | A3 终态门闩 | 迟到的合法 complete 被丢 | 仅丢弃与终态冲突的 error/fix；complete→已终态打审计日志 |
| 3 | A1 ticket_type + skip 规则 | 误跳真实 C++ 单 | 默认仅 `doc` + `module∈{map,content,level,art}`；feature+cpp 仍编译 |
| 4 | B1 串行 Propose | 建单到开发变慢 | 可配置关闭；Propose 超时可降级继续 |
| 5 | B2 LLM 重试 | 多耗 token | 默认 2 次、可关 |

建议评审拍板点：

1. A1 用 **module 硬规则** 还是扩 `ticket.type`？  
2. Propose 失败时：**继续 develop** 还是 **blocked**？  
3. 是否立刻废除 force `testing_done`？

## 八、验收场景（端到端）

1. **地图工单**：TestFPS 新建「角色测试地图」→ 无 UBT 空转；OpenSpec（若开）结束后再 develop；不因 0-error 进 fix 环  
2. **C++ 功能工单**：故意引入语法错误 → `compile_failed` 带 errors → `fix_issues` ≤ max_retries → 修好或 blocked(max_retries)  
3. **环境故障**：引擎路径错误 / UBT 零输出 → 一次 blocked(env)，无 fix 循环  
4. **LLM 无效**：UE develop 首次无效 → 重试 → 仍无效 → blocked(llm_invalid_exhausted)；期间无通用 Web 模板污染仓库  
5. **终态**：blocked 后注入迟到的 agent 结果 → 状态不变，仅有 ignore 日志

## 九、与既有补丁的关系

| 既有项 | 本方案态度 |
|---|---|
| UBT 全空 → error→blocked | **保留**，并扩展为「0 errors 一律环境态」 |
| `_is_noncode_ticket` 关键词 | **降级为过渡**；被 A1 的 type/module 规则替代后可删或仅作兜底 |
| compile `max_retries` | **保留**，仅对「有 errors 的 compile_failed」生效 |
| SkillRunner / OpenSpec MCP | **不冲突**；B1 只约束调用时序 |
