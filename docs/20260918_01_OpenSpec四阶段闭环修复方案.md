# OpenSpec 四阶段闭环修复方案

> 2026-09-18 · 起因：「现在 OpenSpec 在工单能跑起来吗」→「怎么才能完整，是测试环节没有工具？」

## 结论先行

**不是缺工具。** 工具链完整，是两个接线问题：

1. **OpenSpec Verify 挂在了 UE 项目永远走不到的阶段上**（决定性原因）
2. **playtest 在「项目无 Automation 测试」时空转到超时，且超时被判为 error → BLOCKED**

第 3 件事是被这两条掩盖的真问题：TestFPS 里**一个 Automation 测试都没有**，
所以 play_test 阶段即便修好，也只是靠「没测试 = 通过」放行，并不在验证任何东西。

`verified` / `archived` **各 0 条**；`openspec_verify*` / `openspec_archive`

Propose/Apply/Verify/Archive 节点）都是完整的，但后两阶段从未执行过。

### 1.2 带 openspec_stage 的 13 张工单，全部属于同一个项目

全部是 `TestFPS`，traits：

```
["platform:desktop", "category:game", "engine:ue5", "fps", "shooting", "npc", "lang:cpp"]
```

### 1.3 UE 项目 compose 出来的 SOP 里没有 run_tests

`compose_sop(["category:game","engine:ue5"], "feature")` 的 action 序列：

```
write_prd → write_ux_design → write_art_design → design_architecture
  → generate_assets → develop → run_engine_compile → run_playtest
  → run_ci_deploy → code_review → acceptance_review → deploy → fix_issues
```

对比 web/service 项目（`category:service`）：

```
... → develop → run_tests → code_review → ...
```

原因在 `sop/fragments/smoke_test.yaml`：

```yaml
required_traits:
  any_of:
    - category:service
    - category:app
```

TestFPS 是 `category:game`，只匹配 `play_test.yaml`，**不匹配 smoke_test**。

全库校验：`ticket_logs` 里 `run_tests` 相关日志 **0 条**。

### 1.4 而 Verify 的唯一调用点就在 run_tests 里

修复前，`_run_openspec_verify` 全局只有一处调用：

```python
# agents/test.py:192（修复前）
if all_passed:
    await self._run_openspec_verify(context)
```

**这就是根因**：Verify 挂在 `run_tests` 上，而所有带 OpenSpec 的工单都属于一个
没有 `run_tests` 阶段的项目类型。它不是坏了，是被挂在了一条不存在的路上。

Archive 反而是可达的（`deploy` 阶段在 UE SOP 尾部存在），但 Verify 到不了，
`openspec_stage` 就永远停在 `applied`，Archive 的前置条件也永远不成立。

### 1.5 playtest 超时的完整现场

`TK-E2EREAL-09110951`（走得最远的一张，`applied` 态）死因：

```
ToolError:agent:TestAgent.run_playtest — Playtest 超时（600s）
duration_ms = 602143
```

从 DB 里挖出的实际命令：

```
G:\EpicGames\UE_5.7\Engine\Binaries\Win64\UnrealEditor-Cmd.exe
  F:\ADS_Projects\TestFPS\TestFPS.uproject
  "-ExecCmds=Automation RunTests Project.;Quit"
  -nullrhi -unattended -nopause -nosplash -buildmachine -NoSound
  -stdout -FullStdOutLogOutput -AutomationScreenshotsDir=...
```

**排除「没工具」的依据**：
- 引擎解析成功：`UE 5.7`，`UnrealEditor-Cmd.exe` 存在
- 前置 UBT 编译通过：`exit_code=0, target=TestFPSEditor, 93s`
- DLL 存在性检查通过：`UnrealEditor-TestFPS.dll`
- 进程真的起来了：有 pid，读到 100 行 stdout（shader 编译、Slate 初始化、
  WorldPartition 注册、DerivedDataCache 维护全都正常）

**真实死因**：`Source/` 下 `IMPLEMENT_SIMPLE_AUTOMATION_TEST` /
`DEFINE_SPEC` / `IMPLEMENT_COMPLEX_AUTOMATION_TEST` **一个都没有**。
`Automation RunTests Project.` 匹配 0 个测试 → Automation controller 不产生
完成事件 → `;Quit` 永不执行 → headless editor 空转到 600s 被 kill。

讽刺的是 `ue_playtest.py` 早就写了「0 测试视为通过」的分支：

```python
no_tests = total_count == 0 and failed_count == 0
if (exit_code == 0 or no_tests) and failed_count == 0:
    status = "success"
```

但它在 `proc.wait()` **之后** —— 进程不退，永远走不到这一行。

### 1.6 超时被升级成死单

`ue_playtest.py` 超时走 `_err()`，而 `_err` 写死 `status="error"`；
`orchestrator.py:2064` 对任何 `status == "error"` 一律：

```python
blocked_status = TicketStatus.BLOCKED.value   # 等人工介入
```

而 `play_test.yaml` 明明配了可自愈路径：

```yaml
reject_status: play_test_failed
reject_goto: development
```

超时的常见成因（测试挂住 / 项目没测试 / 关卡加载卡死）都是 `reject_goto
development` 能处理的。判成 error 等于把一次可自愈的失败升级成死单。

系统自己的诊断（`action=diagnose`, confidence=0.85）已经指出了这点，
建议第 3 条原文就是「追加 `-TestExit` 参数」。

## 二、改动

### 2.1 Verify 触发点从 run_tests 解耦 → 收口到 orchestrator

新增 `orchestrator._maybe_openspec_verify(project_id, ticket_id, *, stage_label)`
（`orchestrator.py:4640`），两条测试路径共用：

| 路径 | 触发位置 | 适用项目 |
|---|---|---|
| `run_tests` 全绿 | `agents/test.py:192` | web / service（smoke_test fragment） |
| `run_playtest` 成功 | `orchestrator.py:2711` | UE（play_test fragment） |

**为什么放 orchestrator 而不是 Agent 里**：Verify 失败要把工单打成 `blocked`，
而 orchestrator 在 Agent 返回**之后**才写状态 —— Agent 内部写的 `blocked` 会被
随后的 `play_test_passed` 覆盖掉。`run_tests` 那条路径侥幸没踩到，是因为它写状态
的时机恰好在后面，但同一件事分两处实现迟早走样，所以统一收口。

幂等：`openspec_stage ∈ {verified, archived}` 直接返回 True，不重跑 `validate`
（重复跑会多发一条里程碑评论）。

`TestAgent._run_openspec_verify` 本体**保留**——软收尾路径
（`_finalize_openspec_after_done`，`block_on_fail=False`）还在用它。

### 2.2 playtest 空队列能退出 + 超时降级

`actions/ue_playtest.py`：

1. 命令追加 `-TestExit=Automation Test Queue Empty` —— UE 原生参数，
   Automation 队列跑空即退出。这是「空转到超时」的直接解药。
2. 超时分支不再走 `_err()`，改为 `status="playtest_failed"`，并带上：
   - `timed_out: True`（前端可区分「超时」与「真失败」）
   - `_parse_automation_output(partial)` 解析出的 `tests` / `summary`
     —— 超时也要能看出「跑到哪一个测试挂住的」
   - `raw_head` / `raw_tail` / `screenshots` / `engine_used`

这样超时会走 `reject_goto: development` 回开发，而不是 BLOCKED 等人工。

### 2.3 补最小 Automation 测试

新增 `F:/ADS_Projects/TestFPS/Source/TestFPS/Tests/SprintComponentTest.cpp`，
两个用例（测试名以 `Project.` 开头才能被 `test_filter: "Project."` 命中）：

- `Project.TestFPS.SprintComponent.Defaults` — 可实例化、Tick 已开、
  MaxStamina > 0、初始非冲刺态、耐力 0 时 `CanSprint()` 为 false
- `Project.TestFPS.SprintComponent.NoOwnerGuard` — 回归防线：组件未挂到
  `ACharacter` 上时 `StartSprint()` / `StopSprint()` 必须安全 no-op 不崩
  （两者都会解引用 Owner 的 `MovementComponent`）

设计约束：不建 World、不 SpawnActor —— 要跑在 `-nullrhi` 的 commandlet
上下文里，必须无渲染、无关卡依赖。flags 用
`EditorContext | CommandletContext | ProductFilter`（已对照
`UE_5.7/.../Misc/AutomationTest.h` 的 `EAutomationTestFlags_ApplicationContextMask`
与 `_FilterMask` 的 static_assert 约束确认组合合法）。

**已编译 + 已实测通过**（见第三节 3.2）。

## 四、暴露出的结构性缺口：UE 侧没有测试生成器

本次那个 `SprintComponentTest.cpp` **是人工手写的，不是系统产出的**。
下一张 UE 工单来，项目里还是 0 个自有测试。

两条测试路径的分工是不对称的：

| | 生成测试 | 执行测试 |
|---|---|---|
| web / Python | ✅ `TestAgent._generate_test_cases`（LLM 生成 pytest，`_fallback_test_code` 兜底）→ 落盘 `tests/test_xxx.py` | ✅ `_run_pytest` |
| UE | ❌ **空缺** | ✅ `UEPlaytestAction` |

UE 分支跳过 pytest 生成的判断本身是对的（`test.py:150` 注释：「LLM 只会编出
`assert Path("index.html").exists()` 之类的假用例，既污染仓库又必然 fail」），
但它只解决了「不要生成假的 pytest」，没解决「那谁来生成真的 Automation 测试」。
`run_playtest` 只**跑**测试，不**写**测试。

后果：`ue_playtest.py` 里那个 `no_tests → success` 的分支，实际含义是
**「没测试就算通过」** —— play_test 阶段从来没有验证过任何东西。

### 4.1 若要补，五条硬约束（全部来自本次手写的实际踩坑）

1. **必须能编译**。pytest 生成错了只是 fail 一条；C++ 编译不过会让整个 module 挂掉，
   连带 playtest 起不来。所以生成后必须过一次 UBT 才能落盘。
2. **flags 组合受 `static_assert` 约束**。`EAutomationTestFlags_ApplicationContextMask`
   必须命中至少一个上下文；`_FilterMask` 必须恰好是单一 filter。LLM 容易编出编不过的组合。
   已验证可用：`EditorContext | CommandletContext | ProductFilter`。
3. **测试名必须以 `Project.` 开头**，否则不被 `play_test.yaml` 的
   `test_filter: "Project."` 命中。这是 ADS 自己的约定，得显式写进 prompt。
4. **不能建 World / SpawnActor**。跑在 `-nullrhi` commandlet 下，有渲染或关卡依赖
   会让测试自身崩掉。
5. **include 路径要按项目布局挑**。无 `Public/`/`Private/` 分层的项目（如 TestFPS），
   子目录里必须用相对路径 `#include "../Xxx.h"`，否则 C1083。
   ← 这条是实测撞出来的，看头文件推不出来。

### 4.2 实现：`actions/ue_test_gen.py`（已实现）

**挂载点**：新增 SOP fragment `sop/fragments/ue_test_gen.yaml`，
`insert_after: development`、`priority: 97`（> engine_compile 的 95 —— loader 按
priority **升序**插入，数值大的更靠近锚点）。compose 结果：

```
... → develop → generate_ue_tests → run_engine_compile → run_playtest → ...
```

状态链连续（`sop_to_transition_rules` 实测）：

```
development_done      → DevAgent.generate_ue_tests
ue_test_gen_passed    → DevAgent.run_engine_compile
engine_compile_passed → TestAgent.run_playtest
```

**流水线**：

```
① 选目标（本次改动的 .h，跳过 Tests/ 与 *Test.h，默认最多 2 个）
② 已有同名测试 → 直接跳过（人工写的测试比生成的值钱，覆盖了就是事故）
③ 算 include 路径 —— 不问 LLM，机械可算（见下）
④ LLM 生成 → 静态校验，最多 2 轮，把问题回喂给 LLM
⑤ 落盘 → ue_lint run_all_rules，blocking 则删文件回滚
⑥ UBT -SingleFile 实编（30~90s），失败则删文件回滚
```

**两个与原设想不同的决定：**

**① 不让生成的测试「跟着 engine_compile 一起编」，改为就地验证 + 就地回滚。**
原设想是编不过就 reject 回 development。但那样工单会因为**它自己没写的代码**被打回，
DevAgent 拿着一份不是自己产出的报错反复空转 —— 正是 R3 误报那个坑的翻版。
改成 `-SingleFile` 自己验（复用 `ue_compile_check.py:325` 已有的能力），
编不过就 `unlink()` 删掉，仓库里只留编得过的文件，engine_compile 拿到的永远是干净的树。

**② include 路径由 Action 自己算，不进 prompt 让 LLM 猜。**
这是硬约束 #5，纯经验性、看头文件推不出来，交给 LLM 猜等于白烧一轮 90s 编译。
`_include_path_for()` 按 UBT / C++ 的实际解析顺序算：

| 情形 | 产出 |
|---|---|
| 与引用方同级 | `#include "Xxx.h"` |
| 模块有 Public/ 或 Private/ 分层 | `#include "Sub/Bar.h"`（相对锚点） |
| flat layout + 子目录 | `#include "../Xxx.h"` ← 真机 C1083 的那个坑 |

prompt 里把算好的 include 块整段给出并要求**逐字照抄**，静态校验再核一遍它没被改。

**失败语义：永不阻塞工单。** 测试生成是增强不是门禁，它挂了不该让功能进不去 ——
所有失败路径都收敛成 `success=True` + `warnings`。但 warnings 必须带出去，
否则又退化成「静默地没有测试」，跟修之前没区别。

SOP 开关：`ue_test_gen_enabled` / `ue_test_gen_compile` / `ue_test_gen_timeout` /
`ue_test_gen_max_targets`。

### 4.3 前置修复：R3 漏报子目录 include（`actions/ue_lint/rules.py`）

生成器要靠 lint 兜底，而 lint 恰好漏掉生成器最容易犯的错。用第一版会 C1083 的
写法跑 `run_all_rules` → **`issues = 0`，R3 没抓到。**

旧判定问的是「**头文件**是否位于模块根」：

```python
# flat layout：UBT 会把模块根加进 include 路径，同级 #include "Xxx.h" 合法
if p.resolve().parent == module_root.resolve():
    ok = True
```

这个前提是错的。flat layout 下同级引用能过，靠的是 **quoted include 相对引用方目录
查找**，不是 include 搜索路径 —— UBT 并不会把 flat 模块根加进去。于是两头都错：

- **漏报**：`Tests/` 里 include 模块根的头 → lint 放行，真编译 C1083（本次实际踩到）
- **误报**：`Tests/` 里 include **同目录**的头 → 报 blocking，且 suggest 与原文
  逐字相同，DevAgent 拿到无从修改，只能空转到 blocked（正是该豁免当初想避免的事）

改成问「**头文件是否与引用方同级**」，两头都对；找不到时的 suggest 也从
`first.name`（等于没给建议）改成真实相对路径。回归测试
`backend/_test_r3_subdir_include.py` 6 项全绿，其中一项断言 suggest 恰好是
`#include "../SprintComponent.h"` —— 跟我手工撞出来的修法逐字一致。

用真实项目 TestFPS 跑，没有 mock 目录树：这条规则的判定全靠磁盘布局，
mock 出来的树证明不了什么。

### 4.5 真机验证揪出的两个 bug（单测全绿也没抓到）

`backend/_test_ue_test_gen.py` 16 项全绿之后，拿真工程跑
`backend/_probe_ue_test_gen_live.py`（把手写测试临时移出仓库 → 真 LLM + 真 UBT →
无论成败都恢复），**连撞两个 bug，两个都会让 Action 静默什么都不做**：

**① 仓库路径解析错**（`_resolve_repo`）

`git_manager._repo_path()` 只认进程内 `_custom_paths` 注册过的自定义路径，没注册
就退回 `PROJECTS_DIR / project_id`。TestFPS 的仓库在 `F:/ADS_Projects/TestFPS`，
于是解析成 `backend/projects/PRJ-.../`（不存在），Action 报
**「本次改动里没有可测的 UE 头文件」** —— 错得很难查，因为报错信息完全指向另一个方向。

修法照抄仓库既有做法（`actions/chat/_git_base.py:24-28`）：先从
`projects.git_repo_path` 补注册；`context.repo_path` 有值时优先用。

**② UCLASS 解析正则被嵌套括号打败**（`_extract_class_names`）

```cpp
UCLASS(ClassGroup = (Custom), meta = (BlueprintSpawnableComponent))
class TESTFPS_API USprintComponent : public UActorComponent
```

原正则 `UCLASS\s*\([^)]*\)` 里的 `[^)]*` 停在 `(Custom)` 的右括号上，整条失配 →
报「头文件里没有 UCLASS/USTRUCT」。**带 `ClassGroup` / `meta` 的类是绝大多数组件类**，
也就是说这个 bug 一上真项目就必现，而单测因为用的是手编的简化样本完全没碰到。

改成逐行扫（UCLASS/USTRUCT 行 → 往下 8 行内找最近的 `class`/`struct` 声明），
顺带支持宏参数跨行。

**教训**：两个 bug 都是「**跟真实环境接缝处**」的错 —— 一个是路径约定，一个是真实
代码长什么样。纯逻辑单测天然测不到，因为样本是我自己编的，编的时候就带着同一套
错误假设。回归测试因此补了 10 项，其中 `_extract_class_names` 的正样本**直接读真实的
`SprintComponent.h`**，不再用手编样本。

### 4.6 第三个 bug：禁用词扫描没去注释（自己毙掉自己）

改完前两个，真机跑通了一次（生成 → 静态检查 → lint → UBT 编译 → 通过，两个测试名
都带 `Project.` 前缀）。但**再跑两次，连续被自己的静态检查毙掉**，理由都是
「用到了 SpawnActor」，三轮重试全废。

查下来是我自己的问题：`_BANNED_TOKENS` 直接在全文里 `in code`，**没去注释**。而

```cpp
// 不建 World / 不 SpawnActor：这一层只验组件自身的初始契约，
```

正是真机编译通过、playtest 跑绿的那个手写 `SprintComponentTest.cpp` 的第 32 行。
更糟的是我为了提高稳定性刚给 prompt 加的正例里也有这句注释 —— 等于**我一边要求
LLM 照抄这个注释，一边用规则把带这个注释的输出毙掉**。

> 一个连人工写的、已编译已跑绿的样板都判不过的检查，判的是检查自己。

修法：加 `_strip_comments()`，禁用词只扫去掉 `//` 与 `/* */` 之后的代码
（`ue_lint/rules.py` 里本来就有 `_strip_line_comment`，同一个道理，我没照做）。

**为什么单测没抓到**：正样本 `GOOD` 是我手工裁剪的精简版，裁的时候顺手把注释去掉了，
恰好避开这个坑。**自己编的样本会带着自己的盲区** —— 这已经是本节第二次栽在同一件事上
（4.5 ② 的 UCLASS 样本也是）。所以现在正样本**原封不动读真实文件**，并断言
「该文件里确实含有带禁用词的注释」，防止将来有人把那行注释删了让测试变成空跑：

```python
assert "SpawnActor" in src, "前提变了：真文件里已没有含禁用词的注释"
probs = a._static_check(src, INC)
check("真实手写测试（含 `// 不建 World / 不 SpawnActor` 注释）不被误判", probs == [])
```

同时保留「代码里真的用了 SpawnActor 要能抓到」的负样本 —— 去注释不能把检查做钝。

**回归测试合计 28 项全绿。**

### 4.8 真工单端到端：撞出 orchestrator 死循环

4.7 是直接调 Action 验的。真正挂到 orchestrator 上跑一张工单
（`TK-20260918-23a48b`「新增生命值组件 UHealthComponent」，纯 C++、新头文件，
`start_from=architecture_done`），**第一轮空转了 114 次**。

但 orchestrator 不认这个结果。

**根因：`_handle_agent_result` 的 DevAgent 分支是按 action 逐个写死的。**
`run_engine_compile` 有自己的分支并 `return`，`generate_ue_tests` 没有 ——
于是掉进后面「常规 develop / rework / fix_issues」的收尾，产生两处连锁伤害：

| | 后果 |
|---|---|
| ① status 被写回 `development_done` | 而 `development_done` 的 trigger 正是 `generate_ue_tests` 自己 → 派单→成功→写回原状态→再派单，**每秒一轮** |
| ② 结果被存成 `type='code'` 的 artifact | `_build_context` 取**最后一条** code artifact 当 `dev_result` → 真正的 dev_result（6499 字节，带 2 个文件）被 114 条 173 字节的垃圾埋掉 |

②的症状极具迷惑性：第 2 轮起日志全是
**「ue_test_gen 跳过：本次改动里没有可测的 UE 头文件」** —— 指向选目标逻辑，
而根因在三层之外的结果收尾里。所幸 `_pick_targets` 找不到目标就短路，
114 轮里只有第 1 轮调了 LLM，没有烧钱。

**修法**（`orchestrator.py`，`run_engine_compile` 分支之后）：给
`generate_ue_tests` 自己的结果分支，自己写状态、自己 `return`，不碰产物表。
状态**从 SOP 声明里取**（`_sop_success_status_for` / `reject_status`），
不写死字符串 —— fragment 改名这里不用跟着改。非 `success` 走 SOP 声明的返工路径，
不静默当成功放行。

清掉 114 条垃圾 artifact 后重跑，**一次派单，链路贯通**：


**Playtest 通过 5/5**。此前是 3 个（引擎的 `Project.Maps.PIE` + 2 个手写 Sprint），
多出来的 2 个正是生成的 HealthComponent 测试 —— **机器生成的测试真的被编进
模块、被 Automation 跑起来、并且通过了**。这是 4.1 提出的五条硬约束全部落地的证据。

**教训**：Action 自身 28 项单测全绿、真机直调也跑通，仍然在**接线层**翻车。
`_handle_agent_result` 按 action 硬编码分支这件事本身是个坑 —— 新增 SOP
fragment 时很容易忘了配套改它，而忘了的表现不是报错，是**静默死循环**。

回归测试 `backend/_test_ue_test_gen_wiring.py`（9 项全绿）测的是**行为**，

## 五、时间轴层级：从平铺改成阶段树

起因是看时间轴时的一句提问：「进展时间轴没有树形的层级关系？都是平铺的吗？如果
OpenSpec 框架，是否按照 OpenSpec 框架来分步骤、层级？」

先量了一遍再答，结论是**确实全平**：`_tier` 只是 primary/secondary 两级可见性，
`layer` 字段 630 条里 510 条都是 `harness`（没有区分力，只用于日志面板配色），
**没有 `parent_id`** —— `_renderUnifiedTimeline` 就是一个 `map`。

分三件事做，其中第 3 件明确不做。

### 5.1 先修一个让折叠彻底失效的 bug（`_timelineSignature`）

`TK-20260918-23a48b` 有 613 条主轴日志，肉眼一看就是同一段转了几十圈，
但折叠**一条都没折**，压缩率 0.0%。

根因是签名函数里一条豁免规则：

```js
if (item._type === 'comment') return 'c:' + item.id;   // 注释写着「评论是人写的」
```

前提不成立。里程碑评论是 Agent 每轮自动发的。而这张单的重复周期是 5 步：

```
thought_start → thought_done → complete → 【里程碑评论】 → checkpoint
```

评论卡在第 4 步且带唯一 id，于是每轮签名都不同、周期永远匹配不上 → 整个折叠机制
对这类工单完全失效。

这和 4.6 那个 bug 是**同一类错误**：一条豁免规则，它的前提和真实数据不符。

修法是把判定改成**白名单**：只有 `author_type` 为 `agent` / `system` 的评论参与
折叠，其余一律按人处理。这里特意查了库：

| author_type | 条数 |
|---|---|
| agent | 181 |
| system | 47 |
| **human** | 8 |

人写的那一侧值是 `human`，不是 `user`（`renderCommentBubble` 判的也是 `human`）。
**如果写成黑名单 `!== 'user'`，human 会漏进折叠里，把唯一真正不该折的东西折掉。**
白名单错了顶多少折几条，黑名单错了会吞掉人说的话，两种错代价不对等。

效果（真实数据）：

```
修复前: primary 613 -> rows 613 | cycles 0 | 压缩率 0.0%
修复后: primary 613 -> rows  44 | cycles 1 | 压缩率 92.8%
        period=5 x114  DevAgent: thought_start → thought_done → complete → 评论 → checkpoint
```

`x114` 和 4.8 那个死循环的 114 轮**精确对上**。顺带修了摘要里评论显示成 `?` 的问题
（`_timelineGroupLabel` 用 `c.action || '?'`，而评论没有 `action`）。

### 5.2 按 SOP 阶段做树形分组

**分组的权威来源放后端**，不放前端。阶段归属是 SOP 知识（`trigger_on` +
`pipeline_view` 的分组声明），前端再抄一份必然和 yaml 漂移 —— 装上 `ue_test_gen`
fragment 就多一个阶段，前端硬编码的表不会自己长出来。

新增 `sop/loader.py: build_stage_index(config)`，产出
`{groups, by_action, by_from_status}`；`GET /api/tickets/{id}/timeline` 用它给每条
日志标 `_stage` / `_stage_name` / `_stage_group` / `_stage_exact`，并额外返回
`stage_groups`（UI 大组的声明序）。

三处判断值得记下来，都是量过数据才定的：

**① 映射源用 `trigger_on`，不能用 `build_pipeline_stages` 的 `in_statuses`。**
后者被「返工阶段启发式」筛过 —— UE SOP 实测 testing 组的 `in_statuses` 只剩
`play_test_passed / play_test_failed`，`ue_test_gen_passed`、`engine_compile_passed`
全不在里面。拿它映射，一张 UE 工单**最忙的那 580 条**会集体掉进「未归类」。
`in_statuses` 回答的是「工单现在停在哪个格子」，和「这条日志属于哪个阶段」是两个问题。
回归测试里把这点钉死了：断言这些状态能映射**且确实不在 `in_statuses` 里**，
哪天 `in_statuses` 覆盖全了这条会红，提醒人回来重新评估，而不是让注释里的理由悄悄过期。

**② 没有身份的日志继承前一条。** 全库实测 6584 条 `thought_start`、4093 条
`llm_call`、197 条 `checkpoint` 既没有 action 映射也没有 status。只按 ①② 精确标的话
九成日志会挂在「未归类」下，树建了也没用。时间轴是时序的 —— 一条没有身份的日志属于
当时正在跑的那个阶段。标注时区分 `_stage_exact`，继承来的不当权威。
实测覆盖率 **624/630 = 99.0%**，其中精确锚点 239 条。

**③ 前端按「阶段」分段，不按「UI 大组」分段。** 大组会不连续：UE SOP 里
`code_review` / `acceptance` 归在「开发实现」组，但它们跑在 `deploy_ue`（打包）**之后**。
真实推进序是

```
development → ue_test_gen → engine_compile → play_test → deploy_ue → code_review → acceptance
```

按大组折，就得把「开发实现」拆成两块、或者打乱时序 —— 两种都是在骗人。
所以阶段是节点，大组只作为节点标题上的归属标签。回归测试直接断言
`code_review` 排在 `deploy_ue` 之后，把这个理由固化下来。

真机效果（`TK-20260918-23a48b`，613 条主轴 → 10 段）：

```
[未归类]   未归类           6 条
[资产准备] 美术资产生成       1 条
[开发实现] 代码开发          10 条
[测试验证] UE 测试生成      576 条   ← 里面装着 5.1 折出来的 114× 循环
[测试验证] 引擎编译验证       4 条
[测试验证] 游戏玩法测试       2 条
[交付]     打包（UE）        4 条
[开发实现] 代码审查          4 条
[开发实现] 产品验收          4 条
[未归类]   部署             2 条
```

其他几个取舍：

- 默认展开**最后一段**（正在跑的）和**出过错的段**，其余收起；收起的段 body 不渲染
  （懒展开）—— 576 条一次铺开会卡。
- `pipeline_view` 没覆盖的 stage（`planning` / `deploy`）group 为 `None`，显示
  「未归类」，**不硬塞进相邻组** —— 塞了就是把流程图讲错。
- 后端没标阶段（项目无 traits / compose 失败）→ 前端**退回平铺**，保持现状可用，不报错。
- 同一阶段被返工二次进入 → 自然形成两段，不合并（时序比聚合重要）。
- `_findTimelineGroupById` 的正则从 `^tlg-(p|s)-(\d+)$` 扩到 `^tlg-(p(\d+)|p|s)-(\d+)$`：
  阶段树上线后每个阶段各自成池，正则不改的话展开阶段里的循环组会一律回查失败、点开是空的。

### 5.3 OpenSpec 四阶段分层：明确不做

提问里问的「按 OpenSpec 框架分层」，现在做不了，原因是数据不支持：这张单
630 条里 `layer='spec'` 的只有 **2 条**。按 propose/apply/verify/archive 四阶段建树，
会有 628 条无家可归。

而且这正好卡在遗留 #1 上 —— propose 产不出 spec delta（`0/4`），所以 spec 类日志
本来就少。等 propose 修好、spec 日志成规模了再做，届时 OpenSpec 分层应作为
**SOP 阶段树之上的一层叠加视图**（SOP 阶段覆盖 100% 的工单，OpenSpec 只覆盖装了
该 fragment 的），不是替换。

### 5.5 圆点改成真控件（伪元素接不了事件）

用户反馈「这些点应该可以点击，用于折叠展开」。查下来是**结构问题不是绑定问题**：
时间轴左边那排圆点全是 CSS 伪元素 —— `.log-item::before`（styles.css:2119）和
`.timeline-stage::before`。**伪元素不在 DOM 里，接不到任何事件**，
所以不管往哪儿绑 onclick 都不可能点得动。它们看着像控件，其实一直是装饰。

改法是在圆点位置盖一个真实的透明 `<span>` 热区，圆点本身仍由伪元素画，视觉不变：

| 位置 | 热区 | 点击行为 |
|---|---|---|
| 阶段节点 | `.ts-dot` → `toggleTimelineStage(id)` | 展开/收起整个阶段（与标题行同一动作） |
| 日志条目 | `.li-dot` → `toggleLogItemCollapse(this)` | 折成只剩 header 行（`.li-collapsed`） |

三个容易踩空的点，都已落成 `_test_timeline_dots.js`（14 项结构断言，全绿）：

1. **热区必须 `event.stopPropagation()`**。带 `hasExpand` 的条目整行挂着
   `onclick="toggleBlock(...)"`，不拦截就会点一下同时折叠 + 展开详情。
2. **单行条目不挂热区，并把圆点一起收掉**。`_renderReactToolItem` /
   `_renderSkillStepItem` 是没有正文的单行摘要，折起来长度不变 —— 给它们挂热区
   等于造一个按下去没反应的按钮，正是本次要修的毛病。它们的圆点是从
   `.log-item::before` 蹭来的，本身已用 `border-left` 区分层级，所以直接
   `display:none`：**不画不能点的点**。
3. **折叠态不许动 padding**。圆点是 `top:16px` 的绝对定位，不随 padding 走；
   缩了 padding 行会变矮，圆点就掉到行外面去。折叠只降透明度。

另外热区居中要算上圆点的 2px 边框（`::before` 是 content-box，
`width:10px` 实际占 14px），否则 hover 高亮会往左上偏 2px。
嵌在折叠组里的条目圆点原本就 `display:none`，热区也一并收掉
（`.timeline-group-body .log-item > .li-dot`），不留隐形按钮。
