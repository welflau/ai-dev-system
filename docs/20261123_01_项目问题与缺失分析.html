三、需要先修的问题

1. POST /api/projects 路由挂错了函数

backend/api/projects.py 第 57 行的 @router.post("") 下面紧跟的是辅助函数 _auto_init_ads_dir(repo_path, project_name, traits)（第 58 行），真正的 create_project 在第 99 行，前面没有装饰器，没有注册成路由。

证据：

  • 枚举路由得到 ['POST'] /api/projects -> _auto_init_ads_dir，create_project 不在路由表里。
  • 单独挂这个 router 后 POST /api/projects（JSON body）返回 422：缺 query 参数 repo_path、project_name，缺 body 字段 traits。
  • 前端「新建项目」（frontend/app.js:8118）和「导入项目」（frontend/app.js:8383）都调用这个接口。

来源：提交 e37d619（2026-05-19，「新建项目自动初始化 .ads/ 目录」）把新函数插在了装饰器和 create_project 之间。

修法：把 @router.post("") 挪到 async def create_project 上方；补一个回归测试，断言 POST /api/projects 的 endpoint 是 create_project。

说明：聊天里的「确认创建」走 api/chat.py 的 confirm_create_project → CreateProjectAction，是另一条路径，本次没有测试。现有日志里也没有找到 POST /api/projects 的访问记录，所以线上实际受影响的程度没有从运行数据上得到印证。

2. cloud_video 包内循环导入，分层守卫变红

分层守卫输出：

模块 471 | 项目内边 2251 | import 语句 4590 (延迟 1974, 43.0%)
SCC>1: 1 组 (最大 3) | 双向对 2 | 动态导入 11 | 未归层模块 229
违规 93 条 {'DIRECTION': 92, 'CYCLE': 1} | 基线 已登记 | 相对基线新增 1
[新增违规] CYCLE:cloud_video,cloud_video.client,cloud_video.queue

因此这两个测试失败：

  • tests/architecture/test_layer_dag.py::test_no_new_violations_vs_baseline
  • tests/architecture/test_layer_dag.py::test_main_ring_eliminated

环上的导入：

  • cloud_video/client.py:32 顶层导入 cloud_video.queue
  • cloud_video/queue.py:120 函数内导入 cloud_video.client.CloudVideoUnavailable
  • cloud_video/client.py:509 函数内 from cloud_video import lightai，使 client 依赖包本身，而 cloud_video/__init__.py 又导入 client 和 queue
  • cloud_video/lightai.py:28 顶层导入 cloud_video.client.CloudVideoError

这些导入在 HEAD 里已经存在，基线 layers_baseline.json 是 9864edc 时生成的，早于 cloud_video 包的引入。本地 6 个提交推送后，CI 的 layer-dag-guard 会失败。

修法建议：把异常类抽到 cloud_video/errors.py，client、queue、lightai 都从它导入（client 里保留重导出以兼容旧引用）；client.py:509 改为直接导入 cloud_video.lightai 子模块。改完以 python scripts/check_layers.py 的结果为准，不要用更新基线的方式消掉这条违规。

3. CI 不跑测试

.github/workflows/ci.yml 的 backend-test job 安装了 pytest pytest-asyncio pytest-cov，但唯一的验证步骤是：

python -c "from models import TicketStatus; print('Import OK')"

其余情况：

  • flake8 第一遍只查 E9,F63,F7,F82，第二遍带 --exit-zero，不会拦提交。
  • 前端没有 lint、构建或测试步骤。
  • backend/ 根目录下 78 个入库的 _test_*.py / _test_*.js 脚本不在 pytest.ini 的收集范围内（testpaths = tests、python_files = test_*.py），CI 和 pytest 都不会执行它们。

修法：在 backend-test 里加 python -m pytest（working-directory: backend）。全量约 5 分半，可以接受；若嫌慢，再拆出慢用例标记。

四、安全缺口

4. 全部 API 无鉴权

  • backend/config.py 默认 HOST=0.0.0.0、DEBUG=true。
  • backend/main.py:334 起的 CORS 配置是 allow_origins=["*"]、allow_credentials=True、方法和请求头全放开。
  • 在 backend/*.py 与 backend/api/*.py 中搜索 Depends(、HTTPBearer、APIKeyHeader、verify_token、client.host，只有 api/projects.py:38 的用户级 ConfigPack 守卫做了本机限制，其余接口没有任何身份校验。

后果是局域网内的机器，或者用户浏览器打开的任意网页，都可以调用并读取这些接口：

接口 位置 能做什么
GET /api/local-file?path= main.py:1234 按绝对路径读取本机任意图片文件
POST /api/system/open_path main.py:437 在资源管理器中打开任意路径
GET /api/open-in-browser?url= main.py:1250 让本机浏览器打开任意 http(s) 地址
POST /api/llm/config main.py:620 改写 LLM 配置并写回 .env
PUT /api/sop/config main.py:498 改写 SOP 流程配置
聊天与工单接口 api/chat.py、api/tickets.py 驱动 Agent 调用工具，包括 shell

修法建议（由易到难）：

  1. 默认监听改为 127.0.0.1，需要对外时显式配置。
  2. CORS 白名单收紧到本机来源。
  3. 加一个启动时生成的本地 token，前端和桌面壳带上，后端用全局依赖校验。
  4. /api/local-file 限制在项目目录、chat_images、generated-images 等已知根目录之内。

桌面版已核实（2026-11-24）：desktop.py:29 的 APP_HOST = "127.0.0.1"，desktop.py:119 用它调用 uvicorn.run，绑定的是 127.0.0.1:18000，不对局域网开放。

5. shell 工具黑名单覆盖不到 PowerShell 写法

backend/actions/chat/shell_exec.py:27 的黑名单正则列的是 rm -rf、del /f、rd /s、format X: 这类写法，而 Windows 上命令通过 powershell -Command 执行。Remove-Item -Recurse -Force、ri -r -fo 等 PowerShell 写法不在正则里。工作目录虽然限制在项目内，但命令文本本身可以引用任意绝对路径。

该工具文档标注为「Tier 1（需用户确认）」，确认流程本次没有核实。建议把黑名单当作辅助手段，主要依靠确认流程和权限系统；同时把 PowerShell 的删除、格式化、关机类 cmdlet 补进规则。

6. 500 响应返回异常文本

backend/main.py:342 的全局异常处理把 str(exc) 放进响应体。异常信息里可能带本机路径、SQL 片段或上游返回内容。建议响应里只给通用提示和一个可检索的错误 ID，详情留在日志。

五、工程化缺失

7. 依赖与 Python 版本没有锁定

  • backend/requirements.txt 只有下限约束，仓库里没有 lock 文件，也没有 pyproject.toml。
  • 本机环境的 fastapi 是 0.135.1，低于 requirements.txt 要求的 >=0.141.0，测试仍然通过，说明本机环境和声明的依赖已经脱节。
  • Python 版本有四种口径：README 徽章写 3.10+；scripts/check_layers.py 用 tomllib，需要 3.11+；CI 用 3.12；本机是 3.14.3；backend/tools/*/vendor/ 里的 wheel 是 cp311。
  • 3.14 下已出现的警告：
    • backend/api/chat.py:3550 附近有非法转义 \A（SyntaxWarning，后续版本会变成错误）。
    • backend/main.py:63 使用的 asyncio.set_event_loop_policy / WindowsProactorEventLoopPolicy 已弃用，3.16 移除。
    • backend/actions/diagnose_ticket.py:185、:198 使用已弃用的 datetime.utcnow()。

建议：确定一个受支持的版本区间（例如 3.11–3.13）写进 README 和 CI；生成锁定文件；修掉上述三处警告。

8. 版本号和配置文档对不上

  • 版本号有三个值：README 徽章 v0.22，backend/main.py:328 的 FastAPI 应用 0.10.0，backend/main.py:470 的 /api/health 返回 0.13.0。建议收敛到一个常量。
  • .env 模板有两份。根目录 .env.example 给的是 OpenAI 地址和 gpt-4，没有 LLM_API_FORMAT；代码里 LLM_API_FORMAT 默认是 anthropic，照这份模板填会得到格式和地址不匹配的配置。backend/.env.example 更完整，config.py 的注释也说明 backend/.env 是权威配置源。
  • README 的安装步骤先 cd backend 再 cp .env.example .env，没有说明两份模板的关系。建议删除根目录那份，或让它只指向 backend/.env.example。

9. 没有部署方案，日志不轮转

  • 仓库里没有 Dockerfile、docker-compose 或其他部署描述（自有代码范围内只有 backend/requirements.txt）。
  • 未入库的运行产物持续增长：backend/server.log 约 63.8MB，backend/logs/ 198 个文件约 55.6MB，backend/data/ 约 7.9GB，backend/projects/ 约 4.8GB。日志没有轮转或清理策略。
  • 根目录还有 10 个左右的散落日志文件和一个 0 字节的 ai_dev_system.db（均已被 .gitignore 忽略）。

11. 异常被大量吞掉

在自有后端代码范围内（排除 skills、config_packs、tools、tests、_ 开头的文件），except Exception: 或裸 except: 约 556 处，其中约 335 处下一行直接是 pass。这是 git grep 的粗略统计。数量最多的是 api/projects.py、orchestrator.py、api/chat.py、api/tickets.py、llm_client.py。

第 1 条那类问题能长期存在，和这种写法加上 CI 不跑测试有直接关系。建议从 orchestrator.py 和 api/ 开始，至少把静默吞掉改成 logger.debug(..., exc_info=True)。

12. 分层治理只完成一部分

按 check_layers.py 当前输出：471 个模块里 229 个还没有归层；存量违规 93 条，其中 92 条是方向违规：47 条是 L1 的 api.* 直接导入 L3 的 action 和 Agent，27 条是 L3 直接导入 L1 的 llm_client，其余 18 条分散在 orchestrator、plugins.registry、sop 等处；4,590 条 import 语句里 43% 是函数内延迟导入，说明不少环是靠延迟导入绕开的。后续安排见 docs/20261117_01_六层架构改造方案.md。

13. 仓库里混了大量非源码

  • 入库文件共 7,440 个，其中 backend/skills/marketplace/ 下整包拷入的两个插件市场占 5,388 个（codebuddy-plugins-official 3,763，cb_teams_marketplace 1,625）。可以考虑改成 submodule 或按需下载。
  • backend/ 根目录有 152 个入库文件，其中 104 个以 _ 开头，包括调试输出、日志 fixture 和上面提到的 78 个 _test_* 脚本。有价值的应迁入 backend/tests/，其余删除。
  • pywin32、cryptography、pydantic_core 三个 wheel 在 backend/tools/ue_editor_mcp/Python/vendor/ 和 backend/tools/memory_mcp/vendor/ 各存一份，合计约 30MB。
  • backend/llm、backend/models、backend/orchestrator、backend/utils 四个目录在磁盘上是空的，其中 models、orchestrator 与同名的 .py 模块重名，容易引起导入歧义，建议删除。

  2. shell 黑名单旧正则以 \b 收尾，rm -rf /、format c: 这类以非单词字符结尾的命令匹配不上。第 5 条当时只指出了 PowerShell 写法缺失，实际上原本列出的写法也有一部分拦不住。
  3. backend/agents/chat_assistant.py 里有两处非法转义序列，Python 3.12 起会报 SyntaxWarning；同一文件和 backend/api/chat.py 里还各有一处写死的本机绝对路径，已改成按运行位置推导。

验证结果：全量 pytest 868 通过、0 失败（修复前是 762 通过、2 失败），在 Windows 的 Python 3.14.3、Python 3.12.13（按 requirements.txt 新装依赖）和只含入库文件的干净目录下各跑了一轮。Linux、真实服务启动和浏览器端到端没有验证。
