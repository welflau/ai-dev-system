# 工单 Checkpoint 快照与还原方案（对标 Cursor）

日期：2026-08-07  
状态：P0–P3 已实现（见 `dev-notes/2026-08-07_02`～`05`）  
关联：取消工单 Git 回滚（已实现，作兜底）  
关联对话结论：取消/重跑需可还原工作区；Cursor 用写前 Checkpoint，不依赖 Git  

---

## 一、背景与结论

### 1.1 现状

| 能力 | 行为 | 局限 |
|---|---|---|
| 取消工单 | `DELETE .../tickets/{id}` → `cancelled` | 原先不碰仓库 |
| 取消 + Git revert（2026-08-07） | `?revert=true`，按 `ticket_commands` / artifacts / OpenSpec 路径，相对 commit 父节点或主分支 `checkout`/删除 | **依赖 Git 历史**；无 commit（手动挡、半成品、旁路写入）时弱；同需求共享分支时路径级回滚仍可能误伤重叠文件 |
| Cursor Agent | 写前本地 Checkpoint；对话时间轴 **Restore Checkpoint** | 与 Git 分离；官方明确：Checkpoint 只管撤销 Agent 改动，长期版本用 Git |

### 1.2 结论

要做成 Cursor 体验，ADS 需要 **写前文件快照（Checkpoint）** 作为一等公民：

- **主路径**：取消 / 时间轴还原 → Restore Checkpoint  
- **兜底**：无可用 Checkpoint 的老工单 → 现有 Git revert  

二者并存，UI 写清策略。

### 1.3 非目标（本方案不做）

- 整仓镜像备份、整分支 `git reset --hard`  
- 还原 DB 迁移、引擎编译产物、远端已 push 的提交  
- 替代 Git 作为团队协作与发布的版本控制

## 二、目标与验收

### 2.1 产品目标

1. Agent / Skill **改文件前**自动拍 Checkpoint（仅登记即将写入的路径）  
2. 工单时间轴可查看 Checkpoint，并 **一键还原到某点**（确认后执行）  
3. 取消工单默认「还原到本单 ticket_start Checkpoint」，二次确认；可选手动「仅取消不还原」  
4. 不依赖「是否已 git commit」；手动挡、OpenSpec SkillRunner 写入均可回  

### 2.2 验收标准

| ID | 场景 | 期望 |
|---|---|---|
| A1 | 自动挡 develop 写文件后取消并确认还原 | 工作区回到 ticket_start；有新 commit 可选（见策略） |
| A2 | 手动挡只写不 commit 后取消还原 | 同样还原成功（不依赖 commit） |
| A3 | OpenSpec Propose 写入 `openspec/changes/c-xxx/` 后还原 | 目录/文件回到拍快照前 |
| A4 | 时间轴点选中间 Checkpoint Restore | 仅回滚该点之后登记路径的内容 |
| A5 | 无 Checkpoint 的老单取消 + revert | 仍走 Git 兜底，提示「无快照」 |
| A6 | 超大/二进制文件 | 快照跳过或截断策略生效，UI 提示 |

## 三、概念模型

```
┌─────────────────────────────────────────────────────────────┐
│  Checkpoint                                                  │
│  id, project_id, ticket_id, trigger, parent_id?, created_at   │
│  trigger ∈ { ticket_start, before_write, phase_boundary }  │
└────────────────────────────┬────────────────────────────────┘
                             │ 1:N
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  CheckpointFile                                              │
│  path (repo-relative), kind ∈ { created, modified, deleted }│
│  before_hash (内容 SHA256；null = 拍快照时磁盘上不存在)        │
│  byte_size, content_type?, skipped_reason?                   │
└────────────────────────────┬────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  Blob Store（content-addressed）                             │
│  {DATA_DIR}/checkpoints/blobs/{sha256[:2]}/{sha256}          │
│  开发态即 backend/data/checkpoints/…；Desktop 为 runtime/data │
│  同内容多工单共享，按引用计数或 GC 按 TTL 清理                   │
└─────────────────────────────────────────────────────────────┘
```

**还原语义（对齐 Cursor）**：

- `before_hash` 有值 → 将文件写回该内容（mkdir 父目录）  
- `before_hash` 为 null 且 kind=created → **删除**该路径（本单新建）  
- 只动本 Checkpoint（或「从该点到当前」差集）登记过的路径，不做整仓还原  

**差集还原**：Restore 到 Checkpoint C = 对「C 之后产生的所有 Checkpoint 所登记路径」按时间逆序应用各自的 before 状态；实现上可简化为「取 C 的文件表并写回」，若同一 path 在 C 之后多次修改，以 C 时刻的 before 为准需在拍快照时保证 **ticket_start 全量基线 + 每次 before_write 增量** 可组合。推荐：

- `ticket_start`：可为空文件表（标记点），或浅扫描「本单将写入集合未知」时仅作锚点  
- `before_write`：对本次即将写入的每个 path 记录 before  
- Restore 到 C：收集 **created_at > C.created_at** 的所有 CheckpointFile，按 path 取 **最早一次** 的 before（即刚越过 C 之后第一次改该 path 前的内容）写回；并对仅在之后出现的 created 路径删除

## 四、架构与写入拦截

### 4.1 漏斗（必须收口）

所有 Agent 落盘尽量经过：

| 漏斗 | 说明 |
|---|---|
| `git_manager.write_file` / `write_files` | Orchestrator `_handle_git_files` 主路径 |
| `actions.write_file.WriteFileAction` | SkillRunner / OpenSpec |
| QueryEngine / CLI 适配层对 Write、Edit | 防旁路直写磁盘 |

在真正写盘 **之前** 调用：

```text
checkpoint_service.capture_before_write(
    project_id, ticket_id, paths[], trigger="before_write"
)
```

`process_ticket` 认领工单成功后：

```text
checkpoint_service.create_marker(project_id, ticket_id, trigger="ticket_start")
```

阶段边界（可选，P1）：architect/develop/test 完成时 `phase_boundary`，便于时间轴细粒度还原。

### 4.2 模块划分

```
backend/
  checkpoint/
    service.py      # capture / restore / list / gc
    store.py        # blob 读写、hash
    models.py       # 常量与 DTO
  database.py       # checkpoints / checkpoint_files 表
  api/tickets.py    # list / restore；cancel 优先走 checkpoint
  git_manager.py    # write_* 内钩子（或显式注入 service，避免循环依赖）
```

依赖方向：`write_file` → `checkpoint.service` → `db` + 磁盘；**不要**让 checkpoint 依赖 orchestrator。

### 4.3 与现有 Git revert 关系

```
取消工单 + 用户确认还原
        │
        ├─ 存在 ticket_start（或任一可还原 CP）？
        │         Yes → Checkpoint Restore（主路径）
        │         No  → Git revert 兜底（现逻辑）
        │
        └─ 用户选「仅取消」→ 只改 status
```

时间轴单独「还原到此」**只走 Checkpoint**，不自动 Git revert。

## 五、数据模型（草案）

```sql
CREATE TABLE IF NOT EXISTS checkpoints (
    id              TEXT PRIMARY KEY,          -- CP-xxxxxxxx
    project_id      TEXT NOT NULL,
    ticket_id       TEXT NOT NULL,
    trigger         TEXT NOT NULL,             -- ticket_start|before_write|phase_boundary
    parent_id       TEXT,                      -- 可选，链表
    agent_type      TEXT,
    action          TEXT,                      -- develop / openspec_propose …
    note            TEXT,
    created_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS checkpoint_files (
    id              TEXT PRIMARY KEY,
    checkpoint_id   TEXT NOT NULL REFERENCES checkpoints(id),
    path            TEXT NOT NULL,             -- repo-relative，/ 分隔
    kind            TEXT NOT NULL,             -- created|modified|deleted
    before_hash     TEXT,                      -- null = 当时不存在
    byte_size       INTEGER,
    skipped_reason  TEXT,                      -- too_large|binary|io_error
    UNIQUE(checkpoint_id, path)
);

CREATE INDEX IF NOT EXISTS idx_cp_ticket ON checkpoints(ticket_id, created_at);
CREATE INDEX IF NOT EXISTS idx_cpf_cp ON checkpoint_files(checkpoint_id);
```

Blob 不进 SQLite（避免库膨胀）。落盘根目录与现有 `DATA_DIR` 对齐（见 `backend/config.py`）：

| 运行形态 | `DATA_DIR` | Checkpoint blob 路径 |
|---|---|---|
| 开发 / 普通后端 | `backend/data/` | **`backend/data/checkpoints/blobs/{hh}/{sha256}`** |
| Desktop 封装 | `{app}/runtime/data/` | `{app}/runtime/data/checkpoints/blobs/...` |

可用环境变量 `DB_PATH` 改库位置时，Checkpoint 仍跟 `DATA_DIR`（与 DB 同级的 `data/`），保持「运行时数据一处」。

可选表 `checkpoint_blob_refs(hash, refcount, last_used_at)` 做 GC；P0 可用「按工单终态 + TTL 扫目录」简化。

## 六、API 与前端

### 6.1 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/projects/{pid}/tickets/{tid}/checkpoints` | 列表（含 files 摘要） |
| GET | `/api/projects/{pid}/tickets/{tid}/checkpoints/{cpid}` | 详情 |
| POST | `/api/projects/{pid}/tickets/{tid}/checkpoints/{cpid}/restore` | body: `{ confirm: true }`；还原并写 timeline |
| GET | `/api/projects/{pid}/tickets/{tid}/revert-preview` | **扩展**：优先返回 checkpoint 计划，附 `strategy: checkpoint\|git\|none` |
| DELETE | `/api/projects/{pid}/tickets/{tid}?revert=true` | 有 CP 则 restore ticket_start，否则 Git |
| POST | `/api/projects/{pid}/checkpoints/gc` | 手动 GC（ttl_days / keep_active_writes） |

### 6.2 前端

- 取消：预览文件列表 + 「将使用 Checkpoint 还原」/「将使用 Git 回滚」标签  
- 时间轴：`checkpoint` 节点展示触发类型与文件数；操作 **还原到此**  
- 还原确认框：列出将恢复/删除的 path（上限展示 20 +「另有 N 个」）  

### 6.3 时间轴事件

| action | tier | 说明 |
|---|---|---|
| `checkpoint` | secondary 或 primary（ticket_start 建议 primary） | 已拍快照 |
| `checkpoint_restore` | primary | 已还原 |

## 七、策略细则

### 7.1 文件过滤

- 默认只快照文本类；扩展名黑名单：`.exe` `.dll` `.pdb` `.uasset` `.umap` 等（可配置）  
- 单文件上限默认 **2 MiB**；超出记 `skipped_reason=too_large`，还原时跳过并汇总警告  
- 路径归一化：与 `git_manager._normalize_rel_path` 一致；拒绝 `..`  

### 7.2 还原后是否 commit

| 项目 mode | 行为 |
|---|---|
| auto | Restore 后可选 `git add` + commit `[Operator] restore checkpoint …`（与现 revert commit 对称） |
| manual | 只改工作区，不 commit |

### 7.3 并发与共享分支

- Checkpoint 按 **ticket_id** 隔离；还原只写本单登记 path  
- UI 警告：同需求其它工单若改过相同文件，还原可能覆盖  
- 不删除共享 `feat/…-req-…` 分支  

### 7.4 清理（GC）

- 工单 `cancelled` / `deployed` 后保留 **14 天**（可配置）再删元数据与仅被其引用的 blob  
- 进行中工单：每个 ticket 保留最近 N 个 `before_write`（默认 50）+ 全部 `ticket_start` / `phase_boundary`  

### 7.5 安全

- Restore / 取消还原需与工单同 `project_id` 鉴权（与现 API 一致）  
- 不执行任意 shell；只写回已知 path

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 漏斗外 Bash 直写 | P2 补钩；文档声明「仅 ADS 工具写入可 Checkpoint」 |
| 磁盘膨胀 | hash 去重 + TTL + 单文件上限 |
| 同文件多工单互相覆盖 | 还原确认文案警告；长期可考虑 per-ticket worktree（另案） |
| write 热路径延迟 | 同步读旧文件通常可接受；大文件跳过；禁止整仓扫描 |
| 与现 Git revert 双逻辑 | preview 明确 `strategy`；单测覆盖两分支 |

## 十一、与 Cursor 对照（给评审）

| 维度 | Cursor | 本方案 |
