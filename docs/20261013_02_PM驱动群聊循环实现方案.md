# Agent 群聊 PM 驱动循环实现方案

> 日期：2026-10-13
> 状态：✅ Phase 1 已实现（PM 决策循环 + 目标提炼 + 用户介入 + 纪要）
> 前置：`20261012_01_多Agent群聊黑板架构方案.md`（黑板基础设施，已实现 Phase 1）

## 一、背景与目标

现有黑板群聊是「固定回合制辩论」：每条用户消息触发固定的「Round 1 发散 → Round 2 交锋 → 收敛器收敛」，
一次产出结论即结束。体感是「一问一答」的终端式，存在两个明确缺陷：

1. **没有节奏感**：无论话题多复杂或多简单，永远跑同样多的轮次，不该聊时硬聊、该深挖时草草收场。
2. **没有跨消息连贯性**：`transcript` 每次从空开始，Agent 看不到上一条消息的结论与发言，聊不出「接着上面说」的感觉。

本方案把群聊从「固定回合制」演进为「**PM 驱动的动态循环**」——由一个项目经理（PM）角色把控进度：

> PM 记录总结内容 → 合适时发问 → 合适时小结 → 针对小结再发问 → @ 各人意见 → 再发散 →
> 直到达成预期目标 → 给出结论总结。

这套模型与 AutoGen 的 `GroupChatManager`、MetaGPT 的 PM/Manager 角色同源，落到本系统已有
的黑板 + SSE + session 隔离基础设施上，是自然演进而非推倒重来。

## 三、核心模型：PM 决策循环

### 3.1 角色

- **PM** = `OrchestratorAgent`（persona 从「需求拆分/编排」增强为「项目经理」，见 §5）。
- **与会者** = `DevAgent` / `TestAgent`（可扩展），被动应答，不主动抢话。
- **用户** = 会议发起人，可随时介入（需求 B）。

### 3.2 循环结构

每一条用户消息开启一次「会议」，循环如下（伪代码）：

```
1. 初始化
   - 加载/新建黑板（按 _currentGroupSessionId 隔离）
   - 若本场会议尚无 goal：PM 提炼目标（需求 A）→ 写黑板 goal 分区
2. PM 决策循环（最多 max_pm_decisions 次）
   a. 组装 PM 状态视图 = goal + 黑板快照 + 纪要 + 上一动作结果 + 待处理用户介入
   b. PM 做一次 LLM 决策 → 输出动作 JSON
   c. 执行动作
      - ask        ：向 targets（空=全体）发问 → 被点名者并行回复（发散）
      - summarize  ：写纪要小结（summary 分区），不产生回复
      - conclude   ：输出最终结论 + 会议纪要 → 结束循环
   d. 更新黑板 version
3. 结束：SSE 推送最终结论 + 纪要，落库
```

关键区别：**不再是固定 2 轮**，而是 PM 根据状态动态决定「下一步干什么」，直到判断达成目标或预算耗尽。

### 3.3 PM 决策动作 Schema

PM 每次决策输出严格 JSON：

```jsonc
{
  "action": "ask" | "summarize" | "conclude",
  "targets": ["DevAgent"],              // 仅 ask 有效；空数组 = 全体
  "question": "并发安全问题你怎么看？",  // ask 时必填
  "summary": "当前共识：...；分歧：...",  // summarize 时必填
  "conclusion": "## 最终结论\n...",      // conclude 时必填
  "reason": "分歧已明确，可收敛"          // 决策理由（可观测性，展示给用户）
}
```

**动作语义**：

| 动作 | PM 行为 | 与会者行为 | 黑板写入 |
|---|---|---|---|
| `ask`（全体） | 抛出一个问题/话题 | 三人并行回复 | 各人 `proposals`/`facts` 写入 |
| `ask`（@点名） | 只问指定的人 | 仅被点名者回复 | 同上 |
| `summarize` | 阶段小结 | 无 | 追加 `summary` 纪要 |
| `conclude` | 最终结论 | 无 | 终版 `decisions` + `summary` |

### 3.4 收敛判据（PM 内部判断，写入 `reason`）

PM 判定「该 conclude」的条件（prompt 中明确列出）：

1. `goal.acceptance_criteria` 全部有明确结论（facts/decisions 覆盖每个验收点）；
2. 分歧已被明确定位（写进 `open_questions`），且不影响最终结论；
3. 连续两次 `ask` 无新增有效信息（重复发散）；
4. 预算将尽（PM 被迫收束）。

## 四、需求 A：目标提炼

首条用户消息进来、黑板尚无 `goal` 时，PM 先做一次「目标提炼」调用，输出：

```jsonc
{
  "goal": "为 TODO 应用确定 MVP 范围与技术选型",
  "acceptance_criteria": [
    "明确 MVP 功能清单（增删改查 + 完成态）",
    "确定后端技术栈",
    "确定测试策略与关键用例"
  ],
  "participants": ["OrchestratorAgent", "DevAgent", "TestAgent"]
}
```

- 写入黑板 `goal` 分区（`{goal, acceptance_criteria, participants}`）。
- `acceptance_criteria` 是 PM 后续「何时收敛」的客观判据，也是「逐渐达到预期目标」的度量尺。
- 若提炼失败（JSON 解析失败），降级：`goal = 用户消息`，`acceptance_criteria = []`，PM 按「无目标」模式跑（收敛靠预算 + 重复检测）。

## 五、需求 B：用户随时介入

- 用户在会议进行中任意时刻发消息（前端不阻断输入框）。
- 前端把新消息标记为 `user_intervention`，中断当前 SSE（`AbortController`）或注入为下一条待处理输入。
- 后端 PM 决策循环在**每轮决策前**检查是否有 pending 介入；若有，作为**最高优先级输入**注入 PM 决策 prompt：

```
[用户介入（最高优先级）] 用户说：后端就用 Go，别纠结了。
（请优先围绕此介入调整下一步动作；若已无关，可忽略并继续原计划）
```

- 介入内容同时追加进 `summary` 纪要（标 `[用户]` 来源），保证跨消息可回溯。
- 介入可能触发的新一轮会议沿用同一 `_currentGroupSessionId`（同一场群聊），黑板不重置。

## 六、黑板结构扩展

在现有六分区之上新增两分区，`state_json` 结构变为：

```jsonc
{
  "session_id": "...",
  "project_id": "...",
  "version": 8,
  "topic": "当前话题（跟随最新用户消息）",
  "goal": {                          // 需求 A 写入
    "goal": "...",
    "acceptance_criteria": ["..."],
    "participants": ["..."]
  },
  "summary": [                       // PM 纪要（跨消息记忆核心）
    { "author": "OrchestratorAgent", "content": "阶段小结...", "ts": "..." },
    { "author": "user", "content": "后端用 Go", "ts": "..." }
  ],
  "facts": [...], "proposals": [...], "open_questions": [...],
  "decisions": [...], "artifacts": [...]
}
```

- `summary` 是**连续对话的关键**：下一轮 PM 决策、以及后续新用户消息的 PM 决策，都注入最近 N 条纪要，
  让「接着上面聊」成立。
- 收敛器/PM 写 `decisions` 终版（Phase 1 收敛器行为由 PM 的 `conclude` 动作取代）。

## 七、PM Persona 增强

`_AGENT_CONFIG["OrchestratorAgent"].persona` 在 PM 模式下增强为：

```text
你是 PMAgent（项目经理），主持一场多 Agent 技术讨论会。
你的职责：
1. 记录与总结：每次关键讨论后写纪要（summary），沉淀共识与分歧。
2. 控制节奏：合适时发问推进、合适时小结收束，@ 指定成员征求意见。
3. 以目标为导向：始终对照 acceptance_criteria 判断是否已达成，未达成则追问缺口。
4. 及时收敛：达成目标或分歧已定位时，果断给出最终结论，不要无意义拖延。
风格：简洁、有决断，问句具体（"DevAgent，关于并发安全你怎么看？"），不空泛。
```

其余与会者 persona 增加「你是会议参与者，只在被 PM 点名或话题与你专业相关时发言，
回复聚焦被问的问题，不重复他人」约束（抑制刷屏）。

## 八、SSE 事件协议

在现有事件基础上新增/调整（前端 `_sendGroupBoardStreaming` 增量消费）：

| 事件 | 载荷 | 触发时机 | 前端呈现 |
|---|---|---|---|
| `pm_goal` | `{goal, acceptance_criteria}` | 需求 A 提炼完成 | 「🎯 目标」卡片（置顶） |
| `pm_action` | `{action, targets, question?, reason}` | PM 每次决策 | 「PM 决定」过程行（类似思考过程排版） |
| `pm_summary` | `{summary, ts}` | PM 小结 | 「📝 纪要」追加卡片 |
| `round_begin`（已有） | `{round, label}` | ask 时 | 「第 N 轮 · 发散」分隔头（复用） |
| `agent_thought`（已有） | `{agent, thought, round}` | 被点名者思考 | 思考弱化条目 |
| `agent_message`（已有） | `{agent, content, reply_to?}` | 被点名者发言 | Agent 气泡（@引用高亮） |
| `board_update`（已有） | `{board, changed_sections}` | 每步后 | 黑板侧栏 live |
| `converge`（已有） | `{agent, content}` | PM conclude | 收敛结论卡 |

`pm_action` 的呈现是「过程文字」的关键：用户能看到 PM 每步的决策与理由
（"PM：@DevAgent 追问并发安全 —— 理由：这是当前唯一未决的验收点"），
让「把控进度」这件事本身可视化。

## 九、预算与终止条件

| 参数 | 默认 | 说明 |
|---|---|---|
| `max_pm_decisions` | 8 | PM 决策调用上限（含 ask/summarize/conclude） |
| `max_agent_rounds` | 4 | ask 动作的总次数上限（发散轮数） |
| `max_tokens` | 复用 QueryEngine Budget 思路 | 单场会议 token 总预算 |
| 用户手动停止 | 前端 AbortController | 任意时刻中断 |
| 冷场 | PM 决策可输出 ask 强制推进 | Phase 3 可选「随机冷场救火」 |

终止优先级：`conclude 动作` > `预算耗尽` > `用户中断`。预算耗尽时强制 PM 做最后一次 conclude。

## 十、数据持久化

- `chat_blackboards` 表**不变**，仅 `state_json` 结构扩展（加 `goal`/`summary`）。
- `chat_messages`：
  - 与会者发言：`role='assistant', speaker=<Agent>, kind='utterance'`（已有）。
  - PM 决策/纪要/结论：`role='assistant', speaker='OrchestratorAgent', kind='system'`，
    `action_data` 标记 `{"type":"pm_action"|"pm_summary"|"pm_conclude", ...}`。
  - 用户介入：`role='user', speaker='user', kind='message'`（已有）。
- 刷新还原：既有 `group_agent_reply` 气泡还原 + `speaker` 列渲染（已实现），PM 的 system 消息
  走既有 system 分支渲染（收敛小结已有）。

## 十一、API

沿用 `POST /api/projects/{pid}/chat/group/board`，`GroupBoardRequest` 扩展：

```python
class GroupBoardRequest(BaseModel):
    message: str
    images: Optional[List[str]] = None
    chat_session_id: Optional[str] = None   # 已有，会话隔离
    mode: str = "pm"                        # 新增：pm=PM驱动循环（默认）| legacy=固定回合制
```

- 默认 `mode="pm"`，老回合制保留为 `mode="legacy"`（回退/对照用）。
- 前端黑板开关默认走 `pm`；「新旧对照」时切 legacy。

## 十三、分阶段实施路线

### Phase 1（核心闭环，最小可用）
- PM 决策循环（ask/summarize/conclude）+ 预算终止。
- 需求 A：goal 提炼（含降级）。
- 需求 B：用户介入注入 PM 决策。
- 黑板加 `goal`/`summary` 分区 + 落库。
- SSE 新增 `pm_goal/pm_action/pm_summary`。
- 前端：目标卡 / PM 过程行 / 纪要卡。

### Phase 2（体验打磨）
- @点名 `targets` 定向发言（`reply_to` 渲染）。
- 纪要作为跨消息记忆注入（解决「聊不下去」）。
- PM 决策 `reason` 全程可视化。
- 冷场检测 + 随机救火（可选）。

### Phase 3（进阶，谨慎评估）
- 情绪/口癖人格注入（纯 prompt）。
- 表情反应（纯 UI）。
- 打断机制、私聊频道（成本高，独立评估）。

## 十四、风险与取舍

1. **成本上升**：PM 每轮多一次决策调用，一场会议 ≈ `1（goal）+ N（决策）+ M（与会者回复）` 次调用。
   通过 `max_pm_decisions`/`max_agent_rounds` 硬上限兜底。默认预算下约 8-15 次调用。
2. **PM 决策不稳定**：JSON 解析失败降级为「对全体 ask 一次」；连续失败则直接 conclude（保底出结论）。
3. **目标提炼偏差**：goal 提炼错会带偏全场。缓解：goal 提炼后 `pm_goal` 事件先展示，用户可介入纠正（需求 B 天然兜底）。
4. **纪要膨胀**：summary 无限追加会撑爆 token。缓解：只注入最近 N 条（默认 5）+ 每条截断 300 字。
5. **收敛过早/过晚**：PM 判据主观。缓解：`acceptance_criteria` 客观化 + 预算兜底 + 用户可介入强收。

## 十五、验收标准

1. 同一场群聊（同一 session）连续多轮追问，Agent 能引用上一轮结论（纪要注入生效）。
2. PM 能根据话题复杂度决定轮次：简单话题 1-2 轮收敛，复杂话题深入多轮。
3. 用户中途插话，PM 下一轮围绕介入调整方向。
4. 全程「PM 决定」过程可见，最终结论覆盖 `acceptance_criteria` 或明确标注未决项。
5. 预算耗尽时仍有结论（不空转）。

### 验证

- `py_compile` / `node --check` 通过。
- 端到端 HTTP 实测（mode=pm, max_pm_decisions=5）：事件流 `turn_begin → board_init → pm_goal →
  pm_action×3 → round_begin×2 → agent_thought×2 → agent_message×2 → board_update×2 →
  pm_summary → converge → message_done` 完整，PM 正确 @DevAgent 定向追问。

### 实现偏差 / 遗留

- 需求 B（用户介入）：当前「每条用户消息 = 一次介入」在 PM 决策首步注入；进行中打断靠前端 Abort 后重发，
  尚未做「同一流内实时打断」。
- @点名 `targets` 已实现（后端定向回复），前端 `reply_to` 引用高亮未做（Phase 2）。
- 纪要作为跨消息记忆注入：`_pm_state_view` 已注入最近 5 条 summary，满足「接着聊」。
- 修复过程中发现的 bug：`_pm_extract_goal`/`_pm_decide` 缺 `set_llm_context` 导入（NameError）；
  goal 提炼 `max_tokens` 800 → 1500（防截断）；`max_agent_rounds` 耗尽时 `continue` 死代码改为 `break`。
