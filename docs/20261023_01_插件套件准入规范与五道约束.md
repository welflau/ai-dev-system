# ADS 插件套件准入规范与五道约束（以 H5/Phaser 套件为标杆）

日期：2026-10-23  
状态：强制生效（所有新增/迭代的 `backend/plugins/<id>/` 套件必须遵守）  
关联文档：`docs/20261019_01_Action成套插件与公共工具边界方案.md`、`docs/20261015_01_能力自描述与动态组装框架方案.md`、`docs/20261024_01_UE插件对照H5准入约束的缺口与修改方案.md`

---

## 一、背景：为什么需要这份约束？

在把 H5/Phaser 能力从 GameBox 抽成 ADS 插件套件（`backend/plugins/h5/`）并跑真实 6 工单流水线的端到端实战中，我们连续踩到了 **“只有正向执行 Action、缺少配套可观测性与失败闭环”** 带来的典型工程问题：

1. **门禁打回但反思盲猜**：插件定义了 `h5_typecheck_failed` / `h5_playtest_failed` 并通过 `reject_goto: development` 打回给 `DevAgent.fix_issues`，但 `ReflectionAction` 没有该插件的失败信号格式化逻辑，只收到一句 `失败类型: h5_typecheck_failed`，AI 看不到任何 `tsc` 报错行与 `raw_tail`，只能蒙眼盲猜。
2. **安装与构建黑盒运行**：插件内部自动跑 `pip install`、`playwright install chromium`、`npm install`、`tsc`、`vite build`，因为不经过 `SkillRunner` 的 `POST_TOOL_USE` Hook，工单时间轴既没有步骤状态，也没有 **📟 后台任务** 链接。
3. **把环境缺失当代码 Bug 空修**：缺少 Chromium 驱动或切分支被 `git clean -fd` 删掉 `node_modules`、回退 `npx --yes tsc` 调到 npm 假包时，返回了 `*_failed`，导致 `DevAgent` 对着正常的游戏代码空改 3 轮直到 `blocked`。
4. **看板状态失踪与前端类型崩溃**：插件动态状态未纳入看板列兜底导致工单在看板上“消失”；`detail.command` 存成 `List[str]` 数组导致前端 `escapeHtml` 调 `str.replace` 崩溃。

为确保后续接入的任何新插件套件（如 Godot、Unity、微信小游戏、Flutter、Android 等）一次到位、不再重踩上述坑，特制定本准入规范。

## 二、插件套件标准目录结构

每个领域套件位于 `backend/plugins/<plugin_id>/`，标准结构如下：

```text
backend/plugins/<plugin_id>/
├── plugin.json                 # 套件元数据与 required_traits 启用条件
├── reflection.py               # 【必选：凡有门禁打回】失败上下文提取与反思信号构建器
├── actions/                    # 领域 Action 实现（自动注册到 plugins.registry）
│   ├── __init__.py
│   └── ...
├── skills/                     # 知识注入型或工作流型 Skill
│   └── <skill-id>/
│       └── SKILL.md
└── templates/                  # 【可选】工程脚手架模板
```

## 三、五道硬性准入约束

### 约束 1：凡有门禁打回（`reject_status`），必须配套 `reflection.py`

只要插件在 SOP Fragment 或 `x-workflow` 中声明了会触发返工的失败状态（如 `xxx_failed`），**严禁**去改宿主 `agents/dev.py` 和 `actions/reflection.py` 的 `if/elif` 分支，必须在插件目录内提供 `reflection.py`：

```python
# backend/plugins/<plugin_id>/reflection.py
from typing import Any, Dict

# 1. 声明本插件接管的所有失败状态名
HANDLED_FAILURE_TYPES = frozenset({
    "h5_typecheck_failed",
    "h5_playtest_failed",
})

# 2. 从最近一条 reject 日志的 detail JSON 中提取诊断字段写入 context
def enrich_fix_context(
    failure_type: str,
    reject_detail: Dict[str, Any],
    context: Dict[str, Any],
) -> None:
    ...

# 3. 构建喂给 ReflectionAction LLM 的结构化失败信号
def build_reflection_signal(
    failure_type: str,
    context: Dict[str, Any],
) -> str:
    ...

# 4. 【强烈推荐】确定性快修器（0 LLM 调用，秒级自动修正常见编译/类型错误）
def apply_deterministic_fixes(
    failure_type: str,
    repo_path: str,
    compile_errors: List[Dict[str, Any]],
    existing_code: Dict[str, str],
) -> Dict[str, str]:
    ...
```

**`build_reflection_signal` 与 `apply_deterministic_fixes` 必须协同工作**：
1. **结构化报错明细**：精确到 `文件路径:行:列`、错误码及错误描述；
2. **领域专属修复提示（Hints）**：把该引擎/框架最容易犯的 API 误用（如 Phaser 颜色参数 `number` vs `string`、UE 宏遗漏）直接翻译成修改指令；
3. **剥除 ANSI 控制符后的 `raw_tail`**：当正则未能解析出结构化错误（如命令启动失败、配置报错）时，必须把干净的控制台原始尾部贴给 LLM，绝不能让 `0 errors` 变成空反馈；
4. **插件自带确定性快修（`apply_deterministic_fixes`）**：对于编译器已经报出精确文件与行号、且修法 100% 确定的高频领域错误（例如 Phaser `TS2345` 把 `'#RRGGBB'` 字符串传给了只收 `number` 的 `add.rectangle`），插件必须在 `apply_deterministic_fixes` 中直接完成 AST/行级替换返回 `{path: fixed_content}`。`DevAgent` 检测到报错文件已被插件 100% 确定性修好时，**直接跳过 120s 的 LLM 反思与全套重写**，0 Token 秒级过关；即便还有未覆盖的编译错误，`PlanCodeChangeAction` 也会走「编译错误直达快通道」，**只修改编译器点名报错的那几个文件**，严禁再去重新规划和重写无关脚本。

### 约束 2：所有子进程命令与环境自愈必须写入时间轴 + 任务 Log（`TCMD-*`）

插件 Action（常由 `DevAgent` / `TestAgent` 直接调用 `action.run(context)`，不经过 `SkillRunner` Hook）内部执行的任何外部命令（依赖安装、类型检查、构建、试玩）：

1. **命令落库**：必须调用 `command_log.record_traced_command(...)`，同时写入 `ticket_logs`（`action="command_run"`）和 `ticket_command_log`，拿到返回的 `record_id`（`TCMD-...`）。
2. **长步骤打点**：耗时步骤（如自动安装浏览器/依赖、编译构建、运行试玩）在开始前打 `skill_step_start`，结束时打 `skill_step_done` / `skill_step_error`，并将 `task_id=record_id` 写入步骤 `detail`。
3. **结果透传 `task_id` 与字符串 `command`**：
   - `ActionResult.data["task_id"]` 必须带上 `record_id`，供 `orchestrator` 写入 `complete` / `reject` 日志的 `detail_data`；
   - `ActionResult.data["command"]` **必须是字符串 `str`**（用 `shlex.quote` 拼接），**严禁直接塞 `List[str]`**。

---

### 约束 3：环境自愈优先，严禁把环境问题判为代码失败（`*_failed`）

1. **缺依赖先自愈**：检测到缺本地依赖（如缺 `node_modules`、缺本地 `tsc`、缺无头浏览器驱动）时，先在 Action 内自动执行安装命令（并记入时间轴与任务 Log），安装成功后再继续执行门禁。
2. **外部包执行器必须锁包名**：使用 `npx` 等工具兜底时，必须显式传 `--package <real_pkg>`（例如 `npx --yes --package typescript tsc`），防止命中同名恶意/废弃占位包。
3. **环境失败分流**：
   - 若自动安装后环境仍不可用：非核心运行时检查应返回 `success=True, runtime_skipped=True` 并附 `warnings`；
   - 核心必选工具链缺失应返回 `status="error"` 让 Orchestrator 立即转 `blocked` 并触发 `_diagnose_blocked_ticket` 通知人工，**绝不能返回 `*_failed` 触发 `DevAgent.fix_issues` 去瞎改业务代码**。

---

### 约束 4：仓库产物目录隔离与分支切换保护

1. **文件树扫描隔离**：插件产生的重型依赖或构建产物目录（如 `node_modules/`、`dist/`、`Library/`、`Temp/`、`Binaries/`、`Intermediate/`）必须加入 `git_manager.get_file_tree` 的 `_SKIP_DIRS`，避免污染 AI 上下文与触发海量 `git show` 噪音。
2. **分支切换保护**：未纳入 Git 跟踪但跨分支复用的重型依赖目录（如 `node_modules`），必须在 `git_manager.switch_branch` 的 `git clean -fd` 中通过 `--exclude=<dir>` 保护，防止切分支时被清空。

---

### 约束 5：动态状态命名规范与看板可见性

1. 插件引入的阶段状态必须遵循后缀约定，以便 `api/tickets.py::_classify_board_column` 自动归入看板五列：
   - 进行中：`*_in_progress` → 归入「**进行中**」列
   - 阶段通过：`*_passed` / `*_done` / `*_ready` → 归入「**审核中**」列
   - 阶段打回：`*_failed` / `*_rejected` → 归入「**已阻塞**」列
2. 所有新增状态必须在 `backend/models.py::STATUS_LABELS` 中补充中文展示标签。

---

### 约束 6：插件必须派生领域专属产品验收证据（`acceptance.py`）

公共 `AcceptanceReviewAction` 只提供基础的页面截图与通用检查项（如「页面能否正常打开」）。对于 Canvas 游戏、3D 引擎、或 CLI 纯文本评审模式（LLM 运行在隔离目录无法直接读取截图文件），如果插件不提供客观运行证据与关键代码摘要，ProductAgent 会因「看不到截图文件、也看不到源码实现」而判 0 分打回。

**强制规定**：凡是具备专属运行态或门禁报告的插件套件，必须在 `backend/plugins/<id>/acceptance.py` 实现：

```python
async def build_acceptance_evidence(context: Dict[str, Any]) -> Dict[str, Any]:
    return {
        "evidence_markdown": "...",   # 前置插件阶段（如 h5_typecheck / h5_playtest）的客观检测报告 + 核心源码片段
        "extra_check_items": [...],   # 派生该领域的专属验收检查清单
        "acceptance_rules": "...",    # 派生该领域的验收判定准则（严禁因无工具读图判 0 分，以客观报告+代码为准）
    }
```

由 `plugins.registry.build_plugin_acceptance_evidence` 根据项目 `traits` 自动注入到 `AcceptanceReviewAction`。

## 四、新插件套件验收 Checklist

提交新插件套件前，逐项核对：

- [ ] `plugin.json` 已声明 `id`、`name`、`required_traits`，且新 trait 已登记到 `backend/sop/trait_taxonomy.yaml`。
- [ ] 所有门禁失败状态已在 `plugins/<id>/reflection.py` 的 `HANDLED_FAILURE_TYPES` 注册，并实现了 `enrich_fix_context`、`build_reflection_signal` 与 `apply_deterministic_fixes`。
- [ ] 实现了 `plugins/<id>/acceptance.py::build_acceptance_evidence`，将插件门禁的客观运行报告与核心源码摘要派生注入产品验收。
- [ ] Action 内的子进程命令全部接入 `record_traced_command`，时间轴步骤可显示进行中动效，且能点开 **📟 后台任务** 查看完整控制台输出。
- [ ] `ActionResult.data["command"]` 确认为 `str` 类型（非 `list`）。
- [ ] 编写了 `backend/tests/plugins/test_<id>_plugin.py`，覆盖：SOP 组装不重复插阶段、环境缺失自愈/跳过、命令记录挂接、`reflection.py` 信号生成与确定性自愈、`acceptance.py` 验收证据派生、看板列归类。
