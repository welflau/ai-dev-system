## 一、种类：三个美术 Agent + 四个辅助能力

美术工作流不是单一 Agent，而是**三阶段分工 + 四个辅助能力**的体系：

| 角色 | Agent | Action | 职责 | SOP 阶段 |
|---|---|---|---|---|
| 交互设计 | `UXAgent` | `write_ux_design` | 交互流程/布局/状态 + **资产清单初稿** | `ux_design` |
| 视觉设计 | `ArtAgent` | `write_art_design` | Design Token / 视觉规范 / **完整 asset_manifest.yaml** | `art_design` |
| 资产落地 | `ArtistAgent` | `generate_assets` | 检索资产库命中即用，未命中给占位图 | `asset_gen`（仅 game） |

**辅助能力（非 SOP 阶段，按需调用）：**

| 能力 | 入口 | 用途 |
|---|---|---|
| 资产库搜索（Chat 工具） | `SearchArtAssetsAction`（`plugins/content/actions/search_art_assets.py`） | ChatAssistant 直接搜 33000+ 条资产库 |
| 网络搜索入库 | `art_asset_searcher.py::search_and_store` | Pexels / unDraw / Poly Haven 外网搜 → 入库 |
| AIGC 生图 | `image_processor.py::request_image` | LightAI 生图（异步队列），默认 requester=ArtAgent |
| 资产库 REST API | `api/art_assets.py` | `/api/art-assets` 搜索/统计/标记/UE 导入查询 |

### 1.1 资产层 MCP 清单（分散在 3 个 server）

美术/资产相关的 MCP 工具**没有集中在一个 server**，而是分散在 3 个 MCP server：

| MCP server | 工具 | 作用 |
|---|---|---|
| `ads-data`（`ads_data_mcp_server.py`） | `search_art_assets(query, asset_type, style, limit)` | 搜美术资产库 33000+ 条（LIKE 匹配） |
| `ue-bridge`（`ue_mcp_server.py`） | `ue_import_asset(asset_id, project_id, ue_dest_path, asset_name)` | 资产导入 UE Content，生成 uasset |
| `skill-io`（`skills/skill_io_mcp_server.py`） | `gen_image` | AIGC 生图（复用 `GenImageAction`） |
| | `gen_video` / `gen_video_batch` / `download_video` | AIGC 生视频 + 下载 |
| | `check_mode_assets` | 模式资产检查 |

**关键观察**：
1. `gen_image` 是唯一有意识规避"双实现漂移"的 MCP 工具——注释明确写"复用 backend 的 GenImageAction，参数校验/零字节检测/引擎回退都在那里，不要在 MCP 侧重写一份（两份实现迟早漂）"（skill_io_mcp_server.py:373-374）。
2. 与 MagicAI 的差异：MagicAI 资产工具集中在 `asset_library_mcp`（7 个工具），artist 只挂 1 个 MCP；本系统分散在 3 个 server、3 个独立入口，**没有统一的 fallback 链串联**——这正是 AIGC 断链的根因。

### 1.2 统一资产 MCP 收敛评估（2026-11-05）

**核心发现：资产能力有两条消费路径，MCP 只是其中一条。**

| 路径 | 消费方 | 资产工具 | 是否走 MCP |
|---|---|---|---|
| 内部 | ChatAssistant + 工单流水线 | `SearchArtAssetsAction` / `GenerateAssetsAction` / `GenImageAction` | ❌ 走 Action 系统 |
| 外部 CLI | Claude Code / codebuddy（CLI 模式） | `search_art_assets`（ads-data）/ `gen_image`（skill-io）/ `ue_import_asset`（ue-bridge） | ✅ 走 MCP |

**CLI 模式的 MCP 注入现状**（`llm_client.py:1120-1250`）：
- `ads-data`：全局默认始终注入（含 `search_art_assets`）
- `skill_io`：仅 SkillRunner 跑 skill 时注入（含 `gen_image`）
- `ue-bridge`：**不自动注入**，需手动配置 —— 资产导入在 CLI 场景是孤岛

**收敛方案对比**：

| 方案 | 做法 | 工程量 | 收益 | 结论 |
|---|---|---|---|---|
| A 新建统一 server | 新建 `asset_mcp_server.py` 收 3 工具 + 改注入逻辑 | 大 | 一个 `mcp__asset__*` 命名空间 | ❌ 不推荐 |
| B ads-data 加编排工具 | 在 ads-data 加 `resolve_asset`（内部串 search→gen→import） | 小 | CLI 场景获得 fallback 链 | 🟡 可选 |
| C Action 层 fallback 链 | `generate_assets._resolve_one` 接 AIGC 分支 | 中 | **主力场景**（内部工单）获得 fallback 链 | ✅ 优先 |

**建议**：
1. **C 优先**：内部工单流水线是主力场景，fallback 链应在 Action 层做（对应 `_01` 待办"generate_assets._resolve_one 接入 AIGC"），而非 MCP。
2. **B 可选**：仅当外部 CLI Agent 也需要资产 fallback 链时，在 ads-data 加 `resolve_asset` 编排工具（ads-data 已全局注入，最小改动）。
3. **A 不做**：统一 server 工程量大，但内部主力场景根本不经 MCP，收益有限；且 `ue_import_asset` 依赖 UE 同机前提，收敛进统一 server 徒增耦合。

**关键判断**：MagicAI 的 `asset_library_mcp` 集中式设计适合它（Godot 跑在浏览器，所有操作都经 MCP）；本系统的 UE Editor 同机 + 内部 Action 系统为主，**照搬集中式 MCP 是错配**。真正该收敛的是 Action 层的 fallback 链（方案 C），不是 MCP。

**关键设计**：`ArtAgent` 与 `ArtistAgent` 的分工是"**需要什么**"vs"**从哪来**"：
- ArtAgent 产出 asset_manifest（清单，`status: pending`）
- ArtistAgent 消费 asset_manifest，把每条 pending 落地为 sourced / placeholder / skipped

## 二、详细配置（SOP fragments 逐项）

三个 fragment 都用 YAML 声明，由 Orchestrator 按 traits 条件热插拔。

### 2.1 `ux_design.yaml`（交互设计）

```yaml
id: ux_design
insert_after: planning          # 策划完成后
priority: 90
required_traits:
  any_of: [platform:web, platform:wechat, platform:mobile, platform:desktop, category:game]
  none_of: [pipeline:video, category:video]     # 视频项目不走
required_ticket_type:
  none_of: [bug]                                 # BUG 工单不走
stage:
  agent: UXAgent
  action: write_ux_design
  trigger_on: planning_done
  success_status: ux_design_done
```

### 2.2 `art_design.yaml`（视觉设计）

```yaml
id: art_design
insert_after: ux_design         # 插在 UX 之后
priority: 88                    # 低于 ux_design(90)，保证顺序
required_traits:                 # 同 ux_design
  any_of: [platform:web, ..., category:game]
  none_of: [pipeline:video, category:video]
required_ticket_type:
  none_of: [bug]
stage:
  agent: ArtAgent
  action: write_art_design
  trigger_on: ux_design_done
  success_status: art_design_done
```

### 2.3 `asset_gen.yaml`（资产落地，仅游戏）

```yaml
id: asset_gen
insert_before: development       # dev 前
priority: 100
required_traits:
  all_of: [category:game]        # ★ 只有游戏项目才触发
required_ticket_type:
  any_of: [feature]              # ★ 只在新功能需要资产时触发
stage:
  agent: ArtistAgent
  action: generate_assets
  trigger_on: asset_gen_pending
  success_status: assets_ready
  config:
    asset_types: [sprite, tileset, ui_element, icon, illustration]
    fallback_to_placeholder: true   # 未命中 → 洋红斜纹占位图，保证流水线不断
```

### 2.4 ArtAgent 的产出 Schema（`ArtDesignOutput`）

```python
class ArtDesignOutput(BaseModel):
    design_tokens: str = ""          # JSON：colors/typography/spacing/radius/shadow
    component_visual_spec: str = ""  # 组件视觉规范 Markdown
    asset_manifest_items: str = ""   # 资产清单条目（文字格式）
    style_guidelines: str = ""       # 整体风格 2-3 句
    game_sprite_spec: str = ""       # 精灵图规格（仅游戏）
```

### 2.5 asset_manifest.yaml 结构

```yaml
assets:
  - id: nav_home
    type: icon
    description: 首页导航图标 24px outline
    source_hint: iconify          # iconify/ai_generate/pexels/kenney
    status: pending               # pending→sourced/placeholder/manual_required/not_found
```

## 三、调度机制

### 3.1 状态机驱动

Orchestrator 按 fragment 的 `trigger_on` / `success_status` 推进工单状态：

```
planning_done ──UXAgent.write_ux_design──> ux_design_done
ux_design_done ──ArtAgent.write_art_design──> art_design_done
art_design_done ──[asset_gen_pending]──> ArtistAgent.generate_assets ──> assets_ready
assets_ready ──> development
```

### 3.2 三层过滤（代码强制，非 prompt 约定）

1. **traits 条件**：fragment 的 `required_traits`（any_of/all_of/none_of）在 `compose_sop` 时按 `project.traits` 过滤。
2. **ticket_type 条件**：`required_ticket_type`（none_of: bug / any_of: feature）。
3. **运行时跳过**（`orchestrator.py:2281`）：即使 traits 命中，`write_ux_design` / `write_art_design` 还会被 `_needs_design_stage(ticket)` 二次拦截——纯后端/纯 C++ 逻辑工单（module=backend、标题无 UI 信号）跳过设计阶段，避免空转。

### 3.3 完整数据流（ArtAgent → ArtistAgent）

```
UXAgent.write_ux_design
  → 产出 UX设计.md + asset_manifest.yaml（初稿）
ArtAgent.write_art_design
  → 读 PRD + UX artifacts（artifacts 表 type=prd/ux_design）
  → 读 domain_knowledge / agent_spec 注入视觉规范
  → LLM 产出 ArtDesignOutput
  → 写 视觉规范.md + asset_manifest.yaml（完整版，覆盖初稿）+ design_tokens.json
ArtistAgent.generate_assets
  → _load_manifest 读磁盘 asset_manifest.yaml（回退 artifacts 表 art_design）
  → 逐条 _resolve_one：
      1. _search_library（art_assets 表，打分+反义词否决+格式过滤，阈值 0.6）
      2. 未命中 → _make_placeholder（PIL 洋红斜纹图）
      3. 非图像类型（audio/font）→ manual_required
  → 回写 asset_manifest.yaml + 资产落地报告.md
```

## 四、发现的调度问题（疑似死循环）

`server.log` 中 `TK-20261027-「生成桥面与桥身结构几何体并保存为 StaticMesh 资产」` 工单在 **`ux_design_done → ArtAgent.write_art_design` 之间反复流转上百次**（23:33 → 00:07，每 30 秒一次）。

**现象**：这是 UE 项目（traits 命中 `category:game` → ux_design/art_design 被插入），但工单是纯 3D 几何体生成，`_needs_design_stage` 未拦住，ArtAgent 反复执行 write_art_design 但状态始终停在 `ux_design_done`，形成死循环烧 token。

**可能根因**（待确认）：
1. `_needs_design_stage` 的信号词表未覆盖"几何体/StaticMesh/桥面"等 3D 生成类标题。
2. ArtAgent 返回 success 但状态未推进到 `art_design_done`（结果处理链路缺陷）。

**与对标文档的呼应**：这正是 MagicAI 反面教训"约束只在 prompt 无代码兜底"的镜像——本系统的 traits 条件是代码强制的，但 `_needs_design_stage` 的信号词表是不完备的兜底，存在漏网死循环。

## 五、与 MagicAI 美术工作流对标

| 维度 | MagicAI | 本系统 |
|---|---|---|
| 美术 Agent 数量 | 1（artist） | 3（UXAgent/ArtAgent/ArtistAgent） |
| 需求文档 | `art_requirements.md`（designer 产出） | asset_manifest.yaml（ArtAgent 产出） |
| 资产获取优先级 | 四级（prompt 约定） | 两级 + AIGC 断链（代码强制搜库→占位） |
| AIGC 接入 | 已接（混元/Suno/SD） | **已接（LightAI）但未接到 ArtistAgent** |
| 优先级强制 | ❌ 仅 prompt | ✅ 代码（_resolve_one 顺序） |
| 调度配置 | agent_session_config.py 硬编码 | SOP YAML 热插拔 + traits 条件 |
| 场景级生成 | 蓝图未落地 | UE 走 ue_level_gen / ue_blueprint_gen |

**核心差距**：本系统美术工作流的调度配置（SOP fragment + traits 条件 + 跳过逻辑）**比 MagicAI 更成熟**（代码强制、热插拔、三层过滤），但 **AIGC 生成环节反而断链**——`generate_assets._resolve_one` 注释还写"系统尚未接入图像模型"，而 `image_processor.request_image` 已接入 LightAI。
