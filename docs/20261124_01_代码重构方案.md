## 一、结论

六层方案已经消掉了模块之间的循环依赖（SCC 为 0），方向违规还剩 92 条。现在的主要问题在模块内部：逻辑堆在少数几个巨型文件和函数里，而这些地方几乎没有测试。

1. **最该拆的代码恰好是最没有测试的代码。** 自有后端代码的语句覆盖率是 26.9%。最大的几个函数覆盖率接近 0：`process_ticket`（682 行）0%，`_handle_agent_result`（1,026 行）6%，`_call_cli_stream`（493 行）0%。直接拆这些函数没有任何回归保护。
2. **改动集中在大文件上。** 近三个月 112 个提交里，58 个（52%）至少改了 11 个大文件中的一个；`frontend/app.js` 单个文件就占 38 个。
3. **没有数据访问层。** 业务代码里有 804 处 SQL 字面量，分布在 107 个文件；`projects` 表被 55 个文件直接查询，同一句 `SELECT * FROM projects WHERE id = ?` 重复了 45 次。工单状态有 54 个写入点。
4. **前端是一个 35,912 行的脚本。** 1,079 个全局函数、163 个可变全局变量，没有模块、没有 lint、没有测试。

所以重构顺序是：先补安全网和度量（R0），再收口数据访问（R1），然后才拆 `orchestrator`、API 层和 LLM 客户端（R2–R4），前端模块化（R5）可以独立并行。每一步都不改变外部行为，都能单独回滚。

## 三、原则

1. **先有测试再动刀。** 要拆的函数先补特征测试，把现有行为固定下来，再做搬移。
2. **搬移和改行为分开提交。** 纯搬移的提交不改任何逻辑，评审时只需要确认「没变」。
3. **旧入口保留。** 拆出去的名字在原模块保留重导出，和 `cloud_video/errors.py` 那次的做法一致。
4. **用基线棘轮代替一次性达标。** 和 `layers_baseline.json` 同样的机制：度量值登记基线，CI 只允许变好。
5. **按改动频率排优先级。** 先处理改得最多的文件，收益最大。
6. **前端不换框架。** 在现有原生 JS 上做模块化，避免一次重写 3.6 万行。

### R0 安全网与度量

不改业务逻辑。

1. **度量脚本和基线。** 新增 `scripts/code_metrics.py` 和 `backend/metrics_baseline.json`，登记第六节的指标，CI 里只允许变好。本文的数字是用临时脚本算的，这一步把它们变成可复现的。
2. **CI 加覆盖率。** `pytest` 加 `--cov`，产出报告。先登记 26.9% 的基线，不设硬门槛。
   现状：修改过程中没有任何测试会自动触发，CI 的 pytest 步骤也还没提交，见第十一节「测试流程和自动化现状」。
3. **特征测试。** 沿用 `test_orchestrator_skill_branch.py` 的做法（真实 SQLite + 打桩派单和 SSE），补这几处：
   - `_handle_agent_result`：每个 Agent 分支至少覆盖成功和失败两条路径，加上终态门闩和 error 止血两段前置逻辑。**（已完成，57 条用例，见第十一节）**
   - `process_ticket`：熔断、返工重试、跳过、找不到 Agent 这几条提前返回的路径。**（已完成，73 条用例，见第十一节）**
   - `handle_requirement`：拆单成功和失败。**（已完成，63 条用例，见第十一节）**
   - `_call_cli_stream`：把真实 CLI 的输出录成文本，用假进程回放，验证解析出的事件序列。
   - 两个聊天流式生成器：用假的 LLM 流验证 SSE 事件顺序。
4. **补归层。** 把 83 个未归层的业务模块写进 `layers.toml`。这一步可能冒出新的方向违规，按现有规则登记进基线。
5. **根目录脚本归位。** 77 个下划线脚本里仍有价值的改写成 pytest 用例，其余移到 `backend/scripts/dev/`。是否直接删除需要确认。

验收：`_handle_agent_result`、`process_ticket`、`_call_cli_stream` 的行覆盖率各自达到 70%；未归层模块数为 0（归档脚本目录除外）。

### R1 数据访问收口

1. **新增 `repositories/`。** 先做 `projects`、`tickets`、`requirements`、`ticket_logs` 四张表。返回值保持 `dict`，调用方不用改数据结构；`traits` 这类 JSON 列的解码放进 repository（业务代码里 `json.loads` 共 203 处、66 个文件，其中至少 18 处是在解 `traits`）。
2. **先替换重复最多的查询。** `get_project(id)`、`get_repo_path(id)`、`get_traits(id)`、`project_exists(id)` 四个函数能替换掉约 120 处。
3. **事务。** `Database` 增加 `transaction()` 异步上下文，内部复用现有写锁。
4. **状态迁移收口。** 新增 `repositories/ticket_state.py`，一个 `transition()` 完成写状态、更新时间、写 `ticket_logs`、发 `ticket_status_changed` 事件，放在同一个事务里。它只依赖 `database` 和 `events`，归 L2，L1 和 L3 都能调用。54 个写入点逐个迁过来。
5. **迁移版本号。** 用 `PRAGMA user_version` 加一张有序迁移表；现有 `_auto_migrate` 的补列清单整体作为第 1 版保留。

## 七、风险与对策

1. **测试按模块属性打桩。** 现有测试用 `monkeypatch.setattr(orchestrator, "db", tmp_db)` 这类写法替换依赖。如果拆出去的模块自己 `from database import db`，这个桩就不再生效，测试会写到真实数据库。对策：拆出的函数通过参数或上下文对象接收 `db`、`event_manager`，不自己导入；每次搬移后确认相关测试仍然用的是临时库。
2. **功能开发不会停。** 过半提交会碰大文件，长期分支必然冲突。对策：每个搬移提交控制在一个文件、一天内合并；纯搬移的提交登记到 `.git-blame-ignore-revs`，保住 `git blame`。
3. **部分路径无法在 CI 里跑。** CLI 流式调用、UE 工具链依赖本机环境。对策：用录制样本回放；每个阶段合并前按一张手工冒烟清单在本机走一遍（建项目、提需求、跑完一张工单、聊天、桌面版启动）。
4. **桌面版打包。** `desktop.spec` 的 `hiddenimports` 按名字列了 `orchestrator`、`llm_client` 等模块。新增的包如果是通过 `runtime_facade` 动态解析的，需要同步加进去。对策：每个阶段结束后打一次包并启动验证。
5. **工作区有大量未提交改动。** 重构必须从干净的工作区开始。对策：先把现有两批改动（`ai_gen_tasks` 和体检修复第一批）提交。
6. **数据库事务改动。** 给写操作加事务会改变失败时的行为（从「留下半截数据」变成「整体回滚」）。对策：R1 的事务先只用在状态迁移上，其余写操作保持原样。

## 附：度量口径

- **文件范围**：`git ls-files backend` 加上未跟踪但未被忽略的 `.py`，排除第二节开头列出的目录。「自有代码」的行数和函数数包含根目录的 77 个下划线脚本；覆盖率的分母不包含它们；2.4 节的数据访问统计、`json.loads` 和时间调用的计数也不包含它们。
- **SQL 字面量**：引号后以 `SELECT`、`UPDATE`、`INSERT INTO`、`DELETE FROM` 开头，长度 10–200 个字符的字符串；压缩空白后按文本去重。f-string 拼接的片段和超过 200 个字符的语句会漏计，所以这是下限。
- **函数长度**：`end_lineno - lineno + 1`，含嵌套函数。
- **圈复杂度**：1 加上 `if`、`for`、`while`、`except`、`with`、三元表达式、推导式、`assert`、`match case` 的个数，再加布尔运算的额外操作数。
- **宽泛 `except`**：裸 `except`，或捕获 `Exception` / `BaseException`。
- **延迟导入、未归层模块、方向违规**：直接取 `python scripts/check_layers.py --json` 的输出。
- **覆盖率**：在 `backend/` 下执行 `python -m pytest --cov=. --cov-report=json:<文件>`，再按文件范围过滤后汇总。
- **近似重复**：两个函数去掉空行和注释、压缩空白后，用 `difflib.SequenceMatcher` 按行比较，取相同行数占较短函数的比例。
- **提交统计**：`git log --since=2026-08-24 --name-only`。
- **前端计数**：对 `frontend/app.js` 做正则计数；顶层函数指行首的 `function` / `async function` 声明。

这些数字来自本次分析用的临时脚本，没有入库。R0 第 1 步会把它们固化成 `scripts/code_metrics.py`。
