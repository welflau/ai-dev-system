# 请求分类前置层设计方案

> 设计日期：2026-11-05
> 借鉴来源：MagicAI 的 Phase -1 请求分类（A 大改 / B 小改 / C 问答）
> 状态：待设计评审

---

## 一、目标与定位

对标 MagicAI 的 `game_director.md` Phase -1 分类，在 ADS 的**直接建工单**场景（`confirm_direct_ticket`）加一层自动分类，让规模判断不再依赖人工指定，省 token + 跳过不必要阶段。

### MagicAI 分类 vs ADS 映射

| MagicAI | 语义 | ADS start_from |
|---|---|---|
| A 大类变更 | 新游戏/大改，3 步理解→追问→定计划 | `pending`（完整 SOP） |
| B 小改 | 1-2 模块，只调必要 Agent | `architecture_done`（跳过规划+架构） |
| B' 原子任务 | 单人单次 ≤2h | `development_in_progress`（立即开发） |
| C 问答 | 直接答，不启动流水线 | 不建工单（ChatAssistant 已天然实现） |

**关键认知**：ADS 的 `confirm_requirement`（大需求拆单）天然对应 A 大改，走完整流程，**无需分类**。分类只需处理 `confirm_direct_ticket`（直接建工单）场景——判断这个工单该走完整 SOP，还是跳过前置。

## 二、现状基础（已具备，勿重复造轮子）

`start_from` 机制已存在且完整：

1. **字段**：`DirectTicketCreate.start_from`（models.py:296），三档 `pending` / `architecture_done` / `development_in_progress`。
2. **流转**：`create_direct_ticket`（api/tickets.py:1206）`start_status = req.start_from` → 写入 `tickets.status`。
3. **规范层钩子**（`_post_create_layer_hooks`，api/tickets.py:2992）：
   - `pending` → Planner 钩子推 `planning_in_progress`，走完整 SOP
   - `architecture_done` / `development_in_progress` → 跳过 Planner，OpenSpec 钩子单独补 spec
4. **LLM 侧已有 prompt 引导**：`confirm_direct_ticket` 的 MCP docstring（ads_data_mcp_server.py:516-547）已描述 start_from 三档语义，让 LLM 判断。

**缺口**：`start_from` 依赖 LLM 判断（prompt 约定）或人工指定，**无代码强制分类**——正是 MagicAI 反面教训"优先级只在 prompt 无代码兜底"的同类问题。

## 三、分类规则设计（对齐 MagicAI）

### 3.1 对齐点说明

MagicAI 的分类是**两层机制**，非单一跳阶段：

1. **MODIFY 模式判定**（`agent_session.py:202-231`）：`has_modify and not has_new` 或「短消息 + 项目结构已缓存」→ 判定为小改。
2. **关键词评分**（`infer_agents_for_modify`，`agent_session_config.py:86-124`）：`MODIFY_KEYWORD_AGENT_MAP` 对每个 Agent 的关键词计分，取「designer + 得分最高前 2 个 Agent」只注册必要 Agent。

ADS 落地受状态机限制（stage 之间有 `trigger_on`/`success_status` 依赖链，不能中间跳 Agent），只能映射到 `start_from` 三档。但**词表、判定逻辑、评分机制直接对齐 MagicAI**。

### 3.4 决策顺序（对齐 + 保守）

```python
def classify_start_from(title: str, description: str, ticket_type: str) -> str:
    msg = f"{title} {description}"
    msg_lower = msg.lower()

    # bugfix → 立即开发（bug 修复不需设计/规划）
    if ticket_type == "bugfix":
        return "development_in_progress"

    # A 大类变更：新建词 → pending（完整 SOP）
    if any(ind in msg_lower for ind in _NEW_PROJECT_INDICATORS):
        return "pending"

    # B 小改：修改词 或 短消息 → 关键词评分
    has_modify = any(ind in msg_lower for ind in _MODIFY_INDICATORS)
    if has_modify or len(msg) < 100:
        scores = {}
        for agent, keywords in _MODIFY_KEYWORD_AGENT_MAP.items():
            s = sum(1 for kw in keywords if kw.lower() in msg_lower)
            if s > 0:
                scores[agent] = s

        # 涉及设计/资产（Planner/Art）→ 跳过规划，仍走美术+开发
        if any(a in scores for a in ("PlannerAgent", "ArtAgent")):
            return "architecture_done"
        # 纯代码/测试修改 → 立即开发
        if scores:
            return "development_in_progress"

    # 判不准 → pending（保守：短消息/修改词不足以证明是小改，宁可多跑）
    return "pending"
```

### 3.5 保守原则（与 MagicAI 一致）

1. **只降级不升级**：只能把 `pending` 降为更快档位，绝不把用户显式指定的档位升级回 `pending`。
2. **无缓存不分类**（对齐 MagicAI `_phase0_skip_hint` 前置）：仅当项目已有结构缓存（非首次会话）才启用 MODIFY 判定，首次会话一律 `pending`。（ADS 二期：用 Checkpoint/项目结构缓存判断二次会话）
3. **判不准走完整流程**：宁可多跑，不可漏做。

### 3.6 与 MagicAI 的关键差异（诚实说明）

| 维度 | MagicAI | ADS |
|---|---|---|
| 架构 | GameDirector 任务委派，无状态机依赖 | SOP 状态机，stage 有依赖链 |
| 分类落地 | `agent_filter` 只注册必要 Agent（可中间跳） | `start_from` 三档（只能跳前置整段） |
| 粒度 | 细（任意 Agent 组合） | 粗（三档） |

**结论**：ADS 无法做到 MagicAI 的「任意 Agent 组合」（状态机限制），但对齐了**词表、判定逻辑、评分机制**，落地为 `start_from` 三档。

**改动 2**：`api/tickets.py::create_direct_ticket`（1206 行）
```python
# 现状
start_status = req.start_from if req.start_from in _VALID_START_STATUSES else "pending"

# 改后：仅当 start_from 是默认 pending（未显式指定）时，自动分类
if req.start_from == "pending":
    from ticket_classifier import classify_start_from
    start_status = classify_start_from(req.title, req.description, ticket_type)
else:
    start_status = req.start_from if req.start_from in _VALID_START_STATUSES else "pending"
```

### 4.2 如何区分"用户显式指定 pending" vs "默认值"

- `DirectTicketCreate.start_from` 默认 `"pending"`。
- LLM/前端在 `confirm_direct_ticket` 时会显式传 start_from（LLM 判断 + 用户 UI 选择）。
- **方案**：只有当 `req.start_from == "pending"` 时启用自动分类。用户若明确要"走完整流程"，可从 UI 选 `architecture_done` 再选回，或后续加 `auto_classify: false` 开关（二期）。

### 4.3 二期可选增强

- `DirectTicketCreate` 加 `auto_classify: bool = True`，前端可关闭。
- 分类结果回写到 `ticket_logs`，记录"自动分类：pending → architecture_done（命中小改信号'修复'）"，可观测、可回溯。

## 五、风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 误分类跳过必要阶段 | 小改信号误命中，跳过规划导致设计缺失 | 保守词表 + "判不准走 pending" + 只降级不升级 |
| 分类不透明 | 自动降级无记录，难排查 | 二期加 ticket_logs 记录 |
| 信号词表覆盖不全 | 中文/英文词表无法穷尽 | 判不准走 pending，词表只做"明确小改"的降级 |
| 与现有 `_needs_design_stage` 重叠 | 两者都在做"是否需要设计"判断 | 分工：`_needs_design_stage` 判"是否要 UX/美术设计"，`classify_start_from` 判"是否要规划+架构"。粒度不同，不冲突 |
