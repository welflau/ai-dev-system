# Agent 群聊话题分支方案

> 日期：2026-10-14
> 状态：🟡 方案已定，待实现
> 前置：`20261013_02_PM驱动群聊循环实现方案.md`（PM 驱动循环，已实现 Phase 1）

## 一、背景与问题

当前黑板是**扁平累积**：`proposals / open_questions / facts / decisions` 不区分话题，
换话题后旧话题的内容混在新话题里；`topics[]` 只是话题标题的扁平列表，没有结构。

于是出现两个体验问题：

1. **黑板污染**：换话题后，旧话题的提案/共识还堆在上面，新话题的讨论和旧内容混杂——
   「黑板内容和聊天不相关」在话题层面依然存在。
2. **看不到归属**：消息是时间顺序平铺，看不出哪段讨论属于哪个话题。

用户诉求：
- 当前话题能不停追问；也能随时启动新话题。
- 自动识别话题切换。
- 黑板及时反映「分支」结构（或消息视图反映归属）。

## 二、设计决策（三问三答）

### 1. 自动识别话题 —— 靠 PM 显式输出，不用启发式

| 做法 | 精度 | 成本 |
|---|---|---|
| 文本差异（现用） | 差（「上面那个问题的代码」误判新话题） | 零 |
| 相似度 / embedding | 中（阈值难定） | 中 |
| **PM 显式输出** | 高（PM 已读全上下文，天然能判追问 vs 新话题，且能起标题） | 零额外 LLM 调用 |

**结论**：PM 决策 JSON 新增 `topic_transition: "continue" | "new"` + `topic_title`。
PM 每轮顺带输出，不增加 LLM 调用。

### 2. 消息视图 —— 保持时间顺序 + 话题标签，不做完整树

完整话题树（缩进/折叠）割裂群聊的时间流感，属重度 UI 重构。折中：

- 消息保持**时间顺序**。
- 每条消息/收敛结论带**话题标签**徽章。
- 新话题开始时插入「🆕 话题：XXX」分隔行。

### 3. 黑板反映分支 —— 核心：黑板改造成话题树

黑板从「扁平分区」改成**话题节点列表**，每个话题自带分区：

```js
board = {
  session_id, project_id, version,
  current_topic_id,
  topics: [
    { id, title, goal, acceptance_criteria, participants,
      facts[], proposals[], open_questions[], decisions[], artifacts[],
      summary[], status: "active" | "archived", created_at },
  ],
}
```

- 话题内内容不再互相污染。
- 侧栏渲染**话题树**：当前话题展开（目标 + 验收点完成度 + 结论），旧话题折叠成一行
  （标题 + 完成度 ✅ 数），点开看历史。

## 三、PM 决策 Schema 扩展

```jsonc
{
  "action": "ask|summarize|conclude",
  "topic_transition": "continue|new",   // new = 开启新话题节点
  "topic_title": "...",                  // topic_transition=new 时必填
  "targets": [...], "question": "...", "summary": "...", "conclusion": "...", "reason": "..."
}
```

## 四、实现要点

### 后端（api/chat.py）

1. 黑板数据模型改造：`_empty_board` 产出话题树结构（`topics[0]` 为当前话题节点）；
   `_apply_board_writes` / `_board_snapshot_text` 等改为读写 `当前话题节点` 的分区。
2. `_pm_state_view`：注入「当前话题 + 最近话题列表」，让 PM 能看到分支结构。
3. `_pm_decision_prompt`：说明 topic_transition 语义——
   - continue = 延续当前话题追问；
   - new = 用户消息开启新话题（含「回到旧话题继续」也应标 new + title 复用旧标题，
     后端按 title 归并回旧节点，避免碎片化）。
4. `_group_board_pm_generator`：
   - 解析 `topic_transition`；
   - `new` → 归档当前话题（status=archived）+ 新建节点（status=active）作为 current_topic_id；
   - 归并策略：`topic_title` 与已有归档话题标题相似 → 复用该节点（回到旧话题），否则新建。
5. goal 提炼：新话题节点提取新 goal（旧目标随节点归档，不再需要全局 goals[]）。

### 前端（app.js / styles.css）

1. `_renderBoardSummary`：渲染话题树（当前展开 + 旧折叠），验收点完成度按节点内分区算。
2. 消息流：`pm_action` 带 topic_transition=new 时插入「🆕 话题」分隔行；消息带话题标签。
3. 话题折叠交互：点击旧话题标题展开/收起历史。

## 五、取舍与风险

1. **话题碎片化**：追问被误判成新话题。靠 PM 判断 + 「按标题归并回旧话题」压住。
2. **跨话题引用**：「上面第一个问题的代码」——PM 判 continue（回到旧话题）或 new（新话题）。
3. **黑板体积**：话题树累积，归档上限（保留最近 8 个话题，更早只留标题 + 结论摘要）。
4. **兼容**：旧扁平黑板数据（无 topics 树）加载时做一次迁移（把旧分区塞进一个默认话题节点）。

## 六、落地顺序

1. 后端话题树数据模型 + PM topic_transition。
2. 前端侧栏话题树渲染。
3. 消息话题标签 + 「🆕 话题」分隔行（锦上添花）。

先做 1 + 2，3 视效果再定。
