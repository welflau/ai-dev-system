# 独立工单桶设计方案

**创建日期**: 2026-07-14  
**状态**: 待实现  
**背景**: 现有工单必须通过需求→ProductAgent 拆单流程创建，无法直接建单执行。用户需要一种绕过拆单的方式，快速创建并运行单个工单。

---

## 一、核心思路

每个项目维护一个 **`type=standalone`** 的特殊需求（独立工单桶），所有用户直接创建的工单都挂在这里，不走 ProductAgent 拆单。

```
需求列表：
  📋 创建 NPC 角色系统        in_progress
  📋 优化地图加载性能         completed
  🗂 独立工单               in_progress   ← 特殊桶，不走拆单
     ├── 修复 GameMode 崩溃   blocked
     ├── 添加音效管理器        development_in_progress
     └── 更新项目 README      pending
```

---

## 二、方案对比（已选 B）

| | 方案A：每单一个虚拟需求 | 方案B：一个大需求桶（已选） |
|---|---|---|
| 数据结构 | 每个工单 → 各自一个 virtual req | 所有独立工单 → 同一个 req |
| 需求列表 | 一堆 virtual 需求污染列表 | 只多一条"独立工单" |
| 工单上下文（docs_prefix） | 每单独立路径 | `docs/Reqs/standalone/{ticket_id[-6:]}/` |
| 管理 | 分散 | 集中，一眼看全 |
| 实现复杂度 | 中 | 低 |

## 三、数据模型

### requirements 表

`type` 字段新增 `standalone` 值，独立工单桶记录：

```json
{
  "id": "REQ-standalone-{project_id[-8:]}",
  "project_id": "...",
  "title": "独立工单",
  "type": "standalone",
  "status": "in_progress",
  "description": "项目独立工单集合，由用户直接创建，不经过需求拆单流程。"
}
```

**幂等保证**：创建直接工单时先 `SELECT` 是否存在 standalone 需求，不存在才创建。

### tickets 表

独立工单与普通工单结构完全相同，`requirement_id` 指向 standalone 需求，无额外字段。

### docs_prefix

```python
req_short = req_id[-6:] if req_id else "standalone"
docs_prefix = f"docs/Reqs/{req_short}/{ticket_id[-6:]}/"
```

所有独立工单的文档写入 `docs/Reqs/{standalone_req_id[-6:]}/{ticket_id[-6:]}/`，互不干扰。

---

## 四、执行起点（start_from）

用户创建工单时可选从哪个 SOP 阶段开始：

| start_from | 工单初始状态 | 触发第一个 Agent | 适用场景 |
|---|---|---|---|
| `pending`（默认） | `pending` | PlannerAgent | 新功能，需要完整规划+架构+开发 |
| `architecture_done` | `architecture_done` | DevAgent | 已知方案，直接开发 |
| `development_in_progress` | `development_in_progress` | DevAgent（立即） | 明确代码改动，跳过所有前置 |

## 五、后端实现

### 5.1 新增 API 端点

**`POST /api/projects/{project_id}/tickets/create-direct`**

```python
class DirectTicketCreate(BaseModel):
    title: str
    description: str = ""
    type: str = "feature"        # feature / bugfix / refactor / test / doc
    module: str = "other"
    priority: int = 3
    start_from: str = "pending"  # pending / architecture_done / development_in_progress
    estimated_hours: float = 4.0
    auto_start: bool = True      # 创建后立即加入调度队列
```

**处理流程**：
1. 查询或创建项目的 standalone 需求（幂等）
2. 创建工单，`requirement_id = standalone_req.id`
3. 若 `start_from != "pending"`，直接将工单状态设为 `start_from` 值
4. 若 `auto_start=True`，触发 orchestrator 调度

### 5.2 orchestrator._build_context() 兼容

在 `docs_prefix` / `tests_prefix` 构建处加一行兼容判断（`orchestrator.py:2981`）：

```python
req_short = (ticket["requirement_id"] or "standalone")[-6:]
context = {
    "docs_prefix": f"docs/Reqs/{req_short}/{ticket['id'][-6:]}/",
    "tests_prefix": f"tests/{req_short}/",
    ...
}
```

### 5.3 standalone 需求状态自动维护（可选）

standalone 需求不由 SOP 驱动，状态由子工单决定：
- 有任意工单处于非完成态 → `in_progress`
- 所有工单完成 → `in_progress`（桶永远保持活跃，随时接新单）

## 六、前端实现

### 6.1 需求列表区分显示

standalone 需求：
- 图标用 🗂（区别于普通 📋）
- 顶部固定显示
- 默认展开工单列表
- 标题旁显示待处理工单数角标

### 6.2 工单看板"直接创建"入口

工单看板顶部（或右键菜单）加"+ 直接创建工单"按钮，打开弹窗。

**弹窗字段**：
```
标题 *           [                        ]
描述             [                        ]
类型             [feature ▼]   模块 [other ▼]
优先级           [P3 ▼]        预计工时 [4 h]
执行起点         ○ 完整流程（规划→架构→开发）
                 ○ 跳过规划架构，直接开发
                 ○ 立即开始开发
☑ 创建后立即执行

         [取消]  [创建工单]
```

**创建成功后**：自动打开工单抽屉。

### 6.3 工单面板内快捷入口（可选）

在工单列表页也增加一个小入口，或者 AI 助手命令：
```
/ticket 修复 GameMode 崩溃 --start=dev
```
