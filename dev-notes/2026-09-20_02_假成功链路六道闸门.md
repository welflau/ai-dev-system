# 假成功：一个只有一行 console.log 的工单，是怎么一路走到 deployed 的

2026-09-20

## 症状

时间轴上这一行：

```
✅ [1/2] 代码生成 124041ms
```

用户的两个问题：

- 未展示任何生成的、或修改的代码文件，如何就是生产成功了？
- 这些操作，没有后台任务链接？没有什么 bash 执行？

答案是：**它确实没成功**。工单 `TK-20260920-ce79a9`
（「修复相册选文件竞态：focus 兜底提前 resolve 空数组导致导入静默失败」）
最终状态是 `deployed`，而它该改的 `gallery.js` / `post.js` **一行都没动**。

时间轴上没有后台任务链接，恰恰是因为那一轮**没有任何真实产出可链接**。

## 完整链路复盘

从库里把 `ticket_logs` 按时间捞出来，一步步对：

```
00:43:12  create           → pending
00:46:25  write_prd        pending → planning_done
00:48:19  complete         architecture_in_progress → architecture_done
00:48:20  assign           architecture_done → development_in_progress
00:48:21  skill_step_start [1/2] 代码生成 · 开始
00:50:25  llm_call         ⚠️ 39311ms, tokens: 0→0      ← LLM 挂了
00:50:25  skill_step_done  [1/2] 代码生成 · 完成 (124041ms)   ← 照样打勾
00:50:41  thought_start    [ReviewAgent] 开始 code_review
00:51:11  code_review      development_done → review_passed   (3/10, warning)
01:01:21  ToolError        ActionNode[acceptance_review] LLM 调用超时（602s > 600.0s）
01:01:21  accept           review_passed → acceptance_passed  ← 超时却验收通过
01:01:25  complete         acceptance_passed → deployed
```

### 五个独立缺陷串成一条链

**① LLM 返回 `tokens: 0→0`，规则兜底给了个空壳。**
`write_code.py:_fallback` 往 `src/focus__resolve_.js` 写了：

```js
// 修复相册选文件竞态...
console.log('focus resolve loaded');
```

然后 `success=True`。「LLM 挂了」被包装成「开发完成，产出 1 个文件」。

**② `emit_step` 不看产出。** 它只写步骤名和耗时：

```json
{"message": "[1/2] 代码生成 · 完成 (124041ms)", "step_name": "代码生成",
 "step_index": 1, "step_total": 2, "phase": "done", "duration_ms": 124041}
```

没有 `files`，没有 `file_count`。所以那个绿勾**在数据层面就是无条件的**——
它标的不是「做成了」，是「这个函数返回了」。

**③ 僵尸检测替死掉的阶段宣布成功。** 日志里找不到任何一条
`development_in_progress → development_done` 的 `complete` 记录，
但 `code_review` 的 `from_status` 就是 `development_done`。
是 `_poll_once` 里这张表干的：

```python
reset_map = {
    ...
    TicketStatus.DEVELOPMENT_IN_PROGRESS.value: TicketStatus.DEVELOPMENT_DONE.value,
    ...
}
```

开发阶段在后端重启时死掉，僵尸检测把它**前推**成 `development_done`。
下游就在一个只有空壳的仓库上继续跑完了整条流水线。

**④ 代码审查看出来了，但不阻塞。** `3/10`，问题描述一针见血：

> 该文件按任务应实现「focus 兜底不提前 resolve 空数组」的竞态修复，
> 但实际内容仅一行 console.log，没有任何 Promise/focus/数组 resolve 相关逻辑。
> 原 bug 未被修复，用户仍会遇到无声失败。

`block_on_low_score: false`（默认），所以只记了条 warning 日志。这是设计如此，
这次没改——但它意味着**审查这道防线在当前配置下不设防**。

**⑤ 验收超时 602s，读默认值读成了通过。** 这是最要命的一环。
`ActionNode` 降级时做的是：

```python
self.instruct_content = self.expected_type.model_construct()
```

`model_construct()` **不走校验**，直接拿 schema 默认值填。而 `ReviewOutput` 的默认值是
`passed=True, score=6`，acceptance 的 `pass_score` 默认**正好也是 6**。

于是 `score >= pass_score` → `acceptance_passed`。

**「LLM 超时」和「验收 6 分通过」在代码里是同一个对象。**

最后 DeployAgent 部署了什么？`git_files` 里只有：

```
build/Dockerfile
build/docker-compose.yml
docs/Reqs/30f837/ce79a9/deploy.md
```

一个业务文件都没有。而它报告「部署完成，预览地址: http://localhost:9095」。

## 六道闸门

### ① 降级 ≠ 通过（`action_node.py` + 两个评审 Action）

根因不是「降级」这个行为，是**降级后的对象和正常对象长得一模一样**，
调用方没有任何办法区分。加一个标志位，并把降级收进唯一入口防止漏标：

```python
def _degrade(self, reason: str) -> "ActionNode":
    """降级为空模型并标记原因（唯一入口，防止漏标）"""
    self.instruct_content = self.expected_type.model_construct()
    self.degraded = True
    self.degrade_reason = reason
    return self
```

三处 `self.instruct_content = self.expected_type.model_construct()` 全改成
`return self._degrade(...)`。验收侧：

```python
if node.degraded:
    logger.error("🚫 验收降级判不通过: %s | %s", ticket_title[:20], node.degrade_reason)
    score = 0
    passed = False
    status = "acceptance_rejected"
```

代码审查侧同理，置 `score = 0` + `has_critical = True`。报告 md 里也写明
「**本次审查未真正执行**」——不能让人读了报告以为代码没问题。

注意这里**判不通过而不是判错误**：走 SOP 既有的 `reject_goto` 返工，
LLM 恢复了就能过。

### ② `emit_step` 的「完成」必须有产出作证（`base.py` + `dev.py`）

`emit_step` 加 `files` / `reason` 两个参数，`detail_json` 里带上 `files`、
`file_count`、`reason`。`_do_develop` 里三类情况一律判失败：

```python
code_files = list((code_result.get("files") or {}).keys())
dev_notes = str((code_result.get("dev_result") or {}).get("notes", ""))
fail_reason = ""
if code_result.get("status") == "error":
    fail_reason = code_result.get("message") or code_result.get("error") or "代码生成失败"
elif not code_files:
    fail_reason = "未产出任何代码文件"
elif "[降级]" in dev_notes:
    fail_reason = f"仅产出降级模板，非真实实现（{dev_notes[:80]}）"
```

### ③ 增量工单不许用兜底模板（`write_code.py`）

空项目生成脚手架是**有意义的起点**，增量工单生成空壳是**冒充修复**。
按 `existing_code` 是否为空分流：

```python
if existing_code:
    logger.warning("⚠️ WriteCodeAction 降级跳过：项目已有 %d 个文件，"
                   "增量工单不能用空壳模板，标记失败", len(existing_code))
    return ActionResult(success=False, data={...},
        message="LLM 输出无效。项目已有代码，增量修改不能用降级模板"
                "（只会产出空壳文件冒充成功），请重试。")
```

> ⚠️ 改这个文件踩了个坑：`write_code.py` 里的中文注释和字符串
> **在源文件里是 `\uXXXX` 转义序列**，不是 UTF-8 汉字。按看到的中文做
> exact-match 编辑一定失败，得锚定纯 ASCII 的行。改完用
> `'\\u5de5' in source` 确认自己没引入新的转义。

### ④ 僵尸回退重跑，而不是前推成功（`orchestrator.py`）

`reset_map` 整张删掉，换成回退查询。僵尸的语义是「这个阶段半路死了」，
不是「这个阶段做完了」，所以要退回**派单前**的状态让 SOP 重新触发：

```python
async def _zombie_rewind_status(self, ticket_id: str, status: str) -> Optional[str]:
    """来源优先级：
      1. 本次进入该 in_progress 状态时那条 `assign` 日志的 from_status —— 最准
      2. SOP 里 success_status == 本状态的那个 stage 的 trigger_on —— 兜底
      3. 都拿不到 → 返回 None（宁可让它继续挂着等人看，也不谎报完成）
    """
```

优先读 `assign` 日志而不是直接查 SOP，是因为同一个 `in_progress`
可能有多个入口。拿实库验证过：

| 工单 | 入口 | 回退到 | 重新触发 |
|---|---|---|---|
| `ce79a9` | `assign: architecture_done → development_in_progress` | `architecture_done` | develop ✅ |
| 走返工的 | `assign: acceptance_rejected → development_in_progress` | `acceptance_rejected` | rework ✅ |

如果无脑查 SOP，第二种会被退回 `architecture_done`，变成重做一遍开发而不是返工。

`MAX_ZOMBIE_REWIND = 3` 止损（按 `action='zombie_reset' AND from_status=?` 计数），
超了转 `blocked`，避免「死 → 回退 → 再死」无限重跑。回退时补一条 warning 级
`zombie_reset` 日志，把 `stale_seconds` 记下来——这次的 40 秒前推在旧代码里
**一条日志都没留**，这是复盘时最难查的一环。

### ⑤ `CodeChangePlan` 兼容字符串数组（`plan_code_change.py`）

这是零文件的**直接起因**。LLM 经常无视 schema 直接回：

```json
{"files_to_modify": ["gallery.js", "post.js"]}
```

Pydantic 一报 ValidationError → ActionNode 走宽松解析 → 整个 plan 退化 →
零文件 → 回退 WriteCode → 降级模板。**一次格式不合规拖垮整条链。**

三个 `@field_validator(mode="before")` 做归一化：字符串 → `{"path": s, ...}`，
`file` / `filename` / `name` / `file_path` 别名补成 `path`；
`files_unchanged` 反过来（要字符串却收到 dict）。

**顺带查出第二个 bug**：路径对不上时是**静默跳过**的。

```python
if path and path in existing_code:   # ← gallery.js vs src/gallery.js 不匹配
    ...                              #    直接 continue，一个文件都改不到
```

补了 `_resolve_path`：原样 → 归一化斜杠 → 忽略大小写 → 按文件名唯一匹配。
最后一条只在**全仓库该文件名唯一**时才认，否则会把 `a/util.js` 改成 `b/util.js`。
跳过的文件现在记 warning，不再无声。

### ⑥ 前端把产出显示出来（`app.js` + `styles.css`）

`_renderFileChips(names, paths, ticketId, total)` 提成公共函数（原来的 chip
逻辑是内联的），`_renderSkillStepItem` 渲染：

- 有产出 → 文件 chip（可点，跳文件）
- `detail.file_count === 0` → 一个「无产出文件」chip
- 失败 → `.skill-step-reason` 显示原因

CSS 那边有个必须改的点：`.log-skill-step` 是**单行 flex 行**，
不加 `flex-wrap: wrap` 的话 chip 会被挤进那一行压扁。

## 一个关键取舍：可重试，不是 blocked

我最初列的方案里写的是「标记失败让 orchestrator 重试」。**核实后发现这不是当前代码的行为。**
`orchestrator.py:2064` 那一段：

```
ActionResult.to_dict()   success=False  →  status: "error"
orchestrator              status=="error" →  BLOCKED（在 _HARD_TERMINAL 里，无自动重试）
```

如果代码生成失败直接返回 `status: "error"`，**每次 LLM 超时都会变成一张需要人工捞的工单**。
LLM 超时是常态，这个代价不能接受。

所以仿照既有的 `self_test_failed` / `play_test_failed` 先例（它们也是普通状态串、
不是 `TicketStatus` 枚举成员），加了可重试状态 `development_failed`：

```yaml
- id: development_retry
  name: 开发重试
  agent: DevAgent
  action: fix_issues
  trigger_on: development_failed
  success_status: development_done
  branch_only: true          # 只做 reject 分支目标，不参与 _relink_stage_transitions
  config:
    read_existing_code: true
    enable_reflection: true
    reflection_max_prev: 3
```

路径是：记 `action='reject'` 日志（喂 `_reject_count_since_reset`）→
`DevAgent.fix_issues` 带反思重开发 → 累计超 `MAX_RETRIES = 5` 才 `blocked` 止损。

`reflection.py` 新增分支，措辞上刻意和「代码写错了」区分开：

> 这不是「代码写错了」，是**根本没写出来**。
> 🚫 严禁再产出 `console.log('xxx loaded')` 这类占位空壳文件冒充完成。

**OpenSpec 的硬失败故意仍走 `blocked`**（缺 `tasks.md`、skill 未安装）——
重试也修不好，让人看比重试 5 次再让人看更省事：

```python
hard_fail = bool(code_result.get("_openspec_apply_failed"))
return {"status": "error" if hard_fail else "development_failed", ...}
```

新状态在 `models.py` 的 `STATUS_LABELS`（「开发未产出代码」）、
`api/roadmap.py` 的 `_TICKET_PHASE_MAP`、前端 `HARNESS_PHASES` 的开发阶段
`keys` + `jumpStatuses` 里都登记了。另外确认过它**不在** `_TERMINAL_STATUSES` 里、
在 composed rules 里有规则，所以 `_get_all_actionable_statuses()` 会扫到它——
这一步要是漏了，工单会永远卡着不动，而且表面看不出来。

## 这条值得记

**「降级」这个设计模式的默认失败方向，取决于 schema 的默认值——而 schema 默认值
是为了「正常情况下少写点字」挑的，不是为了「异常情况下安全」挑的。**

`ReviewOutput(passed=True, score=6)` 作为默认值非常合理：大部分评审是通过的。
但它作为**失败兜底**是灾难：它让「什么都没发生」等于「一切正常」。

这比一个普通的判断写错更隐蔽——`model_construct()` 那行代码**看起来完全正确**，
它的注释是「解析失败时宽松降级（不崩溃）」，而它做的事确实是不崩溃。
问题在调用方：读 `review.score` 的人不知道自己读的是不是真实数据。

判据：**任何一个「失败时用默认值兜底」的地方，都要问一句
「这个默认值被下游当成结论时，是安全的还是危险的」。**
危险就必须带标志位，而且标志位要收进唯一入口——三处降级点漏一处就等于没做。

同一条的另一个面：**「完成」这个信号本身必须携带证据。**
`emit_step(phase="done")` 原来只证明「函数返回了」，用户读成「做成了」。
这两件事在 LLM 挂掉时完全脱钩，而 UI 上没有任何线索能看出差别。
