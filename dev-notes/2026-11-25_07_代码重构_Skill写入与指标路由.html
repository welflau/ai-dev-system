Skill：在写工单的那一刻检查批次

执行 A 通过了编排器的入口检查，并不代表它到达数据库时仍有权写。旧版的Skill 处理器用工单 ID 更新状态、结果和时间；失败分支还会一并更新诊断。如果 B 刚接手、状态名称没有变化，A 仍能把 B 改为已完成、待人审甚至阻塞。

等待人审、完成（含部分完成）、跳过和阻塞，都已有同一个 _save_status 入口。它现在复用上期的条件更新。阻塞诊断与结果仍是一条 SQL；不匹配就保留 B 的原值，由编排器识别过期并停止。目标状态与来源状态相同也会消费批次，重复回传不能再记一次完成。已经执行的 Git 或 Skill 外部操作不在这条 SQL 的保护范围内。

先复现。 新增的 5 个用例在临时 SQLite 上走真实结果入口。在旧 SQL 执行前先写入 B 的批次、结果与诊断，覆盖四个分支及以 DevAgent、PlannerAgent 为宿主的 Skill。另一个用例让完成目标与原状态相同，再送一次 A 的结果。修改前 5 个全部失败；修改后验证 A 不产生业务日志、评论、事件或派单，B 随后可以正常完成。

第一次相关回归有 3 个旧人审用例失败：手工构造的结果上下文是 *_in_progress，数据库的初始工单却是 pending。真实入口使用数据库中的来源状态。给这三个用例设置相应的数据库初始状态后，原有产物、人审、评论和阻塞断言全部保留并通过。

阻塞竞态用例特意使用无产物的 budget_exceeded，使结果进入 Skill 专属诊断分支；直接传顶层 status=error 会被公共错误处理提前接走，测不到这次修复。
