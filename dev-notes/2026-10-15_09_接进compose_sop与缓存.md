## 一、做了什么

拓扑排序接进生产路径。`compose_sop` 的流程从 7 步变 8 步：

```
① base_stages + required_traits 裁剪
② fragment 插桩（insert_after/before）
③ stage_overrides
④ 悬空 reject_goto 剥离
⑤ ★ skill 链整块插入（新增）
⑥ _relink_stage_transitions
⑦ _merge_pipeline_view（吃 fragment + skill 两种 contrib）
```

新增 `repo_path` 参数（只影响第 ⑤ 步，不传则只扫 backend 内置 skill）。

**向后兼容已验证**：空 repo 时 5 组 traits 的组装结果与不传 `repo_path` 完全一致，48 个基线测试全绿。

## 二、插入位置的硬约束

```python
# 缺省：第一个 branch_only 之前
for i, s in enumerate(composed):
    if s.get("branch_only"):
        return i
```

`_relink_stage_transitions` 跳过 `branch_only` 且不让它们参与 `prev_success` 传递。插在它们后面的话，skill 的 `trigger_on` 会被接到最后一个线性 stage 的 success 上——但**列表顺序显示它在 rework 后面**，状态链的实际走向与列表顺序不符，排查时极易误判。

注入「插到末尾」验证：3 个测试红。

锚点可由 `_core.yaml` 顶层 `skill_block_anchor` 覆盖：

```yaml
skill_block_anchor: {insert_before: acceptance}
```

配在 core 而不是每个 skill 里——skill 不该知道自己在流程的哪个位置，那正是本次要消除的耦合（fragment 的 `insert_after` 就是反例）。锚点 stage 被裁剪时**退回缺省位置而非追加末尾**（否则又违反上面那条约束）。

## 三、补了一道方案没提的防线：stage_id 撞名

skill 的 `stage_id` 与某个 base_stage / fragment 同名时，`_find_stage_idx` 和 `by_action` 的「先到先得」会反查到**错误的 stage**。比如 skill 声明 `stage_id: development`，`_sop_stage_for('development')` 可能返回 skill 的那个，于是 DevAgent 的 config 全错。

加了防撞检查 + ERROR diagnostic，测了「base 的 development 还在且仍是 DevAgent」。

## 四、加了缓存，因为实测 53ms

```
compose_sop: 53.22 ms/call
deepcopy:     0.10 ms/call      ← 500 倍差距
```

`orchestrator._sop_stage_for`（orchestrator.py:309）每次派单都调一次，而 `_get_rules_for_project` 只缓存派生出的 rules、不缓存 config。加缓存后：

```
cold: 89 ms | warm: 0.07 ms | 1357x
```

**返回深拷贝**是必须的——调用方确实会 mutate（orchestrator 读 stage 后改 config、`_merge_pipeline_view` 里的 append）。

失效入口挂在两处：
- `orchestrator.reload_sop`——只清 rules 不清它等于热重载无效（派生 rules 的输入还是旧 config）
- `invalidate_project_rules`——缓存 key 不含 project_id，没法精确清，全清一次代价只是 53ms

## 五、两个假绿，都修了

### a) 缓存深拷贝测试：必须调三次

初版写法「改第 1 个、查第 2 个」——注入「不深拷贝」后**全绿**。

原因：第一次调用是「未命中 → 组装 → 写缓存 → 返回」，它本来就返回独立对象。少了深拷贝只会让**第 2 次之后**的调用共用同一个缓存对象。污染发生在第 2、3 次之间。

实测复现：

```
a is b: False
b is c: True        ← 第 2、3 个调用方共用同一对象
c 被污染: POLLUTED_BY_B
```

改成「改第 2 个、验第 3 个」，再注入立刻红。

### b) pipeline_view 贡献：功能对但没覆盖

注入「不传 `_skill_view_contribs`」→ 全绿。说明代码写对了但没有任何测试覆盖它。

危害是真实的：skill stage 不在任何 pipeline 组里 = **前端完全不可见**，流水线跑着但界面上没有格子亮起。

补了两条：显式 contrib 建组（含 `insert_after` 位置、`reject_status` 进 `running_statuses`），以及无 contrib 时落入默认组（关键是**不能消失**）。

**这是第 5 次踩假绿。** 前四次的规律是「去掉判断会不会产生相同结果」，这次是新形态：**代码路径根本没被任何断言触及**。补充判断标准：

> 变异测试全绿时，先区分两种情况：
> (1) 测试与实现不可区分（输入不够）
> (2) 该代码路径压根没有断言覆盖
> 第二种更隐蔽——它看起来像「功能已实现」，实际上是「没人检查过」。
