# 工单跑过的命令，一行记录都没留 —— 因为唯一跑 shell 的路径是唯一没有审计的路径

2026-09-20

## 症状

用户接着上一份 DevNote（《假成功链路六道闸门》）问：

> 现在工单执行中，那些 Bash 等操作能有记录了吗，能有后台链接了吗？

答案是**没有**。而且第一反应「前端没渲染」是错的——**数据根本没产生**。

前端那条链其实是通的，一路都在：

```
_taskLinkHtml(log) → openTaskFromLog → _TICKET_TASK_INDEX
                   → _selectTaskItem → _renderTaskOutput
```

缺的是链条最上游的**数据源**。`_buildTicketTasksFromLogs` 现在干的事是
**前端拿 `ticket_logs` 现编伪任务**（id 形如 `titk-${log.id}`），
所以那个「📟」点开看到的是日志里那句中文散文，不是命令本身。

## 根因：一个漏掉的关键字参数

`skills/runner.py` 构造 QueryEngine 时把 hooks 透传了下去：

```python
engine = QueryEngine(llm_client=llm, tool_executor=executor,
                     budget=budget, hooks=self._hooks, max_rounds=max_rounds)
```

看着没问题。问题在 `self._hooks` 的来源：

```python
def __init__(self, skill, llm_client=None, hooks=None):
    self._hooks = hooks          # ← 默认 None
```

而三个构造点 `agents/dev.py:212`、`agents/architect.py:107`、
`agents/skill_agent.py:62` **全都是 `SkillRunner(skill)`**——一个都没传 hooks。

`query_engine/engine.py` 里 PRE/POST_TOOL_USE 都在 `if self.hooks:` 守卫内，
于是这条路上 **hook 一次都不发**。

**全库其它每一个 QueryEngine 都传了 `hooks=hook_registry`**
（`agents/base.py:299`、`chat_assistant.py:879`、`:1137`）。只有 skill 这条漏了。

而真正跑 shell 的两个 Action 恰恰**只**在这条路上：

- `GenericCLIAction`（`actions/generic_cli.py`）— skill 声明的每条 CLI（openspec 三件套）
- `ShellAction`（`actions/chat/shell_exec.py`）— builtin `shell`

两者都在 `skills/runner.py:_build_actions` 里建，经 `SkillToolExecutorAdapter`
直接 `action.run(ctx)` 执行——不经 `actions/executor.py:run_action_with_hooks`
（那个函数里 hook 是**无条件** `from hooks.registry import hook_registry` 的，
所以走它的 Action 全都有审计）。

**唯一真正跑命令的路径，成了唯一没有审计的路径。** 这不是巧合——
恰恰因为 skill 是「新接进来的、自成一套的」那条路，它才既独占了 CLI 执行，
又独自漏了 hook 接线。

实库佐证（`backend/data/ai_dev_system_new.db`，注意 `.env` 把 DB 指到了 `_new`）：

| 表 | 行数 | 说明 |
|---|---|---|
| `tool_audit_log` | 5996 | 其中 `openspec*` **0 行** |
| `ticket_logs` | 40035 | 同期 `openspec_propose_started` 11 次、`openspec_apply` 10 次 |
| `ticket_commands` | 22224 | `command` 列全是中文散文，`result` 恒 NULL |

**命令确实跑了 20 多次，一行执行记录都没留。**

顺带查实的两个陈年缺陷：

- `git_manager._run_git` 的 `subprocess.run` **没有 timeout**，
  而它是 `async def` 里的阻塞调用——一次卡死的 `git push` 卡住整个事件循环。
- `tool_audit_log` 里 `git:commit_failed` **2937 行，`ticket_id` 全为空**，
  其中 **2840 行**错误是
  `fatal: Unable to create '.../.git/index.lock': File exists.`
  ——git 提交在大规模失败，而这事在 UI 上完全看不见，也归不到任何工单头上。

## 改动

### 1. 给 SkillRunner 接上 hooks（核心，一行）

在 `__init__` 兜底，**不是**改那三个调用点——否则以后新增第四个构造点还会再漏一次：

```python
if hooks is None:
    try:
        from hooks.registry import hook_registry
        hooks = hook_registry
    except Exception:
        hooks = None
self._hooks = hooks
```

开 hooks 的风险核实过，可控：

- `permission_gate.check` 在 `engine.py:717` 是**无条件**调用的，
  **不在** `if self.hooks` 守卫内——skill 路径本来就已经过闸，开 hooks 不改变这点，
  不会突然多出审批弹窗。
- `shell_rate_limit_hook` 判的是 `ctx.tool_name != "ShellAction"`，
  而注册名是 `shell`（`ShellAction.name`）——**这个 50 次/工单的限流从来没生效过**，
  接 hooks 那一步不会突然开始拦截。（随后单独修了，见改动 9。）
- `failure_library_hook` / `chat_alert_hook` 只在 TOOL_ERROR 触发；
  `nudge_hook` 只在 USER_PROMPT_SUBMIT。

### 2. 结构化字段怎么到 hook：ContextVar 交接

POST_TOOL_USE 的 `ctx.output` 是 adapter 拼好的 `result_text` **字符串**
（`engine.py:759` 填 `output=result_text`），`ActionResult.data` 在 adapter 里
就被 `result.message or json.dumps(...)` 压成一行文本了。

而两个 Action 早就把要的东西准备好了（`{"type":"cli_result", "command":rendered,
"exit_code":..., "output":...}`）。三个选项：

- ❌ **正则解析 `result_text`**：`ShellAction.message` 把命令截到 60 字、
  output 压根不在 message 里。倒推等于**再造一份判据**——
  这仓库已经为「两份判据脱节」写过两遍血泪注释（`app.js` 的 `_logTaskId`、
  `api/tickets.py` 的 `_annotate_chat_anchors`）。
- ❌ **改 adapter 回传 `.data`**：`action_data` 在 `engine.py:786` 会驱动
  `final_action`。`OrchestratorToolExecutorAdapter` 现在恒返回 `None`，
  改了就会让 orchestrator ReAct 路径的 `final_action` 开始有值——
  **协议级行为变更，为了记日志不值得。**
- ✅ **Action 自己 offer 一份结构化记录，hook take 走**。

新建 `backend/command_log.py`：

```python
_PENDING: ContextVar[Optional[dict]] = ContextVar("ads_cmd_pending", default=None)
def offer_command_record(**fields) -> None    # Action 在 return 前调
def take_command_record() -> Optional[dict]   # hook 调，取走即清
async def record_command(*, source, tool, command, cwd="", exit_code=None, ...) -> str
```

ContextVar 已是本仓库既定手法（`checkpoint/context.py`、`llm_client._LLMContext`、
`skills._current_skills` 三处同构）。而且这里**只能**走 ContextVar：
`actions/base.py` 是纯 ABC，Action **没有实例状态**——
`acceptance_review.py:197` 还留着「写 `self.agent_type` 结果 AttributeError」的疤。

时序实测确认：adapter 内 `set` 的值，在 engine 的 async generator 里 emit
POST_TOOL_USE 时读得到（同一 Context，没跨 Task）。

**`take()` 必须取走即清。** 实测调用方 Context 同样看得见这个值，
不清的话上一条命令会漏给下一个工具，把两次执行串成一条假记录。

落点：`generic_cli.py` 四个返回点（成功 / **超时** / `FileNotFoundError` / `Exception`）
和 `shell_exec.py` 四个返回点都 offer。超时和启动失败最值得记——
那正是「什么都没输出」的时候。

### 3. 新表 `ticket_command_log`

**不复用 `ticket_commands`**：那 22224 行里 `command` 存的是
「写入文件: docs/Reqs/30f837/65766b/deploy.md」这样的中文散文，`result` 恒 NULL。
往上加列会让**同一列**里两万行是散文、新行是 argv，读路由无法区分，
等于在旧表上叠一套影子语义。旧表保留只读。

**也不并进 `audit_log_hook`**：`tool_audit_log` 是**计数器**
（`output_summary` 只留 200 字符，5996 行全靠它统计），
新表要的是**可重放的控制台**。两者写入量和保留策略不同，
混进一个函数迟早互相妥协。

⚠️ **建表和索引必须一起写进 `SCHEMA_SQL`，不能走 `_auto_migrate`。**
`_auto_migrate` 是给**加列**用的；`init_tables` 先 `executescript(SCHEMA_SQL)`
再迁移，而 **`executescript` 一条语句失败会整段中止**——
实测：索引引用了尚不存在的列 → `OperationalError`，
且**该语句之后的表全都建不出来**。新表所有列一次给全 + 索引紧随其后就没这个问题。

输出体积策略（这库已 955.9 MB，`artifacts` 独占 614.9 MB，
原始输出直塞 SQLite 正是它涨成这样的原因）：

- ≤ 64 KB → 全量进 `output`
- 更大 → head 8KB + tail 56KB，`truncated=1`，`output_bytes` 记**原始**大小
- **头尾都留**是刻意的（沿用 `ci/strategies/ue.py` 的 `raw_head`/`raw_tail` 约定）：
  头部有「跑的什么、环境如何」，尾部有「错在哪」。只留一头必然丢掉另一半。

ANSI 转义**在写入侧剥**，不在渲染侧：存库剥一次，所有读者都干净。

### 4. `_run_git`：超时 + 记录

**双档超时**：`_GIT_TIMEOUT = 120` / `_GIT_TIMEOUT_NETWORK = 600`
（`push`/`pull`/`fetch`/`clone`/`ls-remote`/`submodule`）。
`rev-parse` 卡 120s 已经是病，而大仓 push 3 分钟是正常的，**一个值盖不住两种**。

超时返回 **124**（GNU `timeout(1)` 约定）而非 1：61 个调用点里遍布 `if rc != 0`，
用 1 和「正常失败」分不开，124 一眼能认。已 grep 确认无任何调用点判具体码值，
并把这条契约写成了断言（`inspect.getsource` 里不许出现 `rc == <非零>`）。

实测 `TimeoutExpired.output` / `.stderr` 在 `text=True` 下是 **str**（非 bytes），
且含超时前已收到的**部分输出**——留下来，这是超时现场唯一的线索。

**必须同时加 `run_in_executor`，这不是可选优化**：`subprocess.run(timeout=)`
是在**调用线程**里 wait 的，`_run_git` 又是 `async def`，不换线程的话
事件循环照样被卡满 120s——超时本身的意义就打了折。
测试里并发跑一个 10ms 计数器来钉这件事（`ticks=16` 才算过）。

记录**按语义过滤，不按调用过滤**。`_run_git` 的动词分布以廉价读操作为主，
且一次逻辑 `commit` 要发 3 次 `_run_git`（add / status / commit）。
一条一行会把面板淹掉，重演 `ticket_commands` 现在 22224 行低价值记录的老问题。

- **写操作** `noise=0`：`commit`/`push`/`pull`/`merge`/`clean`/`init`/`rm`
- **读操作** `noise=1`：`status`/`rev-parse`/`show`/`log`/`diff`/… ——
  **照样入库，但列表默认不显示**
- `add`/`branch`/`remote`/`checkout` 有歧义，看第二个 argv 判
  （`-v` / `--list` / `-` 开头 → 读）
- **失败一律 `noise=0`**，哪怕是 `rev-parse`——失败的 plumbing 往往就是断点
- 为什么不干脆不记 noise：诊断难恰恰难在「什么都没跑」和「跑了但没输出」分不开，
  `?include_noise=1` 正好回答这个

顺带修了 `_emit_git_error_hook`：**压根没传 `ticket_id`**（只有 project_id
+ `agent_type="Git"`），`duration_ms` 也硬编码 0，且只传 stderr
（所以 98 条「nothing to commit」的 error 是空的——git 把它写在 stdout）。
这就是那 2937 行 `git:commit_failed` 全是工单孤儿的原因。一并补上。

**这一步让那 2840 次 `index.lock` 失败第一次在 UI 上可见。**

### 5. 先修一个嵌套 ContextVar 的不对称 bug

ticket 上下文走**既有的** `checkpoint/context.py`
（docstring 写明就是「供 git_manager 等无 ticket 形参的漏斗读取」），不新造。

但 `set_*` 是 merge 语义（只覆盖非空），`clear_*` 却是 `_CTX.set(None)`
**无条件全清**——不对称。于是：

```
orchestrator.py:1535   设工单级 {project_id, ticket_id}
  └─ agents/base.py    嵌套再设 {agent_type, action}
       └─ finally      clear_checkpoint_context()   ← 把工单级的一起清了
```

后续所有 git 操作都变成了没有 `ticket_id` 的孤儿。

加 `push_checkpoint_context()` / `pop_checkpoint_context(token)`（`_CTX.reset(token)`），
把 `agents/base.py` 和 `chat_assistant.py` 两处**嵌套**点改成配对；
**最外层** `orchestrator.py` 保持 set/clear 不动——它确实该清干净。

### 6. 链接：双向指针，写入侧一次配对

时间轴那条日志怎么拿到**真** taskId，关键是**不靠时间猜**。
`command_record_hook` 里一次做完：

1. 先生成 `record_id = generate_id("TCMD")`（先生成，不先写）
2. 写一条 `ticket_logs`：`action='command_run'`，
   `detail` 含 `{message, tool, command, exit_code, duration_ms, cwd, task_id: record_id}`
3. `record_command(..., log_id=log_id)` 写 `ticket_command_log`

两条记录在同一个 hook 里同时创建，`ticket_command_log.log_id` ↔
`ticket_logs.detail.task_id` **天然对齐**。`_annotate_chat_anchors` 里那个
「llm_call 按 ≤3s 时间差配对」的无奈做法，这里不需要。

后端标注（照 `_annotate_chat_anchors` 的既有先例——**一个判断只活在后端，
前端只读字段**）：新增 `_annotate_task_refs(ticket_id, items)`，一条 SELECT 建
`{log_id: record_id}` 映射，给命中的 item 标 `_task_ref`。

`action='command_run'` 的登记：

- 加进 `_SECONDARY_ACTIONS` → 默认进「详细日志」。
  失败的会因 `level='error'` 被 `_classify_tier` **自动提到 primary**，正合需要。
- **不**加进 `api/chat.py` 的 `FEED_LOG_ACTIONS`——工单对话是给人读的叙事，
  逐条命令进去是灌噪音，而且会被标 `_chat_anchor`，多出一个「↗ 对话」死链。

新路由：`GET /api/tickets/{id}/command-logs?include_noise=0`、
`GET /api/ticket-command-logs/{record_id}`（单条全量 output）。

### 7. 前端：伪任务换成真记录，但不删兜底

- `_logTaskId` **优先认后端标的 `log._task_ref`**，拿不到才回落
  `_TICKET_TASK_INDEX`。顺序是关键——反过来的话有真记录的日志仍然点开伪任务，
  这次改动等于白做。
- `_refreshTasksPanelInner` ticket 分支先拉 `/command-logs`，
  与 `_buildTicketTasksFromLogs` 的合成结果合并；合成项里 `log_id`
  已被真记录覆盖的**按 `log_id` 丢掉**，避免同一次执行出现两行。
- 新增 `_recordToTask(r)`，映射成 **`type:'cli_task'`** 的 shape。
  这样 `_selectTaskItem` 的 cli_task 分支、`_renderTaskOutput`、`_formatCliLines`、
  `_colorLine`、复制/显示全部按钮、CSS **全部零改动复用**——
  这是选 cli_task 形状而不是新建 type 的**全部理由**。新开一个 type 意味着
  上面每一项都要再写一遍，然后两份渲染各自演化。
- `_selectTaskItem` 加「id 以 `TCMD-` 开头 → 打 `/ticket-command-logs/{id}`」分支
  （内存表刷新就空了，而老的 `/chat/cli-tasks/{id}` 查不到 TCMD），保证**刷新后仍能拉全量**。
- **`_buildTicketTasksFromLogs` 保留不删**：40035 行历史 `ticket_logs`
  没有对应新记录，删了旧工单链接全灭；且 `_test_log_task_link.js`
  有 54 条断言压着它。

### 8. 实时流：复用 `log_added`，不建新事件族

本轮的命令都是**短命令**（git 单条 <1s，openspec CLI 一次性 `communicate()` 返回），
没有流式行可推，为不存在的流建通道不划算。写完那条 `ticket_logs` 后
照既有字段 publish 一个 `log_added`，前端 `appendLogEntry` 已订阅。

「崩了丢数据」由记录时机本身解决：这是**结束后**落库的一行，不是流式追加，
不存在丢 buffer 的问题——**比现有 `cli_task` 的纯内存流式路径更耐崩**。

### 9. 顺带把 `shell_rate_limit_hook` 真接上（用户指定）

上面接通 hooks 之后，这个限流从「名字不匹配」变成「只差名字不匹配」——
两重失效去了一重，所以把名字也一起改对：

```python
if ctx.tool_name != "shell":        # 原来判的是类名 "ShellAction"
    return
```

**类名和工具名不是一回事**：`ShellAction.name` 返回 `"shell"`，
`skills/runner.py` 也是按 `actions["shell"]` 注册的。历史上它判类名
+ 挂在 skill 路径压根不发的 PRE_TOOL_USE 上，**双重失效**。

`GenericCLIAction` **不进限流**：它的命令主干写死在 skill 的 `command_template`
里，LLM 只能填白名单槽；跑飞的风险和「LLM 自由拼 shell 字符串」不是一个量级。

改名字的时候撞见第二个更隐蔽的缺陷——原实现对**没有 ticket_id 的调用**
（全局 AI 助手对话）用的是同一个终身计数器。后端进程能连跑几天，
攒够 50 次之后**所有对话里的 shell 就被永久锁死**，而且重启才能解。
这个 bug 以前无害，恰恰因为限流从未生效；一改名字它就会立刻发作。
所以两种场景分开：

- **有 ticket_id → 终身计数**。一张工单跑满 50 次 shell 就是跑飞了，正是要拦的。
- **无 ticket_id → 1 小时滑动窗**（`deque` 存时间戳，每次先弹出过期的）。
  那种场景要防的是「短时间内爆发」，不是「累计多少次」。

外加 `_SHELL_COUNTS_MAX_KEYS = 2000` 的 dict 上限兜底——长跑进程里
per-ticket 那个 dict 否则只涨不消。

`_test_harness_p1.py` 的 T1-2 段相应改了：两条原有断言从 `"ShellAction"`
换成 `"shell"`，再加两条——一条钉 `ShellAction().name == "shell"`
（判类名那版永远不会生效），一条钉全局窗**会滑出去**而不是永久锁死。

### 10. `TK-20260920-ce79a9` 回退（用户指定：回退，不是标 cancelled）

上一份 DevNote 的遗留 #2。用了一次性脚本 `backend/_fix_rewind_ce79a9.py`
（默认预演，`--apply` 才写），**不走** `reset_phases` / `PATCH status`——
那两条正规路径都会**正确地拒绝**，而它们拒绝得有道理，不该为一张工单去松：

- `orchestrator._rewind_ticket_status` 查 `_HARD_TERMINAL`，`deployed` 在里面。
- `TICKET_TRANSITIONS[DEPLOYED] == [PENDING]`，状态机不允许从终态跳回中间态。

这是**人工数据订正**，不是该被产品化的流程：它之所以需要，是因为六道闸门修好之前
那张工单**本来就不该走到 deployed**。闸门已修，同样的假成功不会再发生。

做的四件事：

1. `deployed` → `architecture_done`（development 阶段的 `trigger_on`），
   `completed_at` 置 NULL
2. 只删**假成功之后**的 2 个产物（`code_review` / `deploy_config`）；
   PRD（00:46）和架构（00:48）是开发挂掉之前正常产出的，**保留**——
   删了等于让工单白跑两轮
3. **需求一起降回 `in_progress`**：`_check_requirement_completion`
   只会往 `completed` **升**，从不往回降（`all_done` 为假时它什么都不做）。
   不降的话需求会一直挂着「已完成」而底下有张工单正在重跑——
   又是一个「状态说成了、其实没成」，跟这两轮要治的是同一个病。

## 一个测试自身的坑

`command_record_hook` 第一版写 `ticket_logs` 是裸插的。测试里用假工单
`TK-TEST-CMDLOG` / `P1` 一跑就炸：

```
FOREIGN KEY constraint failed
```

`ticket_logs.project_id` 是 `NOT NULL REFERENCES projects(id)`，
`ticket_id` 也 `REFERENCES tickets(id)`。

这个失败暴露的不只是测试数据问题——**生产上如果 project_id 因为上下文丢失而为空，
整条命令记录都会一起丢**，而那恰恰是最需要记录的时候。所以两边都改：

- hook 里把 `ticket_logs` 插入**单独包一层 try** + `log_ok` 标志，
  时间轴写不进去时命令记录仍然保留（`log_id=''`），SSE 推送也按 `log_ok` 门控。
  降级成「有记录但没链接」，而不是「什么都没有」。
- 测试改成**借一张真工单**（`SELECT id, project_id FROM tickets ORDER BY
  created_at DESC LIMIT 1`），清理时只删自己造的那一条 log，
  绝不 `DELETE FROM ticket_logs WHERE ticket_id = ?` 去扫人家的历史。

还有一条：`db.connect()` **不建表**，只有 `init_tables()` 才跑
`executescript(SCHEMA_SQL)`（生产路径由 `main.py` 启动时调）。
测试得自己补 `await db.init_tables()`。

同理，`register_builtin_hooks()` 也只在 `main.py:81` 启动时调一次——
端到端测试里漏了这行，结果是 hook 全注册好了、engine 也 emit 了，
但 registry 是空的，**零条记录且零报错**。单测直接调函数所以没暴露，
恰好是端到端测试该抓的那类问题。
