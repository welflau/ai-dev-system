### 6. 编译死循环止损（P0，根因 A+C 修复）

**根因 A — UBT 零输出误判**（`ue_compile_check.py`）
状态判定改为三分支：`exit_code!=0 且 errors=[] 且 stdout 全空` → 判 **环境级 `error`**（透传 message/error），命中 orchestrator 顶部 BLOCKED 守卫（`_apply_agent_result` line ~1602 检测 `status=="error"`）直接人工介入；不再走 `compile_failed → fix_issues` 空转。原逻辑 `exit==0且无errors→success 否则→compile_failed` 会把"UBA/mutex 环境问题致 UBT 非 0 退出但零输出"误判为编译失败。

**根因 C — max_retries 从不消费**（`orchestrator.py` + `sop/loader.py`）
- `loader.py sop_to_transition_rules`：reject 回跳规则的 `config` 原本只取 `goto_stage.config`（development 的，无 max_retries）。修为从**失败源 stage**（engine_compile，声明 `max_retries:3`）提取 `max_retries` 覆盖进 reject 规则 config。
- `orchestrator.py process_ticket`：dispatch 前，若 rule 带 `_rework_source_stage` 且 `config.max_retries>0`，查 `ticket_logs` 中 `action='reject' AND to_status=当前失败状态` 的次数，`>=max_retries` 直接 blocked（写 warning 日志 + SSE），不再派 fix_issues。
- 实测：故障工单 reject→engine_compile_failed 共 **4 次**；有守卫后 `max_retries=3` 第 3 次失败即 blocked，省掉第 4 次+ 空转。
- 安全性：默认硬编码 rules（testing_failed/acceptance_rejected）无 `_rework_source_stage` 也无 max_retries，守卫自动跳过 → 对未配置流程零行为变化。

## 四、通用 Skill 执行引擎（SkillRunner）—— 用它重构 OpenSpec（阶段1 MVP 已完成）

### 背景
ADS 的 OpenSpec 生成原是把 Claude Code 的 opsx skill 流程**用 Python 硬编码重写**（`_run_openspec_propose` + `_fill_openspec_4_artifacts`：固定 new change→instructions→llm_client.generate 写四件套→validate）。每接一个新三方工具集都得再写一个 `_run_xxx`，不可持续。用户要"通用的、能执行 skill 流程的引擎"，以后接新工具集只加 skill 定义。

关键认知：**ADS 已有成熟的 REACT+QueryEngine 工具循环引擎**（`query_engine/`），本身就是"给 LLM 一批工具+任务，自主循环完成"的内核。缺的是"把 skill 定义 + 通用 CLI 工具喂给引擎"的适配层。方向（用户拍板）：复用 QueryEngine + 先拿 OpenSpec 开刀 + 本轮先出方案（plan 文件 `snazzy-mixing-prism.md`）→ 已批准 → 实现阶段1。

### 阶段1 MVP 落地（新增 5 文件 + 改 architect）
- **`skills/executable_loader.py`**（新）：`load_executable_skill(id, repo_path)` 读 SKILL.md 的 `x-runner` frontmatter（复用 `loader._parse_frontmatter`）。`ExecutableSkill`/`CliToolSpec` dataclass。来源：项目级 `.claude/packs/*/skills/` > backend 内置 `skills/executable_skills/`。
- **`actions/generic_cli.py`**（新）：`GenericCLIAction(spec)` —— 一条声明的 CLI → 一个 LLM 工具。命令主干写死在 skill 的 `command_template`，LLM 只能填模板预留槽（context 预填 cli/change_id/goal/desc，LLM 只填如 `artifact`）。安全：主干白名单 + shlex.quote + `_DANGEROUS_PATTERNS` 黑名单复查（复用 shell_exec）+ cwd 锁 repo_path + per-tool 超时 + 5000 截断。
- **`actions/write_file.py`**（新）：`WriteFileAction` —— 只写 `_skill_output_root` 下、扩展名白名单（.md）、去 ``` 围栏、越界校验。

### 阶段 B —— CLI 模式的工具调用（openspec MCP server，✅ 已完成）

**发现的关键问题**：实测重启后端跑起来了（时间轴出现"OpenSpec Propose 已启动 — 由 SkillRunner 驱动"），但工具是 `Bash`/`Write`/`TaskCreate` 而非我注入的 `openspec_*`。根因：`LLM_API_FORMAT=cli`（codebuddy），QueryEngine 在 CLI 分支（engine.py:264）走 `_call_cli_stream`，**`tools` 参数根本没传给 CLI** —— codebuddy 有自己的 agentic 循环，读 SKILL.md body 后**用它的原生工具**（Bash 跑 openspec-cn、Write 写 md）代劳。结果四件套照样生成，但我的 GenericCLIAction/WriteFileAction 白名单在 CLI 模式全失效。

**准确机制**：CLI 模式下 skill 本身能用（body 作为 system 传给 codebuddy），但 skill 里声明的工具 schema 被无视（没传进去）。=="skill 能调用，但 skill 声明的工具不生效"==。

**解法（用户选路径 B）**：codebuddy **原生支持 MCP**（`--mcp-config`，llm_client.py:693），且 `_build_settings_args` 已有 MCP 注入机制。故把 openspec 能力包成 MCP server，让 codebuddy 以**命名工具** `mcp__openspec__new_change` 调用，取代裸 Bash。安全边界回到 MCP server。

- `backend/openspec_mcp_server.py`（新）：`FastMCP("openspec")`，工具 `new_change`/`instructions`/`write_artifact`/`validate`/`status` —— 薄封装 openspec-cn CLI，cwd=`env OPENSPEC_REPO`，`write_artifact` 限四件套白名单 + 去围栏。与 `ads_data_mcp_server.py` 同款 FastMCP 风格。
- `llm_client.py _build_settings_args`（改）：在 always-on ads-data 之后，**条件注入** openspec server —— `cwd/openspec` 目录存在且 openspec CLI 可用时，加进 `mcp_servers` dict，env 传 OPENSPEC_REPO+OPENSPEC_CLI。验证：TestFPS(有 openspec)→ servers=[ads-data, openspec]；无 openspec 目录 → 只 ads-data（不污染普通项目）。
- `openspec-propose/SKILL.md`（改）：body 改为"**优先用 OpenSpec 命名工具**（openspec_* 或 mcp__openspec__*），不要用原生 Bash 拼命令、不要原生文件写入"，兼容 API 模式（openspec_* cli_tools）和 CLI 模式（mcp__openspec__*）两种命名。

**双模式下的行为**：
- API 模式（anthropic/openai）：QueryEngine 用 SkillRunner 注入的 `openspec_*` 工具（GenericCLIAction 白名单生效）。
- CLI 模式（codebuddy）：codebuddy 用 `mcp__openspec__*` MCP 工具（安全在 MCP server 侧）。
两种模式 LLM 都被引导用命名工具而非裸 Bash，时间轴可见且语义化。

**补充**：项目 `.ads/mcp_servers.json` 注册 openspec server，让 ADS 自己的 MCP 面板（Agent/扩展页）也能发现并显示。已在 TestFPS 创建 `F:/ADS_Projects/TestFPS/.ads/mcp_servers.json`（openspec server 条目），验证 `_load_project_mcp_config` 正确返回。SKILL.md body 加强为"严禁 Bash 拼 openspec-cn"（LLM 遵从度取决于模型能力，DeepSeek v4 可能不如 Claude 严格）。
