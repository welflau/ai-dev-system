## 一、问题

实测真实工单时发现 ArchitectAgent 耗时 19 分钟，其中 83% 花在 OpenSpec Propose：

```
09:55:43  ArchitectAgent 开始
09:58:54  架构设计 LLM 完成              191s
10:14:32  OpenSpec Propose 返回 partial  938s   ← 83%
```

而 `openspec-propose/SKILL.md` 里明明声明了：

```yaml
budget:
  max_rounds: 14
  max_seconds: 300      # ← 声明 300s，实际跑了 938s
```

---

## 二、根因：Budget 只管"轮与轮之间"，管不了"单轮内部"

```
SkillRunner.execute()
  → Budget(max_seconds=300)
  → QueryEngine.run()
      for round in range(max_rounds):
          if budget.check(): break        ← engine.py:391，只在这里检查
          async for ev in llm._call_cli_stream(...)   ← 进去就出不来了
                            └─ deadline = now + self.cli_timeout   (1800s)
```

一旦进入 `_call_cli_stream`，唯一的时间约束是 `LLM_CLI_TIMEOUT`（默认 **1800s**）。
skill 声明的 `max_seconds=300` 对单轮内部**完全无效** —— 单轮跑 938s 时，
`budget.check()` 根本没有机会被调用。

验证：

```python
b = Budget(max_seconds=300.0)
b._start_time -= 938
b.check()   # "时间上限已达到（938.0s / 300s）"  ← 能检测，但没人调
```

---

## 三、修复

给 `_call_cli_stream` 加 `timeout_override` 参数，由 QueryEngine 传入 budget 剩余时间。

```python
# llm_client.py
async def _call_cli_stream(self, ..., timeout_override: Optional[float] = None):
    effective_timeout = self.cli_timeout
    if timeout_override is not None and timeout_override > 0:
        effective_timeout = min(self.cli_timeout, float(timeout_override))
```

```python
# query_engine/engine.py
_remaining = self.budget.max_seconds - self.budget.elapsed_seconds
async for ev in self.llm._call_cli_stream(..., timeout_override=_remaining):
```

三处 `self.cli_timeout` → `effective_timeout`（流式 deadline、超时日志、非流式 communicate）。

**设计取舍**：

- 用 `min(cli_timeout, override)` 而非直接替换 —— `LLM_CLI_TIMEOUT` 仍是硬上限，
  不会因为某个 budget 配大了就突破全局保护
- `timeout_override=None` 时行为完全不变，向后兼容
- 传的是**剩余时间**而非 `max_seconds` —— 多轮场景下第 N 轮不该再拿满额时间

## 四、验证

`_probe_cli_timeout.py`（临时脚本，用假 CLI 不调真实 LLM）：

| 断言 | 结果 |
|---|---|
| `_call_cli_stream` 有 `timeout_override`，默认 None | PASS |
| engine 传的是 budget 剩余时间（非硬编码） | PASS |
| 函数体内无遗漏的 `self.cli_timeout` | PASS |
| 剩余时间随耗时递减（300s → 250s 后 50s） | PASS |
| override=3s + CLI 睡 30s + cli_timeout=1800s → **3.2s 超时** | PASS |
| 不传 override → 正常跑完 2.5s，未被提前 kill | PASS |
| override=9999s 但 cli_timeout=3s → 3.2s 超时（取 min） | PASS |

> 踩坑：第一版测试用 `cli_cmd = f'{python} -c "..."'`，但 `_resolve_cmd` 会对
> cli_cmd 整体做 `shutil.which()`，带参数必然找不到 → 测试 0.0s 返回
> 「找不到可执行文件」，却被我的断言误判为 PASS（只看了耗时没看返回内容）。
> 改成生成 `.cmd` 包装脚本，并在断言里加「必须命中超时路径」的检查。

## 五、影响面

单轮 CLI 超时从统一 1800s 改为各自 budget：

| 场景 | budget | 生效上限 | 变化 |
|---|---|---|---|
| ChatAssistant | 3600s | 1800s | 不变（被 cli_timeout 封顶）|
| Agent (base) | 600s | 600s | **收紧** |
| QueryEngine 默认 | 600s | 600s | **收紧** |
| openspec-propose | 300s | 300s | **收紧** |
| openspec-apply | 720s | 720s | **收紧** |
| openspec-validate | 180s | 180s | **收紧** |

对照本次实测的真实耗时，确认不会误杀：

```
PlannerAgent         69s  < 600   OK
ArchitectAgent 主LLM 191s  < 600   OK
DevAgent.develop    292s  < 600   OK
DevAgent.fix_issues 427s  < 600   OK  ← 余量仅 29%，需留意
OpenSpec Propose    938s  > 300   ← 正是要治的
```

**风险点**：`DevAgent.fix_issues` 实测 427s，距 `AGENT_MAX_SECONDS=600s` 只剩 29% 余量。
若工单更复杂（更多文件、更多轮 ReAct）有被截断的可能。这是 budget 语义本来就该有的
行为（超预算就停），但如果后续发现 Agent 频繁被 600s 截断，应调 `AGENT_MAX_SECONDS`
而不是回退本修复。
