背景

R2 的前两步把 _handle_agent_result 的分支和 process_ticket、handle_requirement 的流程搬出了 orchestrator.py，文件从 6,694 行降到 4,493 行。剩下的 89 个方法仍然挤在 TicketOrchestrator 一个类里： SOP 规则、轮询、状态回退、止损计数、工单日志、报告生成，互相之间没有边界。

方案 R2 第 3 条要求把这些方法按职责分出去，TicketOrchestrator 保留原有方法名并委托过去， 这样 runtime_facade 和直接导入它的 7 个模块都不用改。本篇记录这一步的做法、验证和没有做到的部分。

结果

72 个方法分 10 组搬进了 backend/orchestration/ 下的 10 个新模块，每组一个提交。 orchestrator.py 从 4,493 行降到 1,818 行。方案定的四项验收指标都没有达到，原因见「和方案的偏差」。

做法

形态：模块级函数加转发方法

每个方法的函数体原样搬成新模块里的一个函数，类上留同名方法，只有一句转发。以止损计数里的一个为例：

# backend/orchestrator.py，类里留下的
async def _acceptance_retry_count(self, ticket_id: str) -> int:
    """本工单因「验收 LLM 降级」已重派验收的次数（自最近一次 unblock 起）。"""
    return await failure_counters.acceptance_retry_count(self, db, ticket_id)

_failure_fingerprint = staticmethod(failure_counters.failure_fingerprint)

# backend/orchestration/failure_counters.py，搬过去的
async def acceptance_retry_count(orch, db, ticket_id: str) -> int:
    ...  # 函数体和原来一样，self 写成 orch

十个模块遵守同一套约定，写在每个模块开头的说明里：

  • 函数体从同名方法原样搬来，函数名去掉前导下划线，self 写成 orch。
  • 新模块不导入 database，也不导入 orchestrator。db 由转发方法在调用那一刻传入。 测试用 monkeypatch.setattr(orchestrator, "db", test_db) 换库，这样函数拿到的才是同一个对象。
  • 搬过去的函数之间互相调用，以及调用别的模块里的逻辑，都走 orch.xxx。测试给实例打的桩照旧生效。
  • 状态都放在 orch 上，模块自己不存状态。
  • 函数里的延迟导入保持原样，测试的打桩是打在这些源模块上的。
  • 日志器沿用 logging.getLogger("orchestrator")，日志器名没有变。
  • 新模块里没有依赖 __file__ 这类文件位置的代码。

每组走的 11 步

十组用的是同一套流程，前两组串行跑改坏检查，后八组改成 4 个 worktree 并行。

步 命令 做什么
1 gen_split.py <组> --dry 预演，看要搬哪些方法、哪些名字需要改写
2 gen_split.py <组> 从快照生成新模块，把类里的方法改成转发
3 verify_split.py <组> 搬移核对，和生成脚本分开写，用语法树比对
4 mk_table.py <组> 把这一组的转发、常量、重导出写进接线测试 tests/agents/test_orchestrator_delegation.py 的表
5 spec_add.py <模块> 把 orchestration.<模块> 加进 desktop.spec 的 hiddenimports，桌面版打包时才会带上新模块

生成脚本只做这几种改写：去掉 4 列缩进（多行字符串的续行不动，字符串的值不会变），self 改成 orch， 读了模块级 db 的方法加一个 db 参数，函数名去掉前导下划线，再加上配置里逐条列出的替换。

验证

为什么主要靠语法树比对

拆分之前 orchestrator.py 的语句覆盖率是 24%。待搬的方法体大多没有行为测试， 跑测试证明不了搬移前后行为一样。所以等价性由 verify_split.py 核对，测试只负责新写出来的转发层。

verify_split.py 每组检查的内容（以 polling 那次的输出为例，十组都是 RESULT ALL PASS）：

  • 重新生成一遍，和磁盘上的两个文件完全一致；
  • 被搬的方法和新函数的语法树相等；
  • 字符串常量逐个相同，方法里的注释都带过去了；
  • 类常量在新模块里是同一个值，类属性指向它；
  • 转发方法的签名和原来一样，函数体只有一句转发；
  • orchestrator.py 里其余的语句没有变化、顺序没有变化，其余的非空行逐行相同；
  • 两个模块都能导入，被搬代码读到的全局名字和 orchestrator 里的是同一个对象，日志器是同一个对象；
  • 新模块不导入 database 和 orchestrator，没有 L3 导入。

接线测试

backend/tests/agents/test_orchestrator_delegation.py，321 行，12 个测试函数，表里有 72 行转发、 11 个常量、5 个重导出，参数化之后是 385 条。它测的是转发层：

  1. 新函数的参数表等于原方法的参数表，前面多 orch，读库的再多 db；
  2. 转发时每个参数落在同名位置上，按位置传、按关键字传、只传必填三种方式都测；
  3. db 取的是调用那一刻 orchestrator 模块里的 db；
  4. 返回值原样带回，协程方法仍然是协程方法；
  5. 搬走的类常量和模块级函数，从原来的位置还能取到同一个对象。

test_static_method_is_the_module_function 这条结构测试在 _seq_index 的原实现快照上是失败的。 这是预期结果：它断言的就是「类上的静态方法是模块里的那个函数」，搬之前这句话不成立。

改坏检查

对转发层逐处改坏：调换两个参数、漏传一个参数、把 db 换成别的对象、改掉常量别名、改掉重导出、 调换新函数开头的 orch 和 db。每组另有对照组：不改语义、只把转发方法改写成一行，测试必须仍然通过， 否则说明测试变红和改坏无关。

并行的做法是在 %TEMP%\ads_mut_wt 下建 4 个 detached worktree，每个 worktree 跑四分之一的改坏项， 主工作区只读。每次 4 个 worktree 的基线都是绿的，结束后核对主工作区的文件哈希没有变化。 这 4 个 worktree 已经用 git worktree remove --force 删除并 prune。

这项检查只覆盖转发层，包括别名和重导出。函数体里的逻辑没有被改坏过，它们靠的是上一小节的语法树比对。

和方案的偏差

方案写的 实际做的 原因
分到 SopRules、Poller、RewindService 等协作者类里 模块级函数，第一个参数是 orch 方法之间通过 self 互相调用很密，现有测试又是给实例打桩。做成类需要先理清谁持有哪些状态，这一步只做能用语法树证明等价的搬移
模块名 ChangeImpactFlow change_flows.py backend/change_impact.py 已经存在并且有模块在导入它，避免重名
7 个协作者 10 个模块 多出 bug_flow、agent_state、failure_counters、ticket_log 四组，方案里没有列。方案里的 RequirementFlow 对应的是此前拆出的 requirement_pipeline.py
顺带清掉 orchestrator 到 L3 的 6 条方向违规 没有做 含 L3 导入的 7 个方法没有搬，需要先改成经注册表取 Agent 和 action
验收：orchestrator.py 不超过 1,500 行 1,818 行，差 318 行 同上，那 7 个方法共 744 行
验收：没有超过 150 行的函数 还有 4 个：_build_context 176、_handle_git_files 167、_handle_agent_result 166、_diagnose_blocked_ticket 153 这一步只搬不拆，拆长函数需要先补行为测试
验收：agent_name == 比较为 0 还有 2 处 没有动

行为上有一处细微变化，提交信息里也写了：agent_state.make_ticket_progress_callback 返回的闭包， 现在用的是创建闭包时传进来的 db；原来是在闭包执行时读 orchestrator 模块的全局 db。 只有在创建和调用之间替换了全局 db 才会有差别。调用它的地方是 _build_context（orchestrator.py:1116）和 根目录脚本 _test_v019_ticket_progress.py:109，后者没有跑。

结构上的小变化：_failure_fingerprint 变成 staticmethod 别名之后，类里的 def 方法数从 83 变成 82。

全仓的度量：超过 200 行的函数从 30 个变成 29 个；最长的函数仍是 query_engine/engine.py 的 run（559 行）； 最大的文件仍是 api/chat.py（5,566 行）。generate_requirement_report（206 行）只是换到了 reporting.py，没有变短。 新模块里较长的函数还有 change_flows.reply_to_comment 146 行、change_flows.partial_flow 129 行、 sop_rules.apply_fragment_closeout 102 行、ticket_log.log_agent_thought 102 行。

没有验证的部分

  1. 搬走的函数体没有行为测试。 等价性靠语法树比对，改坏检查只覆盖转发层。
  2. 重启后没有真实工单走完一个阶段。 processing 一直是 0，搬走的函数在真实运行里只触发了启动、轮询和状态查询这几条路径。
  3. CI 没有在这批改动上跑过。 main 没有推送，Ubuntu 加 Python 3.12 下的结果没有见过。
  4. _test_command_log.py 没有完整跑。 原因见上。
  5. 根目录其余的 _*.py 脚本没有跑。 它们不在 pytest 的 testpaths 里，其中靠读源码文本做检查的会随拆分失效。
  6. 两个 MCP 子进程重启后的状态没有确认。 依赖 rules-bridge-mcp 和 graphify-mcp 的功能没有试。 桌面版也没有重新打包，desktop.spec 里新加的 10 行 hiddenimports 没有经过打包验证。
  7. flake8 的 3 条 F824 为什么这次才出现，没有查清。
  8. 工具脚本没有入库。 gen_split.py、verify_split.py、mutate_split.py、mutate_par.py、mk_table.py、 spec_add.py、commit_group.py、split_cfg.py 都在 %TEMP%\ads_r2_3，换一台机器无法重跑搬移核对和改坏检查。 verify_split.py 还依赖每组搬移前的快照，只在该组刚生成时有效，后面的组改了 orchestrator.py 之后重跑会失败。
