## 一、做了什么

`_core.yaml` 的 8 个基础阶段此前是**无条件加载**的（`loader.py:70` 一句 `list(core.get("base_stages"))`）。内容生成类项目会被迫先跑架构设计 → 代码开发 → 代码审查 → 部署才能到达 skill 链。

现在 base_stage 支持 `required_traits`，复用 fragment 的同一套匹配器（`_fragment_matches` 原样传 stage 进去）。新增 trait 维度：

```yaml
pipeline:
  values: [code, content]     # 缺省 = code
```

实测效果：

```
traits=[]                        → 8 阶段，裁剪 0，diagnostic 0
traits=[pipeline:code]           → 8 阶段，裁剪 0，diagnostic 0   （与缺省等价）
traits=[platform:web]            → 11 阶段，裁剪 0，diagnostic 0
traits=[category:game,engine:ue5]→ 15 阶段，裁剪 0，diagnostic 0
traits=[pipeline:content]        → 3 阶段（planning/acceptance/deploy）
                                   裁剪 [architecture, code_review, development,
                                        development_retry, rework]
```

## 二、方案预见了 3 个连带问题，实际是 4 个

方案 §3.1 列的 a/b/c 都按计划实现了。**第 4 个是写代码时才发现的，方案里没有。**

### (a) 首个阶段的 trigger_on —— 已处理

`_relink_stage_transitions` 原来对 `i == 0` 是 `pass`（保留原声明）。能跑通纯靠 `_core.yaml` 里 planning 手写了 `trigger_on: pending` 这个巧合。改成**强制赋值**：

```python
if not seen_first:
    s["trigger_on"] = entry_status      # 原来是 pass
    seen_first = True
```

顺带修了一个原有缺陷：原实现用 `enumerate` 的 `i == 0` 判断「首个」，但 `branch_only` 的 stage 是 `continue` 掉的——如果 branch_only 排在最前面，`i == 0` 会落在它身上，真正的首个线性阶段就走了 `else` 分支。改用 `seen_first` 标志位后，「首个非 branch_only」的语义才真正正确。

### (b) fragment 失锚 —— 已处理

原来锚点找不到只打 warning 后追加末尾。现在区分两种情况：

- 普通失锚（锚点本就不存在）→ 维持 warning
- **锚点是被裁剪掉的** → `logger.error` + 写 `sop_diagnostics`

实测 `pipeline:content + engine:ue5`（无意义组合，但正好触发这条路径）会报 3 条 ERROR：engine_compile / play_test / ue_test_gen 都锚在 development 上。

### (c) pipeline_view 空壳组 —— 已处理

`_merge_pipeline_view` 新增 `dropped_stage_ids` 参数，清理失效的 `sop_stages` 引用；某组清空后整组移除（`synthetic` 组除外，它们靠 `requirement_status`/`merge` 判定，不依赖 sop_stages）。

content profile 下「架构设计」组整组消失，「开发实现」组的 4 个引用只剩 `acceptance`。

### (d) 悬空 reject_goto —— **方案未预见，新增 `_prune_dangling_reject_gotos`**

发现过程：写完 a/b/c 后手工模拟裁剪，打印状态链发现

```
rework (branch_only): trigger=acceptance_rejected, success=development_done
有规则消费 development_done ? False
```

`rework` 仍可达（acceptance_rejected 有规则），但它产出的 `development_done` 没有任何阶段消费 —— 工单走到 rework 就**永久停住**。`development_retry` 的 `development_failed` 更是永远不会被产出，是个不可达的死阶段。

更隐蔽的是 `sop_to_transition_rules:459` 的 `if goto_stage:` —— `reject_goto` 指向不存在的 stage 时，它**静默地不派生 reject 规则**。于是 `acceptance_rejected` 这个状态在规则表里压根不存在，验收一旦拒绝就静默卡死。

处理方式分两种：

| 情形 | 处理 |
|---|---|
| 该阶段是 `branch_only`（只靠这条边可达） | 整体移除，并把自己加进 dropped 集合（链式影响下游） |
| 线性阶段（还有自己的 trigger_on 要接） | 剥掉 `reject_status` / `reject_goto`，退化成「拒绝后停在原地等人工」 |

两种都写 diagnostic。这不解决「内容类项目验收被拒该重跑什么」这个产品问题——那是待定决策——只保证不产生死锁。

### 一个主动的决定：deploy 不裁

内容类项目没有「部署」语义，第一反应是裁掉。但查了三处后放弃：

- `orchestrator.py:64` `_HARD_TERMINAL` 含 `deployed`
- `orchestrator.py:333` `_TERMINAL_STATUSES` 注释写明 `deployed = 流程终点`
- `orchestrator.py:3333` `_check_requirement_completion` 的 `DONE_STATUSES = {testing_done, deployed}`

裁掉它工单会停在 `acceptance_passed` —— 既不是终态、也没有后续规则，**需求永远不会被标完成**。所以保留，由 DeployAgent 对内容项目走空实现，等 skill 链接入时再细化。

## 三、教训：T11c 又是假绿

和昨天 T9b 一模一样的坑，再踩一次。

T11c 初版断言「content profile 下首个阶段的 trigger_on == pending」。注入「去掉强制赋值」的缺陷后——**48 个用例全绿**。

原因：content profile 裁剪后首个阶段仍是 `planning`，而 planning 在 yaml 里手写了 `trigger_on: pending`。所以「保留原声明」和「强制赋值」两种实现产出完全相同的结果，间接测试对此**不可区分**。

而真实风险恰恰在当前输入空间覆盖不到的地方：

- 将来 planning 被某个 profile 裁掉
- 将来有 fragment 插到 planning 之前
- 将来 `_core.yaml` 里 planning 的 trigger_on 被改掉

三种情况下「保留原声明」都会让工单卡死。

补了 `test_t11c2_relink_forces_entry_status_on_first_stage`，**直接测 `_relink_stage_transitions` 的契约**：构造一个首个阶段声明了孤立 trigger_on 的列表，断言被改写成 pending。顺带覆盖 branch_only 排最前的情形、`entry_status` 可定制、不 mutate 输入。再注入缺陷，立刻变红。

**可复用判断**：当一个测试要验证「某个强制行为」，先问「现有输入下，不做这个强制会不会产生相同结果」。会，就说明测试测不到它，必须下沉到被测函数的直接契约。
