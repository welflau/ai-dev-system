背景

体检文档 docs/20261123_01_项目问题与缺失分析.md 的第 10、11、12 条（核心文件过大、宽泛 except、 分层治理只完成一部分）在第一批修复里标成了「长期项」。本轮把这三条展开成一份可以分阶段执行的重构方案。

分析方法

全部用一次性脚本对工作区做静态统计，外加一轮带覆盖率的全量 pytest：

  • AST 统计函数长度、圈复杂度、嵌套深度、宽泛 except。
  • 正则统计 db. 调用、SQL 字面量、json.loads、时间调用、工单状态写入点。
  • python scripts/check_layers.py --json 取延迟导入、未归层模块、方向违规。
  • git log --since=2026-08-24 --name-only 统计近三个月的改动分布。
  • python -m pytest --cov=. --cov-report=json:<文件> 取覆盖率，再按文件范围过滤。
  • frontend/app.js 只做正则计数。

脚本和覆盖率数据放在系统临时目录，没有入库。方案的 R0 第 1 步会把度量固化成 scripts/code_metrics.py。

主要发现

  1. 最该拆的函数几乎没有测试。 自有后端代码语句覆盖率 26.9%（12,646 / 46,998）。 process_ticket（682 行）0%，_handle_agent_result（1,026 行，圈复杂度 153）6%， _call_cli_stream（493 行）0%。
  2. 改动集中在大文件。 近三个月 112 个提交里 58 个碰了 11 个大文件，frontend/app.js 占 38 个。
  3. 没有数据访问层。 业务代码里 db. 调用 1,038 处、114 个文件，其中 api/ 543 处、 orchestrator.py 185 处；工单状态写入点 54 处。Database 没有事务接口。
  4. 前端是单个脚本。 app.js 35,912 行，1,079 个顶层函数，163 个可变全局变量，767 处内联 onclick。
  5. 分层守卫有盲区。 230 个未归层模块里有 83 个是真实业务模块，不受方向律约束； 存量 92 条方向违规里，47 条是 api.* 直接导入 L3，27 条是 L3 导入 llm_client， 其余 18 条分散在 orchestrator、plugins.registry、sop 等处。

方案摘要

顺序的依据是第 1 条发现：先补测试，再动结构。

阶段 内容
R0 度量脚本加基线棘轮，CI 加覆盖率，给巨型函数补特征测试，83 个业务模块补进 layers.toml，根目录 77 个下划线脚本归位
R1 新增 repositories/，Database.transaction()，ticket_state.transition() 收口状态写入，PRAGMA user_version 迁移
R2 拆 orchestrator.py：结果处理器注册表，process_ticket 分步管线，按职责拆协作者类；清 6 条方向违规
R3 main.py 的 25 个路由迁出，api/chat.py 等改成包，路由不写 SQL；清 API 层的 50 条方向违规
R4 llm_client.py 拆成 llm/ 包并保留兼容层，清 llm_client 相关的 28 条方向违规
R5 前端先加 node --check、ESLint、Playwright 冒烟，再按分节拆文件，最后转 ES 模块
R6 异常处理、延迟导入、UE action 公共基类、时间处理、状态判断；清剩余 8 条方向违规

R2、R3、R4 在 R1 之后可以并行，R5 独立。

校对中修正的问题

方案初稿写完后复核，改了五处：

  1. 把 elif 链误读成了嵌套。 初稿写「ArchitectAgent 分支 654 行，里面嵌着 DevAgent 和 ReviewAgent」。 AST 里 elif 表示成 orelse 中的 If 节点，取 end_lineno - lineno 得到的是从该分支到链尾的长度。 沿 orelse 逐段量之后的实际结构：前面 5 个独立 if 块（ArtistAgent 53 行、ArtAgent 28 行、 UXAgent 28 行、PlannerAgent 31 行、UEEditorAgent 56 行），后面一条 654 行的链 （ArchitectAgent 74、DevAgent 187、ReviewAgent 50、ProductAgent 验收 72、TestAgent 178、DeployAgent 85）。

  2. 数据访问的统计混了两个范围。 初稿的 1,190 处 db. 调用、154 个含 SQL 的文件、76 个查 projects 的文件 都把根目录 77 个下划线脚本算了进去，而「去重后 486 种」又是不含脚本的口径。统一成不含脚本： db. 调用 1,038 处、114 个文件；SQL 字面量 804 处、107 个文件、去重 489 种； 直接查询 projects / tickets / ticket_logs / requirements 的文件 55 / 37 / 34 / 19 个。

  3. traits 的 json.loads 计数偏大。 初稿的 45 处来自一个同时匹配 traits 和 .get( 的正则。 改成：json.loads 共 203 处、66 个文件，其中至少 18 处是在解 traits。

  4. 时间调用的描述不完整。 31 个文件是 datetime.now( 和 utcnow() 合计且含脚本的结果。 改成不含脚本的 46 处、29 个文件，并写明两种调用都算。

  5. 方向违规的归因错了。 初稿和体检文档都写 92 条方向违规全部（或大多）是 L3 → llm_client， 方案据此把「清掉 92 条」整个放进了 R4。这个说法是看守卫输出的前十几行得出的，那几行按字母序排， 恰好都是 actions.* → llm_client。跑基线验证时读了 --json 的完整列表，实际分布是： api.* → L3 47 条，L3 → llm_client 27 条，orchestrator → L3 6 条，plugins.registry → L3 / L2 5 条， L3 → L1 其他模块 4 条，sop.* → L3 2 条，llm_client → L3 1 条。 修正后违规按归属分到四个阶段：R2 清 6 条，R3 清 50 条，R4 清 28 条，R6 清 8 条。 R3 因此多了一步，并且带出一条约束：services/ 归 L1，把代码从 api/ 挪过去不会让违规消失， 要经注册表或 runtime_facade 取 action 和 Agent。 同一处还改了两个引用：ProviderRegistry 在六层方案里属于 P2，初稿写成了 P3； L3 里导入 llm_client 的语句实测是 41 条、27 个模块，初稿的 62 处没能复现，已替换。

教训：同一张表里的数字要出自同一个文件范围；统计 if / elif 时要沿 orelse 分段； 守卫的截断输出不能用来下「全部是」的结论，要读完整列表。

基线验证

动手重构前对当前工作区（HEAD 7b9e7f0 加全部未提交改动）跑了一遍，作为 R0 的起点：

  • 全量 pytest：868 个用例全部通过，退出码 0，Windows、Python 3.14.3，连续跑了两遍，结果一致。
  • 分层守卫：退出码 0；SCC 0 组，方向违规 92 条，相对基线新增 0 条，未归层模块 230 个，延迟导入占比 43.0%。

没有验证的部分：Linux 和 CI 上的实际运行、真实服务启动、浏览器端到端、桌面版打包。 868 个用例的覆盖率是 26.9%，所以「全部通过」对 process_ticket 这类零覆盖的函数没有保护作用。

遗留与后续

  • 方案第九节列了 5 个需要评审决定的事项：目标数值、根目录脚本归档还是删除、R4 的协议下沉时机、 前端是否接受「不引入构建工具」、R2–R4 的先后顺序。
  • 重构要从干净的工作区开始。目前工作区里还有 ai_gen_tasks 改动和第一批修复，都没有提交。
  • 覆盖率只在 Windows、Python 3.14.3 下量过一次。
  • 圈复杂度是按 AST 分支节点数自算的，和 radon、mccabe 会有小的出入。
  • 没有审读业务逻辑的正确性，方案只基于结构和度量。

复核命令

# 分层守卫（延迟导入、未归层模块、方向违规），在仓库根目录执行
python scripts/check_layers.py --json

# 覆盖率，在 backend/ 下执行；输出文件放到仓库外，避免留在工作区
cd backend
python -m pytest --cov=. --cov-report=json:$env:TEMP\cov.json
cd ..
