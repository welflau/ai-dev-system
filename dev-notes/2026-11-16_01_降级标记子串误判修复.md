# 降级标记子串误判修复（TK-20261110-48b6af）

## 现象

WebRacing3D 工单「初始化项目脚手架与技术栈」时间轴反复出现：

```
仅产出降级模板，非真实实现（[PlanAndChange] 按确定性文件清单初始化
Vite + TypeScript + Three.js 项目骨架，禁止降级占位。新建 7 个文件：pa）
```

## 根因

`backend/agents/dev.py::_do_develop()` 用**子串**判断 `dev_result.notes` 里有没有「降级」二字（2026-11-10 当时为 `elif "降级" in dev_notes`，后收窄为 `"[降级]" in dev_notes`），命中即判「仅产出降级模板，非真实实现」。

而 `PlanCodeChangeAction` 的 notes 是 LLM 生成的规划摘要：`f"[PlanAndChange] {plan.summary}"`（`backend/actions/plan_code_change.py:350`）。反思 prompt 反复强调「别造空壳 / 禁止降级占位」，LLM 就把「禁止降级占位」写进了摘要本身 —— **明明产出了 7 个真实文件，却因为摘要里含「降级」二字被判成假成功**。

数据库实测（`backend/data/ai_dev_system_new.db`，`ticket_logs` 中 `2026-11-10T00:38:19` 的 reject）：

| 字段 | 值 |
|---|---|
| `file_count` | `7` |
| `files` | `package.json` / `tsconfig.json` / `vite.config.ts` / `src/main.ts` / `src/types/scene.ts` / `src/utils/math.ts` / `src/index.ts` |
| `notes` | `[PlanAndChange] 按确定性文件清单初始化 … 禁止降级占位。新建 7 个文件：…` |
| `notes` 含 `降级` | 是 |
| `notes` 含 `[降级]` | **否** |

判定 → `development_failed`（`dev.py:212`）→ SOP `development_retry` → `fix_issues` 反思重开发。反思只往 prompt 注入「别造空壳」、不改变内容源与判定逻辑，所以下一轮摘要又写「禁止降级占位」→ 同样误判 → **确定性逐轮复现**，这就是「老是出现这个错误」的原因。

## 修复

`backend/agents/dev.py`：降级判定从「notes 子串」改为「标记位置 + 实际产出」双条件：

```python
elif dev_notes.startswith("[降级]") and len(code_files) <= 1:
    fail_reason = f"仅产出降级模板，非真实实现（{dev_notes[:80]}）"
```

理由：真正的降级模板只有 `backend/actions/write_code.py::_fallback()` 的 `notes="[降级] 规则引擎"`（`:148`）或增量硬失败分支（`:128`），且最多产出 1 个 `index.html` / `main.py`（`:135-150`）。`[PlanAndChange]` 前缀 + 多文件 = 真实产出，不该被拦；真降级模板仍被拦截。

只改判定条件，不动内容源、不动防假成功护栏、不改数据库。

- `python -m py_compile backend/agents/dev.py`：OK

|---|---|---|

## 关联

这个具体误判在 2026-11-10 之后已被收窄过一次（`"降级"` → `"[降级]"`），数据库里最新一条该报错停在 11-10，本次修复是防止 LLM 写出带方括号的 `[降级]` 时再次误杀。

但**同一工单仍在循环**，只是报错换成了另一条路径：`write_code.py:121-133` 的「LLM 输出无效。项目已有代码，增量修改不能用降级模板」→ `development_failed` → 5 次后 `blocked` → `api/tickets.py:1702` 的 `unblock` 清零计数续命。只读 DB 实测（`2026-11-16T20:47`）：`status=blocked`，累计 **344 次 llm_call / 25 reject / 20 reflection / 4 轮 blocked→unblock**。

该循环的根因与完整调用链已查明，并于同日实施熔断加固，见下节。

## 治本：脚手架工单走确定性路由（同日续二）

### 根因

`agents/dev.py::_do_develop()` 用 **`existing_code` 是否为空** 区分「全新生成 / 增量修改」。这个判据对「初始化项目脚手架与技术栈」类工单本身就是错的：

- 项目 clone 时写入 `README.md` / `.gitignore`，第一轮降级模板产出的空壳 `index.html` 也会被 `self_test` 落盘；
- 于是 `existing_code` 从第二轮起恒非空 → 走 `plan_code_change`（增量）→ 规划为空 / 零产出回退 `WriteCodeAction` → `write_code.py:121-133` 的「已有代码不许用降级模板」硬失败 → `development_failed` → `fix_issues` → 再落入同一分支，**确定性自锁**。

数据库实证：`TK-20261110-48b6af` 最近 15 条 reject 全部是同一句报错，`llm_call` 累计 344 次。继续调 `existing_code` 语义治不了本，必须给脚手架工单一条**独立的内容源路由**。

### 方案（不动护栏）

新增一个**不经 LLM 的确定性骨架 Action**，在 `dev.py` 的代码生成分支前置路由。不修改 `write_code.py` 的 `_fallback`、`plan_code_change.py`、SOP 配置、插件注册或任何既有护栏。

**新增文件**

| 文件 | 作用 |
|---|---|
| `backend/actions/scaffold_utils.py` | `is_scaffold_ticket(context)` 识别谓词 |
| `backend/actions/scaffold_web.py` | `ScaffoldWebAction`：读模板、token 替换、落盘、返回 `files` |
| `backend/actions/scaffold_templates/vite-three/` | 8 个真实骨架文件（见下） |

**改动文件**

| 文件 | 改动 |
|---|---|
| `backend/agents/dev.py` | 新增 `_run_scaffold()`；`_do_develop()` 在 `existing_code` 分支**之前**插入 `elif scaffold_result is not None`；`hard_fail` 纳入 `_scaffold_failed`（模板缺失 / 写盘失败直接 blocked，不空转） |

**识别判据**（四条同时满足，任一步不确定返回 `False` 回退原路径，借鉴 `ticket_classifier.py:15`「只降级不升级」）：

1. `traits` 含 `platform:web` 且（`lang:typescript` 或 `lang:javascript`）；
2. 标题 + 描述命中脚手架关键词 ≥ 2 个（初始化 / 脚手架 / 技术栈 / 项目骨架 / 目录结构 / 统一入口 / 类型定义 / 共享工具 / 工程配置 / …）；
3. 拆单 DAG 根节点：`sort_order == 0` + `dependencies == []` + **被同需求其它工单依赖**（查 `tickets` 表，不改 orchestrator 的 context 注入）；
4. 排除 `type in {bug, bugfix, hotfix}`。

实测：`TK-20261110-48b6af`（脚手架首单）→ `True`；`TK-20261110-de9d1d`（业务功能单，`sort_order=2`）→ `False`。

**骨架内容**（`vite-three/`，8 文件）

```
package.json        three + @types/three + vite + typescript，dev/build/preview/typecheck 脚本
tsconfig.json       strict / noEmit / moduleResolution bundler，无 phaser types
vite.config.ts      defineConfig + base "./" + outDir dist
index.html          <canvas id="app"> + /src/main.ts 入口（替换空壳）
src/main.ts         Three.js 最小渲染循环（Scene/Camera/Renderer/RAF），import 自建 types+utils
src/types/scene.ts  ViewportSize / SceneContext 共享类型层
src/utils/math.ts   clamp / lerp / degToRad 共享工具层
README.md           目录说明与 npm 命令
```

`package.json` 显式声明 `three` 与 `@types/three`，正好堵住之前验收打回的「`package.json` 未声明 three 依赖，`npm install` 后无法编译运行」。产物是**覆盖式写入模板列出的 8 个文件**（脚手架工单是依赖图根节点，业务模块在后续工单里做），重复执行幂等、不碰仓库其它文件。

**为什么不破坏防假成功护栏**

- notes 用 `[Scaffold]` 前缀而非 `[降级]`，且产出 8 个文件（>1）→ 不命中 `dev.py` 的降级判定；
- 无 `console.log` 空壳、无 `[LLM_UNAVAILABLE]` 占位；
- `success=True` 且 `files` 非空 → 通过 `self_test` 的 7 项检查与磁盘落地验证；
- **完全不改** `write_code._fallback` 的 `if existing_code:` 硬失败分支，`_test_false_success_gates.py` 组 3 的 7 条断言全部保持；
- 失败路径返回 `_scaffold_failed` → `hard_fail` → `blocked`，不伪装成可重试的 `development_failed` 空转。

**回滚**：`sop_config.enable_scaffold_action = false` 可线上秒关；删掉 `dev.py` 的前置分支即 100% 回到原路径。
