背景

TicketOrchestrator.handle_requirement 负责需求分析和拆单：调 ProductAgent、把回传的工单落库、回填依赖、 建开发分支、逐张派单。上一篇结束时它是 orchestrator.py 里最长的函数：456 行，圈复杂度 65，行覆盖率 1%。 没有测试就没法动它，所以本轮分两段做：先补特征测试并确认测试抓得住错误，再按 process_ticket 的做法拆成分步管线。

做了什么

1. 特征测试

新增 backend/tests/agents/test_orchestrator_handle_requirement.py，44 个测试函数，参数化后 63 条：60 条写在拆分之前，3 条是拆分之后补的（原因见「验证」一节）。 特征测试只记录现在的行为，不评判对错。

夹具。 沿用 test_orchestrator_process_ticket.py 的做法：真实 SQLite 加 init_tables()， 用 TicketOrchestrator.__new__ 造实例，只设 _analyzing_reqs 和一个假的 ProductAgent。 需求初始状态是 analyzing。

真跑的部分：_log、建工单、建子任务、建子工单、回填依赖、需求状态改写、PRD 产物入库。

八组用例：

  1. 入口：已在分析、需求不存在、分析途中再次调度。
  2. 准备和执行：开场文案、模型名和超时的取值顺序、代码上下文、项目 traits、on_step 进度、心跳、心跳失败被吞。
  3. Agent 失败：回传非 success、抛异常、被取消、取消后被轮询续跑、错误兜底自身失败。
  4. 记录结果：PRD 入库、产物、规则引擎降级告警、投票留痕、PRD 文件走 Git。

  6. 回填依赖：下标换工单号、自引用、越界、字符串依赖、夹了坏数据时的下标。
  7. 收尾：状态、里程碑、分支（成功、切换失败、创建失败、Git 抛异常）、零工单、派单顺序。

44 个测试函数里有 14 个在结束前查占用标记已释放、没有残留的心跳任务，覆盖正常走完、重复调度、Agent 失败、 异常兜底、取消、零工单这几种出口。其余 30 个只查各自关心的结果。

2. 确认测试抓得住错误

覆盖率。 首版 56 条跑完，handle_requirement（原第 1552–2007 行）的 190 条语句全部执行到， 54 个分支走到 52 个。漏的两个分支都在依赖处理里：依赖全是认不出的值时建单日志不带依赖信息； 字符串形式的工单号指向自己。补 2 条之后是 190/190 条语句、54/54 个分支。此前的行覆盖率是 1%。

改坏检查。 覆盖率只说明代码被执行过。在原函数上逐个做 105 处故意的错误改动 （条件取反、事件改名、默认值改掉、字段丢弃、顺序对调等），每处只跑这一个测试文件，结束后恢复并核对哈希。 第一遍发现 104 处，漏 1 处：把「查不到需求就返回」的判断去掉。去掉之后函数会往下走、 在取标题时出错、进异常兜底；兜底里写日志撞外键，被最外层的 except 吞掉。库里和事件上都看不出痕迹， 原用例只查了这两处。给 test_missing_requirement_returns_quietly 加一条「没有 error 级日志」的断言后，这一处也被发现。

检查过程中又补了 2 条用例，记的是读代码时注意到的行为：

  • test_cancelled_analysis_is_picked_up_by_resume_poll：分析被取消后，下一轮 _resume_stuck_analyses 会重新拆单；
  • test_dependency_indexes_follow_filtered_list：回传里夹一条坏数据时，依赖下标整体错一位。

另有一条用例重写了造数据的方式。test_string_dependency_on_itself_is_dropped 原来靠替换 orchestrator.generate_id 拿到固定工单号，这等于把测试绑在「拆单代码住在 orchestrator.py」上， 拆分之后就会失效。改成在建单日志写入时把真实工单号追加进依赖列表，不再依赖代码位置。 改完后重跑了和依赖有关的 3 处改动，都被发现。

到这里测试文件是 60 条。拆分期间没有改它；拆分后的改坏检查又补了 3 条，见「验证」一节。

钉住的可疑现状

下面这些都按现在的样子写进了断言，本轮没有修。前三条会直接影响用户。

  1. 拆单不在事务里，重试会重复建单。 建工单到一半出错时，已经建好的工单留在库里，需求退回 submitted。 用户点重试，会把全部工单再建一遍。触发方式之一：Agent 回传的某张工单 subtasks 是 None。
  2. 派单出错会把需求退回已提交。 逐张派单时任何一张抛异常，都走同一个兜底：需求从 in_progress 退回 submitted， 工单和分支留着，排在后面的工单这一轮不再派。日志写的是「从 analyzing 到 submitted」，和当时的真实状态不符。
  3. 零工单照样进行中。 Agent 一张工单都没拆出来（空列表、None、不是列表、全是坏数据）， 需求照样走到 in_progress，开发分支照建。
  4. 依赖下标按过滤后的列表算。 回传里不是字典的条目会被滤掉，依赖下标却是 Agent 按原始列表写的。 夹一条坏数据，它后面的依赖就整体错一位，可能指向别的工单，也可能指向自己后被当成自引用丢掉。
  5. 规模按原始条数算。 同一批数据里，被滤掉的条目不建工单，但计入条数，影响工单的起始状态。
  6. 异常路径不清 LLM 上下文。 Agent 抛异常时跳过了 clear_llm_context，上下文里留着这条需求的信息。
  7. 取消时需求停在分析中。 CancelledError 原样抛出，不写日志也不发事件。占用标记会释放， 所以下一轮 _resume_stuck_analyses 会把它重新拆一遍。续跑日志固定写「进程重启后中断」，被取消的情况也用这句话。
  8. 建单日志的目标状态固定写 pending，和工单真实的起始状态（可能是 architecture_done 或 planning_done）无关。
  9. 建单日志里的依赖不滤自引用。 落库的依赖滤了，日志里会把自己也列进去。
  10. 子工单的处理和父工单不一致。 不继承需求级 use_aigc，不写建单日志，不计入拆单数量，不在这里派单，起始状态固定 pending。
  11. Agent 回传非 success 时不发 requirement_error，Agent 抛异常时才发。全仓只有 orchestrator.py 发这个事件， frontend/ 里没有任何地方监听它，所以目前两种情况在界面上都只能从日志（log_added）看出来。
  12. 只有空白的步骤名不回落到默认文案。 analysis_progress_message 对空字符串和 None 会写「等待 LLM」， 对 " " 这样的值不会，去掉空白后心跳文案的冒号后面什么都没有。
