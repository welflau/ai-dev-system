## 二、四种边界的裁决都是有代价的选择

### a) 缺源 → fixed-point 级联

单轮过滤会留下一串拿不到输入的 skill——它们会在**运行期**卡住，而不是组装期就被排除。所以必须迭代到稳定：A 出局 → 它产出的 kind 消失 → 依赖它的 B 跟着出局。

注入「改成单轮」验证：2 个测试红（`cascades_fixed_point` + `partial_cascade_keeps_independent_chain`）。

用 info 级日志而非 warning——缺源不是错误，是「这个项目用不上这个能力」。真正的错误（kind 拼错）已在 discover 的 lint 拦下。

### b) 歧义（一 kind 多 producer）→ 剔除落选者，不「都装」

两个 skill 产出同一 kind 会在同一路径互相覆盖，`latest_per_kind` 取到谁取决于执行顺序，产物总线语义被破坏。真要分叉应该用不同 kind。

裁决 `(-priority, stage_id)`——同 priority 按字典序，保证**可预测**（否则测试写不了）。

注入「都装」验证：3 个测试红。

### c) 成环 → 整条链不组装，**健康的 skill 也一起不组装**

这条最反直觉，专门写了 `test_cycle_also_drops_healthy_skills`。

理由：拓扑序断了就无法保证剩下那部分的执行顺序正确。部分组装会产出「看着能跑但中间断链」的 SOP——orchestrator 把工单推到某个状态后再也找不到下一条规则，静默卡死。宁可退化成纯 fragment SOP（`compose_sop` 会照常工作）。

注入「成环时返回已排好的部分」验证：对应测试红。

### d) 同层稳定 → heap + `(-priority, stage_id)`

不用 heap 的话同层顺序取决于 dict 迭代序，测试写不了、线上不可复现。

另外单独测了 `test_priority_does_not_override_dependency`：**依赖是硬约束，priority 只在同层生效**。低 priority 的 producer 仍必须排在高 priority 的 consumer 之前，否则下游拿不到输入，排序就失去意义。

## 三、一个测试从「断言 key 不存在」升级成「断言后果」

初版：

```python
assert "reject_goto" not in stage
```

注入「加回 reject_goto」确实能抓到，但这个断言太弱——它只说明字段没了，没说明**为什么不能有**。

补了 `test_no_retry_rule_is_derived_for_skill_stages`，直接走 `sop_to_transition_rules` 验证后果。实测带 reject_goto 时派生出：

```
pending            → SkillAgent.skill_demo_draft
demo_draft_failed  → SkillAgent.skill_demo_draft    ← 无限重试
```

工单一失败就重跑同一个 skill，再失败再重跑，唯一止损是全局 `max_retries=5`。对一个 LLM 自由发挥、每轮烧 token 的 skill 来说，这是最糟的默认行为。

**判断标准**：断言「某字段不存在」时，要问「这个字段存在会导致什么」，然后把那个后果也测了。前者是实现细节，后者才是契约。

## 四、复用 `_fragment_matches` 而非自己写匹配

```python
def _matches(skill, traits_set, ticket_type):
    from sop.loader import _fragment_matches
    return _fragment_matches({
        "required_traits": skill.required_traits,
        "required_ticket_type": skill.required_ticket_type,
    }, traits_set, ticket_type)
```

把 WorkflowSkill 包成 frag 形状喂进去。同一套 all_of/any_of/none_of 语义，不建第二份解析——两份解析迟早会漂。

顺带测了一个隐蔽场景 `test_trait_filtered_out_producer_cascades`：**被 trait 过滤掉的 producer 同样会让下游缺源**。这比「skill 自己不匹配」更难发现——下游 skill 的 trait 条件是满足的，它只是碰巧依赖了一个不适用于本项目的上游。

## 五、并行度损失被量化

```
检测到 2 处可并行但已串行化 —— orchestrator 的状态链是单链模型，
阶段间并行需走「阶段内扁出子工单」(dispatch_subtask)
```

拓扑序本能表达「A、B 并行后汇入 C」，但 `_relink_stage_transitions` 会压平成串行链（`transition_rules` 是 `Dict[status → rule]`，一个状态只能映射一条规则）。

本次不解决，只把损失写进 diagnostics。严格线性链不刷这条（`test_strict_chain_has_no_parallel_note`）——无意义的 diagnostic 会让真正的问题被淹没。

## 六、自环的兜底是「继续排序」而非「崩掉」

自环（consumes 和 produces 同一 kind）已在 `discover_workflow_skills` 的 lint 拦下。真跑到 composer 说明有人绕过 discover 直接调（如测试）。

此时处理成「skill 自己产出自己的输入 → 视为源已就绪，继续排序」，而不是整条链崩掉。理由：这是防御性兜底，不该比正常路径更严厉。
