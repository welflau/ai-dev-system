## 一、做了什么

`artifacts` 表增加 4 列，**两处都写**：

| 列 | 定义 | 用途 |
|---|---|---|
| `kind` | `TEXT` | kinds.yaml 登记的 kind，新框架的语义主键 |
| `mime` | `TEXT` | MIME 类型，二进制产物靠它区分 |
| `size_bytes` | `INTEGER DEFAULT 0` | 文件字节数（inline 产物恒 0） |
| `produced_by` | `TEXT` | skill_id 或 agent_name |

```
database.py SCHEMA_SQL 的 CREATE TABLE  → 新库一次建全
database.py _auto_migrate 的 migrations → 老库 ALTER TABLE 补
```

## 二、为什么必须两处都写

这是 `_auto_migrate` 机制的本质，之前没想透：

- **只写 SCHEMA_SQL**：老库的 artifacts 表已存在，`CREATE TABLE IF NOT EXISTS` 对它是 **no-op**，新列永远补不上。
- **只写 migrations**：新库能跑，但建表语句与实际结构脱节，后来者读 SCHEMA_SQL 会以为没有这些列。

两条路径分别由 `test_fresh_db_has_all_columns` 和 `test_migration_on_legacy_db` 守。注入验证过：去掉任一边，对应测试立刻红。

## 三、刻意不建索引，并把这条做成测试

`database.py:1002` 的既有警告（ticket_command_log 上方）说：

> 建表和索引必须都在 SCHEMA_SQL 里一次给全，不要把列挪去 `_auto_migrate`：
> `init_tables` 先 `executescript(SCHEMA_SQL)` 再迁移，而 `executescript`
> **一条语句失败会整段中止**。

对这 4 列而言结论是反过来的：**它们必须走 migrations，因此绝不能有索引引用它们**。老库升级时 `CREATE INDEX ... (kind)` 会在 `ALTER TABLE` 之前执行，该列尚不存在 → 整段 SQL 中止 → 其后所有建表全废。

加了 `test_no_index_references_new_columns` 用正则扫 SCHEMA_SQL。注释拦不住「顺手给 kind 加个索引」，测试能。

实测注入这条索引：**6 个测试同时红**，其中专防它的那条第一个报警。这是本轮最该防的退化。

性能上也不需要：查过线上数据，`artifacts` 单工单最多 436 条，按 `ticket_id` 的既有索引足够。

## 四、刻意不回填 `kind = type`

存量 2246 条的 `kind` 全是 NULL、`size_bytes` 全是 0。

回填看着很顺手，但那等于**声称老产物符合 kinds.yaml 的 file 存储契约**（内容在磁盘、path 有效）。而它们的内容其实在 `content` 列里（上一轮实测：2246 条 content 全非空，path 只有 10 条非空）。一旦 ArtifactStore / injector 按「kind 非空就当文件读」处理，会全线落空。

正确做法是读取侧用 `COALESCE(kind, type)` 区分两套语义。写成了 `test_migration_leaves_existing_rows_unfilled`。

## 五、踩到的坑：测试挂死 2 分钟，不是报错

第一版测试跑起来**完全无输出地挂死**，pytest 被 kill 两次。

### 根因链

1. 第一版 `_make_legacy_db` 只手搓了 artifacts + 3 张 FK 目标表
2. `init_tables` 末尾会调 `_ensure_default_sessions` / `_ensure_global_project`，它们要写 `chat_sessions` 和 `projects`（带 `description` 等列）
3. 抛 `table projects has no column named description`
4. 异常从 `await` 抛出 → **跳过了 `await db.disconnect()`**
5. aiosqlite 用一个**非守护**的 worker 线程跑所有 SQL，漏掉 disconnect 该线程不退出
6. Python 卡在解释器退出阶段 → 测试进程永不结束

用 `faulthandler.dump_traceback_later(25, exit=True)` 才定位到第 3 步。

### 两处修复

**a) stub 改成「先建全再降级」**

```python
conn.executescript(SCHEMA_SQL)          # 完整 schema
conn.executescript("""
    ALTER TABLE artifacts RENAME TO _artifacts_v20;
    CREATE TABLE artifacts (...10 个老列...);
    DROP TABLE _artifacts_v20;
""")
```

绕，但必须这样。附带好处：更贴近真实升级场景——真实老库的其它表本来就是全的。

**b) 加 `_migrated_db` 异步上下文管理器**

```python
@asynccontextmanager
async def _migrated_db(db_file):
    db = Database(db_path=str(db_file))
    await db.connect()
    try:
        await db.init_tables()
        yield db
    finally:
        await db.disconnect()      # ← 保证执行
```

5 个测试全改用它。

### 验证修复确实有效

修完后重跑注入 A（去掉 migrations）：**挂死变成了 5 个正常的 FAILED**，带完整断言信息。

### 可复用的判断

**写涉及 aiosqlite 的测试时，永远不要裸写 `connect(); ...; disconnect()`。** 任何中间步骤抛异常都会让「测试失败」退化成「进程挂死」——后者的排查成本高一个数量级，因为你连 traceback 都看不到。

更一般地：**当测试表现为挂起而非失败时，先怀疑资源未释放，而不是怀疑被测代码死循环。**
