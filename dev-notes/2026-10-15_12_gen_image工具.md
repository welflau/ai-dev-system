```
backend/skills/runner.py              builtin 池 +7 行
backend/tests/actions/test_gen_image.py  27 用例
```

声明方式：

```yaml
x-runner:
  builtin_tools: [write_file, "gen_image:images"]   # 图落到 outputs.root/images/
  outputs:
    globs: ["draft.md", "images/*.png"]
  budget: {max_seconds: 900}
```

`gen_image:<subdir>` 的冒号语法配合 `images/*.png` 这个 glob，让**一次产出 N 张图归同一 kind**——不必为每张图声明一条 produces。

## 二、两个刻意的选择

### a) 阻塞等待，不返回 request_id

REACT 循环是单线程顺序推理。返回 request_id 会逼 LLM 自己写「查状态 → 没好 → 再查」的循环，每次查询烧一轮 turn，还容易卡死在「再查一次」。

`_poll_lightai_task` 内部是 `await asyncio.sleep`，不卡事件循环。代价是占 `budget.max_seconds`——这正是上一轮 orchestrator 加「超预算但 produces 齐全则豁免」的原因（`Budget.check()` 只在轮间生效，生图跑完回来下一轮开头就可能触发超时，而图已落盘）。

### b) 不走 `image_requests` 表 + 占位符

`image_processor.process_image_request` 服务的是「文档先写、图后补」：写 `[IMG_PENDING:id]` → 后台轮询 → 回填。

skill 链的语义是**产物必须在 stage 结束时就绪**——下一个 skill 的 consumes 会立刻去读文件。占位符那套会让下游拿到一个还没有图的路径。

所以只复用底层三个函数，不碰那张表。

## 三、四道前置校验（都在调 API 之前）

| 校验 | 不做的后果 |
|---|---|
| prompt 非空 | 白花一次钱 |
| filename 白名单 | 见下 |
| `_skill_output_root` 存在 | 往仓库里乱写二进制文件 |
| `LIGHTAI_API_KEY` 配置 | LightAI 返 401 → 变成模糊的「生成失败」 |

**filename 是拒绝而不是改名**：改名会让 produces 的 glob 匹配不上，LLM 以为成功了但 `_collect_outputs` 回收到空——stage 判 partial 却看不出原因。

白名单挡的是 `../x.png` / `sub/cover.png` / `cover.exe` / 无扩展名 / 含空格。

另外加了**零字节检测**：下载成功但文件为空时判失败。不拦的话 `_collect_outputs` 会把空文件当成功产出回收，下游拿到坏图却显示「产出齐全」。

## 四、严重失误：`git checkout` 清掉了三轮改动

做注入 D 的清理时用了：

```bash
git checkout backend/skills/runner.py      # ← 还原到 HEAD
```

`runner.py` 从未提交过，这一条把任务 **#8、#12、#14** 对它的全部改动抹掉了：

- #8 `ArtifactOut` / `text_outputs` / `output_paths` / `_collect_outputs` 重写
- #12 `_build_system` 的上游产物渲染
- #14 `gen_image` builtin 注册

发现方式：紧接着 grep `gen_image` 返回 0 行。已逐段手工重建并验证：

```
#8  outputs 是 list: True
#8  二进制标记+kind: [('a.md', False, ''), ('c.png', True, 'cover_image')]
#8  text_outputs 跳过二进制: ['a.md']
#12 渲染上游产物: True
#14 gen_image 注册: True | subdir: images
```

290 passed 复核通过（与丢失前的 263 + 27 新增一致）。

**教训**：变异测试的还原**必须用 `cp` 从备份恢复**，绝不能用 `git checkout`——这些文件大多未提交，HEAD 版本是几轮之前的状态。本轮其余注入用的都是 `cp /tmp/xx_ok.py`，唯独这一次图省事直接 checkout。

更稳妥的做法是用「反向字符串替换」还原（本轮后续注入已改用这个方式），完全不依赖备份文件。

## 五、第 9 次假绿：被前面的 `if` 接走了

注入 D「`elif bt == "gen_image"` 改成 `elif True`」→ 全绿。

原因：`test_not_registered_when_undeclared` 的输入是 `["write_file"]`，它被 `_build_actions` 的**第一个 `if` 捕获**，根本进不到 gen_image 那条 `elif`——条件改成什么都无所谓。

改成用 `mcp__openspec__validate`（真实存在的声明，在 executor 层处理，`_build_actions` 里应当一个 Action 都不建）作为输入，再注入立刻红。

### 假绿形态累计 9 种

| # | 形态 |
|---|---|
| 1 | 场景在当前实现下不可能发生 |
| 2 | 两种实现产出相同结果 |
| 3 | 输入恰好触发了兜底路径 |
| 4 | 调用次数不够 |
| 5 | 代码路径无任何断言覆盖 |
| 6 | 返回值相同，差异只在副作用 |
| 7 | 测试绕过集成点，只测内部函数 |
| 8 | 通过靠的是别处的过滤，不是被测逻辑 |
| 9 | **输入被更早的分支接走，没到达被测分支** |

9 和 8 同源：**测试输入没有真正进入被测代码路径**。

补充判断：

> 测分支条件时，确认输入**真的会走到那个分支**。if/elif 链里，前面任何一个
> 条件先命中，后面的条件改成什么都测不出来。

## 七、新增测试（27 个）

LightAI 三件套全部打桩——真调一次 30-300 秒且花钱。但参数校验、路径解析、失败分支、零字节检测都是纯逻辑，必须真跑：**它们才是这个 Action 里会出 bug 的部分**。

| 组 | 用例 | 锁什么 |
|---|---|---|
| schema | 2 | 字段齐全、**description 警告耗时与重复调用** |
| 成功路径 | 4 | 落盘、参数透传、subdir、非法 enum 回退 |
| 参数校验 | 6 | filename 白名单（参数化 7 种）、空 prompt、前置拒绝 |
| 失败分支 | 4 | 建任务失败、poll 无结果、下载失败、零字节 |
| builtin 注册 | 4 | 注册、subdir 语法、共存、**按需注册** |
| 产物衔接 | 1 | 生成的图被回收为 binary + kind 正确 |

`test_description_warns_about_cost` 是个容易被忽略的点：LLM 看不到实现只看 description，不写明「耗时长、别重复调」它会为同一张图反复调用，一张图能耗光整个 skill 的预算。
