## 背景与决策链

从「给个 GitHub 链接自动把外部仓库接成 ADS 插件」讨论到「多 CLI 环境覆盖」，连续几轮澄清：

1. Skill 骨架放在 `.codebuddy/skills/plugin-import/`（项目级、CodeBuddy 单 CLI）。
2. 核实发现 ADS 派单给 CLI 时 cwd 是**被托管项目仓库**或**隔离临时目录**（`backend/llm_client.py:1472-1492`），ADS 不传 skill 目录参数、不改 HOME → 项目级文件对派单无效。
3. 提出路线 A（写装机脚本复制到 `~/.<cli>/skills/`）与路线 B（ADS 主动注入全文）。
4. 用户指出「套件页面点安装就行了吗」→ 核实 `backend/pack_installer.py` 确实是分发器，但被三处限制卡住：`:111-113` 白名单只有 2 CLI、`:312` 目标根固定项目目录、`:289-292` skills 落到 `packs/<pack>/` 子目录；且端点全是 `/{project_id}/packs/...`（`api/projects.py:3632`），`project_packs.project_id NOT NULL`（`database.py:965-971`）。
5. 用户澄清「ADS 调用的 CLI 可以是 CodeBuddy 也可以是 Claude 等等，要能覆盖多个 CLI」，接着提出「安装套件到用户目录，应该可以用户选择」。
6. **本轮拍板**：不写独立装机脚本，直接把「安装范围」做成用户可选 —— 项目级保持原样，新增用户级路径，一次解决覆盖多 CLI / cwd / 换机器 / 复用现成分发器四个问题。按核实出的 7 条改动点落地。

### 实现中的两个取舍（已写进代码注释）

- **用户级不做模板变量替换**：`{{project_name}}`/`{{repo_path}}` 保留原文，避免无项目上下文时被抹成空串（`pack_installer.py` `_install_files` 内）。
- **用户级强制 4 CLI**，不受个别 Pack 旧 `targets` 声明不足限制，保证「一次装好、任意后端可用」。

### 兼容性

- `scope="project"` 为默认值，`create_project.py:311,478` 的自动安装路径完全不变，仍写 `<project>/.{cli}/packs/<pack>/`。
- 项目级端点返回结构未变；用户级端点不写 `ticket_logs`（`project_id NOT NULL`，`database.py:430`），只记 `user_packs`。卸载只删记录不删用户目录文件，与项目级 `remove_pack` 语义一致。
- 前端 `installPack(packName)` 不传 forcedScope 时读面板选择器，缺省 `project` → 老行为不变。

> **措辞订正（安全评审后补，见 `dev-notes/2026-11-19_01` §11/§12）**：提交说明与本文早先写的「项目级行为不变」不够准确 —— 第 7 条把 13 个 `pack.json` 的 `targets` 从 2 个 CLI 扩到 4 个后，**项目级**安装也会跟着多创建 `.cursor/` / `.workbuddy/` 目录（本文 §「未做 / 待办」第 4 条已承认）。准确说法是「项目级安装的**路径与端点语义**不变，但**目标 CLI 集合**由 2 个扩到 4 个」。

### 卸载语义（明确）

`DELETE /api/projects/packs/user/{pack_name}` 与项目级 `DELETE /{project_id}/packs/{pack_name}` 都**只删 `user_packs` / `project_packs` 记录**，不删除已 copy 到 `~/.{cli}/` 或项目目录的文件 —— 这些文件一旦写入即归用户所有。响应 `note` 字段已写明。若需彻底清理，请手动删除对应目录。
