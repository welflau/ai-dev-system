## 三层融合 Step 14 — Partial Flow + SpecVersionManager

### `spec_version_manager.py`（新文件）

**SpecVersionManager**：管理单个工单的 OpenSpec specs 版本。

| 方法 | 说明 |
|---|---|
| `read_current_specs()` | 读取 `openspec/changes/{ticket_id}/specs.md` |
| `snapshot()` | 备份为 `specs.v{n}.md`，返回版本号 |
| `apply_delta(new_content)` | 覆盖写入 specs.md |
| `save_version_to_db()` | 持久化到 `ticket_spec_versions` + 更新 `tickets.spec_version` |
| `current_version` | 当前版本号（备份文件数 + 1） |

**`generate_spec_delta()`**：LLM 生成 specs 增量。
- 输入：current_specs + change_request + affected_specs
- 输出：保留原有场景 + 新增/修改相关场景的完整 specs.md
- 失败降级：在原 specs 末尾追加变更请求作为占位场景

### `orchestrator._partial_flow()`

```
评论"加个需求：导出需要日志"
  → SpecVersionManager.snapshot() → specs.v1.md 备份
  → generate_spec_delta() → LLM 生成含新场景的完整 specs
  → apply_delta() → 写入新 specs.md
  → save_version_to_db() → ticket_spec_versions + spec_version + openspec_stage='proposed'
  → change_count + 1
  → 含架构关键词 → reset_phases("architecture")
    否则         → reset_phases("development")
  → 回复：「规范已更新至 v2，重置阶段：开发→测试→验证」
```

**架构关键词检测**：`架构 / 数据库 / 接口 / API / 数据结构 / architecture / database / schema`

**失败降级**：`_partial_flow` 异常时回落到 `_tweak_flow`，保证工单不卡死。

## 三层融合 Step 15 — Breaking Flow

### `orchestrator._breaking_flow()`

```
评论"改成实时看板吧，不做导出了"
  → 当前工单 status → 'cancelled'
  → LLM 从评论提取新需求标题（_extract_title_from_comment）
  → 创建新工单（source_ticket_id 指向原工单，status='pending'）
  → 原工单留记录：「已关闭，新工单 #xxx 已创建」
  → 新工单留来源记录：「由 #yyy 变更派生，原因：...」
  → ticket_logs layer=harness action=breaking_change
```

**`_extract_title_from_comment()`**：LLM 从评论提取 10-20 字标题，失败用评论前 30 字。

**失败降级**：创建新工单失败时，推 error 级人工介入通知。
