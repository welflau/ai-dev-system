## ComicAI 调研结论（只读，逐行核对）

**ComicAI 的排队只有一块**：`frontend/src/api/index.ts:2551-2582` 的模块级手写信号量
（`_h3cloudActive` + `_h3cloudWaiters` FIFO + `acquire/release`）。
**后端没有任何通用调度器** —— `video_mnmx.py:5` 明写「只做代发+透传，不缓存任务状态」；
`generation.py` / `libtv.py` / `liblib.py` 是三份各自独立的内存结果表 + `create_task`，
全仓 `asyncio.Queue` 零命中。所谓「任务面板」`taskQueueStore` 只是展示层，不做调度。

规则（上游 `Docs/鼠鼠工具-视频生成API文档.md:22`）：闲时 0-8 点每账号 5 并发、白天不限；
一个名额从 acquire（`:2720`，try 之前）到 release（`:2791-2792`，finally）覆盖
提交 + 429 退避 + 轮询 + 取直链全程。查询/下载各 1 次/秒限速见 `:18`。

### 三处缺陷（本次移植时修正，不照抄）

1. `new Date().getHours()`（`:2558`）用**浏览器本地时区**，服务端多机/多用户不一致。
2. acquire 排队期间**不监听 abort**，只在被唤醒时才检查 `signal.aborted`（延迟取消）。
3. 等待**无超时上限**，慢任务占住名额时后来者永久挂起。

另注：ADS `cloud_video/client.py` 头部注释引用的 `index.ts:2504-2747` 是**旧行号**
（ComicAI 文件后续改动过，实际 semaphore 在 `:2551-2582`），已在方案 §16 记录。

## 实现要点

- **动态上限**：`limit_now()` 按时段返回 5 或 0（不限）；`asyncio.Semaphore` 上限构造时固定，
  表达不了「白天不限/闲时 5」，所以自己维护 `_active` + `deque[Future]`。
- **无 Lock**：所有共享状态读写都在**不含 await 的同步段**内，asyncio 单线程天然原子；
  也避免了 `asyncio.Lock` 绑定到某个 event loop 后跨 loop 复用的问题。
- **取消**：`wait_for(fut)` 超时/取消会 cancel 该 fut，`_wake()` 用 `fut.done()` 跳过已放弃的
  waiter，不把名额授予取消的任务；`CancelledError` 分支清理 waiter，无名额泄漏。
- **超时**：`WAIT_TIMEOUT` 到点抛 `CloudVideoUnavailable`，文案明确「未提交，不会改打别的后端」——
  调用方 Plugin 已有 `_blocked()` 分流（`env_missing → blocked`），无需改动。
- **全程占用**：`async with slot()` 的 try/finally 保证异常路径也释放；下载也在名额内
  （与 ComicAI release 在取到 file-url 之后略有差异，更保守）。
- **时区**：`ZoneInfo(IANA名)`，不可用时按 `TZ_OFFSET` 回退到固定 UTC 偏移，
  绝不用服务器本地时区；支持跨午夜时段（如 22-6）。

### 测试自身一处 Python 3.14 兼容问题（已修）

初版在 `asyncio.run()` 之外先构造 `asyncio.gather(*[worker() ...])` →
`RuntimeError: There is no current event loop`。改为在 loop 内 `_gather()` 创建协程。
