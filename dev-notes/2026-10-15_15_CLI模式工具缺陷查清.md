## 一、结论：风险成立，而且比推测的更彻底

`20260802` 方案 §六.5 的推测是「CLI 模式下 skill 声明的自定义工具不生效」。
静态检查证实了它——**不是「传了但被忽略」，是根本没传**。

### 三条证据

```
证据1  LLMClient._call_cli_stream 的参数:
       ['messages', 'temperature', 'max_tokens', 'resume_session_id', 'timeout_override']
       含 tools: False

证据2  QueryEngine.run 的 CLI 分支（165 行）里 `tools` 出现次数: 0

证据3  tools 的唯一消费者:
       engine.py:279  self.llm._call_anthropic_tools_stream(current_messages, tools, system, ...)
```

`tools` 参数走到 `QueryEngine.run` 之后，在 `api_format == "cli"` 的分支里**从头到尾没被提及一次**。

## 二、完整的失败链条

```
SkillRunner._build_actions()  组装 write_file / read_file / gen_image
        ↓  tools = [a.tool_schema() ...] + DONE_SCHEMA
QueryEngine.run(messages, system, tools, context)
        ↓  api_format == "cli"
CLI 分支：只传 messages，tools 被静默丢弃
        ↓
CLI 用自己的原生工具（Write / Read / Bash）
        ↓  原生 Write 的相对路径基于 cwd = projects.git_repo_path（llm_client.py:1407）
文件落在仓库根，而非 outputs.root
        ↓
_collect_outputs 只扫 outputs.root + globs
        ↓
扫不到 → status = partial，产物总线拿不到任何东西
```

实测两个 skill 的目录落差：

| skill | outputs.root（相对 cwd） | LLM 原生 Write 的落点 |
|---|---|---|
| demo-outline | `artifacts/aaa111/bbb222/content_outline/` | 仓库根 |
| openspec-propose | `openspec/changes/add-foo/` | 仓库根 |

**没有任何报错指出原因**——文件确实写进了仓库，`status` 只是 partial。

## 三、为什么前一轮的真机验证超时

现在明白了：CLI 拿不到 `write_file`，会自己决定怎么完成任务——可能用 Bash 探索目录、可能反复读文件确认路径。500s 跑不完不是环境慢，是**任务在 CLI 眼里是开放式的**（prompt 让它「用 write_file 写入 outline.md」，但它没有这个工具）。

## 四、唯一的出路：MCP server

CLI 能命名调用的只有 MCP 工具（`mcp__<server>__<tool>`）。`llm_client._build_settings_args`（:850）把 server 写进 `--settings`。

**openspec 就是这么做的**（llm_client.py:888）：

```python
if _os_cli and (_Path(cwd) / "openspec").is_dir():
    mcp_servers["openspec"] = {
        "command": _python_exe,
        "args": [str(_backend_dir / "openspec_mcp_server.py")],
        "env": {"OPENSPEC_REPO": cwd, "OPENSPEC_CLI": _os_cli},
    }
```

而 `openspec_mcp_server.write_artifact`（:97）解决了路径问题——它从 `OPENSPEC_REPO` 环境变量拿仓库根，自己拼 `openspec/changes/<id>/<artifact>.md`，**LLM 只传 change_id + artifact + content，不碰路径**。

这正是 skill builtin 工具的修复范本：需要一个 `skill_io_mcp_server.py`，把 `write_file` / `read_file` / `gen_image` 包成 MCP 工具，用环境变量接收 `outputs.root`。

## 五、提示词层面的既有缓解

`openspec-propose` 的 body 里写了：

> ⚠️ **严禁**：`Bash("openspec-cn ...")`、`Write("openspec/...")`。
> 这些操作**必须通过** OpenSpec 命名工具完成

这是「工具传不进去，至少引导 LLM 去调 MCP 版本」。

**demo 链没有这段**——因为它们的 builtin 工具还没有 MCP 对应物，无路可走。写了测试断言 demo skill 的 body 里不含 `mcp__`，一旦接上会红并提示更新结论。

## 七、这个缺陷对框架的实际影响

| 模式 | skill 能否执行 | 产物能否回收 |
|---|---|---|
| API（anthropic/openai） | ✓ | ✓ |
| CLI（claude/codebuddy/cursor） | 能跑但工具不可控 | **✗ 一律 partial** |

当前环境是 `LLM_API_FORMAT=cli`，所以**框架在当前配置下跑不出完整产物**。

但这不否定前面 16 个任务：
- 组装、排序、产物总线、状态推进全部与 LLM 模式无关，已验证
- 唯一受影响的是「LLM 怎么把文件写到指定位置」这一环
- API 模式下整条链是通的（e2e 用的打桩 execute 等价于 API 模式的行为）

## 九、修复方案（下一步）

新建 `backend/skills/skill_io_mcp_server.py`，仿 `openspec_mcp_server.py`：

```python
# 环境变量接收上下文，LLM 不碰路径
SKILL_OUTPUT_ROOT  # outputs.root 渲染后的绝对路径
SKILL_REPO         # 仓库根（read_file 用）
SKILL_ALLOWED_EXTS # 扩展名白名单

@mcp.tool()
async def write_output(filename: str, content: str) -> str: ...
@mcp.tool()
async def read_repo_file(path: str) -> str: ...
@mcp.tool()
async def gen_image(prompt: str, filename: str, ...) -> str: ...
```

接入点：`_build_settings_args` 加条件注入（`_llm_ctx` 里有 skill 上下文时）。

需要同步改的：
1. skill 的 body 补 `mcp__skill_io__*` 的备选工具名（照 openspec 的写法）
2. `SkillRunner` 在 CLI 模式下把 `outputs.root` 透给 `_llm_ctx`
3. 本文件的 8 个断言全部要改
