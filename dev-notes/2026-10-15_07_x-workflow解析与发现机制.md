## 二、顺手修了一个真实 bug：只扫 `.claude`

`_find_skill_dir` 原实现：

```python
packs = Path(repo_path) / ".claude" / "packs"
```

但 ADS 支持四种 IDE 的 pack 目录（`api/projects.py:3066` 的同款遍历用了 `cursor/claude/codebuddy/workbuddy`），而**ADS 自己的 ConfigPack 装的是 `.codebuddy`**（`plugin_scanner.py:13` 写明）。

也就是说：**装进 `.codebuddy/packs/*/skills/` 的 skill 一直发现不了。** 当前没有项目级 skill 实例（全库 `find -name SKILL.md` 在 projects 下 0 结果），所以没人踩到。

抽出 `_project_pack_skill_roots` 统一四种目录，`_find_skill_dir` 和 `discover_workflow_skills` 共用。注入「只扫 .claude」验证：6 个测试红。

## 三、`skill_id` 与 `stage_id` 分开

```yaml
# 目录名（skill_id）：demo-draft      连字符，文件系统习惯
# 流程标识（stage_id）：demo_draft    蛇形，会变成 SOP stage.id
```

不强制相等的理由：`stage_id` 直接派生状态名 `{stage_id}_done` / `{stage_id}_failed`，而 orchestrator 按状态名查 `transition_rules`。如果 stage_id 带连字符或大写，派生出的状态名会与 SOP 其它地方的蛇形约定不一致 —— 对不上就是**静默卡死**（不报错、不超时、工单不动，和前几轮 base_stages 裁剪踩的是同一个坑）。

所以加了 `_STAGE_ID_RE = ^[a-z][a-z0-9_]*$` 强制校验，参数化测了 6 种违规形态（`Demo-Draft` / `demoDraft` / `demo.draft` / `2demo` / `_demo` / `demo draft`）。

## 四、kind lint 接在发现期（第 1 道闸落地）

```python
lint = lint_kind_refs(wf.skill_id, wf.consume_kinds, wf.produce_kinds)
if not lint.ok:
    for err in lint.errors:
        logger.error("❌ %s（%s）", err, md_path)
    continue          # 该 skill 出局
```

三类拦截（都写了测试）：

| 情形 | 为什么必须拦 |
|---|---|
| kind 拼错 | 下游 consumes 永远匹配不上 → 静默少跑一步 |
| produces inline kind | 老读取方 `WHERE type='prd'` 取 content 会落空 |
| 自环 | 拓扑检出环 → **整条链**不组装，一个笔误拖垮全局 |

反向（consumes inline kind）明确允许 —— 新 skill 读老产物是合理需求，也写了测试。

**ERROR 级而非 warning**：日志里带上 `md_path`，让人能直接定位到哪个文件写错了。

## 五、容错边界：坏文件不拖累整次扫描

`discover_workflow_skills` 对每个 skill 独立 try：

- SKILL.md 读失败 → 跳过该 skill
- frontmatter 解析失败（`_parse_frontmatter` 内部已吞异常返回 `{}`）→ 当作无 x-workflow
- 目录没有 SKILL.md → 跳过
- `x-workflow` 结构错 → ERROR + 该 skill 出局

测了「一个 broken 文件 + 一个 good 文件 → 只发现 good」。

组装器拿到的是**全集**，所以任何一个 skill 挂掉整次扫描都会让其它 skill 一起消失 —— 这个容错不是锦上添花。

## 九、一个设计决定：`artifacts.kinds` 在函数内 import

```python
def discover_workflow_skills(repo_path: str = "") -> List[WorkflowSkill]:
    from artifacts.kinds import lint_kind_refs
```

不放模块级的理由：`skills.executable_loader` 是 SkillRunner 的依赖，而 `artifacts` 包未来会被 orchestrator 用。模块级交叉 import 容易在两边都长大后变成环。已验证当前无循环导入。
