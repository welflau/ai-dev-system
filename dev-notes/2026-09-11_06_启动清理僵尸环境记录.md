## 一、问题

`project_environments.status` 会永久停留在 `running`。

预览服务是 `subprocess.Popen` 起的 `python -m http.server`，**随后端进程退出而死**，
但 DB 记录不会被更新。前端读这张表显示"运行中"，点进去是个 404 链接。

实测两个库的存量：

```
data/ai_dev_system.db      running=8   实际存活=0
data/ai_dev_system_new.db  running=12  实际存活=0
```

**20 条全是僵尸**，最老的记录停留在 5 月。

---

## 二、原有自愈逻辑为什么不够

`api/projects.py:1129` 本来就有自愈：

```python
actually_running = key in DeployAgent._preview_servers
if env.get("status") == "running" and not actually_running:
    UPDATE ... SET status = 'inactive'
```

但它**只在用户访问环境列表接口时才触发**。没人点那个页面，记录就一直脏着。
而且只修当前查询的那个项目，不覆盖全表。

---

## 三、修复

`main.py` 的 `lifespan` 启动钩子里加全表重置：

```python
stale = await db.fetch_all("SELECT id FROM project_environments WHERE status = 'running'")
if stale:
    await db.execute("UPDATE project_environments SET status = 'inactive' WHERE status = 'running'")
    logger.info("已重置 %d 条僵尸环境记录（上次退出时未清理的 running）", len(stale))
```

**状态值用 `inactive` 而不是 `stopped`** —— 第一版我写的是 `stopped`，
检查时发现 `api/projects.py` 的自愈逻辑用的是 `inactive`。两处不一致的话，
前端会遇到一个它不认识的第三种状态。改成对齐。

存量数据单独清理（带端口存活探测，只重置真死的）：

```
ai_dev_system.db:      重置 8 条  [9166, 9204, 9066, 9219, 9011, 9048, 9093, 9122]
ai_dev_system_new.db:  重置 12 条 [9229, 9219, 9011, 9203, ..., 9096, 9256]
最终:  两库均 100% inactive
```

`inactive`。**这是预期行为** —— 后端重启后 `DeployAgent._preview_servers`
内存表已空，那个进程变成了无法管理的孤儿（停不掉、重启不了）。
状态如实反映"系统管不了它"比谎称 running 更有用。

## 六、遗留

- **孤儿进程本身没处理**：如果后端非正常退出（kill -9），
  `python -m http.server` 子进程可能继续活着占端口。下次部署同一项目时
  `deploy_env` 会因端口占用失败（`proc.poll() is not None` 分支返回 None）。
  彻底解法是记录 PID 并在启动时清理，本次未做。
