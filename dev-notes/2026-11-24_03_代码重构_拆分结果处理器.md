## 背景

  这是拆分时最容易搬错的地方。

### 2. 拆分（R2 第 1 步）

新增包 `backend/orchestration/`：

```
orchestration/
  __init__.py                    包说明，依赖方向 orchestrator → orchestration
  result_handlers/
    __init__.py                  三张注册表，pre_skill_handler() 和 agent_handler()
    context.py                   ResultContext、HANDLED、ResultHandler
    dev.py                       handle_html_prototype、handle_dev
    artist.py art.py ux.py planner.py ue_editor.py
    architect.py review.py product.py tester.py deploy.py
```

共 11 个处理器文件、12 个处理器函数。函数体是原分支逐行搬出，只做了四种机械替换：
缩进减 8 格；`self.` 换成 `orch.`；裸 `return` 换成 `return HANDLED`，落到尾部的路径在末尾加 `return new_status`；
`_fire_knowledge_distill(` 换成 `ctx.fire_knowledge_distill(`。

`_handle_agent_result` 保留公共前置和尾部，中间的分支链换成分发：

1. 构造 `ResultContext`；
2. 查 `pre_skill_handler(agent, action)`，目前只有 `("DevAgent", "write_html_prototype")`；
3. 没命中且是 skill 结果，走 `_handle_skill_agent_result` 后返回；
4. 查 `agent_handler(agent, action)`：10 个 Agent 按名字登记，`ProductAgent` 只在 `acceptance_review` 下命中；
5. 仍没命中就保持原状态，否则执行处理器，返回 `HANDLED` 时直接结束；
6. 尾部不变：发 `ticket_status_changed`，等 0.5 秒，命中规则就继续 `process_ticket`。

## 设计决定

- **`db` 经 `ctx.db` 传入。** 测试用 `monkeypatch.setattr(orchestrator, "db", test_db)` 换库。
  处理器如果自己 `from database import db`，这个桩就失效，测试会写到真实库。这是方案第七节的第 1 条风险。
- **`_fire_knowledge_distill` 留在 `orchestrator.py`，由调用方传入。** 它内部导入 L3 模块，
  属于存量的 `orchestrator` → L3 违规。留在原处，违规不会换一个模块名重新登记，等 R2 后续统一清。
- **返回值约定。** 原函数有两种出口：分支里直接 `return`（不发事件、不续派），以及落到尾部。
  处理器用返回值区分：`HANDLED`（即 `None`）对应前者，状态字符串对应后者。
- **logger 名沿用 `"orchestrator"`。** 日志过滤和现有排障习惯不用跟着改。
- **函数内的延迟导入原样保留。** `failure_library`（验收、测试）和 `api.milestones`（测试、部署）
  拆分前就是延迟导入，测试也按这个路径打桩。
- **新文件一律 LF、无 BOM；`orchestrator.py` 保持原有的 CRLF。** 避免把换行差异混进 diff。

## 与方案的偏差

1. **处理器签名。** 方案写的是 `async def handle(ctx) -> None`。实际是 `-> Optional[str]`，
   因为尾部的「发事件、续派」要保留在公共位置，处理器得告诉调用方新状态是什么。
2. **「找不到处理器就标 blocked」没有做。** 这会改变现有行为（现在是状态不变、照常走尾部），
   而本轮的原则是只搬不改。特征测试里有一条用例钉住了现状，要改的时候改那条用例即可。需要确认后再动。
3. **Agent 名字面量没有消失，只是换了位置。** `orchestrator.py` 里的 `agent_name ==` 按正则计数从 14 处降到 2 处
   （一处是 `SkillAgent` 判断，一处在注释里），另有 1 处 `agent_name in (...)` 没动。名字现在集中在
   `result_handlers/__init__.py` 的注册表里。交给插件注册要等六层方案的 `ProviderRegistry`。
4. **处理器内部没有再拆。** `handle_dev` 207 行、`handle_test` 197 行，仍超过方案 150 行的目标。
   逐行搬移才能用 AST 证明等价，内部整理留到下一步，那时已有特征测试保护。

## 验证

环境：Windows，Python 3.14.3；flake8 用的是另一个 Python 3.12.13 环境（flake8 7.5.0）。

| 检查 | 结果 |
|---|---|
| 特征测试，拆分前 | 57 条通过 |
| 特征测试，拆分后 | 57 条通过 |
| 逐分支 AST 对比 | 12 个处理器全部一致 |
| 全量 pytest | 925 条通过（原 868 加新增 57），退出码 0 |
| `python scripts/check_layers.py` | 退出码 0；SCC 0 组；方向违规 92 条，相对基线新增 0 |
| `flake8 --select=E9,F63,F7,F82` | `orchestrator.py`、`orchestration/`、新测试文件均为 0 条 |
| `py_compile` | `orchestrator.py` 和 `orchestration/` 下 14 个文件通过 |

AST 对比的做法：取 `git show HEAD:backend/orchestrator.py` 里的 12 个分支体，再把新处理器按上面四种替换
反向还原，比较两边的 `ast.dump`；同时核对每个处理器的出口类型（收尾或落到尾部）和原分支一致。
这一步证明函数体是等价搬移，特征测试则证明分发顺序和公共前置、尾部的衔接没变。

新测试单独跑时的覆盖率：`_handle_agent_result` 92.2%（拆分前全量测试下是 6%），
`orchestration/` 包 98%（470 条语句漏 10 条，都是延迟导入失败时的 `except` 分支）。

## 已知影响

- 读 `_handle_agent_result` 源码做断言的代码要改看处理器模块。仓库里搜到的只有上面那一个脚本。
- 新增 Agent 时要在 `result_handlers/__init__.py` 登记。漏登记的后果和以前漏写分支一样：
  状态不推进，同一条规则反复命中。
- `art.py`、`ux.py` 里有 3 处不带占位符的 f-string（flake8 F541），是原代码带过来的。
  为了保持逐行等价没有改，它们不在 CI 的检查范围内。
