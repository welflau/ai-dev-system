## 背景

用户截图：顶栏指标条要求新增「AI 任务」个数，统计提交的生图/生视频任务，
页面显示列表 + 进行/等待/完成个数。三个拍板：全覆盖埋点、徽标显示总任务数、全量保留列表限 50 条。

## 调研结论（为什么必须新建层）

- 现有唯一生成任务表 `image_requests` 只覆盖生图 3 个 `request_image()` 入口；
  `actions/gen_image.py` skill 链生图明确不落表。
- 生视频 4 类入口（`cloud_video/` 的 MiniMax H3 / LightAI、videoclaw VC sandbox、
  director lightai 直连 / CLI 后端）**全部零落库**，状态只在上游 HTTP / 内存队列。
- 无通用 `tasks`/`generation_tasks` 表；`cli_task_log`/`ticket_command_log`/`automation_runs`
  语义都不匹配。不改入口做不出「完成数 + 明细列表」。

## 关键设计

- **不重复计数**：云端 dispatch 单点埋点覆盖 director/videoclaw 云端分支，
  只有不走 dispatch 的 VC sandbox / director lightai 直连 / CLI 后端单独埋。
- **记录失败不影响生成**：公共层 + 各埋点都 try/except；公共层用函数内延迟 import
  database，保持 `cloud_video/` 顶层零业务依赖。
- **零改动原表**：`external_task_id` 关联 IMG-*，`update_by_external` 更新。
- **4 态**：waiting / running / done / failed；徽标=累计总数，面板三态 + 失败数。
- **状态变量前置**：`_aiGenTasksPanelOpen` 的 let 放在 `refreshMetrics()` 之前（TDZ 坑，§19 已踩过）。

## 三个实现坑（都已修）

1. **`track_task` contextmanager 默认标 done 不安全**：`gen_image.py` 的失败分支是
   `return` 不是抛异常，会误标 done。删掉这个多余抽象，改显式 `record`/`update`。
2. **fire-and-forget `create_task`**：初版 `_ai_fail` 用 `create_task` 不 await，状态更新
   可能丢失。改成 async helper + 每个分支显式 `await`。
3. **测试跨 event loop 死锁**：初版 `test_ai_gen_tasks.py` 用 `@pytest.mark.asyncio`，
   与项目其它 `asyncio.run` 测试组合跑时因 `Database._write_lock` 绑定 loop 而挂住
   （2 分钟无输出）。改成同步 test + 单个 `asyncio.run` 包整个场景后组合跑 4s 完成。
   期间 kill 了两个挂住的后台任务（`Bz6bJg` / `QEOGBW`）。

## 边界

- 新表只记录接入后提交的任务，历史不回填。
- DB 全量保留（用户选择），列表只取最近 50 条。
- `image_requests` 的 `failed` 列代码从不写，本层在 ASCII 兜底记 failed，两者不自动同步。
