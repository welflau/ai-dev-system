## 一、问题

`ux_design.yaml` / `art_design.yaml` 的触发条件只看**项目 traits**：

```yaml
required_traits:
  any_of: [platform:web, platform:wechat, platform:mobile, platform:desktop, category:game]
```

任何桌面或游戏项目全都命中，**与工单本身是否涉及界面无关**。

实测：给 UE 项目加一个纯 C++ 的 `SprintComponent`，照样跑完整 UX 交互设计 +
视觉规范，产出 `UX设计.md`、`视觉规范.md`、`design_tokens.json`、
`asset_manifest.yaml` —— 空转 153s，产物无人使用。

## 二、修复

复用既有的 `_is_noncode_ticket` 模式（orchestrator 层拦截 + 跳到 success_status），
新增 `_needs_design_stage(ticket)`：

```
module ∈ {frontend, design, character, ...}（非 other/非后端类）  → 走设计
标题/描述命中 UI 信号（中文子串 / 英文整词）                    → 走设计
其余                                                          → 跳过
```

判定策略与 `_is_noncode_ticket` **相反**：那个是"命中关键词才跳过"（黑名单），
这个是"命中才保留"（白名单）—— 因为漏做设计的代价高于多跑 153s。

`process_ticket` 里把原来的单条跳过逻辑改成统一的 `_skip_reason` 分支，
新增 `write_ux_design` / `write_art_design` 两个 action 的处理，
跳转目标走 `_sop_success_status_for`（不硬编码状态名，与 09-10 那次修复保持一致）。

## 三、中途踩的坑：英文子串匹配几乎全员误命中

第一版关键词表中英混在一起用 `kw in text` 子串匹配。中文没问题（无词边界概念），
英文全线崩坏：

| 关键词 | 会误命中 |
|---|---|
| `ui` | b**ui**ld / g**ui**de / req**ui**re / s**ui**te / circ**ui**t |
| `form` | **form**at / per**form**ance / trans**form** / plat**form** |
| `icon` | sil**icon** / sem**icon**ductor |
| `chart` | **chart**er |
| `style` | **style**sheet |

`build`、`format`、`performance` 这些词在工单里极其常见 —— 等于绝大多数工单
都会被判为"需要设计"，修复形同虚设。而且这种错**测不出来**：断言只看
"frontend 没被误跳"的话永远是 PASS。

**修复**：拆成 `_UI_KEYWORDS_CN`（子串匹配）+ `_UI_KEYWORDS_EN`（正则分词后
整词匹配），英文表同时补齐单复数变体（icon/icons、style/styles/styling）。

## 六、收益与风险

**收益**：按历史数据，31% 的工单能省掉 UX+Art 两阶段。按实测 153s/单算，
139 张工单可省约 112 分钟 LLM 时间。

**风险**：关键词表是启发式，必然有判不准的情况。设计上已偏向保守
（判不准就走设计），最坏情况是回到现状（多跑 153s），不会漏做设计。
若发现某类工单被误跳，往 `_UI_KEYWORDS_CN/EN` 加词即可，不需要改逻辑。
