# 后台轮询的 git 命令归不上项目，和两处把日志刷爆的打印

2026-09-20

## 症状

上一份 DevNote（《工单命令落库与后台链接》）把命令落库接通之后，用户重跑
`TK-20260920-ce79a9` 验收，后台日志**逐 token 刷屏**：

```
22:30:09 [events] WARNING  SSE publish 无订阅者 channel=project:PRJ-20260920-097430 event=ticket_llm_token
22:30:09 [llm] INFO  🖥️  CLI stdout[20600]: {"type":"stream_event","event":{"type":"content_block_delta",...
22:30:09 [events] WARNING  SSE publish 无订阅者 channel=project:PRJ-20260920-097430 event=ticket_llm_token
```

同时查库发现头 60 行 `ticket_command_log` 里 **54 行 `ticket_id=''` 且 `project_id=''`**。

三件事，两个是日志噪音，一个是归属缺口。

## 一、SSE「无订阅者」每次 publish 都打 WARNING

`events.py:41-46` 原来是无条件打：

```python
if not subs:
    logging.getLogger("events").warning("SSE publish 无订阅者 channel=%s event=%s", ...)
```

而 `ticket_llm_token` 是**每 60 字符**推一次（`llm_client.py:1551` 的
`_TOK_THRESHOLD = 60`）。一次 agent 流式回答就能刷上千行，把真正的错误全埋掉。

**而且判断本身是错的。** `project:PRJ-...` 没有订阅者只意味着**浏览器没开着
那个项目页面** —— 无头跑工单时这是常态，不是异常，不该报成 WARNING。

改成两件事：

- **分级**：`ticket_llm_token` / `chat_token` / `heartbeat` 这类高频流式事件
  降到 DEBUG（默认 INFO 级别下压根不打）；状态变更类事件**保持 WARNING**
  —— 那种没人收确实值得注意。
- **按 `(频道, 事件)` 节流**，每 60s 最多一条，折叠时带上
  「过去 60s 另有 N 条同类，已折叠」。不是简单丢弃：排查「推了但前端看不到」
  时这条日志仍然是唯一线索，只是不该每条都打。

外加 `_NOSUB_LOG_MAX_KEYS = 500` 的 dict 上限（长跑进程兜底，同
`hooks/builtin.py` 里 `_SHELL_COUNTS_MAX_KEYS` 的处理）。

实测 **1000 条 `ticket_llm_token` → 1 条 DEBUG**；状态类事件仍 WARNING 且第二条
被折叠；有订阅者时完全不提醒。四个公开签名（`publish` / `subscribe` /
`event_generator` / `publish_to_project`）都没动。

## 二、CLI stdout 每 50 行贴一次原始 JSON

`llm_client.py:1424`：

```python
if _raw_lines_seen <= 3 or _raw_lines_seen % 50 == 0:
    logger.info("🖥️  CLI stdout[%d]: %s", _raw_lines_seen, line[:400])
```

一次流式回答两万多行 `text_delta`（截图里 `stdout[20600]` / `[20650]` /
`[20700]` 三条间隔 50，正是它），每 50 行贴 400 字符。

头 3 行保留全内容 —— 那是**确认 CLI 真在输出、格式对不对**的唯一手段，有价值。
之后改成每 2000 行只打一句进度：

```python
elif _raw_lines_seen % 2000 == 0:
    logger.info("🖥️  CLI stdout 已收 %d 行（累计 %d 字符）", _raw_lines_seen, len(full_text))
```

原始行仍然全量进 `logger.debug`，真要逐行看开 DEBUG 就有。

**这两处都不是命令落库那轮引入的** —— `events.py` / `llm_client.py` 都不在那轮
改动清单里。是工单真跑起来、CLI 流式输出上来才显形的存量问题。

## 三、54 行记录归不上项目 —— 但不是我以为的那个原因

先说结论怎么改了两次，因为中间那次是**误判**，值得记下来。

**第一次判断（错的）**：以为是 DevAgent 在 `_react_with_think` 里跑的 git 调用
没接上上下文，属于漏斗覆盖缺口。

**实际是什么**：查 42 条孤儿的命令构成和时刻，规律一眼就出来了：

```
git rev-parse develop  ×78     22:30:54.434   ← tick
git rev-parse main     ×13     22:31:54.967   ← tick + 60s
                               22:32:55.xxx   ← tick + 120s
```

只有两个命令，整齐的 60 秒周期。那是 `ci_pipeline.start_scheduler`
（`DEVELOP_CHECK_INTERVAL = 60`）→ `_check_develop_build` / `_check_master_build`
→ `_get_branch_head`（`ci_pipeline.py:589`）→ `_run_git`。

`ci_pipeline.py` 和 `image_processor.py` 里 **`checkpoint` 出现次数都是 0** ——
这两个项目级后台轮询压根没设过上下文。

**关键区分：`ticket_id` 留空在这两处是对的。** 它们确实没有工单 —— CI 轮询是
项目级的、图片请求是异步任务，硬塞一个 ticket_id 就是**伪造归属**，比空着更坏。

真正错的是 `project_id` 也空着 —— **项目明明是知道的**（`_scheduler_tick` 的
`for project in projects` 手里就有）。不设的话连「哪个项目在刷 git」都答不了。

所以改动很窄，两处各加一次 push/pop：

```python
for project in projects:
    project_id = project["id"]
    tok = None
    try:
        tok = push_checkpoint_context(project_id=project_id, agent_type="CI",
                                      action="ci_scheduler_tick")
        await self._check_develop_build(project_id)
        await self._check_master_build(project_id)
    except Exception as e:
        logger.warning("项目 %s CI 检查失败: %s", project_id[:8], e)
    finally:
        pop_checkpoint_context(tok)      # pop(None) 是 no-op
```

几个刻意的选择：

- **用 `push`/`pop` 而不是 `set`/`clear`**。CI 调度器和 orchestrator 跑在**同一个
  进程**里；`clear_checkpoint_context` 是无条件 `set(None)`，一次 CI tick 就能把
  正在处理的工单的 `ticket_id` 抹掉 —— 那正是上一轮在 `agents/base.py` 修掉的
  同一个 bug（见 2026-09-20_03 改动 5）。这条专门写了断言压着。
- **每轮循环独立 push/pop**，不是循环外包一次。否则 B 项目的 git 命令会记到
  A 项目头上。
- **`agent_type="CI"`** 而不是落到 `_record_git_command` 的兜底值 `"Git"`，
  这样 CI 轮询和 Orchestrator / DevAgent 发起的调用在面板上分得开。
- `finally` 里无条件 `pop(tok)`：`pop_checkpoint_context(None)` 本身是 no-op
  （上一轮加的），所以不用先判 `if tok is not None`。

`image_processor._replace_placeholder` 同理 —— 它调 `git_manager.read_file`
（→ `git show HEAD:path`）和 `write_file` / `commit`，正是那 6 条 `git:show`。

## 一个测试自己踩的坑

端到端那段第一版**整段 SKIP** 了，理由是 `repo_exists()` 返回假。而 CI 轮询
明明正在对这些项目跑 git —— 矛盾。

查出来：`_repo_path` 优先读 `self._custom_paths`，那是个**进程内缓存**，
全新测试进程里是空的，于是回落到 `PROJECTS_DIR / project_id`。而真仓库在
`F:\Projects\TestTPS`、`F:\ADS_Projects\MyFlappy` 这类**外部路径**上
（记录的 `cwd` 列直接印证了这点，6 个 cwd 正好对上 6 个 active 项目）。

生产里由 `api/projects._ensure_repo_path` 在请求路径上从 `projects.git_repo_path`
恢复（它的注释写明「防止重启后丢失」）。测试得自己补这一步：

```python
if proj["git_repo_path"]:
    G.git_manager.set_project_path(pid, proj["git_repo_path"])
```

这跟上一轮 `register_builtin_hooks()` 只在 `main.py:81` 调一次是**同一类坑**：
生产的启动/请求路径上有一步初始化，测试进程里没有，于是测试静静地测了个空。
上次的表现是「零条记录且零报错」，这次是「整段 SKIP」—— 后者还算容易发现。

## 验收

`backend/_test_bg_attribution.py` **27 通过 / 0 失败**：

- 两个轮询点确实接了 push/pop，且**都不用 `clear`**、都不编造 `ticket_id`
- 三个项目连续 tick **不串台**，循环后上下文干净
- **CI 的 push 不污染工单级上下文**：外层 `set` 了 `TK-REAL` 之后嵌套 push/pop，
  `ticket_id` / `project_id` / `agent_type` 全部幸存并还原
- 端到端走产生那 42 行孤儿的同一条路（`_get_branch_head` → `_run_git`
  → `_record_git_command`）：`project_id` 有了、`ticket_id` 仍为空、
  `agent_type='CI'`、失败的 `rev-parse` 判定为非噪音
- **反证**：不 push 上下文时 `project_id` 确实为空 —— 证明上面那条不是碰巧

SSE 节流实测：1000 条 `ticket_llm_token` → 1 条 DEBUG；状态类事件仍 WARNING。

回归：`_test_command_log.py` **83/0**、`_e2e_command_log.py` **29/0**、
`_test_harness_p1.py` 14 passed / 1 failed（仍是既有的 `input_summary` 那条）。
`import main` 成功（`ci_pipeline` 新增了模块级 `from checkpoint import ...`，
确认没引入循环依赖，`checkpoint` 侧也没有反向依赖）。

`_test_startup.py` 仍在 `await db.close()` 挂掉 —— `Database` 没有 `close`

## 遗留

1. **`git rev-parse develop` 在反复失败**，`exit 128`，10 次以上：

   ```
   fatal: ambiguous argument 'develop': unknown revision or path not in the working tree.
   ```

   这些仓库**没有 `develop` 分支**，而 `_check_develop_build` 每 60s 对每个
   active 项目探一次，失败了就 `return`，**没有缓存、没有降级记录、没有降频**。
   6 个项目 × 每分钟 = 每天约 8600 次注定失败的 git 调用。
   这正是命令落库换来的东西 —— 以前它只会静静地 `rc != 0` 然后走 fallback。
   要修的话是 `_check_develop_build` 里先判分支存在性并缓存结果，不在本轮。
2. **`cli_tool` 来源仍是 0 条、`command_run` 时间轴仍是 0 条** ——
   openspec 三件套这一轮还没跑到。所以时间轴上目前还是没有 📟 链接，
   「任务」Tab 看得到 git、时间轴点不进去。要等一轮真的跑到 openspec 才能验。
3. **`git_manager.read_file` 没有 `_ensure_repo_path` 等价保护**：
   任何不经 `api/projects` 的入口（后台轮询就是）在进程重启后拿到的是默认路径。
   这次 CI 能跑对是因为 orchestrator 早先的请求已经把 `_custom_paths` 填好了 ——
   **顺序依赖，不是保证**。值得在 `_repo_path` 里做一次 DB 回查兜底。
4. 上一轮的遗留（四个测试的腐化、UE/http.server/Chrome 截图无记录、
   `cli_task_done`、限流阈值 50 待实测）都还在。
