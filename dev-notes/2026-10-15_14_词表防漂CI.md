## 二、扫出了 3 处既存的 trait 漂移

这是本轮最有价值的发现。全库扫描后：

| fragment 里写的 | 词表里实际是 | 差异 |
|---|---|---|
| `i18n` | `quality:i18n` | 缺维度前缀 |
| `multiplayer:true` | `features:multiplayer` | 维度错 + `:true` 后缀 |
| `prototype:html` | `lifecycle:prototype` | 维度错 + value 错 |

`_normalize_trait`（api/projects.py:1377）还会把裸 `i18n` 补成 `i18n:true`，更对不上。

**后果**：这 3 个 fragment 的 `required_traits` 永远不会被满足。`i18n_check` / `multiplayer_stress` / `html_prototype` 的 `prototype:html` 分支**实际上是死代码**——除非有人手工往 DB 里塞这些非法 trait。

### 为什么不在这轮修

改 fragment 的 trait 会改变它们的激活条件。需要先确认线上没有项目依赖当前（失效的）行为。`test_known_trait_drift` 把现状钉死并列出完整对照表，修的时候它会红——那是预期的。

### 真正的价值是 `test_no_new_trait_drift_in_sop`

> 让漂移**停止增长**。

已知 3 项白名单之外出现任何新的词表外 trait 就红。这正是 trait_taxonomy 缺了快两年的那道闸。

## 三、线上 DB 的 trait 漂移更严重（11 项）

```
feature:auth / feature:bullet-hell / feature:charts / feature:powerup-system
feature:responsive / feature:wave-spawner / framework:phaser
genre:platformer / singleplayer / style:pixel-art / ui:antd
```

全是 LLM 建项目时自创的（代码库里 grep 不到），词表里没有 `feature` / `genre` / `style` / `ui` 这几个维度。

**没有给 DB 数据加断言**——线上数据会变，把它写进测试等于让 CI 依赖生产状态。这条记在这里，作为"detector 侧也需要词表约束"的证据。

## 四、三条「只有静态检查能发现」的断言

### `test_produces_glob_matches_runner_outputs`

`x-workflow.produces` 的 glob 必须出现在 `x-runner.outputs.globs` 里。

不一致的后果极其隐蔽：`_collect_outputs` 用 `{glob: kind}` 反查归类 → glob 对不上 → 文件被回收但 **kind 为空** → SkillAgent 跳过登记（它只登记有 kind 的）→ 下游 consumes 永远拿不到。**全程无报错，status 还是 success。**

### `test_stage_ids_globally_unique`

与 base_stages / fragments 的 stage.id 撞名检查。compose_sop 里有运行时防撞，但那时 skill 已经不生效了。

### `test_every_registered_kind_is_reachable`

孤儿 kind（登记了但无 producer 也无 consumer）是词表膨胀的前兆——下一个人会以为它有用而去 consumes 它，然后发现永远匹配不上。

## 五、一条守护测试设计的测试

```python
def test_demo_priorities_stay_inverted():
    assert cover > draft > outline
```

demo 链的 priority **必须与依赖顺序相反**。这是上一轮的刻意设计：同向的话「拓扑排序生效」在 demo 链里不可观测（只按 priority 排也得出同样结果）。实测正是靠这个反向设置，让「拓扑换成纯 priority 排序」的注入变红 6 个 e2e。

谁把 priority 改回同向，这条会红并提示「那样会让 e2e 失去鉴别力」。

**这是第一次写「测试的测试」**——保护的不是产品行为，而是另一个测试的鉴别力。
