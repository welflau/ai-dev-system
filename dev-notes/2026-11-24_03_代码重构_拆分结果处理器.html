背景

重构方案里最长的函数是 TicketOrchestrator._handle_agent_result：1,026 行，圈复杂度 153， 行覆盖率 6%。方案要求先补特征测试再动结构，所以本轮分两步做：先在原代码上把每个分支的行为钉住， 再把分支逐行搬到独立模块。全程不改外部行为。

做了什么

1. 特征测试（R0 第 3 步的 _handle_agent_result 部分）

新增 backend/tests/agents/test_orchestrator_result_branches.py，919 行，57 条用例。

  • 夹具沿用 test_orchestrator_skill_branch.py 的做法：真实 SQLite 加 init_tables()， TicketOrchestrator.__new__ 造实例，派单、SSE、知识蒸馏、里程碑刷新等外部依赖打桩。
  • _log、_write_phase_comment、_apply_fragment_closeout、_acceptance_retry_count 真跑， 断言直接查库里的工单状态、ticket_logs 和产物表。
  • 覆盖范围：
    • 公共前置：6 个终态的门闩、3 种 error 止血、媒体文件暂存、片段 closeout 短路；
    • 在分支内收尾的 Agent：HTML 原型（含「排在 skill 判断之前」）、Artist、Art、UX、Planner、UEEditor 成功和失败；
    • 落到尾部的 Agent：Architect、Dev（typecheck 4 种、development_failed、自测 blocking、成功、并发竞态 3 种）、 Review、验收（通过、拒绝、降级重试后 blocked、SOP trigger）、Test（playtest 4 种、通过 3 种、失败）、 Deploy（packaged、deployed）；
    • 没有处理器的 Agent：状态保持不变并照常走尾部。
  • 每条用例都用 _assert_tail 或 _assert_no_tail 钉住「是否发 ticket_status_changed 并继续派单」， 这是拆分时最容易搬错的地方。

这 57 条先在拆分前的代码上跑通，再在拆分后的代码上跑通。

2. 拆分（R2 第 1 步）

新增包 backend/orchestration/：

orchestration/
  __init__.py                    包说明，依赖方向 orchestrator → orchestration
  result_handlers/
    __init__.py                  三张注册表，pre_skill_handler() 和 agent_handler()
    context.py                   ResultContext、HANDLED、ResultHandler
    dev.py                       handle_html_prototype、handle_dev
    artist.py art.py ux.py planner.py ue_editor.py
    architect.py review.py product.py tester.py deploy.py

共 11 个处理器文件、12 个处理器函数。函数体是原分支逐行搬出，只做了四种机械替换： 缩进减 8 格；self. 换成 orch.；裸 return 换成 return HANDLED，落到尾部的路径在末尾加 return new_status； _fire_knowledge_distill( 换成 ctx.fire_knowledge_distill(。

_handle_agent_result 保留公共前置和尾部，中间的分支链换成分发：

  1. 构造 ResultContext；
  2. 查 pre_skill_handler(agent, action)，目前只有 ("DevAgent", "write_html_prototype")；
  3. 没命中且是 skill 结果，走 _handle_skill_agent_result 后返回；
  4. 查 agent_handler(agent, action)：10 个 Agent 按名字登记，ProductAgent 只在 acceptance_review 下命中；
  5. 仍没命中就保持原状态，否则执行处理器，返回 HANDLED 时直接结束；
  6. 尾部不变：发 ticket_status_changed，等 0.5 秒，命中规则就继续 process_ticket。

3. 配套改动

  • backend/layers.toml：orchestration 归入 L1，和 orchestrator 同层。
  • desktop.spec：hiddenimports 增加 orchestration 包和它的 13 个子模块。
  • backend/_test_false_success_gates.py：第 7 节有两条检查读 _handle_agent_result 的源码找 development_failed 的处理，改成读 handle_dev 的源码。

设计决定

  • db 经 ctx.db 传入。 测试用 monkeypatch.setattr(orchestrator, "db", test_db) 换库。 处理器如果自己 from database import db，这个桩就失效，测试会写到真实库。这是方案第七节的第 1 条风险。
  • _fire_knowledge_distill 留在 orchestrator.py，由调用方传入。 它内部导入 L3 模块， 属于存量的 orchestrator → L3 违规。留在原处，违规不会换一个模块名重新登记，等 R2 后续统一清。
  • 返回值约定。 原函数有两种出口：分支里直接 return（不发事件、不续派），以及落到尾部。 处理器用返回值区分：HANDLED（即 None）对应前者，状态字符串对应后者。
  • logger 名沿用 "orchestrator"。 日志过滤和现有排障习惯不用跟着改。
  • 函数内的延迟导入原样保留。 failure_library（验收、测试）和 api.milestones（测试、部署） 拆分前就是延迟导入，测试也按这个路径打桩。
  • 新文件一律 LF、无 BOM；orchestrator.py 保持原有的 CRLF。 避免把换行差异混进 diff。

与方案的偏差

  1. 处理器签名。 方案写的是 async def handle(ctx) -> None。实际是 -> Optional[str]， 因为尾部的「发事件、续派」要保留在公共位置，处理器得告诉调用方新状态是什么。
  2. 「找不到处理器就标 blocked」没有做。 这会改变现有行为（现在是状态不变、照常走尾部）， 而本轮的原则是只搬不改。特征测试里有一条用例钉住了现状，要改的时候改那条用例即可。需要确认后再动。
  3. Agent 名字面量没有消失，只是换了位置。 orchestrator.py 里的 agent_name == 按正则计数从 14 处降到 2 处 （一处是 SkillAgent 判断，一处在注释里），另有 1 处 agent_name in (...) 没动。名字现在集中在 result_handlers/__init__.py 的注册表里。交给插件注册要等六层方案的 ProviderRegistry。
  4. 处理器内部没有再拆。 handle_dev 207 行、handle_test 197 行，仍超过方案 150 行的目标。 逐行搬移才能用 AST 证明等价，内部整理留到下一步，那时已有特征测试保护。

AST 对比的做法：取 git show HEAD:backend/orchestrator.py 里的 12 个分支体，再把新处理器按上面四种替换 反向还原，比较两边的 ast.dump；同时核对每个处理器的出口类型（收尾或落到尾部）和原分支一致。 这一步证明函数体是等价搬移，特征测试则证明分发顺序和公共前置、尾部的衔接没变。

新测试单独跑时的覆盖率：_handle_agent_result 92.2%（拆分前全量测试下是 6%）， orchestration/ 包 98%（470 条语句漏 10 条，都是延迟导入失败时的 except 分支）。

没有验证的部分

  • 桌面版打包。 desktop.spec 只确认了语法能解析，没有实际打包和启动。
  • 真实服务启动和端到端流程。 没有起服务跑一张真实工单；CLI 流式调用、UE 工具链都没有经过。
  • Linux 和 CI。 只在本机 Windows 上跑过。
  • _test_false_success_gates.py 整体。 只单独确认了改动的两条检查在 handle_dev 源码上成立， 脚本本身没有完整跑。
  • _test_ue_test_gen_wiring.py。 这个脚本真调 _handle_agent_result，按理不受影响， 但它写真实数据库并依赖一个固定的项目 ID，本轮没有跑。

已知影响

  • 读 _handle_agent_result 源码做断言的代码要改看处理器模块。仓库里搜到的只有上面那一个脚本。
  • 新增 Agent 时要在 result_handlers/__init__.py 登记。漏登记的后果和以前漏写分支一样： 状态不推进，同一条规则反复命中。
  • art.py、ux.py 里有 3 处不带占位符的 f-string（flake8 F541），是原代码带过来的。 为了保持逐行等价没有改，它们不在 CI 的检查范围内。

遗留与后续

  1. process_ticket（682 行，覆盖率 0%）是下一个目标：先补特征测试，再做 R2 第 2 步的分步管线。
  2. _handle_skill_agent_result（255 行）可以按同样的方式搬进 result_handlers/，它已有 test_orchestrator_skill_branch.py 保护。
  3. handle_dev、handle_test 的内部整理。
  4. 「无处理器即 blocked」是否要做，需要确认。
  5. R0 的其余几步都还没做：度量脚本和基线、CI 覆盖率、handle_requirement / _call_cli_stream / 聊天流的特征测试、 83 个业务模块补归层、根目录脚本归位。
  6. 工作区现在叠了三批未提交改动（ai_gen_tasks、体检修复第一批、本轮拆分），提交时建议分开。
