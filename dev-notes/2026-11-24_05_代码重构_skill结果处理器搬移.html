背景

R2 第 1 步把 _handle_agent_result 里按 Agent 名分的 12 个分支搬进了 orchestration/result_handlers/， skill 阶段的分支当时留在 orchestrator.py：_handle_skill_agent_result（255 行）加三个辅助方法。 它自己发状态事件、自己决定要不要继续派单，和其他处理器的收尾方式不同，所以单独留到这一轮。 本轮把它搬过去，外部行为不变。

做了什么

1. 先在原实现上补用例

tests/agents/test_orchestrator_skill_branch.py 原有 31 条用例，原第 2406–2736 行的 112 条语句漏 8 条 （92.9%），50 个分支走到 40 个。搬之前先补 7 条，全部在原实现上跑通：

  • test_skill_gate_file_paths_all_sources：确认卡预览路径、预览 URL、产物总线、skill 相对路径四个来源和去重；
  • test_skill_gate_file_paths_tolerates_bad_shapes：字段不是预期类型时不报错，结果截到 20 条；
  • test_skill_gate_file_paths_strips_leading_dots：钉住一处可疑现状，见下文；
  • test_waiting_human_non_dict_and_no_files：waiting_human 不是字典、没有产物文件；
  • test_waiting_human_ready_status_fallbacks：待确认状态的回退；
  • test_blocked_survives_artifact_query_failure：查产物表出错时 blocked 收尾照常完成；
  • test_no_dispatch_when_ticket_vanishes：状态推进后查不到工单时不派单。

补完后这段代码是 112/112 条语句、50/50 个分支。

2. 搬移

新增 backend/orchestration/result_handlers/skill.py，361 行，四个函数：

新位置 原位置 行数
handle_skill(ctx) TicketOrchestrator._handle_skill_agent_result 256
_resolve_skill_success_status(orch, …) TicketOrchestrator._resolve_skill_success_status 25
skill_produces_satisfied TicketOrchestrator._skill_produces_satisfied（静态方法） 14

文件由脚本按行号区间从搬移前的 orchestrator.py 生成，生成后没有手改。

orchestrator.py 这边：

  • 删掉这四个方法和小节注释，5,236 行降到 4,907 行。
  • 分发处原来直接 await self._handle_skill_agent_result(...) 然后 return，现在取 result_handlers.handle_skill 作为处理器，走和其他处理器相同的 new_status = await handler(ctx) 和 HANDLED 判断。分发顺序没有变：（Agent, action）精确匹配，然后 skill，最后按 Agent 名。
  • 新增模块级函数 _synthesize_blocked_diagnosis(**kwargs)，函数内延迟导入 actions.diagnose_ticket， 通过 ResultContext.synthesize_blocked_diagnosis 交给处理器。

handle_skill 没有登记进按 Agent 名查的注册表。skill 结果靠 is_skill_run_result 识别，宿主 Role 可以是任何 Agent。

  • tests/e2e/test_demo_chain.py：_drive_chain 改调新入口。
  • actions/gen_image.py：文档字符串里的函数引用改成新位置。
  • desktop.spec：hiddenimports 补 orchestration.result_handlers.skill。

和原文的差别

原第 2406–2736 行共 331 行。308 行原样搬走，其中 15 行有词元替换；23 行没有搬，其中 20 行非空， 是四个函数的签名、两个 @staticmethod 和那条 actions.diagnose_ticket 的导入。替换只有四种：

  1. self 写成 orch；
  2. 辅助方法去掉 self. 和下划线前缀；
  3. _resolve_skill_success_status 多一个 orch 参数；
  4. 诊断函数改成 ctx.synthesize_blocked_diagnosis。

另外函数开头加了从 ctx 取局部变量的 11 行，末尾加了 return HANDLED。

  • 待确认状态：sop_config._ready_status 和回传的 success_status；
  • 成功状态：回传的 success_status 和 sop_config._success_status。

这段代码的语句和分支覆盖率已经是 100%，这两条优先级仍然没有用例钉住。补了 test_waiting_human_ready_status_prefers_sop_config 和 test_success_status_result_beats_sop_config， 再跑这两处改动，都被发现。这两条是搬移之后写的，没有在原实现上跑过；它们断言的行为由核对脚本的逐行比对保证和原实现一致。

从 7b9e7f0 算起，orchestrator.py 从 6,694 行降到 4,907 行。orchestrator.py 里剩下的两个超过 200 行的函数是 handle_requirement（456 行，圈复杂度 65）和 _generate_requirement_report（206 行，圈复杂度 37）。 result_handlers/ 里超过 200 行的是 handle_skill（256 行，圈复杂度 53）和 handle_dev（207 行，圈复杂度 36）。

度量是本轮重写的临时脚本按方案附录的口径算的。第一次算出 46 个超过 200 行的函数， 原因是没有排除 tests/、config_packs/、tools/；按附录的范围排除后是 30 个，和上一篇对得上。

这一轮没有解决的事

  1. handle_skill 只是换了位置。 它仍是 256 行、圈复杂度 53，内部三条路径（待确认、成功、blocked）没有拆。 全仓超过 200 行的函数数因此没有变化。
  2. 到 L3 的依赖没有消除。 actions.diagnose_ticket 的导入从处理器里移到了 orchestrator.py 的 _synthesize_blocked_diagnosis，仍是一条 L1 到 L3 的延迟导入，已在守卫基线里。 方案要求的「经注册表取得 action」要等 R2 第 3 步或 ProviderRegistry。
  3. 处理器仍调用 orch 的 5 个成员：_log、_write_phase_comment、_sop_stage_for、 _get_rules_for_project、process_ticket，其中 4 个是私有方法。

钉住的可疑现状

skill_gate_file_paths 用 lstrip("./") 清理路径开头。lstrip 的参数是字符集合， 所以开头连续的点和斜杠会被全部去掉：

  • .ads/notes.md 变成 works/ads/notes.md，点开头的目录名丢了那个点；
  • ../up/a.md 变成 up/a.md。

受影响的是人审节点展示给用户的产物路径列表。test_skill_gate_file_paths_strips_leading_dots 按现状断言， 本轮没有修。要修的话把 lstrip("./") 换成只去掉 ./ 前缀，同时更新这条用例。

临时目录里的备份和脚本丢了

前两步（结果处理器、分步管线）的备份文件和核对脚本放在 %TEMP%\ads_fix。本轮开始时发现这个目录下的文件 都不在了，只剩四个子目录，原因没有查到。后果：

  • 上一篇写的搬移核对脚本、改坏检查脚本、度量脚本无法重跑；
  • 前两步搬移前的 orchestrator.py 备份没有了。要回退那两步，只能从 git show 7b9e7f0:backend/orchestrator.py 出发手工处理，因为工作区里同一个文件叠着三步改动。

本轮的备份和脚本在 %TEMP%\ads_r2_3，同样没有进仓库，同样可能丢。 把核对脚本和度量脚本收进 scripts/，或者尽快分批提交，都能消掉这个风险，需要确认。

没有验证的部分

  • 桌面版打包。 desktop.spec 只确认了语法能解析，没有实际打包和启动。
  • 真实服务启动和端到端流程。 没有起服务跑一张真实的 skill 工单。测试里 process_ticket、SSE 都是桩。
  • Linux 和 CI。 只在本机 Windows 上跑过。
  • 根目录的 _test_*.py 脚本。 没有跑。查过两处读 orchestrator.py 源码的检查： _test_command_log.py 找的 requirement_id=ticket.get 仍有 1 处匹配； _test_openspec_verify_trigger.py 找的 async def _maybe_openspec_verify 还在， 它另一条「play_test 成功分支已接 Verify」的检查在 2026-11-19_01 那篇里就记为早已失败，和本轮无关。
